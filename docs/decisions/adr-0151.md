## Context

Scene monitoring needs sun-times to tell day, dusk, night and dawn apart, so the
2026-08-14 scene work added a **Site location** section — `siteLatitude` /
`siteLongitude` — to `pipeline-analytics`' global settings, with this comment
justifying the placement:

> They live on THIS addon rather than in `system-config`'s yml sections for one
> concrete reason: `getSection()` is NODE-LOCAL and reads empty on an agent, and
> scene evaluation runs on whichever node is designated for post-processing.

The constraint was real and the conclusion was wrong. Two things were true at
once and only one of them got weighed:

1. **`getSection()` really is node-local.** A coordinate typed on the hub is
   invisible to an agent, and the evaluating node is frequently an agent. Any
   design that stores this in a yml section is broken on a two-node cluster, and
   would have been broken silently — the resolver falls back to a UTC clock
   split, which produces plausible-looking sunrises that are one to two hours
   wrong.
2. **Where the building is, is not a property of an analytics addon.** The
   second consumer of sun-times has exactly two options once the value lives in
   `pipeline-analytics`' store: reach into another addon's settings (addons
   never import each other, and the store is namespaced by addon id), or grow a
   second coordinate knob. That second knob is [D62](adr-0062.md)'s failure
   verbatim — this repo has already shipped two switches that wrote a store
   nobody read.

There was also a usability gap nobody had a home for. Left blank — which is the
state every install ships in — the fallback is the UTC clock split. An operator
has no reason to suspect the setting exists, so the common case is the wrong
case, forever.

## Decision

The site coordinates are a **system setting**, served by the `system` capability
(`getSiteLocation` / `setSiteLocation` / `detectSiteLocation`) and persisted in
the hub's `system-settings` collection under the key `site-location`. Every
consumer reads them through that one authority over the transport, which is what
makes them correct on an agent — a cap call routes to the hub, a `getSection()`
does not.

**The value carries its provenance.** `source` is `operator-set` or
`derived-from-ip`, and the UI shows which. On the first read that finds nothing
stored the hub derives a default by geolocating its own public IP, exactly once:
one request, bounded, and the **outcome persisted either way**, so a hub with no
internet pays four seconds once in its life and never retries on a read path.
The only retry is an operator pressing detect, and detect refuses to overwrite an
`operator-set` value.

Rejected alternatives, both for concrete reasons:

- **A `system-config` yml section.** Cleanest-looking, and node-local — the
  original failure, restated.
- **Leaving it on `pipeline-analytics` and having the second consumer call
  `ctx.api` into it.** There is no cap on that addon exposing it, adding one
  would model a site fact as an analytics fact, and it would still be the
  addon's job to decide the site's default.

## Consequences

- `pipeline-analytics` no longer declares a `site-location` settings section. Its
  `siteCoordinates()` is now a cross-node `system.getSiteLocation` call behind
  the same 5-minute cache. A read failure still degrades to `null` and the coarse
  clock split — the fallback is unchanged, only its trigger is.
- Coordinates an operator already typed are **not lost**: the first system-level
  read that finds nothing migrates them from the old addon store and records them
  as `operator-set`, because they were.
- The hub now makes one outbound request to a third-party geo-IP endpoint, once
  per installation, unless the operator sets the location first. It sends
  nothing but the request itself; the IP is what the endpoint reads, and reading
  it is the entire mechanism. Two no-key HTTPS endpoints are tried in order.
- Anything else that needs a site fact (solar schedules, weather, timezone
  inference) now has an obvious home and must not add a second one.
- `system.cap.ts` is a framework file: this is **train-bound**. The
  `pipeline-analytics` half is an addon deploy.

## Enforcement

`server/backend/src/__tests__/cap-providers/site-location.spec.ts` pins the three
properties that would rot silently: the failure marker is persisted so the
lookup never repeats, a failed *read* propagates rather than reading as "not
configured" (which would send the derivation off to overwrite a real value —
[D49](adr-0049.md)'s shape applied to a fallible read), and detect refuses to
clobber `operator-set`. Each was verified by removing the fix and confirming the
spec fails.

Nothing guards the placement rule itself; it is review-only. The tell that it has
been violated is a second latitude field appearing anywhere in a
`globalSettingsSchema()`.
