## Context

[D57](adr-0057.md) bounded the RTSP join burst at a module constant,
`PRIME_MAX_SPAN_MS = 2000`. Two things were wrong with leaving it there, and the
second is the dangerous one.

**The bound is not a cluster property.** The pre-buffer ring holds
`[most recent keyframe AU .. now]`, so a burst's span at join time is the elapsed
time since the camera's last IDR — uniform in `[0, idrInterval]`. The fraction of
joins a fixed bound withholds is therefore `1 - bound/idrInterval`: zero for a
1.8 s-GOP camera, about a half for a 4 s-GOP one. The premise that a long-GOP
camera would be *permanently* withheld is wrong — it keeps its instant start on
the joins that happen early in its GOP — but the asymmetry is real and no single
value resolves it.

**The two join paths share a surface, and the docs already claimed a property
that did not hold.** `docs/architecture/data-planes.md` stated the burst was
"paced and bounded, on BOTH paths". It was not: `webrtc/session.ts` replays its
bootstrap unbounded, and only the restreamer withholds. Both read one accessor,
`StreamBroker.getRtpPreBuffer()`, so the plausible-looking tidy-up — enforce the
bound once, at the shared source, instead of in each consumer — would have
silently starved every WebRTC viewer while every existing test stayed green. The
doc asserting the wrong invariant is what would have made that change look
correct.

A first attempt at pinning the exemption was itself vacuous: the test drove the
broker through `pushVideoRtp`, which fills the ring and the `onVideoRtp`
subscribers but never calls `rtspRestreamer.pushRtpPassthrough`. Every "the RTSP
consumer received nothing" assertion passed because nothing was ever offered to
it.

## Decision

The join-burst bound is resolved per `(camera, camStreamId)` by the single
function `resolveJoinBurstBound`, from a cluster-wide default in the stream-broker
addon's global settings — declared **without** `perNode`, because ingest is a
movable role and a per-node value would make a camera's join behaviour depend on
which node owned its ingest ([D52](adr-0052.md), [D56](adr-0056.md)) — overridden
per camera stream via `DeviceOverride.joinBurstMaxSpanMs`. It is supplied to the
restreamer by a PULL read on every join, never captured at construction.

The bound gates the RTSP RESTREAM consumers and nothing else. **WebRTC must always
be able to take the last GOP**, and no withholding, trimming or keyframe latch may
be placed at or above `getRtpPreBuffer()`.

## Consequences

- `maxPackets` stays a fixed constant. It is a defensive backstop against RTP
  timestamps that stopped describing the stream, not a tuning knob, and no
  camera's GOP is a reason to raise it.
- `maxSpanMs` is clamped to `[250, 6000]`, and `0` means "inherit", never
  "withhold everything" — a cleared number input posts `0`, and honouring it
  would make every consumer of that camera start one IDR interval late with no
  error anywhere. So "configurable" can never mean "D57 turned off".
- Raising the bound past ~2 500 ms re-admits the burst span that a real-time
  re-emitter forwards to its peer as jitter. For a long-GOP camera the usually
  correct fix is to shorten the camera's IDR interval, not to raise this.
- A cluster-default edit must push into every live broker: a broker is created on
  the first dial and reused for the life of the stream, so a value only stored
  would apply to cameras published afterwards and to no others.
- The `restream prime` and `restream dropped packets` lines now carry
  `boundSpanMs` / `boundPackets`. A withheld join produces only the second line,
  so the bound that caused it has to be readable there.

## Enforcement

`stream-broker/__tests__/webrtc-join-burst-exemption.spec.ts` pins the exemption
against the realistic regression, not a paraphrase of it: bounding the shared ring
inside `getRtpPreBuffer()` turns four of its tests red. It carries an explicit
POSITIVE CONTROL, because the RTSP-side assertions are all "received nothing" and
a harness that failed to reach the restreamer at all would satisfy every one of
them. `__tests__/join-burst-bound.spec.ts` pins precedence and the `0`/clamp
rules; `__tests__/rtsp-prime-bound-config.spec.ts` pins that the bound is read per
join and that the tighter muted live-edge rule is unaffected by raising it. Each
was confirmed to fail when its fix is removed. No guard script — the invariant is
a data-flow shape, and the module doc on `join-burst-bound.ts` plus the corrected
`data-planes.md` paragraph are where a reviewer meets it.
