## Context

The update mechanism used to keep the previous framework copy (N-1), boot a new
version on *probation*, wait for a confirmation, and automatically roll back if it
did not arrive. The intent was obvious and good. The result was not:

- Disk held two full closures per node, on hardware where that matters.
- "Probation" is a state, and states need a durable record — so there was a state
  file, which could be corrupt, which needed a `stateFileCorrupt` path.
- Automatic rollback fires on *absence* of a signal. A slow boot, a network blip
  during the confirmation, an operator restarting at the wrong moment — each looks
  identical to a bad version, and each got silently reverted.
- The safety net was never observed to save an update, and its failure modes were
  observed.

## Decision

One copy. `applyServerUpdate` stages the closure into `.staging-*`, arms a pending
root-swap marker and restarts; the starter swaps `current/` at boot. There is no
probation boot, no N-1 retention and no automatic rollback. `RootUpdateService`
hardcodes `previousVersion: null`, `rolledBack: null`, `stateFileCorrupt: false`,
and never reports `awaiting-confirmation`.

Recovery from a bad version is an explicit update to a known-good version.

## Consequences

- Half the update state machine went away, and with it the class of bug where the
  recovery mechanism was the thing that broke.
- The UI surface that consumed those fields could never render, and was removed —
  the rollback button, the `previousVersion` / `seedVersion` rows, three banners.
  Dead UI that describes a capability the server no longer has is worse than
  absent UI: it tells the operator a safety net exists.
- Confirmation copy must not promise a rollback. It did, for a while, after the
  mechanism was gone.

## Enforcement

Structural: the fields are literals, so no path can populate them. Review for the
copy.
