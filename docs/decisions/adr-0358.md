## Context

The export announced a `snooze` select on every camera and a `snoozed` binary
sensor plus a `snooze` select on the Notification Center device, fed by
`notificationRules.listSnoozes`. That method is `caller: 'required'` — a
user sees their own windows and the global ones, an admin sees all — and an
addon has no user. So the read failed on every reconcile (280 warnings a day
on 2026-09-05), the selects sat on `unknown` forever, and the write path
worked while the read path could not: a control that can be set but never
read back.

Two alternatives were on the table. A system-tier read of only the GLOBAL
windows would keep the selects honest for the household-wide case and still
lie for per-user ones. Keeping the entities as write-only controls keeps a
knob nobody can verify. The operator's call: remove them.

## Decision

The export carries no snooze surface: no camera `snooze` select, no
Notification Center `snoozed` / `snooze`, no `listSnoozes` read, no
`createSnooze` / `cancelSnooze` route. Snoozes are set and read where the
caller identity exists — the viewer and the admin UI.

## Consequences

- Entities already registered in a Home Assistant instance disappear on the
  next structure announce; the custom component prunes what the hub stopped
  announcing.
- The component's recorded fixtures (`entity_change_camera.json`, 51
  components) predate this and still carry `select-snooze`; regenerate them
  from the catalog when the component is next touched.

## Enforcement

`entity-catalog.spec.ts` no longer lists `select-snooze` among a camera's
components; `command-routes.spec.ts` has no snooze route. Review only.
