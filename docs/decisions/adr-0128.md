## Context

Overnight on 2026-08-13 the hub recorder stopped producing footage in bursts of
9–27 minutes (04:44:33Z → 05:11:22Z, and repeatedly from 02:30Z on) across
devices 104/101/102/1441. Those holes are the recording gaps behind the 80%
timelapse coverage.

**The obvious explanation was wrong, and checking it is what found the real
one.** The suspicion was a blocked event loop — synchronous `fs` over shfs/FUSE,
the same class as the addon-pipeline deploy wedge. Two facts refute it:

- The recorder's hourly retention sweep fired at 04:44:33.261Z and 05:44:33.262Z
  — 3600.001 s apart, straight through the alleged stall. A blocked loop delays
  timers; this one did not drift by more than a millisecond.
- There is not one synchronous `fs` call anywhere under
  `packages/addon-pipeline/src/recorder/**`.

What actually wedged was the periodic pass, through a chain where each link was
individually defensible:

```
tick → checkIdleWriters → for (device of stalled) await recoverWriterGaveUp
     → detachDevice          // device leaves `active` — recording STOPS here
     → evaluateDevice → performAttach
     → listAllProfileSlots + one getStreamWithCodec per profile
```

Both attach RPCs were unbounded. `CapabilityHandle.call` gates *readiness*
(10 s) and then does `return fn()` untouched, so each request fell through to
the 60 s UDS default in `kernel/transport/socket-channel.ts`. The broker was
degraded that day (516 UDS timeouts), and the arithmetic did the damage: one
camera on three profiles costs up to 4 × 60 s, and the fan-out was **serial**,
so four cameras reached ~16 minutes inside a single pass.

The silence follows from the same chain, and is why it went undiagnosed for so
long. During recovery every device is detached — so it is absent from `active`,
which is exactly the map the liveness watchdog scans — and present in
`attaching`, so `evaluateDevice` returns early. Nothing to converge, nothing to
report, no line logged. `idleMs=546335` against `boundMs=90000` is not a
watchdog that fired late; it is a watchdog reporting the first moment it was
*allowed to look*, nine minutes past its bound, because the liveness check and
the convergence sweep shared one pass.

## Decision

A periodic recovery pass in the recorder obeys three rules. **Every RPC it makes
is bounded** — the readiness gate is not a bound, and the transport default is
not a bound anyone chose. **It fans out in parallel across devices**, because
each serial await is time during which every *other* device in the set is
already detached and recording nothing. And **the cheap liveness question runs
on its own timer**, never queued behind the expensive convergence sweep; each
pass refuses to overlap itself and logs the turn it drops, with `inFlightMs`.

## Consequences

- A hung broker now fails an attach in 20 s instead of 60 s. Nothing is lost:
  the device stays on the readiness-restore queue and the next pass retries it.
  The cost is that a genuinely slow first RTSP dial over 20 s is abandoned and
  retried rather than waited out.
- Recovery is parallel, so a degraded broker sees N simultaneous acquires rather
  than N sequential ones. That is deliberate — the alternative measured in lost
  footage — but it means the broker, not the recorder, is where any admission
  control for this burst has to live.
- Two timers exist where there was one. `onPlacementTick` stays on the
  convergence pass; anything expensive added later must go there too, or the
  liveness guarantee this record buys is silently spent.
- The recorder is its own runner (`resolveRunnerId` = `execution.group ??
  addonId`, and the recorder manifest entry declares no group), so none of this
  ever touched the stream-broker. Verified live: recorder pid 267770,
  stream-broker pid 267746. A recorder stall does **not** starve the broker.

## Enforcement

`packages/addon-pipeline/src/recorder/addon/__tests__/recording-controller-stall-bound.spec.ts`
— four tests, each verified to fail against the pre-fix controller: the bound is
named in the abandoned attach, a wedged device does not block its neighbour, the
liveness watchdog keeps cadence while convergence is stuck, and a skipped pass
says so. The third exists specifically to fail if the two passes are ever merged
back into one; it was confirmed red against a re-merged controller. No guard
script — review only for the "bound every new RPC" half of the rule.
