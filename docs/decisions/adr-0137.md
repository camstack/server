> Superseded in part by [D630](adr-0630-an-arm-is-refused-by-openings-armed-around-only-by-name.md): the second-press bypass is replaced by an explicit Arm anyway, and a per-mode non-blocking list is added. Refusal on open contacts and two-phase exclusions stand.

## Context

[D134](adr-0134.md) traced the operator's "un messaggio di errore quando non può
essere armato" [an error message when it cannot be armed] and recorded what it found: **the panel never refuses an arm.**
`alarmPanel.arm` returns `z.void()`, `requiresCode` is false, every mode in
`availableModes()` is armable, and the coverage warning D134 added is explicitly
a report rather than a refusal. The blocking semantics the operator's words
imply — the `advanced-notifier` reference's `bypassableDevices`, where a sensor
that is active at arm time prevents the mode — "would need a sensor-state
authority this hub does not have".

It has one now. Seven Home Assistant contact sensors were adopted the same day
(3243 porch, 3248 bathroom P0, 3254 hallway P1, 3260 cameretta, 3266 cantina,
3272 retro, 3278 finestra camera), the `contact` slice is `durability:
'restored'`, and `DEVICE_STATE_READERS` already collapses it to `open` /
`closed` — the same reading the `deviceState` gate uses for the panel itself.

Two things about the live installation shaped the design more than the reference
did:

- **The sensors are linked to no camera.** `resolveSensorEventCameras` drops a
  sensor-cap state change that resolves to zero cameras (`no-camera`), so those
  seven contacts emit **no `SensorEvent` at all** — no history row, no
  `onSensorEventPersisted`, and therefore no device-event rule can fire on them.
  A mirror fed purely off the event path would have been permanently empty here.
- The operator's own `[TEST] Intrusione Home — contatti` rule (`8b7b2aa1`) is
  gated `armed_home` on panel 1023, names those seven ids in
  `conditions.devices` and filters `sensorKinds: ['contact']` — which is exactly
  the derivation coverage already walks.

## Decision

**Which sensors block is DERIVED, from the rules, per mode.**
`alarmBlockingCandidates(rules, panel, mode)` takes the enabled rules gated on
`armed_<mode>` for this panel whose `sensorKinds` name `contact`, and reads
their `conditions.devices`. No list on the panel, no per-mode setting, no second
authority (D62) — the same source, walked the same way, as `alarmModeCoverage`.
A contact rule with NO device scope blocks nothing and says so: it covers every
contact on the hub, and a refusal naming devices the operator never associated
with the alarm is one they cannot act on.

**The arm path refuses, and it is the panel that refuses.** `arm()` asks an
injected `NcAlarmArmGuardHook` for the contacts that read open, through ONE
targeted `readDeviceStates` of at most those ids, with the `NcDeviceStateCache`
mirror as the fallback. Fail-open in all three ignorance cases — no guard, a
read that threw, a sensor neither source can answer for — each with a line,
because refusing an arm on ignorance sends the operator to shut a window that is
already shut. The candidates also join the cache's watched set, so the reconcile
tick keeps them readable on a hub where they emit no events.

**The refusal is a THROW plus a notification, and the split is a train.** The
hub's generated router validates this method against the HOST's copy of
`alarmPanelCapability`, which says `z.void()` — an addon that answered a
structured refusal would have it rejected by the router in front of it. So
`NcAlarmArmRefusedError` carries the machine-readable half to whoever called the
cap, and `alarm-arm-refused` — a fifth `NcSystemEventKind` — carries the
operator's half through the ordinary durable outbox (D126). Post-train, `arm`
gains a result shape; until then the phone is the channel that works, and it is
the one that matters when the caller is a notification button.

**The second press inside 60 s arms anyway, and the bypass is the
confirmation.** The reference makes bypassability a per-mode configuration
list; this makes it an act. The first press says which window is open, the
second says "I know". It expires, because a confirmation that outlives the
sentence it confirmed is not one, and it is per MODE: confirming `home` never
confirms `away`.

**An excluded sensor is re-armed by the OPEN that follows a close — never by
the close.** This is the sharp part. The rule that arms the alarm fires on a
contact's state CHANGE, so lifting the exclusion when the window shuts would
make shutting the window the thing that sets the alarm off. The exclusion has
two phases (`open` → `closed` → gone), both persisted with the machine in the
panel's own config, and the panel refuses a trigger whose attribution names an
excluded sensor — which is why `NcRuleFireRef` now carries `sourceDeviceId`:
`alarm-panel.trigger` takes a device id and nothing else, so the note handed
over in-process is the only way the panel can learn WHICH sensor is about to set
it off.

## Consequences

- **`alarmPanel.arm` can now fail.** Every caller — the admin UI, the viewer,
  a notification action button, a rule sequence — must be able to show an error.
  The action plane already turns a throw into the page that says so.
- A rule cannot be authored on `alarm-arm-refused` until the enum ships in a
  `@camstack/server` closure, exactly as D134 recorded for `alarm-arming`. The
  panel's `announceTargets` announcement is the pre-train delivery.
  `historySystemEventKind()` downgrades it to **`alarm-disarmed`** — the state
  the panel is actually in at that instant; downgrading to `alarm-armed` would
  put an arm that never happened in the list of arms. Delete both downgrades
  when the closure ships.
- The history view now renders with the row's frozen `textCount`. It did not,
  so every pluralised system sentence read as its `other` variant: a row a phone
  showed as "the porch window is open" appeared in history as "1 sensors are
  open" — one row, two sentences.
- **The seven live contacts still emit no device event**, so on this hub the
  exclusion lift and the arm-time fallback both ride the 30 s reconcile tick,
  and the operator's `[TEST]` contact rule cannot fire at all until the sensors
  are linked to a camera (or the ingest learns to attribute an unlinked sensor
  to itself). That is a separate gap, recorded here because the refusal path
  works regardless: it reads the contact SLICE, not the event.
- **A coverage exclusion is now asked only of a device that can answer it.**
  `detectionActive: false` is a switch on a camera and an ABSENCE on a contact
  sensor, which has no detection pipeline and never will. Reading the second as
  the first reported the whole of `home` as excluded the moment seven contacts
  joined it — live at 17:48, "Attivo tra 30 secondi — ma ogni dispositivo
  coperto da questa modalità è escluso: non proteggerà nulla" [Active in 30 seconds — but every device covered by this
  mode is excluded: it will protect nothing], about a mode
  arming seven working sensors. `alarmSkipReason` gates it on `isCamera`.
- The bypass has no configuration surface, deliberately. If per-mode
  bypassability is ever wanted, it is a filter over the same derived candidate
  set — never a second list of sensors.

## Enforcement

- `alarm-arm-guard.spec.ts` — the candidate derivation (disabled rule, other
  mode, other panel, non-contact rule, unscoped rule) and every branch of
  `decideArm` including the expiry and the mode isolation.
- `alarm-exclusions.spec.ts` — the two-phase lift, the unreadable reading, the
  durable round-trip with the phase, and the id-only legacy blob.
- `alarm-arm-refusal.spec.ts` — the whole thing on the REAL device: refusal
  leaves the panel disarmed, the bypass arms, the excluded sensor cannot
  trigger, the refused trigger drops its attribution, the lift, and a restart
  mid-armed that keeps the exclusions and their phase.
- `alarm-notifications.spec.ts` — the refusal as a durable row rendered in a
  language, the bypassed names in the armed and arming sentences, and
  `NcRuleFireRef.sourceDeviceId` surviving the rule → runner → panel journey.
- `alarm-texts.spec.ts` — the three new keys exist and render non-empty in both
  locales, singular and plural.
- Neutralisation confirmed: disabling the exclusion check in `trigger()`,
  removing the `NcAlarmArmRefusedError` throw, lifting the exclusion on the
  close, and dropping `sourceDeviceId` from `fireRefFor` each fail the tests
  that claim them. The `closed` phase not being persisted was found this way —
  the first implementation saved only the re-arm.
