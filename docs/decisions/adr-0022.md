## Context

`unraid/camstack.xml` and `unraid/camstack-agent.xml` were written by hand in
early July and never touched again. By the time anyone read them they described a
system that no longer existed, and nothing had noticed, because a container
template is XML that nothing compiles, nothing imports and nothing runs.

Both pointed at container images the release workflow does not publish. The
single-image collapse had folded `camstack-server` and `camstack-agent` into one
`camstack` image whose role is chosen at boot by `CAMSTACK_ROLE` — a variable
neither template set. A stranger following either template would have pulled
nothing at all.

The rest was worse, because it would have appeared to work:

- The hub mapped `/recordings` and never set `CAMSTACK_MEDIA_ROOT`. The share was
  mounted and then ignored; recordings went to `/data` and filled the cache.
- Neither mapped `/dev/bus/usb`, so the Coral USB permission fix-up in the
  Dockerfile entrypoint was dead code — the accelerator initialises and then
  sheds every frame.
- Neither declared a restart policy, so the container does not come back after a
  host reboot.
- The agent left `/config` unmapped although the image declares it a `VOLUME`, so
  Docker minted a fresh anonymous volume on every re-create.
- The icon URL pointed at a file that does not exist in the repository.

And underneath all of it, the thing that made every link decorative: both
templates pointed their `<Icon>` and `<TemplateURL>` at
`raw.githubusercontent.com/camstack/server`, which is a **private** repository.
Those URLs answer 404 to everyone except the people who could not notice, because
they are members and their browser is authenticated. `ghcr.io/camstack/camstack`
is private too, so the image cannot be pulled anonymously either.

The live containers were right about most of this; the templates were the copy
that rotted. That is the point. Comparing the two Unraid boxes against the repo
turned up nine separate disagreements, every one of them a fact that is written
down twice.

Writing a more careful XML file was tried first, in the sense that the previous
templates *are* the careful version — they carry long explanatory comments about
why `--shm-size=2g` is required and which env-var names the server really reads.
The care did not survive contact with a rename. Prose in a file nothing checks
decays at exactly the same rate as prose in a file with no comments at all.

## Decision

`unraid/*.xml` is generated by `scripts/deployment-templates.ts` and must never be
hand-edited. Everything the repository already declares — the published image
name, the version, the exposed ports, the declared volumes, the environment
variables the image bakes and the ones the server actually reads — is read out of
the `Dockerfile`, `.github/workflows/release.yml` and
`server/backend/src/boot/boot-config.ts` at generation time. What remains genuinely
undeclarable — which host paths an Unraid user should map, the network mode, the
runtime flags, the prose — is declared once in the `ROLES` spec in that file and
cross-checked against the derived facts by `scripts/check-deployment-templates.ts`.

Distribution forced a second choice. The request was to ship "via a plugin", and
an Unraid `.plg` is a real, versioned, auto-updating mechanism — it looks like the
right answer. It is not. Community Applications' feed entry is either a container,
keyed on `<Repository>`, or a plugin, keyed on `<PluginURL>`; there is no entry
kind for "a plugin that supplies Docker apps", so a `.plg` can never put CamStack
in the Apps search, which is the entire purpose. A `.plg` *can* write XML into
`/boot/config/plugins/dockerMan/templates-user/`, and a search across every public
`.plg` on GitHub turns up exactly one project doing so — a template-authoring
tool, not an application. The mechanism exists and the ecosystem has declined to
use it.

The generated files therefore target a **CA template repository**, and a separate
public one, because this repository is private and CA will not list a private
repo.

## Decision (distribution)

CamStack's Unraid templates are distributed as a Community Applications template
repository — a small public `camstack/unraid-templates` — not as a `.plg` plugin
and not from this repository. `unraid/` is generated in exactly that repo's
layout (`ca_profile.xml` and `icon.png` at the root, templates under
`templates/`), and every URL a template contains must resolve inside a public
CamStack location. Copying `unraid/` into the distribution repo is a deliberate
manual step.

## Consequences

- A rename of the published image, a new `EXPOSE`, or a new `VOLUME` changes the
  templates on the commit that makes the change, via the pre-commit hook.
- The spec is still hand-written, so a *wrong* description is still possible. The
  guard proves the template agrees with the image, not that the defaults are wise.
- Every runtime flag now needs a recorded reason in `EXTRA_PARAM_REASONS`. An
  unexplained flag is one nobody dares remove and nobody can justify, and both
  templates carried one.
- The generated banner cannot contain a double hyphen, because XML comments may
  not. This is not a stylistic point: Unraid rejects the whole template and the
  container silently never appears. The first generated draft had exactly this
  bug and `xmllint` caught it, so the guard now checks it too.
- Local secrets stay local. The live `templates-user` XML on the hub contains the
  real admin password and JWT secret; the generated template ships empty fields.
  These two files are not interchangeable and the repository copy is not a backup
  of the running one.
- Publishing needs the operator: a public `camstack/unraid-templates` repo, a
  public GHCR package, and one submission at `ca.unraid.net/submit/new`. The
  guard cannot check any of the three, because all three are facts about the
  outside world. `docs/architecture/unraid.md` lists them.
- The copy into the distribution repo is manual and will be forgotten. That is
  accepted rather than automated: pushing to a second repository from CI needs a
  cross-repo token, and the alternative failure — a stale public template — is
  visible and recoverable, whereas a leaked token is not. If it becomes a real
  problem, automate it then.
- **A template change reaches new installs only.** Unraid's
  `DockerClient::updateUserTemplate()` is disabled in the shipping code and
  returns before doing anything; an installed container keeps a frozen snapshot,
  and re-installing creates a second container rather than updating the first.
  So a change existing users must adopt has to be absorbed by the image, not
  expressed in the template. This constrains every future template edit and is
  the single most important thing on this page.

## Enforcement

`scripts/check-deployment-templates.ts`, wired into `.github/workflows/ci.yml` and
`.husky/pre-commit`. It re-derives the templates and fails on drift, then checks
the on-disk XML against the image contract independently: the image is the one
`release.yml` pushes, every environment variable is one the code reads, every
`VOLUME` is mapped, every published port is EXPOSEd, a mapped path the server
locates by env var has that variable set to it, and the Coral bus mapping is
paired with its cgroup rule.
