## Context

The multi-device balancer's stored device map defaults to opt-OUT: every
discovered accelerator is `enabled: true` unless the operator stored
`enabled: false` (spec C2), with CPU as the single opt-IN exception. When the
Coral executor landed, the working rule was "selectable, never auto-picked" —
but nothing enforced it, and the opt-OUT default quietly violated it.

On 2026-08-01 the hub's plugged-in Coral (`edgetpu:usb`) — which no operator
had ever enabled — entered the session rotation alongside `openvino:gpu` and
`openvino:npu` (all tied at zero load, round-robin), so every third session of
camera 101 landed on the tflite pool. The auto model resolution then returned
`yolo26n` (no tflite build) because `resolveDefaultDetectionModel`'s fallback
skipped its own format-build check, and every frame burned a 3-retry model
download (~5.5 s): 101 fell from 12.8 fps / 58 ms to 2.4 fps / 5532 ms for
hours. The operator's mental model was "the Coral is disabled" — because they
had never enabled it.

The tried-first alternative was to keep opt-OUT and rely on the (new)
capability gate alone. That makes the dispatch *survivable* but still wrong:
a Coral runs a DIFFERENT, weaker model family (tflite SSD MobileNet vs the
YOLO family every other accelerator runs), so auto-enrolling it silently
changes detection *quality* on a third of sessions — not just placement.

## Decision

`edgetpu` devices join CPU as opt-IN in `mergeInferenceDevices`: a probed
Coral with no stored entry is `enabled: false`. It surfaces in the UI and in
`getNodeInferenceDevices` as available-but-disabled; an operator who wants it
balanced stores `enabled: true` explicitly. No dispatch path may route a
camera root to an edgetpu pool the operator has not opted in.

## Consequences

- Plugging in a Coral does nothing until it is enabled — by design. The
  "plug and it works" behaviour is forfeited in exchange for detection
  quality never changing without an operator action.
- A Coral-ONLY node has no auto-enabled accelerator; its runner serves
  cameras from the default (CPU) pool until the operator opts the Coral in.
- The executor-side capability gate (`resolveStepsForDispatch`) remains the
  backstop for the same failure class arriving via explicit pins.

## Enforcement

`node-inference-devices-cap.spec.ts` pins all three behaviours: unconfigured
Coral merges `enabled: false`, explicit `enabled: true` wins, and an
unconfigured Coral never appears in `resolveInferenceDeviceEligibility`'s
eligible set. `default-detection-model.spec.ts` separately pins that the
resolver never returns a format-less model id for any backend×format.
