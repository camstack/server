## Context

The Alexa link is two credentials pointing in opposite directions, stored in two
different places:

1. **The hub-side session** — the token Amazon presents to us. A row in
   `oauth_sessions`, created by `oauthExchangeCode` at consent.
2. **The Amazon push grant** — the LWA token we present to Amazon, harvested by
   `POST /addon/export-alexa/oauth/lwa-tokens` and stored in this addon's own
   `AlexaSettings.tokens`. It is what `LwaEventGateway` uses to push motion,
   doorbell, battery and Add/DeleteReports.

Only the first was operable. Admin → System → Identity → Linked Sessions can
revoke it, and `oauthRefresh` / `oauthVerifyAccessToken` both re-read the row, so
revocation bites on the very next directive. But nothing removed the second: the
LWA refresh token is Amazon's and survives our revocation entirely. An operator
who "unlinked" from the admin UI would have left the Event Gateway pushing
events at the account they had just disconnected, indefinitely — the only thing
that ever removes a linked account today is Amazon happening to answer 403
(`lwa-event-gateway.ts`, `removeLinkedAccount`).

Two things turned that from untidy into the only path that matters. The Alexa
descriptor was changed to `refreshTokenTtlSec: 'never'` (2026-08-09) because a
30-day refresh silently killed the skill a month after setup — so **nothing
expires, and revocation is now the sole severance**. And the skill is distributed
as a **beta**, so it is absent from the public skills catalogue and the operator
cannot rely on the Alexa app's "Disable skill → re-enable → re-link" route to
force a fresh link. The CamStack side had to be able to do it, and had no control
that could.

The first design considered was a per-account unlink. It cannot be built: nothing
in this system learns which Amazon account completed a link. Alexa's
account-linking contract hands our own token back, we never call
`api.amazon.com/user/profile`, and both the `oauth_sessions` row and
`LinkedAccount.userId` carry the CAMSTACK user who consented. Two Amazon accounts
linked by one operator are indistinguishable. The second considered was a new
`oauth-integration` cap method to list/revoke an integration's own sessions —
rejected because it would put a single addon's need on the `@camstack/types`
publish train when `userManagement.listOauthSessions` / `revokeOauthSession` are
already reachable from an addon (mesh calls carry a synthetic admin context).

## Decision

An integration's unlink control lives on **that integration's own settings page**
and severs **both** halves in one action: it revokes every ACTIVE
`oauth_sessions` row for its `integrationId`, and it discards the external-side
grant that the addon itself stores. It stores nothing of its own to do this —
each half is written through the authority that already owned it, per
[D62](adr-0062.md). Revoking the session alone is not an unlink and must not be
described as one. It is all-or-nothing whenever the external identity is not
recorded, and it revokes *every* active row rather than the newest, because
`oauthExchangeCode` mints a fresh row per link and never retires the previous
one.

## Consequences

- The addon must be able to reach `userManagement.listOauthSessions` /
  `revokeOauthSession`. Both are `auth: 'admin'`; addon calls pass because
  `createMeshTrpcContext` builds an admin context. If that ever narrows, this
  control breaks and the operator is left with no severance path at all.
- `listOauthSessions` returns every session for every integration and
  `revokeOauthSession` takes an opaque id, so the integration filter is the
  caller's responsibility (`selectAlexaSessionIdsToRevoke`). A filter that
  matched too widely would revoke Home Assistant's link.
- Because scopes are frozen at consent — `oauthRefresh` re-mints from the token's
  own claims, never from the descriptor — this unlink is also the only way a
  widened `requestedScopes` set ever takes effect. That has to be said on the
  control, or a scope change looks like it did nothing.
- No `DeleteReport` is sent first. It would need the very grant being discarded,
  and its delivery cannot be verified (a 2xx is envelope acceptance, not
  delivery); Amazon drops the endpoints itself on unlink. Ghosts stay the job of
  the existing purge action.
- `exportedEndpoints` / `exportedSignatures` are cleared with the grant: they mean
  "what Alexa was last told", and a stale signature would suppress the reconcile's
  re-push after the next link.

## Enforcement

Unit tests on the pure selection
(`packages/addon-export-alexa/src/__tests__/link-status.spec.ts`) cover the two
ways the filter can be wrong: including a revoked row, and dropping the older of
two active rows. The both-halves property itself is review-only — there is no
guard that a future integration's unlink clears its own external grant, and the
Alexa link is in daily production use, so the mutation has never been executed
against the live hub.
