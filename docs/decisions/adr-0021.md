## Context

`HOST_EXTERNAL_SPECIFIERS` (`packages/system/src/kernel/host-externals.ts:28`)
lists `sharp` and `node-av` as host-provided: an addon bundle leaves those
imports unbundled, and the runner's resolver hook anchors them inside
`CAMSTACK_FRAMEWORK_DIR/node_modules`. That redirect is live in production — the
addon runners exec out of the active root closure, so the hook does not take its
early-return, and 25 of 26 installed addons on the hub carry **no**
`node_modules` at all. They resolve those two natives exclusively through it.

The runtime already treated their presence as an invariant.
`REQUIRED_NATIVE_PACKAGES` (`packages/node-root/src/root-single-copy.ts:142`)
names `better-sqlite3`, `sharp` and `node-av`, and
`findMissingNativePrebuilds` (`packages/node-root/src/root-single-copy.ts:179`)
**aborts** any server update whose staged closure lacks a `.node` for one of
them — once when staging (`packages/node-root/src/root-update-service.ts:487`)
and again in the starter before the swap
(`packages/node-root/src/root-single-copy.ts:261`). The Docker image asserts the
same three by hand.

**The failure: nothing in the closure declared them.** `@camstack/server`'s
`dependencies` named neither. They arrived *transitively*, because three seed
addons that `@camstack/server` happens to depend on —
`packages/addon-decoder-nodeav`, `packages/addon-pipeline`,
`packages/addon-post-analysis` — declare them as ordinary dependencies and npm
hoists them to the closure root. `addon-pipeline`'s `node-av` declaration is
dead (no source file in it imports `node-av`), so a load-bearing production
guarantee rested partly on a manifest that was already wrong. Removing those
declarations as cleanup — which looked like a safe tidy-up — would have deleted
the only path by which `node-av` enters the published closure; the next
`applyServerUpdate` on every node would have been refused, fail-closed, and the
fleet frozen. The invariant was enforced at runtime and satisfied by accident at
build time.

The second half of the failure is a straight contradiction inside one package.
`host-externals.ts:28-29` says *the framework provides these*.
`RUNTIME_NATIVE_KEEP` (`packages/system/src/kernel/fs-utils.ts:41`, `:43`) says
*install these per addon* — it keeps `node-av` and `sharp` in an addon's
stripped manifest so the installer's `npm install` re-fetches them into the
addon's own `node_modules`. Both ship in `@camstack/system`, and the two models
produce visibly different nodes: the hub (installed via the staged-swap path,
which skips npm entirely) has addons with zero `node_modules`, while an agent
installed through the tarball path carries a 416 MiB private `addon-pipeline`
— its own copy of `node-av` shadowing the closure's.

## Decision

A native library an addon may import is **host-provided**: it is declared in the
server closure (`server/backend/package.json`), listed in
`HOST_EXTERNAL_SPECIFIERS`, and asserted by `findMissingNativePrebuilds`. An
addon **requests** it — an import its bundler externalises — and never
**installs** it. Adding one, or changing its version, is therefore a server
update, not a `camstack deploy`.

Corollary: the closure must declare every third-party host-external explicitly.
A host-external that reaches the closure only as some other package's transitive
dependency is a bug even while it works, because the declaration is what the
resolver hook's promise is made of.

The eligible set is **N-API** natives that upstream ships prebuilt for every
target platform: `sharp` and `node-av` today. `better-sqlite3` is the
grandfathered exception in the other direction — it is deliberately *not*
host-external (no addon imports it; only `@camstack/system`'s sqlite-storage
builtin does), it is node-gyp, and it keeps its own ABI-matched re-fetch path
(`packages/system/src/kernel/deps/ensure-addon-natives.ts`).

## Consequences

- A native version bump costs a publish plus `applyServerUpdate` on every node,
  and an Electron rebuild (~28 min of CI). It cannot ride an addon deploy.
- Version skew across nodes stays safe **within a major**: each node's closure
  version must satisfy the range every addon installed *on that node* declares,
  which `^6` / `^0.35` gives automatically. A **major** bump is the hazard — the
  closure and the addons must go out as one wave, agents first.
- The root's declared range must stay at least as loose as every addon's, or npm
  resolution changes under a declaration that was meant to change nothing.
- No ABI pinning is accepted. That is a property of the eligible set, not a
  wish: N-API binaries are one-per-platform-arch and stable across Node and
  Electron, and the packaged desktop app runs the server under a bundled bare
  Node rather than Electron-as-Node, so Electron's ABI never enters it.
- `RUNTIME_NATIVE_KEEP` still contradicts this rule for `node-av` and `sharp`.
  Removing them from it is the step that makes the closure the only source on
  every node — and reclaims ~460 MiB on an agent and ~104 MiB in a dev data dir.
  It is sequenced after every node runs a closure that declares them.

## Qualifies D18 — and does not reverse it

[D18](adr-0018.md) removed `@camstack/shm-ring`, calling out its cost as *"it is
a native host-external, so it pins ABI compatibility across every node; it needs
a prebuild per platform and a CI job to produce them"*. Read as a blanket
prohibition on native host-externals, this record looks like a reversal. It is
not, and the difference is the one D18's own sentence turns on:

- `shm-ring` is a **node-gyp** native *this project builds*. ABI-specific, so
  Node 22 vs 24 vs Electron each need a distinct binary — hence the pinning, and
  hence `prebuild-shm-ring.yml` and `scripts/check-prebuilds.sh`, which exist <!-- drift-ok: deleted in D763 -->
  solely because we produce those binaries ourselves.
- `sharp` and `node-av` are **N-API**, published upstream as platform sibling
  packages (`@img/…`, `@seydx/…`) containing a ready `.node`. Nothing compiles on
  any target, on any node, ever. We build and ship nothing for them.

And they were not introduced here: all three natives were already in every
closure when D18 was written, and `REQUIRED_NATIVE_PACKAGES` already named them.
D18's decision stands unchanged — `shm-ring` stays removed, for exactly the
reason D18 gave.

## Enforcement

**Live, fail-closed:** `findMissingNativePrebuilds` refuses a staging closure or
a root swap that lacks a `.node` for any of `better-sqlite3` / `sharp` /
`node-av`, at both the staging and the starter gate. A node cannot end up
running a closure that breaks the resolver hook's promise; it stays on its
previous version instead.

**Not enforced, and worth knowing:** nothing checks that every entry in
`HOST_EXTERNAL_SPECIFIERS` is *declared* in `server/backend/package.json` — that
is precisely the gap this record was written about, and it is currently held by
review alone. Nothing forbids an addon from declaring a host-external as its own
dependency either; three do today, and they are load-bearing until the closure
declaration has reached every node. Both are proposed guards, not existing ones.
`REQUIRED_NATIVE_PACKAGES` and `HOST_EXTERNAL_SPECIFIERS` are also two
hand-maintained lists in two packages that must agree; deriving one from the
other is the way to stop them drifting.
