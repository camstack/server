## Context

On 2026-08-24 at 12:38:36Z the group entity (retired by D330) wrote eleven
sealed rows for ONE group on camera 111 in 1.7 s: eleven different random
ids, the same two members, timestamps clustered to the millisecond. The
minute before, hub-main had logged 138 `UDS request timed out after 60000ms`
and the runner had stood still for ~2.5 min. Diagnosed 2026-09-05 from
`git show 160200681^` and `/data/logs/camstack-2026-08-24.log`:

1. The sealer ran on a 5 s timer with **no single-flight latch**
   (`void this.groupSealer?.flushIdle(...)`, `index.ts:8665`), next to a
   track sweep that had one and said so in a comment.
2. A group stayed **selectable until its persist resolved** — `idleGroups`
   re-selected it every tick while the previous persist was still in flight
   (`group-sealer.ts:107-117`).
3. The duplicate gate was a **read-then-insert** on a random UUID key
   (`group-store.ts:143,177`): N concurrent reads all saw "no members", and a
   store keyed on `randomUUID()` cannot refuse anything. Row and members were
   N+1 separate `set` calls, so a timeout in the middle left a row without
   membership and the gate read "empty" forever after.
4. The gate read sat outside the `try`: a timeout aborted the pass in
   silence.

The test passed because its fake store answered `membersOfTracks: []`
forever and never recorded what `insert` wrote — the fake supplying what
production forgot to fetch. Two more writers (`sealWindow`, `recoverCamera`)
shared the same gate on the same buffer.

A partial unique index on `(deviceId) WHERE sealedAt IS NULL` was proposed
as the defence for the successor entity. Against THIS failure it would have
blocked none of the eleven rows: they were born `sealed: true`.

## Decision

A durable session entity (the `Summary`, and any successor):

1. is **created open under a deterministic key** — `id = f(deviceId,
   openedAt)` — with an upsert, so a repeated write is a no-op, not a row;
2. is **sealed by a conditional transition on the existing row**
   (`updateWhere { id, sealedAt: null }`), never by an insert; a second
   sealer updates 0 rows and knows it;
3. keeps **"at most one open per camera" in the store** — a unique index on
   an `openDeviceId` column that is the device id while open and NULL once
   sealed (SQLite unique indexes ignore NULLs) — and reads open/sealed from
   the row; RAM is a cache that may lie;
4. writes the **row and its members in one call** (`insertMany`), never as
   N+1 round trips;
5. runs its sweep **single-flight**, the way `TrackCloser` does, and never
   `void`s an async sweep without a latch;
6. treats a **failed gate read as "abort the write"**, never as "nothing
   there" (D49), and logs every branch that drops work with
   `tags: { deviceId }`.

The partial unique index is the net under 1–3, not the mechanism.

## Consequences

- The sealer becomes idempotent under retries and restarts; the eleven-row
  case collapses to one row and ten `updated: 0` transitions.
- A store timeout during a seal leaves a row OPEN, which the next sweep
  seals again — the failure mode is "sealed late", never "sealed twice".
- Tests must use a store fake that RECORDS writes and answers reads from
  them, and must run the sweep twice concurrently.

## Enforcement

`summary-store.spec.ts` (deterministic key, seal-in-place returns 0 on the
second call, unique open-per-camera) and `summary-sealer.spec.ts` (two
concurrent sweeps → one row). Review only for new callers.
