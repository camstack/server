## Context

On 2026-08-07 at 12:04:22 UTC a real doorbell press on camera 101 fired
correctly at the source — `virtual-doorbell: pressed` — one day after
[D72](adr-0072.md) repaired the gate that had been eating presses. The event
reached both exporters. The operator got nothing: no iPhone doorbell
notification, no Echo announcement.

Neither chain could say why, and for opposite-looking reasons that are the same
reason.

**HomeKit produced no line at all.** `buildDoorbell` subscribes to
`DoorbellOnPressed` and calls `DoorbellController.ringDoorbell()`, which returns
`void`. Inside hap-nodejs the ring reaches
`HAPConnection.sendEvent(aid, iid, …)`, which opens with

```js
if (!this.registeredEvents.has(aid + "." + iid)) { return }
```

A connection that has not SUBSCRIBED to that characteristic is skipped in
silence, and a ring with no subscribed connection evaporates without a word
anywhere in the stack. "Delivered to a phone" and "dropped on the floor" were
therefore the same observation: nothing. Every hypothesis about the HAP side —
did the event cross the fork boundary, does the accessory have a Doorbell
service, is it paired — had to be answered from outside the process (the
persisted `AccessoryInfo` says `category: 18`, two paired clients; the parent's
`child event patterns` shows `doorbell.onPressed` appearing right after 101's
accessory is built). None of that should require reading a pairing blob over
SSH.

**Alexa produced a line that could not be wrong.** `alexa lwa-gateway: doorbell
press posted` was logged whenever `fetch` resolved and `response.ok` was true —
no status, and no acknowledgement of what a 2xx from the Event Gateway means. It
means the ENVELOPE parsed. Amazon answers `202 Accepted` to a well-formed event
aimed at an endpoint that cannot act on it and discards it in the cloud, so the
one interesting failure mode is indistinguishable from success.

That failure mode is reachable here by construction. Alexa keeps its own copy of
every endpoint's capability list, refreshed by nothing but an
`AddOrUpdateReport` we push — and every push trigger the addon had was an
OPERATOR action (expose, unexpose, account link, the manual "Re-sync devices"
button). None fires when a camera's capability bindings change. A camera that
gains the `doorbell` wrapper AFTER it was exposed therefore keeps a cloud-side
endpoint with no `Alexa.DoorbellEventSource` and `displayCategories: ['CAMERA']`
— permanently, and every press is accepted and dropped. For 101 that had not
happened (the log shows a push on 08-04 with `isDoorbell=true`), but only luck
distinguished this camera from one where it had, and nothing in the system could
tell the two apart.

Two smaller things were found in the same read. The payload's
`endpoint.scope.token` carried the literal `replaced-by-authorization-header`,
on a comment's unverified claim that "Amazon ignores the scope.token value" —
the Smart Home spec puts the bearer token in both the header and the scope, and
a 202 cannot disprove the claim either way. And every early return on the
doorbell path (device not in the registry, camera not exposed) was silent.

## Decision

**A forward that can silently discard work states its own delivery, and an
export that advertises a shape to a remote registry reconciles that shape
against the bindings that are its authority.**

Concretely, for every export chain:

1. **Delivery is reported, not assumed.** A hop whose failure mode is a silent
   return is probed before the call and the outcome logged, tagged `deviceId`:
   HomeKit logs the count of HAP connections actually subscribed to the
   characteristic and says at `warn` when it is zero; Alexa logs the HTTP status
   on success as well as failure, and the success line says out loud that a 2xx
   is acceptance of an envelope. A library that returns `void` is not permission
   to log nothing.

2. **The advertised shape is reconciled against the binding authority.** The
   endpoint set a device would build NOW is hashed
   (`endpointsSignature` — endpoint ids, display categories, declared interfaces
   including instance names; deliberately NOT the whole payload, so a friendly
   name edit costs nothing) and compared with the signature last pushed. On
   drift, re-push. The trigger is `DeviceBindingsChanged`, debounced per device,
   plus one pass at boot — because bindings ARE the authority for which
   interfaces an endpoint has. An unchanged shape performs zero remote calls and
   zero writes, which is precisely what makes it safe to hang off binding churn.

3. **A payload carries what the spec says it carries**, and is built per
   attempt from the credential that attempt will use — so a token refresh can
   never ship a body whose embedded token contradicts its own header.

## Consequences

- **A stale cloud registry is now self-healing and, more importantly, visible.**
  `alexa sync: endpoint shape drifted` names the before/after signature and the
  interfaces; the doorbell path pre-flights the same signature and warns when
  the endpoint Alexa knows cannot receive the press. The first boot after this
  change re-pushed all three exposed endpoints (`from=never-recorded`).
- **The HomeKit doorbell now has three distinct outcomes in the log** — armed at
  accessory build, `SINGLE_PRESS pushed to HomeKit` with a subscriber count, or
  `rang but NO HomeKit controller is subscribed`. The last one is a real
  condition, not a hypothetical: each `camstack deploy` republishes the
  accessory on a fresh ephemeral port, and iOS takes time to re-resolve and
  re-subscribe. A press in that window was previously indistinguishable from a
  working one.
- **What this still does NOT prove.** Neither change can observe the Apple or
  Amazon side of the last hop. A subscribed connection is not a delivered
  notification (iOS per-accessory notification settings), and a correctly
  advertised `DoorbellEventSource` is not an announcement (the Alexa app's
  per-device doorbell-announcement toggle and the Echo selection). The rule is
  that the hub proves everything up to the boundary and says where the boundary
  is — not that it claims the boundary does not exist.
- **Cost.** One extra per-device signature in the addon store, one debounced
  rebuild per bindings change (no remote call unless the shape moved), and a
  cheap read of hap-nodejs internals on the ring path.

## Enforcement

- **Tests.** `endpoint-signature.spec.ts` pins that gaining/losing an interface
  or a display category moves the signature while capability order and a
  friendly-name edit do not; `sync-engine-reconcile.spec.ts` pins the drift
  re-push, the no-op on an unchanged shape, and that an empty build never pushes
  and never destroys a recorded signature; `doorbell-delivery.spec.ts` pins the
  zero-subscriber detection and that an unrecognised hap-nodejs shape degrades
  instead of throwing on the ring path; `event-scope-token.spec.ts` pins the
  bearer token in every payload.

  Both fixes were confirmed to go red when removed: neutering the drift
  comparison fails exactly the two drift properties, and neutering the
  zero-subscriber predicate fails three.
- **Guard.** None. The rule is about a shape of code, not a token a script can
  grep for — review only, which is worth knowing when trusting it.
