## Context

Install, update, uninstall and restart are four operator-facing verbs, and it is
tempting to give each its own mechanism — in particular to make "update" cheap by
swapping module code inside a live process. In-process hot-reload of an addon
means old and new code coexist: closures captured by timers, event listeners
registered by the previous version, half-migrated state. The failures it produces
are not reproducible, which makes them unfixable rather than merely hard.

## Decision

All four verbs reduce to the same two operations: (re)spawn the addon's
`addon-runner`, or stop it. There is no in-process hot-reload. A changed manifest
re-registers the node's whole capability set atomically through the
[D3](adr-0003.md) handshake.

## Consequences

- An addon update costs a process restart. That is the price of every version of
  the addon being a clean process, and it is worth paying.
- Because the manifest re-registers *whole*, a partially-booted addon can never
  advertise a partial capability set.
- Co-located addons ([D2](adr-0002.md)) restart together — one process, one
  lifecycle.

## Enforcement

Review. Structurally the loader offers no reload seam, which is the intended form
of enforcement: the wrong thing is not expressible.
