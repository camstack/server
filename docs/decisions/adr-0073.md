## Context

The detail/CLIP enrichment plane appeared to have two independent pixel sources
and had one. `TrackDetailDispatcher.runOnce` tried `frameHandle`, then — on a
miss — `cropJpeg` captured by `captureCrop`. But `captureCrop` is NATIVE-STRICT
(S4): it asks the decode worker for the same ROI from the same native lease and
returns `null` on exactly the miss that sent the dispatch there. The two halves
failed together, `MAX_CONSECUTIVE_FRAME_MISSES` (3) was reached in three
consecutive ticks, and the step was abandoned for that track for ever.

The miss is not an edge case. `NATIVE_LEASE_TTL_MS` is 1 200 ms; the dispatcher
ticks at 1 000 ms with 2 in flight per device behind 500–900 ms inferences. The
window is structurally unreachable for most dispatches, and the measurement said
so: ~3 600 runner-side `no crop source resolved` drops per 3 h, on all three
nodes, chronic, not node-specific.

`resolveCrop` had a `frameJpeg` branch the whole time — added for the embedding
rebuild by [D52](adr-0052.md), reachable by no live caller. The 160 MB
`RetainedFrameStore`, with a 3 s / 16-frame per-device floor, was never consulted
for a detail crop.

The same shape sat one layer over, in the media ladder.
`TrackStore.markSnapshotPending` advanced `lastSnapshotAt` at the moment a
snapshot was DECIDED, and its own docblock stated the consequence: *"No rollback:
if the write later fails the slot is simply lost."* Its four siblings all advance
their bookkeeping in the dispatch `.then`, from the ids that actually persisted.
`snapshot` was the only kind with no retry of any shape — 197 lost in 3 h.

And the diagnostics that would have shown either of these were designed in pairs
with one half at debug. The runner's native-miss classification
(`no-registry-entry` / `worker-lease-gone`, with `handleAgeMs`) was debug while
the caller's round-trip line was warn; the pinned-frame resolve logged its throw
at debug and its `null` return not at all, while the batch loss it causes has
always been a warn — 383 batch losses in 3 h, `pinned: false` on 100% of them,
and no line anywhere saying why.

Two directions were rejected before this one. Raising the lease TTL: it treats a
1 200 ms window as the problem when the request is routinely seconds late, and it
costs decode-worker RAM on every camera to serve the tail. Relaxing
`MAX_CONSECUTIVE_FRAME_MISSES`: it makes a track retry a source that cannot come
back, which is what that bound exists to stop.

## Decision

**A fallback must not share the failure mode of the source it backs up.** The
detail plane's crop ladder is `frameHandle` → `frameJpeg` → `cropJpeg`: the
handle first because it is free when it hits and is the only rung that yields a
`nativeCropRef`; the FULL frame second, fetched from the node that owns the
handle and handed to the runner UNCUT so the rectangle still comes from
`deriveDetailCropRect` and the one cluster convention ([D52](adr-0052.md)); the
pre-cut tile last, because the caller decided its rectangle and because it shares
rung 1's failure. The full frame is requested at the frame's OWN width and a
reply at any other scale is REFUSED — the runner reads `parent.bbox` as pixels of
the image it is handed, and a crop on scenery is worse than no crop.

**Every media kind advances its cadence clock only on landing.** A capture that
is decided may move the gate synchronously (the anti-burst debounce), but a
capture that did not persist gives the interval back, bounded — three consecutive
non-landings, reset only by a landing ([D60](adr-0060.md)).

**Both halves of a diagnostic pair share a log level**, and a miss's level
follows its CONSEQUENCE: a native miss the RAM tier is allowed to serve stays
debug, one the caller is handed as `null` is a warn carrying the reason.

## Consequences

- **The derived crop is sub-native.** A full-frame request falls back to the
  retained ≤640 detection raster, so a rung-2 crop is cut from that rather than
  from the native surface. It is honest sub-native and never upscaled — the same
  contract `captureDisplayCrop` already has — and `CropSource.source` reads
  `'derived'`, not `'native'`, so no `nativeCropRef` is forwarded and leaf
  children stay on the tile. The alternative on this path is not a native crop;
  it is no crop and a permanently abandoned step. Face and plate enrichment
  therefore get a lower-resolution input where they previously got none, and if
  a recognition-quality regression appears this is the first place to look.
- **`cropJpeg` is now nearly dead weight**, since the native miss that empties
  rung 1 empties it too. It is kept because it costs a call only when rung 2 also
  failed, and because the rebuild path's contract for it is unchanged.
- **The rung-2 fetch is not CaptureScheduler-routed.** The dispatcher already
  bounds itself at 2 in flight per device and the fetch happens only after rung 1
  missed; queueing it behind the media lane would routinely push it past the 3 s
  retained window and turn the fallback into a second guaranteed miss. This is a
  deliberate second exemption alongside the existing `cropJpeg` one.
- **D9/D18 hold.** One compressed JPEG per track per dispatch, on demand, after a
  miss. Not frame-rate traffic and never raw pixels.
- **A conceded snapshot slot does not reset the failure count.** Resetting it
  hands the same dead camera three fresh per-frame retries after every conceded
  slot — a 4x capture rate on the camera already failing. The first draft did
  reset; the end-to-end spec measured 13 returned intervals where the bound says
  3, which is how it was caught.
- The runner's native-crop line moved to warn only for the `miss` tier. Its
  volume is the ROI-miss rate (~20/min cluster-wide), not the total miss rate.

## Enforcement

Tests, each confirmed red with its fix removed:

- `packages/addon-pipeline/src/pipeline-runner/__tests__/detail-crop-ladder.spec.ts`
  — which rung wins, that a derived tile carries no `nativeCropRef`, and that a
  rung-1 miss reaches the drop line with its reason.
- `packages/addon-post-analysis/src/pipeline-analytics/__tests__/detail-frame-jpeg-fallback.spec.ts`
  — reproduces the production shape (handle `null` AND `captureCropBase64`
  `null`), so nothing can pass because a fake supplied what production cannot
  fetch. Includes the wrong-scale refusal.
- `__tests__/snapshot-rollback.spec.ts` drives the store and then the REAL
  `evaluatePeriodicSnapshot`, so restoring the clock without the movement bbox
  still fails; `__tests__/snapshot-rollback-e2e.spec.ts` boots the addon and reads
  its log, because a correct store method proves nothing about whether the frame
  loop calls it — the shape of this defect and of the last two beside it.
- `__tests__/device-log-tags.spec.ts` and the orchestrator's
  `dispatch-log-device-tag.spec.ts` pin `tags: { deviceId }` on the device-scoped
  lines; each source-shape assertion was checked against the pre-fix source.

No guard script. The invariant "a fallback does not share its primary's failure
mode" is a claim about causes, not a pattern in the text, and a grep-guard that
pretended otherwise would read as verification.
