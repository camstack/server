## Context

An addon that crashes on startup — bad config, missing native module, a device
that answers with something unparseable — will crash again immediately when
respawned. An unbounded respawn loop turns that into a busy loop that consumes a
core, floods the log with the same stack trace, and hides the original error under
thousands of copies of itself. The node stays "up" while doing nothing useful,
which is worse than being visibly down.

## Decision

`CrashSupervisor` respawns a crashed runner with exponential backoff, but stops
after `MAX_CRASHES_IN_WINDOW` crashes inside `CRASH_WINDOW_MS` and marks the
runner **`failed`** — a terminal state. Recovery from terminal is an explicit
operator action.

## Consequences

- A persistently broken addon fails loudly and stays failed, with its first stack
  trace still findable.
- A transient crash (a camera dropping mid-handshake) still self-heals, because
  the window resets.
- No code path may respawn a runner outside the supervisor, or the bound is
  bypassed.

## Enforcement

Review. The constants are the contract; changing them is a decision, not a tuning
exercise.
