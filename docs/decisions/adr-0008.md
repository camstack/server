## Context

There was more than one event mechanism, and — more damaging — no stated
guarantee for any of them. Without a guarantee, every author has to guess, and the
guess is always "it arrives", because in development it always does. Cross-process
broadcasts drop: a node reconnecting, a child restarting, a broker mid-handshake.
Code that treated a dropped event as impossible left durable state permanently
wrong, and the bug surfaced hours later somewhere unrelated.

## Decision

One bus. Emit and subscribe **only** through `ctx.eventBus`.

Delivery is two-tier and the caller cannot tell the difference: hub-local addon
children exchange events with the hub over the UDS channel (the parent bridges
them onto the in-hub bus); across nodes they travel as per-category Moleculer
broadcasts (`camstack.evt.<category>`) into a single `$event-bus` service.

And the rule that matters: **events are telemetry and may be dropped.** If a
dropped message would leave durable state wrong, use an RPC — or an event *plus*
an RPC snapshot-reconcile on `$node.connected`, which is what the readiness
registry does.

## Consequences

- "Did it arrive?" is answerable per call site by asking which mechanism was used,
  instead of being unanswerable.
- Some flows carry both an event (fast, lossy) and a periodic authoritative
  re-pull (slow, correct). That duplication is deliberate and should not be
  "simplified".
- Event categories are a typed enum, never plain strings, so a category cannot be
  invented at a call site.

## Enforcement

`scripts/check-event-bus-usage.ts` ([D11](adr-0011.md)) fails the build on a
hand-rolled `camstack.evt.*` topic. `scripts/check-event-kind-coverage.ts` fails
the build when an eventful sensor/control cap has no taxonomy entry. Both wired
into CI. The telemetry-vs-RPC judgement itself is review-only.
