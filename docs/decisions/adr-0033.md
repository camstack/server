## Context

Every settings mutation in an addon context is read-modify-write:
`readAddonStore` → merge the caller's patch → `writeAddonStore`. `readBlob`
answered `{}` for BOTH "this addon has no settings yet" and "the read failed",
because its `catch` returned the same empty object as a miss.

On 2026-07-31 the UDS transport stalled for over a minute. The log shows the
sequence:

```
04:06:23  recorder — readiness: UDS snapshot request failed: UDS request timed out after 60000ms
04:06:50  recording stopped {pipelineKeys=[101|native:main, slot-3, sub]}
04:09:56  settings write failed (addon-settings/root) — transport error … timed out after 60000ms
04:12:16  recording stopped {pipelineKeys=[102|…]}
```

A read timed out, answered `{}`, the patch was merged onto nothing, and the
write persisted a blob containing only the patch. The recording configuration
for all three recording cameras came back as `{"enabled": false, "bands": []}`.
Two and a half hours of footage were never written.

Nothing looked broken. An emptied config is indistinguishable from an operator
switching recording off, so `getStatus` reported `enabled: false` truthfully and
no alarm existed to contradict it. The operator noticed, not the system.

The tempting fix — retry the read, or widen the timeout — does not close it: any
read can still fail, and the failure mode is silent data loss rather than a
visible error.

## Decision

A settings read reports three outcomes, not two: `value`, `missing`, `failed`.
A read-modify-write **refuses to write** when the read failed, and logs the
refusal at `error`. Only a genuine `missing` merges onto `{}`.

Refusing loses the PATCH, which is recoverable — the caller still holds it and
re-applies it on the next write. Writing loses everything the patch does not
mention, permanently.

## Consequences

- A settings write can now be REFUSED, so a caller that treats `writeAddonStore`
  as infallible will silently keep an unpersisted value. That is the intended
  trade: an unpersisted patch beats a truncated store.
- Plain readers (`readAddonStore`, `readDeviceStore`, section reads) keep the
  soft `{}` fallback so a boot path still degrades to defaults. That is safe
  ONLY because their value is never written back — if a new caller ever
  round-trips a plain read into a write, this record is violated.
- `@camstack/system` is host-provided, so shipping this needs a publish plus
  `applyServerUpdate`; `camstack deploy` cannot carry it.

## Enforcement

Unit tests in
`packages/system/src/kernel/moleculer/__tests__/settings-read-guard.spec.ts`,
including one that asserts a single-field patch over a stored recording config
keeps its `bands` — the exact field that was lost.

No guard script: "a read whose result is later written" is not detectable by
grep without false positives. Review only, which is why the consequence above is
stated as a rule rather than left implicit.
