## Context

[D67](./adr-0067.md) built the ffmpeg primitive — one argv builder, one spawn
wrapper, one set of encode constants, one hwaccel authority — and declared three
things it did not do. Each carried a `MIGRATION PENDING` entry in
`scripts/check-ffmpeg-primitive.ts`, which is how they were found.

**`acquireEgressTranscode` was a method with no body.** Its schema, its
exact-match sharing key and its immutability rule were all in and tested, and
`npm run codegen` had emitted the tRPC router — so the method was *callable* and
answered "is not a function". A capability that is declared, routed and
unimplemented is worse than an absent one: every layer between the caller and
the gap reports success.

**Alexa's egress was a `derived:alexa-<id>-<hash>` stream**, and three separate
things were wrong with it. It is a *publicly selectable camStream*, so a browser
viewer or the recorder could attach and one Alexa consumer's downgrade dragged
every co-tenant to 360p. Nothing ever retracted it — one per (device,
profile-hash), for the life of the hub. And it encoded **Opus that never reached
a session**: Opus in MPEG-TS is `stream_type 0x06`, while
`stream-broker/rtsp/mpegts-demux.ts` maps only `0x0f` (aac), `0x03`/`0x04` (mp2)
and `0x81` (ac3), so every frame libopus produced was discarded at the demuxer.
Pure CPU, behind a comment describing it working.

**HomeKit still assembled its own argv**, including the two flags that took a
year to find: a forced `-g` (x264 defaults to 250 frames, which at the 10 fps we
dial is one IDR every 25 s) and `-bsf:v dump_extra` (ffmpeg's RTP muxer declares
`AVFMT_GLOBALHEADER`, so libx264 hides SPS/PPS in extradata that HAP's own SDP
cannot carry).

The obvious route for Alexa was tried first and rejected on reading: teach
`WebrtcStreamTarget` an `egress-transcode` variant. Every variant of that union
resolves to a **broker**, and the primitive returns a **url** — bridging them
means teaching `BrokerWebrtcServer` to consume an `RtspRestreamer` directly,
which is a change to the session subsystem with no way to exercise it here (no
hub, no Echo).

## Decision

**A consumer that needs an encoded stream calls
`streamBroker.acquireEgressTranscode` and releases the handle it gets back. It
does not publish a stream of its own to hold its encode, and it does not build
an argv.** Where a consumer needs the result as a broker rather than a url, it
publishes the ACQUIRED url as an ordinary `pull-rtsp` stream keyed on the
`pipelineKey`, marked `autoEligible: false`, and retracts it when
`releaseEgressTranscode` reports `refcount: 0`.

The derived mechanism is untouched and stays: `derived-feeder-controller.ts`,
the `derived:<name>` concept and its lifecycle wiring are for reshaping a
badly-behaved SOURCE under operator control, which is a different job from a
consumer's private egress. Alexa being its only caller today is a fact about
today's callers, not a licence to remove it.

## Consequences

**The refcount's boundaries are decided, not incidental.**
`EgressTranscodeManager.shutdownEntry` removes its entry from the map
*synchronously*, before it awaits `stop()`, so an acquire that interleaves with
the last release either finds a live entry (and revives it, cancelling the grace
timer) or finds none (and spawns a fresh child). It can never be handed a
corpse. A re-acquire inside the stop grace revives rather than respawns, because
that window is exactly when a consumer that released to change one parameter
comes back.

**A consumer that dies without releasing still leaks a refcount.** This was
considered and deliberately not closed. A lease TTL is the obvious fix and it is
the wrong one here: there is no renew method to build it on, and a TTL a live
consumer fails to renew kills a working stream — a worse failure than a stray
ffmpeg an operator can see in the broker panel. What IS done: every holder
releases on every failure path it owns (Alexa releases when the publish fails
and when `handleOffer` throws, because no `SessionDisconnected` follows either);
a double release is refused and logged at `warn` rather than silently driving a
live child's count to zero; and `destroyAll` stops every child, so a leak never
outlives the broker process. It stops being benign the moment the holder is on
another node — the same condition that gates a transcode running off-hub.

**Two argv values changed, both deliberately.** Alexa gains `-level 3.1` (its
SDP advertises `profile-level-id=42e01f`, which IS Baseline 3.1, and its encoder
was unconstrained — the defect class that kept HomeKit black for a year) and
loses the in-band Opus encode. HomeKit's `-s WxH` becomes `-vf scale=W:H`;
equivalent for a plain rescale, and NOT interchangeable once another `-vf` is in
play, so a future filter must compose rather than collide.

**Alexa's path gains one loopback RTSP hop** — ffmpeg → restreamer → broker dial
→ session, where the derived push broker went ffmpeg → push ingress → session.
No re-encode, and the same pattern the recorder and pipeline-runner already
ride. **It has not been exercised against a live Echo.**

**HomeKit's SPAWN stays in `camera-streams.ts`,** and its allowlist entry now
says why rather than `MIGRATION PENDING`: `FfmpegProcess` decides a child is
live from its first stdout byte, and a HomeKit session has no stdout at all —
its outputs are two RTP sockets and its liveness signal is
`videoPacketsForwarded` on the loopback the JS-side SRTP encrypt reads. Its
hardware→software retry gates on four further session-scoped conditions,
including whether the CONTROLLER asked to stop. Teaching the wrapper a mode per
consumer is the same mistake as one builder per consumer.

### What is NOT true yet — superseding D67's list

D67's "what is NOT true yet" is stale from here; this is the current list.

- **Still open.** Nothing selects a node: every caller passes no pin, so every
  transcode lands on the hub. The source stream must be reachable FROM the
  chosen node, and the broker's restream urls are hub-local —
  `substituteRtspHost` rewrites the CONSUMER's dial address, not the producer's.
  There is no lease TTL and no `transcodeNode` role, so a holder on another node
  that dies leaks a child on a host nobody is looking at.
- **Now true.** The method has a body, it refcounts, and its returned url is
  host-substituted per caller from `hostname` — so a caller one `nodePin` away
  gets a url it can dial. Nothing in `EgressTranscodeManager` assumes
  hub-locality.
- **New.** The primitive's egress is VIDEO-ONLY: its sink is an elementary
  Annex-B bytestream and the restreamer's audio plane is a separate RTP path.
  A request carrying an audio encode is served without it, and **says so** at
  `warn` with `tags: { deviceId }` rather than dropping the plane in silence.
  `TranscodeEgress` already has an opt-in RTP audio sidecar; it is not wired in
  here because it is not live-verified end to end, and enabling an unverified
  path by default is worse than not having it.

## Enforcement

`scripts/check-ffmpeg-primitive.ts`, which lost two `MIGRATION PENDING` entries
to this work: HomeKit's builder exemption is **gone** (`buildSessionInvocation`
returns an `FfmpegInvocation`, so Rule 1 no longer has anything to exempt — a
future `build…FfmpegArgs` there fires the guard), and HomeKit's spawn entry now
records a boundary instead of a to-do.

Rule 3 already refuses a cap method taking a `pipelineKey` alongside encode
parameters, which is what would reintroduce a mutable shared handle.

Behaviourally: `egress-transcode-manager.spec.ts` covers exact-match sharing,
single-flight, the revive-inside-grace and stop-in-flight races, and the
double-release refusal; `stream-ffmpeg-argv.spec.ts` asserts `-g` and
`-bsf:v dump_extra` by token AND by position on both HomeKit branches, and pins
the input half and the whole audio leg byte-for-byte;
`alexa-egress-primitive.spec.ts` pins the pre- and post-migration argv and names
both deltas. Each was removed once and confirmed red before being kept.

Not enforced by anything: that a consumer actually releases. That is the leak
above, and it is review-only.
