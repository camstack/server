## Context

`filesystem-browse` was born sandboxed: `browse` and `createDir` shared one
containment guard against `storageAllowedRoots`, an addon config whose defaults
are `['/mnt', '/Volumes', '/media', homedir()]`.

On the live hub that sandbox described a machine that does not exist. `/Volumes`
and `/media` are macOS/desktop conventions absent from the container, `/mnt` is
present but **empty** — and every storage location the hub actually uses
(`/recordings`, `/data/backups`) sits **outside every allowed root**. So the
"Add Location — Filesystem" path picker offered four chips, three of them dead,
and refused to browse to the directory the node's own recordings are written to:

```
browse {"nodeId":"hub","path":"/"}           → path "/" is not within an allowed root
browse {"nodeId":"hub","path":"/recordings"} → path "/recordings" is not within an allowed root
browse {"nodeId":"hub","path":"/mnt"}        → { entries: [], 219.7 GB free / 506.1 GB }
```

The operator asked for the obvious thing — suggest the directories that exist at
`/` — and it could not be built, because the cap could not answer.

Widening the config was tried first and is not available: the legacy
`addons.getConfigSchema / getConfig / updateConfig` tRPC endpoints were removed,
and `FilesystemStorageAddon` implements none of the three settings levels. There
is no operator surface for `storageAllowedRoots` at all. Its "defaults" are
effectively hardcoded framework constants, which is exactly how the operator
described the chips.

Making the roots `['/']` (option A) was rejected: one guard governs both verbs,
so it would have handed `createDir` write reach over the entire node to buy a
read-only listing.

## Decision

The guard is split by verb. `browse` is read-only discovery and is confined only
by `assertBrowsablePath` — the path must be absolute, and nothing more, so the
picker can list `/` and everything under it. `createDir` keeps
`assertWithinAllowedRoots`: writes stay inside `storageAllowedRoots`. Allowed
roots are therefore **write roots**; do not re-read them as a read boundary.

## Consequences

- An admin (the cap is `auth: 'admin'`, `internal: true`) can enumerate
  directory names anywhere on any node hosting the cap. Directory names only —
  no file contents, no file listing, no writes.
- `createDir` still refuses the paths the picker can now reach. Browsing to
  `/recordings-high` and clicking "new folder" fails until that path is inside a
  write root. That gap is deliberate under this record; closing it means giving
  the operator a real surface for `storageAllowedRoots`, not widening the guard.
- The admin UI must tolerate a node that still refuses `/`: the framework half
  of this change is only live once a `@camstack/server` containing it is
  installed on that node, and each agent carries its own `@camstack/system`.
  `PathBrowser` falls back to `listAllowedRoots` chips, which is exactly the old
  behaviour, so the UI half is safe to deploy first and on its own.

## Enforcement

Tests, and they are the neutralisation kind: `path-guard.spec.ts` pins that
`assertBrowsablePath` accepts `/` and rejects a relative path;
`filesystem-browse-provider.spec.ts` pins that `browse` lists a directory
outside every write root **and** that `createDir` is still refused inside a
directory `browse` happily lists — the two halves cannot leak into each other
without a red test. On the UI side `path-browser.spec.tsx` pins both the real-`/`
chips and the older-framework fallback.
