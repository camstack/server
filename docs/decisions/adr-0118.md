## Context

The operator's ask, verbatim: the timelapse notification must carry a preview
image *"come per le altre rule"* [as for the other rules] — every detection rule's card shows a picture,
a timelapse's showed only text. He named his own the reference NVR advanced-notifier
plugin as the reference; reading it settled two questions that were about to be
guessed wrong.

The plugin draws its label text with **`sharp` compositing an inline SVG**
(`drawingUtils.ts`: a `<rect>` plus `<text font-family="sans-serif">`), not with
ffmpeg `drawtext`. That matters here for a reason the reference does not have:
this hub carries TWO ffmpeg builds and they disagree — `/usr/bin/ffmpeg`
(6.1.1) has `drawtext` compiled against libfreetype, `/data/deps/ffmpeg`
(7.0.2-static) does not. A `drawtext` preview would therefore appear or vanish
depending on which binary a node resolved, and the failure would look like a
per-node bug rather than a missing filter. `sharp` is already this package's
image dependency and already draws labelled overlays this exact way
(`shared/frame/box-drawer.ts`).

The plugin also gets its still from a live snapshot chain
(detector → decoder → cached → `takePicture`). That is right for a detection,
which is about *now*, and wrong for a timelapse: a still taken at 06:05 shows
daylight and an empty driveway under a card about last night.

## Decision

The preview is the **middle frame of the rendered timelapse**, extracted with
one `ffmpeg -ss <mid> -i <file> -frames:v 1` (input seek — an output seek
decodes ten hours to get there) and titled by `sharp` compositing an SVG. The
seek point comes from an `ffprobe` duration, because the
frame count is NOT derivable from the rule: the select predicate keeps a frame
when the cadence has ELAPSED, so a window with gaps yields fewer frames than
`windowSec / cadenceSec` (live: 576 where the arithmetic says 1,200). A failed
probe costs the middle frame, not the preview.

**AMENDED 2026-08-12, same day, by the operator on seeing it live:** the
composition is a **blurred background plus a large centred title**, not a
bottom caption bar. At notification-card size a caption strip is a footnote you
squint at and it covers the bottom eighth of the only picture the card has. The
middle frame is blurred (`sharp.blur`, sigma = width/96 clamped to 4…12 — 10 at
the 960 px cap, so a 360p and a 1080p render are blurred to the same DEGREE),
scrimmed with a full-frame black rect at 0.38, and the title is drawn bold and
white at ~1/12 of the frame WIDTH, centred on both axes with
`text-anchor="middle"`, each line laid twice (an offset dark copy first — a
white title over a bright frame otherwise disappears, and librsvg filter
support is not worth betting a preview on). The title wraps to at most TWO
lines, shrinking in 10% steps to a 14 px legibility floor before the tail is
elided. **An empty `previewText` ships the plain, UNBLURRED frame** — the blur
exists only to make the title pop, so blurring a picture nobody writes over is
strictly a loss. This is the advanced-notifier look the operator asked for.

**AMENDED again, same day:** `previewMode: 'image' | 'gif'` (default `'image'`).
A GIF is twelve cheap INPUT seeks across the render at 480 px, each frame given
the same blur + title, assembled by **sharp** (`join: { animated: true }` +
`.gif()`, per-frame delay 330 ms ≈ 3 fps, `loop: 0`) and published `image/gif`
BEFORE the video. Assembly is sharp and not ffmpeg `palettegen`/`paletteuse` for
the same reason the title is not `drawtext`: this hub carries two ffmpeg builds
that already disagree about an optional filter, and a second bet on one would
reproduce the same per-node coin flip. Over 3 MB the animation is thinned to
every other frame, then abandoned; a GIF that cannot be assembled DEGRADES to
the still, and the published mime is what the bytes ACTUALLY are — never what
the rule asked for. Default `'image'` because a rule that never asked for an
animation must not start paying a dozen seeks per window on the deploy that
shipped it.

**Detection counts, same amendment.** The window's per-class counts
(`{{detections}}`, `{{detectionSummary}}`, `{{count_<class>}}`) are aggregated
from **the same `listTracks` array the dense-range plan is built from** — never
a second query, because a count that came from its own read could disagree with
the ranges the video was cut from and nothing outside could tell. That read is
now explicitly bounded at 2,000 (`TIMELAPSE_TRACK_QUERY_LIMIT`): the store's
default is 50, so a busy night both planned from the newest fifty tracks and
would have reported "50 persone" for a night that held four hundred. Selection is
`reportClasses` (absent/empty = every class seen); the summary is appended to the
DERIVED body only when the total is non-zero, and never when the operator wrote
his own body — `{{detectionSummary}}` is how he asks for it there. Placeholder
keys are `\w+` only, which is exactly what `renderTemplate` matches.

The title is a plain optional `previewText` field on `TimelapseRule` —
`{{camera}}`/`{{rule}}`/`{{from}}`/`{{to}}`, the SAME vocabulary and the same
renderer as the title and body; absent means `Timelapse {{camera}}` and an
empty string means "the plain frame, no title". It is not part of
`TimelapseTemplateSchema`, so clearing the template cannot silently clear it.
`TimelapseRule` is a plain zod schema, not a cap — this needs no `codegen` and
no image rebuild (verified: `npm run codegen` produced no diff, and both addons
build `self-contained`, which inlines `@camstack/types`).

Both artifacts come out of **one** `readExportBytes`, and both ride the existing
NC artifact plane. The row carries `NcOutboxPayload.artifacts` (plural), **image
first** — a notifier that shows one attachment shows the picture.

## Consequences

- Every step is best-effort and independent: no ffmpeg on the node, a failed
  probe, a failed extraction or a failed title each cost only what they own,
  and each logs with `tags: { deviceId }`. A timelapse never fails for want of
  a picture.
- `NcOutboxPayload.artifact` (singular) is still READ by the dispatcher and
  never written. Outbox rows are durable; a row enqueued before this deploy and
  still waiting on an unreachable target would otherwise lose its video. The key
  disappears on its own once the last old row drains — do not "clean it up"
  before then.
- The addon now spawns processes. It is bounded (`PREVIEW_FRAME_TIMEOUT_MS`,
  `maxBuffer`) and runs once per window per camera, not per frame.

## Enforcement

`preview-frame.spec.ts` pins the argv verbatim (input seek before `-i`, mjpeg to
stdout), the title layout (wrap → shrink → elide, centred, sized to width) and
the composite: a fine vertical grating loses >70% of its stdev when a title is
present and is returned byte-identical when it is not — neutralisation-checked
by deleting the `.blur()` call, which reddens exactly that test; `artifact-publish.spec.ts`
pins one read / two artifacts and that a preview failure never costs the video;
`timelapse-scheduler.spec.ts` pins that `{{camera}}` resolves against the display
name — neutralisation-checked. No guard script.
