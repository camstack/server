## Context

The Backups page modelled one "entry" as one `backups`-typed `StorageLocation`,
with the cron and retention embedded on the per-location
`BackupDestinationPolicy` (a 1:1 coupling). Two consequences forced a change:

- An operator could not express "run this cadence, and write the SAME archive to
  the NAS *and* the offsite bucket". Each location carried an independent cron, so
  a two-target nightly backup meant duplicating the cron on every location and
  hoping they stayed in sync. The archive bytes are identical across
  destinations; splitting the schedule per-location was the wrong axis.
- "Add destination" on the Backups page opened the location wizard and created a
  brand-new filesystem path — duplicating the location-creation flow that already
  lives on the Storage page. Operators reported the two surfaces as confusingly
  redundant.

The open sub-question was where retention lives once one schedule targets many
locations. Per-location retention was the incumbent; the alternative was
per-entry. Per-location loses the ability to say "this nightly job keeps 14
copies" in one place — two schedules hitting the same location would fight over
its single retention number, and the operator would have to reason about the
intersection. Per-entry keeps the knob next to the cadence that produces the
archives.

## Decision

A backup **entry** is a first-class `BackupSchedule` object
(`{id, label, cron, enabled, locationIds[], retentionCount, dataSources?}`),
persisted in the `backup_schedules` table owned by the backup orchestrator. The
entry owns the cron cadence AND the retention count; on fire (or "Run now") it
builds ONE archive and fans it out to every id in `locationIds`, pruning each to
the entry's `retentionCount` via `trigger({destinations, retentionCount})`. A
`StorageLocation` is pure storage config (created on the Storage page); it no
longer carries a schedule. The scheduler tick iterates schedules, never the
per-location policy cron.

## Consequences

- `backup.trigger` gained an optional `retentionCount` override; when present it
  supersedes each destination's own policy retention (manual runs still fall back
  to the per-location default).
- The per-location `BackupDestinationPolicy.cron` is now legacy — the scheduler
  stops reading it and drives off `backup_schedules` only, so there is no
  double-fire. There is deliberately NO auto-migration: an operator recreates
  their schedule as an entry (the fleet is small and the entry model is the point
  of the redesign). Existing archives at each location are untouched.
- The admin-UI Backups page lists entries (name · locations · retention ·
  schedule · Run now / Edit / Delete). Location creation happens only on the
  Storage page — the old "Add destination" wizard on the Backups page is gone.
- Two schedules may still target the same location; each prunes that location to
  its own `retentionCount`, so the effective kept-count at a shared location is
  the max of the schedules that write to it. This is accepted: retention is a
  floor per producing schedule, not a global cap on the location.

## Enforcement

Review only, plus the schedule-store and scheduler unit tests
(`schedule-store.spec.ts`) that pin the CRUD contract and JSON array
round-trip. There is no guard preventing a future addon from re-adding a
per-location cron path; the scheduler reading only `backup_schedules` is the
behavioural contract.
