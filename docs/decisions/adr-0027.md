## Context

The backup must be a whole-folder `tar` of the data root's operator state
(`addons/`, `addons-data/`, plus top-level `config.yaml` + `tls/` +
`auto-update.json`), with no per-file allowlist and no encryption — restore is
"untar and boot". An earlier design went the other way (an allowlist perimeter +
AES crypto + a live-DB snapshot) and produced archives nobody could trust to
restore; it was rejected.

A whole-folder tar is only correct if those folders contain **nothing
regenerable or huge**. Two things violated that:

1. **`addons/` carried per-addon `node_modules`.** The installer ran
   `npm install` per addon for every declared runtime dependency — 74k files /
   1.34 GB of redundant trees on the live hub, which stalled the backup walk. A
   prior pass cut the pure-JS bulk (self-contained dists), but natives were still
   installed per addon: `node-av`/`sharp` were *both* host-external *and* kept in
   `RUNTIME_NATIVE_KEEP`, so they were installed redundantly; `node-pty`/`ssh2`
   resolved from per-addon copies; and `onnxruntime-node` sat in the keep-list as
   dead metadata (the Node ONNX path was replaced by Python-subprocess inference).
2. **The scrub-pack keyframe cache lived in `addons-data/<recorder>/scrub-packs`.**
   It is a regenerable cache of the LOW recording segments (rebuilt on demand),
   yet it sat inside the backup perimeter — and its source segments (`/recordings`,
   a top-level mount) are *not* backed up, so a restored cache would be orphaned.

## Decision

Define the backup perimeter by **location, not by a list**: `addons/` and
`addons-data/` must contain only operator state, so everything regenerable or
large lives outside them. Concretely: (a) `addons/` is `node_modules`-free —
`RUNTIME_NATIVE_KEEP` is empty, pure-JS deps are bundled into the self-contained
dist, and every addon-importable native is **host-external** (declared once on
`@camstack/server`, resolved from the framework closure via
`HOST_EXTERNAL_SPECIFIERS`); (b) the scrub-pack cache is rooted under the
recordings storage root, not `addons-data`. The whole-folder tar is then correct
by construction, with no exclusion list.

## Consequences

- A native an addon imports must be added to `@camstack/server`'s dependencies
  **and** to all three `HOST_EXTERNAL_SPECIFIERS` mirrors, or its import fails at
  runtime (the addon-runner resolver hook has no fallback). The version is
  whatever the server pins — an addon cannot choose its own.
- `better-sqlite3` stays out of the host-external set on purpose: addons persist
  through the storage cap, so a stray `import 'better-sqlite3'` must fail loudly.
- A lib with **optional** natives that the bundler cannot inline (e.g. `ssh2`'s
  `cpu-features`) must be host-external, not bundled.
- The scrub-pack cache is co-located with the recordings it derives from; a
  one-time migration removes the stale `addons-data` copy on first boot. Packs
  rebuild on demand, so nothing is lost.
- The backup service can drop its denylist, crypto, and live-DB snapshot logic:
  the perimeter is now trivially tar-able (a WAL checkpoint before the tar keeps
  the SQLite file consistent).

## Enforcement

- `host-externals.spec.ts` pins the canonical `HOST_EXTERNAL_SPECIFIERS` and a
  drift guard parses the two bootstrap-isolated mirrors (starter + loader hook)
  and fails if they diverge.
- `fs-utils.spec.ts` asserts `stripBundledDeps` keeps nothing for a self-contained
  addon (host-external natives are dropped, not installed).
- `scrub-pack-service.spec.ts` covers the lazy `cacheDir` resolver used to root
  the cache outside `addons-data`.
- `system-backup.service.spec.ts` pins the whole-folder round-trip and the WAL
  checkpoint: a live WAL-mode DB, restored and opened with its `-wal`/`-shm`
  sidecars deleted, must still carry every committed row — which holds only
  because `createArchive` checkpoints the WAL into the main file first.
- The `node_modules`-free invariant of a deployed `addons/` is otherwise
  review-only — there is no CI check that the live install tree is empty.
