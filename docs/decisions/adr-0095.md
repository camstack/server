## Context

A snapshot image is a plain HTTP GET with a Bearer header. It needs nothing from
the WebSocket, and `use-snapshot.ts` has carried a docblock saying so since the
last time somebody forgot:

> This used to be gated on `state === 'connected'`, and that is why every card
> went "unavailable" when the app came back from the background: iOS suspends the
> socket … the URL can never change again — and nothing recovers until the socket
> does. The images themselves would have loaded fine the whole time.

[D93](adr-0093.md) made the image URL carry a frame identity, and that identity
comes from `snapshot.getSnapshotOverview` — a tRPC query, over the WebSocket,
gated on `state === 'connected'`. So the socket dependency came back, one level
of indirection away from the comment warning against it.

The symptom was different enough to hide it. The old bug made cards go
*unavailable*; this one made them go *stale but plausible*. `expo-image` is
URL-keyed and never revalidates (D93), so a URL that stops changing is a tile
that paints the same frame forever. The operator's report was "lo snapshot sembra
freezato" — which is what a correct-looking image that never updates looks like.

The missing distinction was between two things the client had been treating as
one: **"the hub says this camera has no frame"** is an answer, and a stable URL
is the right response to it (advancing it would request a sleeping battery camera
every window, forever). **"We have not heard from the hub"** is not an answer,
and a stable URL there is a permanent freeze.

## Decision

A client that derives a resource's freshness from a *gated* query must degrade to
a **timer** when that query cannot be reached — never to a constant.

Concretely: `resolveSnapshotUri` takes `identityKnown` separately from
`lastCapturedAt`. While the identity is unknown the URL advances on a coarse 30 s
counter — exactly the behaviour that existed before the overview did — so the
worst case is "stale by up to 30 s", never "frozen". The counter starts at zero,
so a healthy launch (the overview answers in about 5 s) never pays for it.

## Consequences

- Three states, not two: versioned (identity known), stable (known to have no
  frame — a sleeping battery camera, deliberately not hammered), and
  slow-advancing (identity unknown).
- The fallback is a floor, not a mechanism. Anything that makes it the common
  path — a chronically disconnected socket — is a bug in the transport, and this
  hides it from the user rather than from the logs.
- Any future surface mounted OUTSIDE `SnapshotOverviewProvider` degrades to the
  30 s timer instead of freezing, so forgetting the provider is no longer fatal.

## Enforcement

`camstack/src/data/__tests__/snapshot-media-url.spec.ts` — with
`identityKnown: false` the URL must differ across successive `fallbackTick`s;
with `identityKnown: true` and a null `lastCapturedAt` it must NOT change, and a
known identity must never be overridden by the fallback. Removing the fallback
turns the first red.

Verified live: 8 URL flips in 60 s with a watched camera, each fetch returning
different pixels (distinct SHA-256), and no fetch at all when the identity had
not moved.
