## Context

`applies-to` in a document's frontmatter does two different jobs at once:

1. it **claims** code — "this page describes these files", which is what a
   coverage index needs in order to say which parts of the system nobody has
   written about;
2. it **arms staleness** — `check-docs-drift.ts` marks the page suspect when any
   claimed file changes after `last-verified`, which is what keeps a page from
   quietly describing last month's code.

For a focused page the two coincide and the single key is exactly right. They
come apart the moment a page legitimately describes a **class**.

`docs/architecture/device-model.md` describes how every device provider works.
Twenty provider packages implement that pattern and seventeen of them are claimed
by no document at all — a real hole, and the honest fix is for `device-model.md`
to say it covers them. The measurement behind
`docs/design/documentation-map-and-plan.md` §2.4 puts a number on it: seventeen
units, closed by one line of frontmatter.

Adding `packages/addon-provider-*/**` to that page's `applies-to` was tried on
paper first, and it destroys the freshness signal. One of twenty providers
changes almost every day, so the page would be permanently suspect, its
`last-verified` would mean nothing, and the `--max-stale` ratchet — which only
ever goes down, and which had just been walked from 19 to 0 — would be pinned
above zero forever by a page nobody could ever verify into the green. The guard
would still be running and would have stopped saying anything. That is the exact
failure mode D19 exists to avoid: a signal degraded into a number people learn to
ignore.

The alternative considered and rejected was to leave `applies-to` alone and let
the coverage index simply report class-level pages as covering nothing. That is
cheaper and it lies: it reports seventeen holes that a written, correct document
already fills, so the index would send the next session to write pages that exist.

## Decision

Two frontmatter keys, with two distinct meanings, and no key ever does both jobs:

- **`applies-to:`** — *"I verified this page against these files on
  `last-verified`."* It claims coverage **and** arms staleness. Unchanged
  meaning; every existing document keeps working with no edit.
- **`covers:`** — *"this page describes these files."* It claims coverage and
  **never** arms staleness. A page whose only claim on a file is `covers:` can
  never go suspect because of that file.

Both keys are validated the same way: a glob that matches nothing is a hard
failure, because a claim on deleted code is wrong under either meaning.

`covers:` is for a page that describes a class, a pattern or a contract that many
units implement. It is **not** an escape hatch for a page you do not want to
verify: if a page is the primary description of a subsystem, its files belong in
`applies-to` and the page is expected to be re-read when they move.

## Consequences

- The coverage index (`docs/reference/coverage.md`,
  `docs/reference/subsystems.md`) joins on `applies-to ∪ covers`; the staleness
  ratchet joins on `applies-to` alone. Those two set expressions live in one
  place — `claimGlobs()` and `stalenessGlobs()` in
  `scripts/lib/docs-frontmatter.ts` — so the two halves of the docs system cannot
  drift into disagreeing about what a claim is.
- A page can use both keys: `applies-to` for the code it was written against,
  `covers` for the class it generalises to. `device-model.md` is the intended
  first instance.
- Coverage becomes cheap to claim and freshness stays expensive to claim, which
  is the right way round. The failure this forbids is the reverse: buying an ✅ in
  the index by widening the key that also promises verification.
- The generated index will now show a third state that `applies-to` alone could
  not express — *described but never verified against* — and that is information,
  not noise: it is precisely the 22 units that today are claimed only by ADRs.

## Enforcement

`scripts/check-docs-drift.ts` validates `covers:` globs and deliberately excludes
them from the staleness computation; `scripts/__tests__/subsystem-map.spec.ts`
pins both halves — a `covers:`-only document contributes coverage and contributes
zero staleness globs. Removing the exclusion turns that spec red.
`scripts/check-subsystem-map.ts` fails on a dead glob under either key.
