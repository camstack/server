## Context

`object-clip` is one vector index and cosine similarity is only meaningful
between vectors produced the same way. Two paths wrote into it:

- the **live detail plane** — `runDetailSubtree` padded the parent box by
  `DETAIL_CROP_PADDING_RATIO = 0.15`, did not square it, and encoded it through
  the pipeline's `clip-embedding` step;
- the **embedding rebuild** — `pipeline-analytics` cut its own window with
  `DEFAULT_CROP_MARGIN = 0.2`, squared it by default, and called
  `api.embeddingEncoder.encode` directly, bypassing the pipeline entirely.

So the index held two feature spaces, and which one a search ranked against
depended on whether a rebuild had touched that track. `embedding-rebuild.ts`'s
own docblock described this exact hazard as the reason it exists; it had been
producing it on every run. Nothing failed and nothing logged — search quality
simply became a function of maintenance history.

The first fix proposed was to route the rebuild through
`runDetailSubtree({ cropJpeg, … })`, since that input already existed as the
"lease is gone" fallback. It does not work, and the reason is the whole point of
this record: `resolveCrop`'s `cropJpeg` branch takes the caller's JPEG
**verbatim** and applies no padding. That change would have unified the ENCODER
while leaving the crop derivation exactly where it was — a fix that reads as
verification while the defect stands.

Two follow-on placements were also rejected. `DeviceStepConfigSchema.settings`
is per-(node, device), and the runner's own `globalSettingsSchema()` is
per-node: either would let two accelerators in one cluster cut differently into
one shared index — the same defect, relocated. And the attach config
(`RunnerCameraConfigSchema`), the obvious orchestrator→runner channel, is built
at **eleven** call sites; a cluster constant threaded through eleven builders
eventually reaches ten of them, and the cameras attached by the eleventh cut
differently with no signal.

## Decision

The crop rectangle for a detail/enrichment step is derived by exactly one
function, `deriveDetailCropRect` in `@camstack/types`, and only the **runner**
calls it. Any caller with stored pixels sends a FULL frame
(`runDetailSubtree({ frameJpeg })`) and lets the runner cut; `cropJpeg` keeps its
narrow meaning — an already-cut tile, used verbatim, no padding — and is only
for the lease-miss retry. The convention that function takes (padding ratio +
squaring) is a **single cluster-wide** `pipeline-orchestrator` global setting,
read by the runner through the hub-routed `addon-settings` cap with no
`nodeId`. It is never per-node, never per-device, and never a per-call argument.

## Consequences

- A rebuild now requires the camera to be **attached** with `clip-embedding`
  enabled. That is a real loss of reach — a decommissioned camera's tracks can no
  longer be re-embedded — and it is why `RebuildOutcome` gained a `notRunnable`
  counter distinct from `failed`, plus a per-track warn tagged with the
  `deviceId`. A pass that rebuilds nothing must say which kind of nothing.
- The rebuild ships a full key-frame JPEG per track over the cap instead of a
  small crop. Acceptable only because it is a maintenance pass at roughly 1 Hz,
  compressed, and never on the frame plane ([D9](adr-0009.md),
  [D18](adr-0018.md)).
- `cropMargin` / `square` are gone from `pipelineAnalytics.rebuildObjectEmbeddings`
  and from the rebuild button. Changing the convention is now an operator action
  on the cluster setting, followed by a rebuild — which is the honest sequence,
  since changing it invalidates the stored index either way.
- The default is `{ paddingRatio: 0.15, square: false }` — the LIVE convention,
  not the rebuild's. Any other default would have invalidated every stored vector
  on the day it shipped.
- Unsquared edge clamping keeps the live path's TRUNCATE behaviour exactly;
  squaring slides inward instead, because a truncated square is not square.
- One path is deliberately left outside the guarantee: the detail dispatcher's
  lease-miss retry (`captureCropBase64` →`cropJpeg`) still decides its own tile,
  padded 0.15 with `padBbox`'s shift-inward clamp. It matches the default
  convention in the only value that differs in practice, and it is a degraded
  retry, but it is not covered by the single derivation. Closing it means giving
  the dispatcher a full frame it does not have.

## Enforcement

`scripts/check-clip-crop-single-owner.ts`, wired into CI's repository-guards
loop. It fails if `deriveDetailCropRect` is declared outside its owner module, if
any file outside the single cutter (`detail-subtree.ts`) imports it, if
`embedding-rebuild.ts` regains an image library or an `.extract(` call, or if a
second detail-crop convention constant is declared anywhere.

Deliberately conservative: every check is a declaration or an import, never a
judgement about arithmetic. It cannot see a hand-inlined `bbox.w * 0.15` that
never names itself — nothing without false positives can — but it makes the
shared function single, stops the rebuild silently regaining a cutter, and
blocks a second named convention.

Tests: `packages/addon-pipeline/src/pipeline-runner/__tests__/detail-subtree.spec.ts`
`(g)`/`(g2)` prove the `frameJpeg` branch cuts through the same function, with the
same arguments, as the frame-handle branch;
`packages/addon-post-analysis/src/pipeline-analytics/__tests__/rebuild-through-pipeline.spec.ts`
proves the rebuild sends a full frame and not a tile; the scope of the setting is
pinned in `packages/addon-pipeline-orchestrator/src/__tests__/detail-crop-settings.spec.ts`
and `packages/addon-pipeline/src/pipeline-runner/__tests__/crop-convention-source.spec.ts`.
