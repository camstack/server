## Context

`docs/design/2026-08-13-durable-value-tracking-and-runtime-state.md` opened on a
finding: `device-runtime-state` held **0 rows** on the live hub while D96 had
counted 1,118 six days earlier. Two independent read paths agreed, across two
container lifetimes. It was written up as a live regression in the persist path
and made Phase 0 of the plan.

**It was not a regression, and the persist path was never broken.** Runtime
state has always been written by `ConfigManager.createSettingsView
.writeDeviceRuntimeState` → `setAddonDevice('__device-state', …)`, i.e. into
`addon-device-settings` under a synthetic addonId, ONE ROW PER (device, cap):
`__device-state:101.device-status`. That routing is unchanged since the initial
commit (`git log -L` over the block: two touches, both cosmetic). The collection
named `device-runtime-state` is declared at every boot in
`CANONICAL_KV_COLLECTIONS` and has **no writer anywhere in the repo**.
`docs/design/2026-08-03-storage-table-map.md` §3.5 had already found exactly
this and written "there are two device-runtime-state stores and the named one is
the empty one" — ten days before a second session re-derived it from the other
end and drew the opposite conclusion. Re-measured on the live hub on
2026-08-13: **1,268 `__device-state` rows across 374 devices**, growing, and
D96's 1,118 was the same prefix count. Nothing was ever lost.

So the defect is real but it is a NAMING defect with a cost attached, and the
cost is the interesting half. `setAddonDevice` is a `DELETE` over the device's
key prefix plus **one `INSERT` per cap slice**, in one transaction. An
eight-slice camera paid nine statements per flush, once a second, to persist a
1.3 KB blob the design believed cost a single upsert — on a SQLite file on shfs
whose checkpoint has been measured stalling hub-main for 25 s (D96). The decoy
table cost one whole analysis session; the row-per-slice write has been costing
commits for the life of the installation.

The second half of the problem is who gets to be on disk at all. The whitelist
is `cap.runtimeState !== undefined`, which is not a decision anybody makes — it
is inherited by declaring a shape. Measured over 25 minutes on 358 devices:
5,765 slice changes, of which **3,897 (~90 % of the byte rate) come from two of
the 62 caps**, `audio-metrics` and `zone-analytics`, whose restored value is a
two-hour-old dB reading rendered as current. Of the 1,868 that remain, **~937
are a clock advancing under an unchanged value**: `battery` wrote its blob 526
times without one percentage moving, `privacy-mask` 22 of 22,
`humidity-sensor` 67 of 75, `numeric-sensor` 251 of 669.

## Decision

**One row per device, in `device-runtime-state`.** `getDeviceRuntimeState` /
`setDeviceRuntimeState` / `clearDeviceRuntimeState` on the settings backend own
the whole cap map as a single JSON blob. The legacy `__device-state:` prefix
stays READABLE — a hub booting on this code restores what it wrote on the old
code — and the first canonical write per device retires that device's legacy
rows. Nobody may reintroduce a per-(device, cap) row for runtime state.

**A slice reaches disk only if its capability declared
`durability: 'restored'`.** The marker lives in the `*.cap.ts` next to
`runtimeState`, defaults to `'session'`, and is MANDATORY (guard below): the
choice appears in the diff. Behavioural cap metadata lives only there (D4), so
the kernel holds no whitelist that could disagree.

**A write happens only on an EFFECTIVE change.** At flush time the persistable
blob is deep-compared against what is believed to be on disk, ignoring the
fields the cap named in `volatileStateFields`. Those fields are still WRITTEN —
they simply do not, alone, justify a commit. The comparison is against DISK, not
against the previous tick, so clock-only drift cannot accumulate into a write.

**The mirror and the `DeviceStateChanged` event are untouched by both gates.**
`createRuntimeStateBridge.ensureFresh` detects a successful refresh by a clock
field advancing; a mirror that swallowed clock-only updates would make every
landing poll look like a failure. Only the disk write is gated.

**The same principle binds `cluster-node-history`**: `snapshot()` writes on a
descriptor change, or once per 5 minutes, not on every 30 s topology poll.

## Consequences

- Projected fleet write rate for runtime state: **~1.0–1.6 M/day → ~5×10⁴/day**
  (~96 % reduction), and the amplification per write drops further because a
  flush is one upsert instead of `1 + N` statements.
  `cluster-node-history`: **8,640/day → ~864/day** for the same three rows.
- A `'session'` slice is now genuinely lost on restart. That is the point for
  `audio-metrics`, `camera-streams` and `motion`; it is a cold window for
  anything wrongly classified, and the classification is reviewable in one
  generated file (`RUNTIME_STATE_POLICY`) instead of 62.
- `device-status.online` now survives a restart for all 358 devices. The
  restored value is NOT a claim about now — it is the previous observation that
  turns the first real reading into a comparison instead of a phantom
  transition. That is D130's rule, at the mechanism level rather than per
  feature.
- A cap whose clock field is CONTENT (`doorbell.lastPressedAt` — the slice is
  the record) must say so, in `CLOCK_FIELD_EXEMPTIONS` with a reason.
- The empty `device-runtime-state` table stops being a decoy. Any future probe
  of "does runtime state persist" reads the right number.
- Framework-bound: `@camstack/types` + `@camstack/system` + `server/backend`.
  None of it is live until a `@camstack/server` containing it is installed.

## Enforcement

- `scripts/check-runtime-state-durability.ts` (CI): a cap declaring
  `runtimeState` without `durability` fails the build; a `'restored'` cap
  carrying a clock-named field that is neither in `volatileStateFields` nor
  exempted fails the build. Both rules verified by neutralisation, on both cap
  shapes (inline `z.object` and named schema const).
- `packages/system/src/builtins/sqlite-storage/__tests__/device-runtime-state-collection.spec.ts`
  pins the collection, the one-row-per-device shape, the legacy read fallback,
  the per-device migration, and the statement count per flush.
- `packages/system/src/builtins/device-manager/__tests__/runtime-state-persist-gate.spec.ts`
  and `device-state-mirror-durability.spec.ts` pin both gates end to end;
  removing either gate fails them.
- `server/backend/src/core/agent/__tests__/cluster-node-history-store.spec.ts`
  pins the 5-minute bound and the descriptor-change edge.
