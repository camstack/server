## Context

The crop path has a standing rule, written into the code that implements it:
model-input crops go through the native-strict `captureCrop`, which returns
`null` on any native miss and **never** an upscaled ≤640 raster tile; display
crops (plate and face gallery tiles) go through `captureDisplayCrop`, which
falls back to the retained full frame — keyframe-native tier, or the runner's
≤640 RAM tier, honest sub-native and never upscaled. The rationale is stated at
the call site: *"an upscaled / low-res crop must NEVER be fed to the recognition
models."*

The confirmation gate re-runs object detection on a crop, so by that rule it is
a model input and takes the strict path. That is what it did, and it is how a
brick wall entered camera 636's track feed as a `vehicle` on 2026-08-01: the
native lease was gone, `captureCrop` returned `null`, and a boolean verdict with
no third value wrote "could not measure" as "confirmed". Over the preceding
twelve hours, ~57 of 126 births (45%) were confirmed without ever being
measured.

The first fix — a three-valued verdict plus a deferral that re-tries the birth
on later frames — closes most of that gap, because the miss is transient and the
next frame usually has a crop. It does not close all of it. A birth whose
deferral runs out still has to be decided, and the only two options are: allow
it unmeasured (the original defect, merely rarer), or measure it on a worse
crop.

An in-attempt retry was tried first and removed. It slept ~60 ms between crop
fetches on the synchronous frame path `processFrame` awaits, and it duplicated
what the deferral already does on the next frame with a fresher box — two
mechanisms for one job, one of which blocked the pipeline.

## Decision

**On an EXHAUSTED deferral, and only then, the confirmation gate may take its
crop from `captureDisplayCrop` instead of `captureCrop`.** No other model-input
consumer may. The gate answers a classification question — "is this a vehicle or
a wall?" — where the ≤640 sub-native tier is sufficient; the rule's rationale is
about recognition (whose face, which plate), where resolution decides the match.
The exception is scoped to `fetchFallbackCrop`, is reachable only for candidates
the caller has marked exhausted, and is unreachable from every other path.

## Consequences

- A small number of birth decisions are made on a lower-resolution crop than the
  detector normally sees. A wrong decision here suppresses a real track or
  admits a false one — bounded by how rare exhaustion is, which is why the
  exhaustion path logs at `warn` with the elapsed time and attempt count.
- The face and plate paths are unchanged and must stay unchanged. If a future
  change routes recognition through the fallback, this record does not cover it.
- "Model-input crops keep `captureCrop`" is no longer true as stated. It is now:
  *recognition* inputs keep `captureCrop`; the confirmation gate is the one
  classification consumer with a documented exception.
- The alternative this rejects — failing open on exhaustion — is not neutral. It
  is the original defect, and it is silent.

## Enforcement

Review only, plus two partial signals: `fetchFallbackCrop` is optional on
`ConfirmationGateDeps` and is passed by exactly one caller, and the gate refuses
to call it for a candidate the caller did not mark exhausted (unit-tested). No
guard prevents a future consumer from wiring `captureDisplayCrop` into a
recognition path; that remains a code-review matter, which is worth knowing when
weighing how much to trust this rule.
