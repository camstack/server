## Context

A derived stream is an ffmpeg transcode of a source camera stream into a
self-contained **MPEG-TS on stdout**, demuxed back into `EncodedPacket`s by
`MpegTsDemux` and pushed into a `derived:*` broker. Its audio has to survive
that carrier, and twice it did not.

The first attempt died at the argv: the shared builder maps
`EncodeProfile.audio: 'passthrough'` to `-an`, which is right for WebRTC (werift
carries audio out of band) and drops the track here. Fixed on 2026-07-17 by
remapping `passthrough` → `-c:a copy`.

The track was still missing, and stayed missing for another four weeks, because
a copy has to survive **two** hops and it only clears the first. Measured with
ffmpeg 7.1: a `pcm_mulaw` (G.711) track copied into `-f mpegts` does not fail
the invocation — ffmpeg logs `Stream 1, codec pcm_mulaw, is muxed as a private
data stream and may not be recognized upon reading`, writes stream_type `0x06`,
and keeps muxing video happily. `MpegTsDemux` adopts an elementary audio PID
only for `0x0f` (AAC) or `0x03`/`0x04` (MP2), so it never saw audio, never
called `onAudioInfo`, and the derived broker never learned it had a track: its
probe read `audio: null` forever, which is exactly what a stream with no
microphone looks like.

Every camera in this fleet speaks G.711. **No `derived:*` stream has ever
carried audio, on any camera, in the whole log history.** It surfaced when
camera 108's `low` profile — the profile the audio analyser follows — was
remapped onto a derived stream on 2026-08-10: zero audio chunks and zero
`pipeline-analytics:audio-events` lines from that moment, with a healthy-looking
stream and no error anywhere.

## Decision

The **carrier** decides a derived stream's audio, not the profile. When the
profile asks to carry the source's audio (`passthrough`, or an explicit
`{codec: 'copy'}`), `resolveDerivedAudio` emits `-c:a copy` ONLY when the
source's observed codec is one that survives both hops — today that set is
`{aac}` — and otherwise re-encodes to mono AAC. An unobservable source codec
takes the AAC branch: the unknown must never resolve to the branch that mutes
the camera. The re-encode is reported, not silent — the decision is returned
with the argv and the spawning manager logs it once per feeder with
`tags: { deviceId }`.

Never add a "fallback to a native stream" here. A derived stream that cannot
carry audio is a bug in the derived stream, and substituting a different stream
would hide it (see [D156](adr-0156.md)).

## Consequences

- One AAC encode per derived stream with audio (a mono voice track — negligible
  against the video re-encode that is the derived stream's whole purpose).
- The re-encode deliberately does NOT force a sample rate. A G.711 mic is
  8 kHz; upsampling to the 48 kHz camera preset would spend bitrate on nothing,
  and the ADTS header carries the true rate to `parseAdtsAudioParams` either
  way. The broker's push-audio path then decodes AAC through the `audio-codec`
  cap, exactly as it already does for the reference detector/RTMP sources.
- A source with no audio at all stays silent and does not error: ffmpeg's
  default stream selection simply finds no audio stream to encode (verified).
- MP2 is deliberately NOT in the copyable set although the container and the
  demux both accept it: `StreamBroker.pushAudioInfo` has no MP2 decode, so a
  copied MP2 track would announce a track it cannot turn into PCM chunks — a
  second way to be silent, with a descriptor that makes it look fine.
- The probed snapshot needs no change: it is built from `BrokerStats.audio`,
  which follows `onAudioInfo`.

## Enforcement

`stream-broker/__tests__/derived-transcode-args.spec.ts` pins the decision per
source codec (and that an operator's explicit audio encode is honoured
verbatim). `stream-broker/__tests__/derived-stream-feeder.spec.ts` pins the
mechanism with a real ffmpeg-produced fixture: a TS carrying a COPIED G.711
track yields video packets and zero `onAudioInfo` — so re-introducing the copy
fails a test that shows why.
