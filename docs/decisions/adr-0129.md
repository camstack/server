## Context

[D45](adr-0045.md) decided one copy of every host-provided package per node, one
resolution path, no seeding. Two years of shipping later the fleet still held
four: the image starter closure, the image framework seed, the legacy
`<dataDir>/framework`, and the active `server-root/current` deposit — plus, on
the agent, a fifth under `<dataDir>/addons/@camstack/system`. D45 recorded the
migration as scheduled work and it never happened, because the two halves of it
pull in opposite directions:

- **remove the seeds** and a node whose closure did not survive an update has
  nothing to boot from;
- **keep the seeds** and every node carries a second answer to "which version is
  this", which is precisely the failure D45 was written after.

Measured on 2026-08-13, one hub: `/opt/camstack-hub` 921 MB, the framework seed
510 MB, the addon seed 43 MB, `<dataDir>/framework` 509 MB, `<dataDir>/addons`
265 MB. The addon seed is the smallest tree of the lot and the most expensive:
five bootstrap packages had two truthful versions at once (`addon-pipeline` seed
1.2.64 against 1.2.69 installed, `admin-ui` 1.2.47 against 1.2.50, …).

One discovery decided the shape. `<dataDir>/framework` **cannot be removed by
removing it**: the entrypoint re-seeded it whenever
`$FRAMEWORK_DIR/node_modules/@camstack/system/package.json` was absent, so the
purge recorded in the 2026-08-12 handover was undone by the next container
restart — 509 MB, back on the module search path, silently.

## Decision

**The image seed is a FALLBACK, not a steady state. A node converges to one copy
of everything only after it has booted correctly, and the same code does it on a
hub and on an agent.**

1. **The image keeps `@camstack/server` and the SYSTEM packages** (`/opt/camstack-hub`,
   `/opt/camstack-seed-framework`). They are what a broken closure boots from.
2. **The image carries NO other addon.** Every non-system addon is single-copy,
   always, installed from the registry during the initial boot.
3. **At first boot the version is `latest`.** The system is addons-agnostic:
   there is no version contract between the closure and an addon, so there is no
   pin, no range and no adopt-by-semver. Whatever lands is what the node keeps —
   an installed copy is never replaced by a bootstrap ([D90](adr-0090.md)).
4. **After a healthy boot the node deletes its redundant DATA-side copies** —
   the legacy `<dataDir>/framework` tree and any host-provided package under the
   addon root. `<dataDir>/addons/@camstack/system` on an agent goes with it
   ([D107](adr-0107.md)).
5. **The entrypoint re-creates the framework tree on ONE condition**: the active
   closure has no `@camstack/system`. That boot is logged as `FALLBACK`, in
   words, twice.
6. **The sweep is gated by health, not by time.** Before a node is up, the copies
   it removes are the recovery path. The gates are: boot confirmed healthy ·
   an active closure exists (never in baked mode) · `@camstack/system` actually
   resolved from inside that closure · the candidate is not inside the closure,
   not under `/opt`, not on the module search path.

## Consequences

- A fresh node with no registry gets **no addons** and still boots: every
  required infra capability (`storage-provider`, `data-store-provider`,
  `storage`, `settings-store`) is a builtin of `@camstack/system`, which comes
  from the closure the image keeps. The answer to a registry outage is "boot,
  install nothing, say so loudly" — never a boot-time retry, which is a refusal
  by another name (D45: *"non dovremmo mai prevenire il boot"*).
- The image loses the property that a fresh `/data` is fully functional offline.
  That is the deliberate trade for one version per node, and the fallback that
  remains is the one that keeps a node BOOTING, not the one that keeps it
  complete.
- `camstack deploy`, the Admin UI and the back-fill are unchanged; the addon root
  simply has one writer fewer.
- A cleanup that runs at the wrong moment bricks a node, so every gate has a test
  that fails when the gate is removed, verified by neutralisation.
- `CAMSTACK_SINGLE_COPY_CLEANUP=off` stops the sweep without editing code. A
  destructive step that cannot be turned off from the outside is one an operator
  has to patch a container to stop.

## Enforcement

- `scripts/check-single-copy-layout.ts` — the ratchet. `Dockerfile » seed-addons-tree`
  went 10 → 0 and is now absent from the baseline, so re-introducing an addon
  seed tree fails the build. The remaining buckets (`seed-framework-tree` 7,
  `legacy-framework-dir` 4 + 4, `framework-dir-override` 2 + 4) are the deliberate
  fallback and the next step, in that order.
- `server/backend/src/__tests__/single-copy-cleanup.spec.ts` — 24 tests over the
  pure planner, the discovery and the executor. Three gates were neutralised one
  at a time and each broke tests (3 / 1 / 1).
- `server/backend/src/__tests__/entrypoint-framework-fallback.spec.ts` — extracts
  the fallback block from the REAL Dockerfile and runs it: healthy closure seeds
  nothing, absent closure seeds and prints `FALLBACK`. It also asserts the image
  carries no addon seed, no `COPY` of one and no `CAMSTACK_BUNDLED_ADDONS_DIR` —
  that env is what makes the launcher install from a local tree, so a leftover
  would send the bootstrap looking for a directory that is not in the image.
- Reported, never fatal: the boot prints the first-boot plan and the cleanup plan
  in full, including a blocked sweep and every copy it left behind
  ([D45](adr-0045.md) § Enforcement stays in force — no inventory or sweep may
  end a process).
