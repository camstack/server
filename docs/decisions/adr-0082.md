## Context

The `osd` cap already existed: it probes a camera's overlay slots and writes a
literal string into one, and the Hikvision provider implements it against the
ISAPI `/overlays` endpoints. What it could not do is decide WHAT the string
should say. An operator asking for "show the temperature in overlay 2, but only
while the alarm is armed" had nowhere to put that.

The obvious move — grow the `osd` cap a `source` field and let each driver
resolve it — is the one that had to be rejected. It buys "the temperature" once
per vendor, and the second request ("the humidity too") is another code change
in every driver.

A reference implementation of this feature elsewhere was studied. Its data model
is a closed enum of source kinds (`Text`, `Device`, `Template`, `FaceDetection`,
`BatteryLeft`) fanned out into a second enum of ten reader types, each with its
own branch — nine of which read one specific interface. It also rewrites every
overlay on every camera on a fixed 5-second interval regardless of whether the
value moved, which on a read-modify-write firmware API is two HTTP round-trips
per slot per tick, forever.

## Decision

Overlay CONTENT is owned by a separate orchestrator addon (`osd-manager`) over
the existing device-scope `osd` cap. The driver cap keeps exactly one job:
write this string into that slot. Three rules follow, and each is what makes the
orchestrator cheaper than the per-driver version:

1. **A source is `(capName, valuePath)` over the kernel's device runtime-state
   mirror, never an enum of source kinds.** Every cap-keyed slice any device
   publishes is bindable the day that cap ships, with no branch here and no
   change in the editor — the picker is derived from the cap definitions
   (`stateLeavesOf`), so it cannot offer a value the resolver would fail to read.
   `static` and `clock` are the only two non-state sources, because neither has
   a device to read.
2. **The display gate reuses `NcConditionsSchema` and `NcScheduleSchema`
   verbatim** — the notification centre's condition vocabulary — rather than a
   parallel model. Sharing forced `isScheduleActive` out of the notification
   centre's rule engine and into `@camstack/types`: addons never import each
   other, so the alternative was a second copy of window arithmetic, free to
   drift, with nothing that fails when it does.
3. **A slot is written only when its rendered text CHANGED.** `lastWritten` is
   that memory; a failed write drops the entry so the next pass retries rather
   than believing the camera carries text it rejected.

## Consequences

The renderer's facts are device state, not a detection record, so only a subset
of the shared condition vocabulary can be answered: `devices`, `deviceState` and
the schedule. `setSlotBinding` REFUSES a binding naming any other condition, at
write time, listing what is supported. It deliberately does NOT accept-then-
fail-closed the way `evaluateRule` does. Failing closed in the notification
centre sends no notification, which is invisible; failing closed here renders a
permanently blank overlay, and a blank overlay is indistinguishable from a broken
camera. Widening the set means giving the renderer the facts to answer it — a
live detection subject would unlock `classes`, `zones` and `minConfidence` — and
`getConditionSupport` is the one place that claim is made.

Every non-write outcome is reported and named (`gated` / `unreadable` /
`unchanged` / `disabled` / `unbound` / `failed`, each with a `reason`), because
all of them look identical on the camera.

`osd-manager` is a NEW capability, so it reaches production only through a
published `@camstack/server`; an addon deploy alone will not expose the route.

## Enforcement

`packages/addon-osd-manager/src/__tests__/osd-manager.spec.ts` pins the refusals
(unknown slot, firmware-owned slot, unsupported condition — the last asserting
nothing was persisted) and the write-once property, including that a moved value
writes again, so the guard cannot degrade into a one-shot latch. Disabling the
change-detection branch fails 2 tests; verified, not assumed.
`gate.spec.ts` asserts every id in `OSD_SUPPORTED_CONDITIONS` exists in
`NC_CONDITION_CATALOG`, so the supported set cannot name a condition the shared
vocabulary dropped.
