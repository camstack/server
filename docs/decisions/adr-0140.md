## Context

Tier B of the ecosystem-export plan: give Home Assistant the platforms it
actually has. A cover exported through the nine platforms the 0.3.x component
built was a state `sensor`, two writable `number`s and three `button`s —
automatable, and not a cover: no `cover.open_cover`, no position in the
more-info dialog, and every dashboard card that expects a cover refuses it. A
lock was a `switch`, and a `switch` reports a JAMMED door as unlocked, which is
the answer that makes an "is everything secure" automation say yes.

The blocker was never the mapping. It is that **the hub and the component ship
on different trains**: the hub is deployed when the operator deploys it, the
component is updated through HACS when the operator decides to. There is no
release either side can assume about the other.

The failure that shape already produced is in the repository: the export has
been announcing `alarm_control_panel` components since the native export
shipped, and no released component ever built that platform. Every alarm panel
an operator exported produced one warning line in Home Assistant's log and **no
entity at all**. Nobody noticed, because "no entity" and "nothing was exported"
look identical from Home Assistant's side.

Two ways to know what the other side can build were considered:

1. **A version gate.** `if component >= 0.4.0 use the native platform`. Rejected:
   the version-to-platform table would live on the hub, be a second copy of a
   fact the component already knows, and rot on the first component release that
   adds a platform — at which point the hub is the thing standing between an
   operator and the entity they installed the update for.
2. **Infer from behaviour.** Send the native component and watch for an error.
   Rejected outright: there is no error to watch. The component logs a warning
   locally and drops the component on the floor; the POST is a 200.

## Decision

**The component publishes the platforms it builds, and the hub gates on that
list.** `GET /api/camstack/version` answers `{version, platforms}`, read from the
component's own `PLATFORMS` constant, and `component-support.ts` negotiates per
broker at the top of every reconcile. The version travels for the log line and
for nothing else. A 404 means "pre-native component" — information — and is the
only reason the legacy set is assumed; a timeout, a 500 or a rotated token means
nothing was learned and moves nothing.

**An upgrade applies at once; a downgrade needs two consecutive reads that
agree.** Losing a platform migrates every entity built on it, and that is
destructive work driven by a fallible read ([D49](adr-0049.md)).

**A native platform is STRUCTURE only.** A native component names the topics the
degraded entities already published on, so the projector is untouched and the
value plane cannot disagree with the entity plane. What a native entity reads it
owns and is announced once; what it does not read stays exactly as it was.

**A control appears only when its descriptor is `writable`** — the same flag
that tracks `CAP_COMMAND_ROUTES`. A native cover on a hub that cannot move a
cover is a read-only cover, never a cover with buttons that call nothing
([D62](adr-0062.md)).

## Consequences

- **A device is announced once, to every broker that receives it**, so its plan
  can only use platforms ALL of them build. Two Home Assistant instances on
  different component versions hold each other back until both are updated. The
  alternative — a plan per broker — buys a rare case at the price of the export's
  single identity path.
- **An entity that gains a native platform is a NEW entity.** Home Assistant
  keys its registry on `(platform, integration, unique_id)` and an entity cannot
  change domain in place at any version, so `sensor.x_cover` is removed and
  `cover.x_cover` is created with the same `unique_id`, on the same device. The
  recorder history under the old id stops and does not carry across; automations
  and dashboards pointing at it must be repointed. **The component raises a
  persistent notification naming every entity id that moved**, because nothing
  else would say so until an automation failed to run.
- **Structure now reads a value.** A native `climate` carries the modes the
  device accepts, and `availableModes` lives on the slice and nowhere else — so
  `CatalogDevice.capSlices` is passed to the catalog. It is announced, not
  published: an option list that changes arrives on the next reconcile's
  `entity_change`, exactly as a renamed zone already does.
- **A platform named in `HaPlatform` is not a platform anyone builds.** Adding
  one is now three places: the union, the native table, and the component's own
  `PLATFORMS`.

## Enforcement

`__tests__/component-support.spec.ts` covers the negotiation, including that a
downgrade is withheld and that a timeout is not an answer.
`__tests__/native-platforms.spec.ts` walks both tables and asserts every slice
field a native binding names exists in the capability's own status schema —
the same authority `scripts/check-export-coverage.ts` holds the degraded table
to. On the component side, `tests/test_version_view.py` asserts the platform
list is read from `PLATFORMS` rather than kept by hand, and every fixture under
`tests/fixtures/entity_change_*.json` was generated by running this repo's own
`entity-catalog.ts`, so a control name or a topic that drifts fails there.
