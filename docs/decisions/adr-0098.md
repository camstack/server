## Context

A `scope:'system', mode:'collection'` cap fans its array methods across every
provider and routes everything else to ONE, selected by the out-of-band
`{ addonId }` pin. The pin resolves through
`CapabilityRegistry.getProviderByAddonId`, which returns `null` for an id nobody
owns.

`null` is also what the hub root returns when a cap legitimately lives in a
forked hub worker, and `resolveProviderForCall` could not tell the two apart: on
a local miss it fell through to `remoteProxy(cap, 'hub')`, whose Moleculer
prefix lookup answered from the FIRST hub-side provider. Measured live on the
hub, 2026-08-09:

```
deviceExport.getStatus { addonId: 'export-alexa' }         → linked   | exposed: 3
deviceExport.getStatus { addonId: 'homeassistant-export' } → unlinked | exposed: 0
deviceExport.getStatus { addonId: 'questo-non-esiste' }    → linked   | exposed: 3
```

The third line is a fabricated id receiving Alexa's status, with no error and no
log. All 24 collection caps shared the one resolver, so all 24 shared the hole.

What made it urgent rather than cosmetic: the Home Assistant component reads its
exported-device set pinned to `homeassistant-export` precisely so it does NOT
get the unpinned aggregate (Alexa's 3 + HomeKit's 3 merged — the operator's
original "it imported everything" bug). With this fallthrough, one missing,
renamed, crashed or not-yet-deployed addon and the component would have silently
imported ALEXA's devices while looking exactly like success.

The `nodePin(nodeId)` half of the same mechanism was checked and is sound: an
unknown nodeId already raises `PRECONDITION_FAILED` naming the node.

## Decision

**An EXPLICIT top-level `{ addonId }` pin that resolves to no provider is
refused, with a `BAD_REQUEST` naming the id and enumerating the valid ones, and
it is logged.** The refusal fires BEFORE the hub-proxy fallthrough — after it,
the proxy has already answered. It applies only when the cap has at least one
registered provider: with zero, the fallthrough is the legitimate
"cap resident in a forked hub worker" route and stays.

Only the explicit selector is refusable. The `addonId` recovered from a nested
mutation payload (`upsertTarget({ target: { addonId } })`) is a best-effort
heuristic over a domain object, and keeps its pre-existing first-provider
behaviour rather than starting to 400 on an incidental field.

## Consequences

- A caller that pinned a stale, renamed or undeployed addon now gets a loud,
  self-explaining failure instead of somebody else's data. That is a behaviour
  change: integrations pinning an id that was silently wrong will start erroring
  — which is the point.
- A provider registered from another node carries the key `<addonId>@<nodeId>`.
  A bare pin does not match it and is now refused; the enumeration in the error
  shows the suffixed key, so the caller can see what to ask for. No second
  resolution rule was added to paper over this.
- Still open, and NOT fixed here: a cross-node pin (`{ nodeId, addonId }`
  together) strips the `addonId` before proxying, so the remote node's own
  router resolves the collection without it and answers from ITS first provider.
  The pin is dropped silently exactly as it used to be locally.
- `CapRouterServices.rejectUnresolvedAddonPin` is OPTIONAL so a
  framework-live-update version skew (older server, newer builder) degrades to
  the old fallthrough rather than crashing.

## Enforcement

- `scripts/check-addon-pin-refusal.ts` (CI "Repository guards"): the hook is
  declared, called before the fallthrough, passed by both collection call sites,
  implemented server-side, and that implementation both throws and logs.
- `server/backend/src/__tests__/cap-routers/collection-addon-pin.router.spec.ts`
  drives the REAL registry + real server resolution (not the harness stub) and
  sweeps EVERY mounted collection cap, asserting a fabricated pin refuses. The
  fix was removed and the spec re-run to confirm it fails without it.
