## Context

Painting a recorded moment used to have four mechanisms, stacked in pairs.

Playback fetched the WHOLE segment covering an instant — 103 KB on `low`,
8.8 MB on `high` — to decode one GOP out of it. Scrub asked the server to build
a 60 s keyframe PACK, cache it on disk and sweep it under a retention job, with
a whole-segment fetch behind it for windows that had no pack or when the pack
tier latched itself dead.

Every one of them is a bulk transfer standing in for a pointwise question:
*what are the bytes for the frame at T?* Every recorded segment already answers
it. ffmpeg writes `+frag_keyframe+empty_moov+default_base_moof`, so each
`moof`+`mdat` pair opens at a keyframe and is independently decodable, and the
trailing `mfra`/`tfra` maps presentation time to the byte offset of the `moof`
holding that sync sample. `mfro` is by specification the last box in the file,
so the index is reachable by reading the tail. Verified present on 80/80 sampled
segments, both codecs, all three profiles.

What forced the decision was not the bandwidth. It was a night in which a seek
control died and it could not be attributed: the manifest, the index, the
profile, a deploy and two different tiers were all live candidates, and the
operator staring at a frozen frame had no way to tell which path they were even
on. Every failure that session was an AMBIGUITY failure.

The alternative considered — and rejected — was to introduce byte-range reads
behind a flag, defaulting off, and compare side by side on a real device. That
is the cautious-looking option, and it is the one that preserves the defect:
a second way for a seek to resolve is a second way for it to fail.

## Decision

Recorded media is read by HTTP byte range, resolved through the segment's own
`mfra`. There is no second path: no whole-segment fetch, no server-built scrub
pack, no flag selecting between them. A segment the mechanism cannot read is a
failure of that mechanism, to be fixed there — not routed around.

Playlists survive, but only to say WHICH segments exist and where the gaps are.
They never move media.

Scrub reads `low` and takes only the keyframe sample, whatever the playback
profile, and keeps its own index window.

## Consequences

The bar is higher, not lower. Play, pause, ±10 s and frame-step all funnel
through one `seek`, so a defect here reads as "the player is dead". That is the
point: the failure is loud and singular instead of intermittent and ambiguous.

Degradation happens INSIDE the mechanism, never beside it. A segment whose
`moov` will not parse loses exact fragment selection and falls back to a
proportional pick; a run with no known timescale claims the rest of its segment.
Both are worse reads, not other mechanisms.

A cold seek costs three round trips (init, index, fragment) and every later one
in the same session costs one, because the `moov` is cached per profile and the
`mfra` per segment. Measured through a remote tunnel: ~200 ms and ~45 KiB per
scrub position on `low`, 0 ms warm.

`ScrubPackService`, its disk cache and its retention sweep are now unreachable
and are to be deleted, not left dormant. Dormant code describing a design we no
longer use reads as verification of it.

Abandoning work is now a socket close rather than a server-side cancellation:
fast scrubbing needs no `ScrubPackAbortedError` machinery because there is no
server-side build to abort.

## Enforcement

A test in `webcodecs-playback-tier.spec.ts` asserts that every media request
carries a `Range` header — a rangeless GET is the old path, and it would
otherwise be invisible, since playback would still work, just by moving
megabytes. A second test asserts a scrub reads `low` regardless of the playback
profile. Both were verified to fail when the behaviour is removed.

Correctness of the arithmetic is pinned separately: `runExtent`'s round trip
(a run's own start must select that run) is swept over every rounding case in
`byte-range-loader.spec.ts`, and `scratchpad/_e2e-walk.mts` walks real archive
segments through the shipping code on both codecs and all three profiles.
