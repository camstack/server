## Context

`pipelineOrchestrator.getNodeInferenceDevices({nodeId:'agent-a'})` answered
`reachable:false` 84 times in 24 h on the live cluster while the same call to
`MacMiniAgent.localdomain` answered fine. Seven admin-UI surfaces read that
method, so the N100 agent appeared to have no accelerators at all.

The working hypothesis was a lossy event path: the node logged
`platform-probe readiness reconciled via direct probe RPC (ready event lost)`
90–120 s into every boot, which reads exactly like "the `ready` delta never
arrived, so the hub's registry never learned the provider". That hypothesis was
wrong in a way worth recording, because **the log line that suggested it was
itself the bug**.

What actually happened, in order:

1. At `2026-08-07T16:40:08+02:00` `/data/addons/@camstack/system` on
   `agent-a` was renamed to `system.bak-pre-unshadow` — a builtin-shadow
   cleanup (the `/data` copy was stale and was shadowing shipped code). On the
   HUB that directory really is a shadow. **On an AGENT it is the only copy**:
   `bootCoreAddons` scans `resolveAddonPackageDirs(config.addonsDir)` and nothing
   else, and the image's addon seed **deliberately excludes it** —
   `Dockerfile:76` is `const SYSTEM = new Set(['system','types','sdk',
   'shm-ring','ui-library'])` and the entrypoint's `NEED_ADDONS` restore copies
   only `/opt/camstack-seed-addons/@camstack/.`. So an agent container's
   builtin infra addons arrive ONLY via an operator `camstack deploy
   packages/system`, and once removed nothing re-seeds them.

   The Mac mini survived the identical cleanup for one reason:
   `resolveAddonPackageDirs` keys on the presence of a `package.json`, not on
   the directory name, so its `system.bak-pre-1272-…` (which kept
   `package.json` + `dist`) is still discovered and loaded. agent-a's
   `system.bak-pre-unshadow` was left holding only
   `node_modules/better-sqlite3/build` — no `package.json`, not scanned. 14
   packages became 13, and the whole infra layer went with it.
2. The next boot (`18:57:58`) came up with **zero** infra addons —
   `filesystem-storage`, `sqlite-settings`, `storage-orchestrator`,
   `hub-forwarder`, `metrics-native`, `platform-probe`. It printed four
   `Required infrastructure addon for "…" not found` lines and **continued**,
   because a missing required addon only logged while a *throwing* required addon
   aborted. The node reported `healthy`, registered its 14 forked addons, ran a
   camera, and looked normal.
3. Those four lines never left the box. The one addon that ships an agent's logs
   to the hub (`hub-forwarder`, the `log-destination` provider) is in the same
   missing package. **The failure was unobservable by construction.**
4. `registerNode` therefore carried a manifest with no `platform-probe`, and
   `CapRouteResolver.nodeKnowsCap` (`cap-route-authority.ts` → the manifest)
   correctly answered "no provider". `reachable:false` was the truth. The Loki
   histogram is unambiguous: 1 occurrence before 19:00, 84 after.
5. Meanwhile detection-pipeline on the agent kept logging "readiness reconciled
   … (ready event lost)" — because `probePlatformReadinessDirect` issued an
   **unpinned** `platformProbe.getCapabilities`. On an agent a forked child's
   unowned cap call hits `onUnownedCall` with `getResolver: () => null` and no
   outbound in-process lookup, so it goes straight to `forwardToHub` → the HUB's
   probe. Every such line ever logged on an agent proved the *hub's* probe had
   finished. A node with no probe at all looked like a node with a lossy bus.

Three separate defects, one shape: **the hub's picture of a node is a pure PUSH
that nothing re-derives, and every gate around it was willing to answer with
something other than the node itself.**

A fourth, smaller one made the diagnosis slower than it needed to be: the
orchestrator's `probeNodeInferenceDevices` WARN named the node in `tags` only,
and the shipped line carries `meta` — 84 identical Loki lines, none of which
could say which node.

## Decision

1. **An agent refuses to boot when a `required: true` infra capability resolved
   to no addon.** `InfraCapability.required` is documented as "boot aborts when
   this capability's addon fails to initialize"; an addon that is not even
   present has failed harder. Both branches now agree
   (`server/backend/src/agent/infra-boot-guard.ts`), and the throw names every
   missing capability at once — they vanish together, for one reason.
2. **`$agent.reload` re-runs the atomic `registerNode`.** The reload is the last
   step of every `camstack deploy` to an agent and it mutates both `loadedAddons`
   and the capability registry, while `triggerUpwardRegistration` fires only on
   boot, on a child's `$agent.registerNode`, and on hub `$node.connected`. A
   capability the node GAINS after boot was invisible to the hub until the next
   restart. Reconcile hung on an existing trigger — no timer, no poll, no shadow
   registry (D3).
3. **A node's readiness reconcile is PINNED to that node.** The direct probe RPC
   carries an inline `nodeId` (the pin that survives the forked-addon → parent
   UDS hop, `parent-unowned-call.ts`), so a successful answer proves the LOCAL
   probe finished. A node whose own probe is unreachable now reports NOT ready —
   which is the truth, and which routes to the conservative-floor WARN that says
   so.
4. **A per-node WARN names the node in `meta` as well as `tags`.** Tags are the
   grouping key; only `meta` reaches the shipped line. The per-node question is
   the only question ever asked of these lines.

## Consequences

- An agent whose `/data/addons/@camstack/system` is missing or unreadable now
  crash-loops instead of running degraded. That is louder and it is correct: such
  a node cannot store, configure or probe itself, and — worse — its manifest
  makes every hub routing decision about it wrong while it looks healthy. The
  optional caps (`platform-probe`, `metrics-provider`, `log-destination`) are
  unaffected; only the four genuinely-required ones abort.
- `/data/addons/@camstack/system` on an agent is **not** a shadow to be cleaned
  up. Deleting or renaming it deletes the agent's builtins. On the hub it is a
  shadow. Anyone repeating the "unshadow" cleanup must do it hub-only.
- **Blast radius of the guard is the set of agents whose addons dir has no
  loadable `@camstack/system`.** Today that is exactly one node — the one that
  is already broken. But because the image never seeds it, a GREENFIELD agent
  container will now crash-loop until `camstack deploy packages/system` has run
  against it, where before it came up silently gutted. That is the intended
  trade, and it makes the missing step in the greenfield procedure impossible to
  skip. Whether the image *should* seed the builtins is a separate open
  question — it is the more permanent fix and it is not made here.
- `$agent.reload` now costs one extra acked `registerNode` RPC. `registerNode` is
  an idempotent replace (D3), so the no-op case is cheap and safe.
- The "readiness reconciled (ready event lost)" line becomes rare and truthful.
  If it stops appearing on agents entirely, that is the expected outcome — it was
  firing on hub evidence.

## Enforcement

- `server/backend/src/agent/__tests__/infra-boot-guard.spec.ts` — the guard,
  including the exact four-capability shape agent-a booted with.
- `server/backend/src/agent/__tests__/agent-reload-reregisters.spec.ts` — the
  reload reconcile, including the `loaded: []` case (a RE-load of an existing
  addon whose manifest gained a capability reports no diff).
- `packages/addon-pipeline/src/detection-pipeline/__tests__/probe-readiness-reconcile-pinned.spec.ts`
  — the discriminating case: a fake cap plane where only the HUB has a probe must
  yield NOT ready. Remove the pin and all four assertions fail.
- Nothing guards "do not rename `@camstack/system` out of an agent's addons dir"
  — the boot guard converts it from silent to immediate instead, which is the
  enforcement that matters.
