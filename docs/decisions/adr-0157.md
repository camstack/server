## Context

The audio condition shipped on 2026-08-12 with ONE semantics for both filters:
over a window of `samplingSeconds`, at least `hitPercent`% of the audio samples
must be hits, where a hit satisfies every filter present (`dbThreshold`,
`labels`). Defaults: 60% of 10 s.

It could not fire. The analyzer emits roughly one inference frame per second,
but YAMNet puts a macro label on only **one to three frames per episode** — even
through continuous crying. The maximum `hitPercent` ever measured on the live
installation's whole history was **40**, below the shipped default of 60. The
operator's rule `4d7dbe2a-5eb7-48f5-9ed4-1cb1085d34a0` (labels `crying` +
`scream`, no dB threshold, 60% over 10 s) therefore could never notify, and
nothing said so: the window simply never confirmed, so there was no line to
grep, no failed condition, no verdict. The delivery chain below it was fine —
the outbox delivers.

Two things made it worse rather than merely wrong:

- **The editor offered a level floor seeded at −30 dBFS.** Real crying on this
  installation measures −55…−26 dBFS, so turning the level filter on with the
  offered value narrowed the rule to a band most of the sound never reaches. A
  seed that authors a rule which cannot fire is worse than no seed.
- **A percentage of frames is the wrong question for a sparse classifier.**
  Lowering `hitPercent` to 10 would have "fixed" the live rule and left the
  same trap for the next one, because the right number depends on how talkative
  the model happens to be about that class.

## Decision

An audio rule works in **exactly one of two modes**, and the mode is not a
stored field — it is **which filter the rule carries**, read in one place
(`audioModeOf` in `@camstack/types`):

- **LABEL mode** (`labels` present): the rule fires on the **first frame** the
  classifier labels with one of them. No window, no hit percentage —
  `hitPercent` and `samplingSeconds` are ignored and hidden by the editor. The
  per-label confidence gate is the analyzer's own `classificationMinScore`,
  applied per device before the frame reaches the Notification Center; the
  rule's `throttle` cooldown is the only other brake.
- **LEVEL mode** (`dbThreshold` present, no labels): unchanged — the sampling
  window is the condition.

Naming neither filter stays fail-closed. Naming BOTH is not authorable: every
editor writes through the shared `patchAudio`, which clears the other filter on
each write, and a legacy rule carrying both resolves to LABEL — the mode that
fires.

## Consequences

- **The migration is free and silent.** A stored labels-only rule becomes a
  label rule and starts working with no operator action; a stored threshold-only
  rule keeps its window verbatim. The live rule `4d7dbe2a` fires from the next
  reload tick.
- **No second switch.** The alternative — an explicit `mode` field on
  `NcAudioConditionSchema` — was rejected: this repo has twice shipped a knob
  that disagreed with the authority it was supposed to describe, and an optional
  discriminator that can contradict the fields it discriminates is that failure
  again. The cost is that the mode is implicit in the data; the benefit is that
  it cannot be wrong.
- **The schema shape is unchanged**, so no cap-router or wire migration. Zod
  cannot express "exactly one of" without a `ZodEffects` the cap path would have
  to special-case, so the exclusivity is enforced at the one write path and at
  the one read path instead.
- **A label rule can fire once per labelled frame.** During a long episode that
  is a handful of events, collapsed by the rule's cooldown. No re-arm timer was
  added: a second, invisible throttle is exactly how the first version came to
  not fire.
- The runtime spec (`AudioWindowSpec`), the engine subject
  (`NcAudioWindowSubject`) and the rule-test payload are now discriminated
  unions on `mode`, so a consumer cannot read a window off a label match.
- The offered level floor moved from −30 to −55 dBFS, and the editor states
  which way the scale runs plus the measured band.

## Enforcement

Tests, in three layers, each of which fails if the mode logic is reverted:

- `packages/types/src/notification/__tests__/audio-condition.spec.ts` — the mode
  derivation, the exclusivity of `patchAudio`, and the offered floor;
- `packages/addon-post-analysis/src/notification-center/__tests__/audio-rule-matcher.spec.ts`
  — including the sparse case the window cannot answer (2 labelled frames in 60);
- `packages/addon-post-analysis/src/notification-center/__tests__/rule-engine-audio-window.spec.ts`
  — the pairing, including the stored shape of the live rule `4d7dbe2a`.

Type-level: the discriminated unions make a cross-mode read a compile error. No
guard script — there is no drift surface to scan, because the mode has exactly
one reader (`audioModeOf`) and exactly one writer (`patchAudio`).

Operationally, the reload tick now logs the watched audio specs
(`audio watched specs`, plus one `audio rule watching camera` line per scoped
camera with `tags.deviceId`), and a confirmation logs as `audio label matched`
or `audio window confirmed`. The absence of any such line was the whole reason
this took a day to diagnose.
