## Context

D41's push depth failed in the field on the day it shipped, and the root cause
was not the transport, the codec, or the feeder — all three were proven working
(three pushed frames rendered within a second on a clean drag; Loki
2026-08-02 20:34:46). It was the SEAM: the viewer runs TWO recorded surfaces
(the server feeder pushing on the track, and a client-side decode tier painting
a canvas over it), so every drag needs a choreography — gate, overlay, deferred
go-live, a liveness proof for the selector — and each piece of that
choreography is a place to fail. The incident was exactly such a piece: a
per-begin profile pin tore the server feeder down mid-drag, eight
rebuild-and-rebase cycles a minute, while an open-but-mute session kept being
selected because "open socket" is not "painting". The stop-gap then abandoned a
session that WAS painting, because renders happened on the video element and
the selector lived beside the canvas — two surfaces, two truths.

The operator's framing, after seeing it: "Non riusciamo a implementare lo
stesso meccanismo tramite la stessa connessione WebRTC? Potremmo spedirci sia
scrub, playback e live sullo stesso collegamento cambiando i puntatori." [Can't we implement
the same mechanism over the same WebRTC connection? We could ship scrub, playback and live
over the same link by switching the pointers.] The
reference player studied for D41 works exactly this way, and the property that
matters is structural: **when frames ride the track the viewer is already
watching, liveness needs no proof — you can see it.** There is no second path
to select, so the entire mute-session failure class cannot exist.

What was tried first and did not work — three DEPLOYED pull-model attempts,
each measured insufficient by the operator on a real slow link in a single
day: (1) the retargetable sweep with budget + pipelining ("vedo sempre solo un
frame ogni tanto"); (2) push-as-a-tier beside a client decode surface (mute in
the field within minutes — the choreography incident); (3) the corrected
choreography ("non mi convince… vedo solo qualche frame qua e là. Andiamo con
la implementazione finale e basta. Unifichiamo tutto sotto webrtc"). That
third verdict is what moved this record to ACCEPTED and the design to
implementation on 2026-08-02.

## Decision

One WebRTC session per viewer per camera, and ONE output: the media track.
Live, recorded playback and scrub are the same stream whose SOURCE POINTER the
server moves; the client sends intent (pointer moves), never media decisions.

**The pointer model.** The per-viewer `TimelineSession` (which already exists
and already owns the gate) is the single authority:

- `live` — the shared live broker feeds the track (gate open).
- `recorded(epoch, rate)` — the feeder reads the archive (D31: located and
  read by byte ranges through the recording cap) and paces AUs onto the track.
- `scrub(target)` — the feeder's keyframe sub-mode: a mutable target, a
  receiver-credit-paced keyframe train (the D41 depth-3 machinery, kept).

Client intent = the existing control-channel vocabulary (`seek`,
`scrubStart/scrubTo/scrubAck`, `scrubCommit`, `setRate`, `stepFrame`,
`setProfile`, `goLive`) — all idempotent, all pointer moves.

**What is REMOVED.** The viewer's client-side recorded decode tier (the
WebCodecs canvas over the live video) and with it: the canvas overlay, the
`previewReady` reveal dance, the deferred go-live, and the push-liveness proof
in the scrub selector. The client-pull byte-range tiers (sweep, strip) remain
exactly as D41's ladder specifies, but demoted to the NO-SESSION fallback (the
legacy recording page, a session that failed to open) — never a parallel
surface over an open session.

**Transitions, and the GOP ring.**

- live → recorded/scrub: gate the live feed; the feeder bursts IDR→cursor
  prefix (playback) or pushes the covering keyframe (scrub). RTP continuity
  via the existing one-shot rebase on source switch.
- recorded/scrub → live: `goLive` ungates and replays the live broker's GOP
  pre-buffer from its keyframe (`requestKeyframe` → bootstrap replay), so
  live resumes decodable immediately instead of waiting for the camera's next
  IDR. The ring is NOT touched by recorded modes — it keeps filling from the
  source, so a return to live is always warm.
- scrub → recorded: the commit is `scrubCommit(epoch)` — a feeder seek. The
  last pushed scrub keyframe holds on the track until the seek's burst
  replaces it: the recorded→live flash is impossible BY CONSTRUCTION, because
  nothing else can appear on the track between two pointer states.

**Server cost per session.** One feeder per viewer in recorded modes (zero in
live): segment byte-range reads + one JS demux per fragment (keyframe-only
during scrub, LRU-cached, ≤8 fragments ≈ a few KB), repacketization on push.
Scrub traffic is bounded by receiver credit (≤2 keyframes in flight per
viewer); playback by the pace loop. This is the cost the admin-ui timeline
already pays per viewer today — the change multiplies deployment of an
existing per-viewer cost, it does not introduce a new kind.

## Consequences

- **What it buys.** The mute-session class dies (no second surface, no
  selection, no proof); the choreography dies (no gate/overlay/deferred-go-live
  interleavings — the incident's actual cause); scrub-to-play becomes one
  message; the viewer stops shipping a WebCodecs decode path for recorded at
  all (less client CPU, fewer WKWebView codec edge cases).
- **What it costs.** Recorded playback CPU moves client→server (demux +
  repacketize per viewer); the server becomes the single point of recorded
  playback failure (mitigated: the pull ladder remains as the no-session
  fallback); rate>1 playback and frame-step must be verified at feeder quality
  on the real viewer, not just admin-ui.
- **What it forbids.** Any new client surface that paints recorded media over
  an open session's track; any scrub/playback selection that cannot be
  disproven by looking at the track.
- **What must be true before implementing** (in order): (a) the Task-1 fixes
  hold in the field — `scrub:push-drag-end` shows `renders > 0` on real slow
  links across multi-drag sessions, and `scrub-feeder:pushed/parked` confirm
  credit pacing behaves; (b) feeder playback (not just scrub) is exercised by
  the viewer behind a flagless selector the way D41 mandates — session first,
  pull fallback; (c) audio via the feeder (Opus path) is verified on the
  viewer; (d) a per-node session cap and the existing session teardown are
  confirmed to bound feeder count; (e) the recording-only page keeps the pull
  ladder (it has no session by design).

## Enforcement

(1) `scripts/check-single-recorded-surface.ts` (wired into CI's guard loop)
fails the build if any embed page/component references a client recorded
decode engine again — the deleted module names are the tripwire, and the
byte-range scrub fallback stays permitted by name. (2) `scrub:push-drag-end`
and `scrub-feeder:pushed` stay queryable — sessions open with `renders = 0`
reopens this record, exactly as D41's tier-usage clause does for the ladder.

Amended 2026-08-03, from the first field session on the unified track: (1)
`positions: 0` drags and "No footage" for reachable moments were BOTH the
feeder discarding `nearestEdgeMs` — seeks and scrub targets outside coverage
now SNAP to the nearest footage (`recorded:seek-snapped` /
`scrub-feeder:snapped`; a gap state now means true absence in both
directions, logged); (2) the scrub train gained SWEEP mode — a steady forward
drag within a 4 s target window pushes the predicted frames between the last
pushed AU and the target (contiguous timestamps, browser-decoded in
sequence), while a fling/backward/non-adjacent move stays an IDR jump with a
discontinuity stamp; degradation to jump-only is emergent (a slow, ack-gated
tick cadence grows the per-tick delta past the window) and the mode is on
every `scrub-feeder:pushed` line plus a per-drag `scrub-feeder:drag-end`
summary {jumps, sweeps, aus}. The keyframe-only scrub demux (and its ffmpeg
fallback) died with it — scrub demuxes the full GOP like playback. Measured
on real `low` segments (both codecs): IDR every 3 994 ms at 25 fps, IDR ≈
19-26 KB vs ≈ 40-44 B per predicted frame — sweep gives ~40 ms granularity on
footage ALREADY recorded, which made the "denser camera keyframes" question
moot (halving the GOP would have cost ≈ +0.5 GB/day/camera of low tier and
helped only future footage).

Amended 2026-08-03: **the adaptive ladder must not act while the pointer is off
live.** It predates this record and is armed purely on the `/adaptive` stream id
(`startAdaptive`), so it kept ticking through recorded playback and scrub — and
its only action, a tier switch, is a close-and-recreate re-offer that disposes
the `TimelineSession` AND its feeder, dropping the viewer back to live with
nothing to re-issue the pointer. 13 of the 18 sessions that renegotiated in 24h
were in recorded playback when they did (`recorded: live RTP GATED` on the line
before). The signal is meaningless there too: the live feed is gated, so receiver
feedback measures the feeder, and a downgrade cannot shrink a file while an
upgrade cannot enlarge one. `AdaptiveController.suspend` now replaces the tick
whenever `TimelineSession.currentMode === 'recorded'`. The recorded profile stays
fully decoupled from the live tier — an adaptive target enters recorded playback
at `mid` regardless of the rung the ladder is on.

As-built (2026-08-02): client `RecordedTrackSession`
(`embed/src/playback/recorded-track-session.ts`) over the existing control
vocabulary — no protocol change; the WebCodecs engine stack (tier, engine,
video/audio pipelines, frame ring, clock, loader, demux, capability probe —
~2 400 lines + specs) deleted; the page's recorded surface is the track, the
canvas remains only for the no-session scrub fallback; recorded audio rides
the shared audio sender, so the single `muted` prop is the entire mute
surface. One deviation from the sketch above: the scrub release sends
`playRecorded` (which carries the PLAYBACK profile) rather than a bare
`scrubCommit`, because the scrub sub-mode pins the server profile to `low`
and a bare commit would resume playback at thumbnail quality; the
track-holding property is identical.

Amended by [D733](adr-0733-a-tier-change-stays-on-the-session-the-viewer-already-has.md)
(2026-10-07): a live tier change the negotiated session can carry is no longer a
close-and-recreate re-offer — the track moves to the new rendition in place, and
the TimelineSession survives it.
