## Context

On a weak network the scrub was "molto povero": the operator dragged, waited,
and got one late frame instead of a train. The investigation (2026-08-01/02)
found the client-pull model structurally serial — one keyframe read in flight,
positions in between never fetched at all, and one stalled socket able to wedge
the pump for the whole session. A studied reference player with the same
recorded-media problem behaves differently in kind, not degree: its scrub rides
an ALREADY-OPEN duplex session (its live peer connection remotely, a dedicated
socket locally), the server *pushes* a ~30-frame train of low-res keyframes
sweeping from the current position toward a **mutable** target inside a 1 s
budget, a new drag position retargets the running sweep instead of cancelling
anything, and frames that outrun the budget are skipped, not waited for.

Two of those techniques — the retargetable budgeted sweep and skip-on-deadline
— were portable into our client-pull tier and shipped (
`byte-range-scrub-tier.ts`). What could NOT be ported without an architecture
change is the transport property: client-pull pays a request→response round
trip per frame and cannot be pushed to; on a 300 ms RTT pipe that caps the
train at ~2-3 fps no matter how small the frames are. The lookahead pipelining
shipped alongside softens this to roughly transfer-rate, but a push stream has
no per-frame RTT at all.

Meanwhile a second failure shape has already cost months here: the thumbnail
STRIP tier — built, tested, cheap — sat dark behind a constant
(`SCRUB_STRIP_DEPTH = false`) because it had a gate but no selection rule
anyone owned. A tier that exists without a rule to pick it is dead code that
looks like a capability. The operator has ruled: the strip STAYS as an option
("mi va bene cambiare architettura mantenendo la strip"), so this record must
define a ladder with a selector, not crown a single winner.

What was tried first and did not work: per-position aborting (latest-wins)
painted one frame per gesture; conflate-to-newest painted the destination but
never the path; both are documented in the tier header. Naive "enable the
strip everywhere" was rejected by the operator — the byte-range model is to be
made good, not replaced by the filmstrip.

## Decision

Scrub previewing is a LADDER OF THREE DEPTHS, each with a stated cost, and the
tier is chosen per position by an explicit, logged selection rule — never by a
build-time constant.

**The depths:**

1. ~~**Strip** — pre-rendered thumbs, ~3 KB per ranged read, bitmap-cached,
   trajectory prefetch. Cheapest; blind to anything newer than the strip
   writer's cadence, and absent for pre-boot hours.~~ **RUNG REMOVED
   2026-08-03 — see the amendment at the foot of this record. The ladder is now
   two depths; everything else below stands.**
2. **Byte-range keyframe** (today's default) — the segment's own `mfra` plus
   the keyframe sample off `low` (~45 KB), now with the retargetable sweep,
   per-gesture budget, skip-on-deadline and thin-pipe lookahead. Exact to the
   GOP; pays one round trip per frame.
3. **Pushed keyframes** (the proposed change, operator "favorevole") — a
   recorded-scrub service on the node that owns the archive holds a mutable
   `targetEpochMs` per viewer session and PUSHES the sweep train of `low`
   keyframes over a connection that is ALREADY OPEN — the embed's live WebRTC
   peer connection (data channel) when one exists, else the hub WebSocket.
   `scrubTo` becomes one tiny retarget message; frames arrive with no
   per-frame RTT. The server reuses the same `mfra`/keyframe arithmetic the
   client tier uses today (D31 byte-range reads against its local archive —
   the read model does not fork). Client-side decode and paint stay exactly
   as they are: the push replaces the FETCH, not the painter.

**The selection rule** — decided in the scrub tier, per position, in this
order, and the chosen depth appears in the `scrub:drawn` log line (it already
does: `depth: strip | keyframe`):

- If a push session is OPEN and healthy → push (it is strictly cheaper per
  frame once it exists). Opening one is attempted when a drag begins and a
  live connection is already up; failure to open falls through silently to 2.
- ~~Else if measured throughput (`ByteRangeSource.throughputBytesPerMs`, already
  rolling) is below the keyframe tier's sustainable rate for the current drag
  velocity, AND the strip covers the hour → strip.~~ (removed 2026-08-03)
- Else → byte-range keyframe (the sweep).

The fallback direction is always DOWN-COST, never down-fidelity-silently: a
tier that cannot answer logs why (`scrub:no-segment`, `scrub:skipped`,
`strip:thumb-failed` exist today; the push tier must log its session state
transitions the same way).

**Interaction with standing rules.** D31 holds: recorded media is byte-range
only, no whole-segment fetch — the push service performs the same
`mfra`-indexed keyframe reads, server-side, against its local files; nothing
re-introduces segment streaming. D9 holds: pushed scrub frames are COMPRESSED
encoded keyframes (~45 KB `low` IDR), never raw frames, and they ride a
network connection to a viewer, not a process boundary on a node; the service
lives in the process that already owns the archive (recorder / stream-broker),
so no new frame-rate IPC path appears.

## Consequences

- **What it buys.** Scrub cadence on a thin pipe becomes transfer-bound
  instead of RTT-bound; the server can pace, coalesce and retarget with full
  knowledge of what is in flight (the client cannot); and the same session
  can later carry the commit's first playback GOP, making release-to-playing
  one message instead of a cold fetch chain.
- **What it costs.** A new server-side per-viewer session with lifecycle
  (open on drag-begin, retarget, close on commit/idle) — session leaks are
  now possible where none were; a second scrub data path to keep observable
  (mitigated: one shared read model and the same log vocabulary); data-channel
  plumbing on the embed's peer connection, which today carries only media.
- **What it forbids.** Adding a fourth path, or gating any tier behind a
  build-time constant again — `SCRUB_STRIP_DEPTH` is to be DELETED when the
  selector lands, replaced by the rule above.
- **What had to be true before committing to depth 3 — and what the field
  said.** (a) The sweep + lookahead was implemented, deployed, and tested by
  the operator on a real slow link the same day: "su rete lenta vedo sempre
  solo un frame ogni tanto" — the pull model is RTT-bound at its floor, so
  depth 3 was built (ACCEPTED on this evidence, 2026-08-02). (b) The data
  channel is the `camstack-control` channel the live player ALREADY negotiates
  into its offer — no new channel through TURN; frames ride the existing media
  track, not the channel. (c) Session lifecycle rides the existing per-viewer
  `TimelineSession` (disposed with the WebRTC session — no new reaper needed;
  the per-node cap is the existing session cap). (d) The selector — not a flag
  — enables it: the tier takes the push depth first whenever the session is
  active, and `SCRUB_STRIP_DEPTH` is deleted.
- **Depth-3 shape as built.** Server: the broker feeder-scrub sub-mode with
  RECEIVER-CREDIT pacing (`scrubAck` control message; cap 2 outstanding; at
  zero credit the newest target parks — a timer never releases work), retarget
  by mutable pending target. Client: `PushScrubSession`
  (`embed/src/scrub/push-scrub-session.ts`) — one retarget message per
  position, render-driven acks (`requestVideoFrameCallback`, position-message
  fallback), a live-straggler guard, and a deferred go-live so the
  recorded→live flash stays impossible. Known residual: if EVERY outstanding
  frame is lost in RTP and no render ever fires, the drag stalls until the
  commit (which seeks by another path) — accepted for v1, logged.


## Amendment — 2026-08-03: the STRIP RUNG IS REMOVED

This is not a revision of the reasoning above; it is the Enforcement clause
below firing exactly as written, and the answer it demanded being taken.

**The measurement.** A production read of the `scrub:drawn` lines showed
`depth: strip` at **zero** — not rare, zero — including on camera 101, whose
strip files had just been rebuilt by `regenerateStrips` (130 files covering
3 days). Every painted scrub frame in the window came from `depth: keyframe`
or the push session. The tier was not losing narrowly; it was never selected.

**Why it could not win.** D42 (the recorded-media session) demoted the whole
client-pull ladder to a NO-SESSION fallback. When a session is open the push
depth takes every position before the selector reaches the velocity rule; when
no session is open the page is the legacy recording page, where a drag fast
enough to trip `step > keyframe interval` is not the normal gesture. Between
D41 landing and this measurement, the rung had no reachable path to selection.

**The history this closes.** The rung was dark behind a build-time constant
(`SCRUB_STRIP_DEPTH = false`) for months, then dark behind a selection rule
this record wrote to fix exactly that, then dark behind the D42 demotion. The
operator's decision is that it goes rather than receive a fourth attempt at
being chosen: *"la strip non è mai stata usata — via."* [The strip has never been used — remove it.]

**What was removed** (commit of this amendment): the recorder's writer,
format, store, HTTP routes and `regenerateStrips` custom action; the
`stripsEnabled` recording-config field and its admin-UI checkbox + regenerate
button; the embed's `StripClient` and the `strip` depth of
`ByteRangeScrubTier`; the `strips` entity of `relocateFootage`;
`keyframeInstants` (its only consumer was the writer).

**What was deliberately NOT removed.** The `.strip` FILES on disk — deleting
operator data is the operator's decision, not the code's. The layout is
`<recordings root>/<deviceId>/strips/YYYY/MM/DD/HH.strip` and the profile
walkers already skip non-profile directories, so the leftovers are inert.
Byte-range keyframe reads (D31) and the D42 push path are untouched: the
ladder lost a rung, it was not dismantled.

**What a future reader should take from this.** A tier is not a capability
until something *picks* it under a load that actually occurs. This one was
built, tested, cheap, correct and measured at zero — three times over. Before
adding a cheaper depth to this ladder again, state the gesture that selects it,
and pair the change with the Loki query that will prove it fired.

## Enforcement

Nothing mechanical yet — review only, plus one measurable tripwire: the
`scrub:drawn` log line carries `depth`, so a Loki query can prove which tiers
actually fire in production. If a quarter passes with a tier at zero
selections, that tier's rule (or the tier) is wrong and this record must be
amended — the strip's dark year is the failure this clause exists to prevent,
and on 2026-08-03 it is the clause that ended the strip. When depth 3 is
implemented, a guard script must fail CI if `SCRUB_STRIP_DEPTH` (or any
successor build-time tier gate) reappears in `embed/src/**`.
