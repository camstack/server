## Context

The Home Assistant component (0.5.12, already released) shows the CamStack panel by framing the
admin UI through a same-origin relay on HA — `https://<ha>/api/camstack/p/<grant>/…`
→ `https://<hub>:4443/…` — so the browser never has to trust the hub's
self-signed certificate. The relay forwards the path WITHOUT its prefix and
names the prefix in `X-Forwarded-Prefix`. The reference NVR integration does the
same thing, and its UI survives it.

Ours did not. The admin UI was written for the hub root, and the root is the
one mount where two spellings are indistinguishable: `'/api/x'` and
`hubPath('/api/x')` produce the same bytes. Under the relay they do not.
`dist/index.html` referenced `/assets/…`, `/favicon.svg`,
`/manifest.webmanifest` root-absolute; `<BrowserRouter>` had no `basename`;
31 literals in 22 files spelled a hub route (`fetch('/api/auth/session')`,
`` `/api/addon-assets/${id}` ``, `'/addon/terminal/io'`, `'/viewer/camstack/'`)
and six places used `window.location.origin` as the server base (the SDK's
`serverUrl`, the two stream players, the health probe, the media-URL copy
chip). Every one of those is a request that leaves the relay: a root-absolute
path is exactly the thing `<base href>` does NOT rewrite, and on HA the
`/api/…` tree is a different application, so the failure is not even a 404 —
it is HA's own API answering an admin-UI call.

Two alternatives were on the table and were rejected:

- **Make the relay rewrite.** Rewriting HTML, JS chunks, JSON bodies and
  `Location` headers on the fly is what a relay cannot do correctly for a
  Module-Federation host whose chunk names are hashed and whose remote
  entries come out of tRPC responses. It also leaves every future literal a
  latent break.
- **Read `document.baseURI` everywhere.** Without a `<base>` the base URI is
  the document URL, so `/devices/5` reads as a mount of `/devices/` — the
  admin UI would break at the root, which is where it runs today. And a
  second reader of the same `<base>` in `ui-library` (the snapshot hook, the
  scene gallery, the MF remote loader all compose hub URLs) was the shape that
  produced two stores nobody agreed on before (D62).

## Decision

**The shell says where the page is mounted, and there is one reader of it.**

1. The relay sends `X-Forwarded-Prefix: /api/camstack/p/<grant>` (no trailing
   slash) on every request and forwards the path without it. Without the
   header the hub behaves exactly as before.
2. The hub, when it serves the admin shell (`GET /`, a deep route, an
   `/addon/…` deep link that is not an addon route, or `/index.html` by
   name) with a VALID prefix — `/[A-Za-z0-9_\-./]*`, no `..`, no `//`, no
   query, ≤ 512 chars, anything else is treated as absent — injects, first
   in `<head>`: `<base href="<prefix>/">` and
   `<meta name="camstack-mount" content="<prefix>/">`. The shell is
   `no-store` and carries `Vary: X-Forwarded-Prefix` in both cases. The
   login bounce (`302 /login?next=…`) goes to `<prefix>/login`; `next` stays
   hub-root-relative and the SPA re-mounts it.

   The marker spelling is not ours to choose: HA 0.5.12 is already released
   and probes the hub before it will frame the panel — it asks for the index
   with `X-Forwarded-Prefix: /camstack-mount-probe` and searches the FIRST
   16 KB of the body for the literal `name="camstack-mount"`, with no
   session. So the shell stays PUBLIC (it is served before the auth check,
   and was already), the meta goes first in `<head>` rather than anywhere in
   it, and `spa-mount.spec.ts` asserts it the way that client reads it.
3. `packages/ui-library/src/lib/hub-mount.ts` is the only module that reads
   that fact — the meta first, a lone `<base>` on the same origin second,
   `/` otherwise — and resolves it ONCE. It offers `hubPath()` (same-origin
   path under the mount), `hubOrigin()` (the SDK `serverUrl`: origin + mount,
   no trailing slash; the SDK and the players append `/trpc`, `/api/webrtc`,
   `/adaptive-probe` themselves), `hubUrl()` / `hubWsUrl()`, and
   `routerBasename()`. The admin UI's `src/lib/mount.ts` re-exports it and is
   the admin UI's only import point.
4. The build is relative: `vite base: './'`, relative `href`s in
   `index.html` and the manifest. The files the SHELL serves from its own
   root — `/brand/*`, `/icons/*`, `/favicon.svg`, `/manifest.webmanifest` —
   are hub paths too, and are the ones that hid: with every route prefix
   already wrapped, a prefixed browser run still put six
   `/brand/logo-horizontal-dark.svg` requests on the HA origin. A relative
   `brand/…` is not the fix either, because at the root mount it would
   resolve against `/devices/5/`; they go through `hubPath` like the rest. Chunks find their siblings through
   `import.meta.url`, so the Module-Federation host bootstrap needs nothing
   else. A server-stamped `bundleUrl` (`/api/addon-widgets/…`,
   `/api/addon-pages/…`) is hub-root-relative and is re-mounted by the loader
   that registers it.
5. A resolved base KEEPS its path prefix. `resolveProbeOrigin` used to strip
   `serverUrl` to its origin; under a path-mounted relay the origin is HA,
   and `/adaptive-probe` exists only under the prefix.

## Consequences

- At the root nothing changes, byte for byte — `hubPath('/api/x')` is
  `/api/x`, `hubOrigin()` is `window.location.origin`, the router basename
  is empty. `mount.spec.ts` pins that.
- The backend change travels with `@camstack/server`: `camstack deploy
  packages/addon-admin-ui` alone ships a relative build that still works at
  the root, but the shell is not injected until a server containing
  `spa-mount.ts` is published and applied. Until then the relay has no
  effect.
- Server-side redirects other than the login bounce (`/api/oauth2/authorize`,
  `/api/embed-auth`, `/viewer` → `/viewer/camstack/`) still answer with
  root-absolute `Location`s. They are reached directly, not through the
  relay's panel frame; a relay that wants them has to rewrite `Location`.
- The viewer (`/viewer/camstack/`) is an Expo export with its own base and is
  out of scope here; the nav link to it is mounted (`hubPath`), the app
  itself is not.
- An addon's own widget remote, built outside this repo, that spells a hub
  path itself is not covered by the guard. It reaches `ui-library` as a
  singleton, so `hubPath` is available to it.
- Per-origin browser state (localStorage token, the `camstack_session`
  cookie at `Path=/`) is keyed by the RELAY's origin under the relay — a
  login there is a login there, and does not leak to or from the hub's own
  origin.

## Enforcement

- `scripts/check-hub-paths-through-mount.ts` (CI) fails on a string literal
  into a hub route tree (`/api`, `/trpc`, `/addon`, `/assets`, `/auth`,
  `/ws`, `/viewer`, `/health`, `/adaptive-probe`) or into the shell's own
  static root (`/brand`, `/icons`, `/favicon.svg`, `/manifest.webmanifest`,
  `/sw.js`) that is not the direct
  argument of `hubPath` / `hubUrl` / `hubWsUrl`, and on `location.origin`
  used as a base, across `packages/addon-admin-ui/src` and
  `packages/ui-library/src`; a router pattern or a path composed on a
  resolved `serverUrl` prop says why with `// hub-path-ok: <reason>`. It
  refuses a marker without a reason.
- `hub-mount.spec.ts` (with and without the injection, invalid mounts,
  resolve-once), `mount.spec.ts` (the admin UI sees the same resolution),
  `spa-mount.spec.ts` (prefix validation, injection placement, a Fastify
  `inject` of the three header cases, `Vary`, and the released HA probe
  read back through a 16 KB window), and `spa-shell-cache-headers.spec.ts`
  (both admin shell routes go through `sendSpaShell` — a raw send would now
  drop the injection as well as the cache policy).

## Evidence

Driven in a real browser (Playwright) against the real hub through a local
stand-in for the HA relay, mounted at `/x/g1`, serving the built `dist` with
the same injection the backend performs, proxying everything else to
`https://192.168.x.x:4443/` with the prefix stripped and the header added,
and answering **404 to anything that arrives outside the prefix**:

| | before the static-asset fix | after |
| --- | --- | --- |
| requests to the relay | 216 | 215 |
| under `/x/g1/` | 210 | **215** |
| escaped the prefix | 6 (`/brand/logo-horizontal-dark.svg`, 404) | **0** |

Login, a client-side navigation to `/x/g1/system/cluster`, a HARD RELOAD of
that deep route, and `/x/g1/devices/289` all worked; the tRPC WebSocket
opened at `ws://…/x/g1/trpc`; 130 asset requests, 59 `/api/*`, 19 `/addon/*`
all under the prefix. The two remaining 404s are hub content that is simply
absent (a provider icon, a snapshot for device 105) and were routed
correctly. No WHEP offer fired within the window, so `/api/webrtc` is
covered by unit test and by inspection of its one composition site
(`${serverUrl}/api/webrtc`, `serverUrl = hubOrigin()`), not by the browser
run.
