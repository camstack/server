## Context

The HomeKit live stream has never rendered, in a year of attempts. Each round
picked a hypothesis, shipped a fix and re-measured the same two facts: how long
the session lasted, and who ended it. Both stayed the same.

On 2026-08-06 the instrumentation round finally made the return path visible,
and it killed the belief the whole investigation had rested on. The accessory
counted inbound RTCP per leg and logged which of the two gate outcomes fired:

```
videoRtcpReceived=21/34   audioRtcpReceived=0
videoGate=packet@577ms    audioGate=timeout@1001ms
mediaStarved=false        drops={}
```

**iOS does probe us.** Twenty-one and thirty-four RTCP packets in two sessions,
and the video gate opening on a real controller packet at 577 ms rather than on
its 1 s fallback. "iOS never sends us anything, so the return path is broken"
was false for the video leg, and every fix aimed at it was aimed at nothing.

That is where counting stopped paying. Knowing the controller spoke narrows
nothing further: a controller receiving perfect video and refusing to render it
sends the same *number* of RTCP packets as one receiving garbage. Both remaining
families of cause — a transmit-side defect (SRTP, packetisation, MTU,
sequencing) and a decode-side one (parameter sets, profile/level, timestamps,
RTP pacing) — are consistent with every number in that block.

The controller had been answering the question the whole time. Inside each
Receiver Report, iOS states in its own words what it received: fraction lost,
cumulative packets lost, extended highest sequence number, interarrival jitter.
We were decrypting none of it. A mature open-source HomeKit camera bridge
decrypts exactly this on every inbound RTCP message; that is the piece this
implementation lacked.

The same reference resets a **30 s session idle timeout** on each of those
messages and kills the stream when it lapses. Adopting the read without the
timeout is a deliberate split, not an oversight — see Consequences.

## Decision

When a remote endpoint reports on media we sent it, **decode the report**. A
counter of inbound packets is not observation of a return path; it answers
"is anyone there", which is a question that stops being interesting the first
time the answer is yes.

Concretely, for `addon-export-hap`: every inbound RTCP datagram is
SRTCP-decrypted and walked as a compound packet, every Receiver Report block is
folded into a per-leg tally, and the tally plus a derived `LossVerdict`
(`transmit-suspect` / `decode-suspect` / `no-reports`) appears in
`export-hap: stream session summary`. A datagram that cannot be decrypted or
parsed increments a distinct `unreadable` counter and books a named drop —
**"we could not read what the controller said" must never render identically to
"the controller said nothing"**, because those point at opposite subsystems.

And: **inbound RTCP is diagnostic only. It must not drive a teardown.**

## Consequences

- The summary line answers the question the next session actually has. Read
  `videoLossVerdict` first; `videoReceiverReports` carries the raw numbers
  behind it.
- **No idle watchdog, and this is the third time that has had to be written
  down.** The reference implementation's 30 s timer is precisely the shape a
  ~31 s teardown gets misdiagnosed as, and this codebase spent a long time
  chasing one before proving it has none (neither the delegate nor `hap-nodejs`
  contains such a timer). The measured sessions since are 9.8 s and 12.1 s —
  a 30 s watchdog could not have fired in either, so it would add a way to kill
  a session and no diagnostic value whatsoever. The existing
  `export-hap: stream heartbeat` covers the observable half and **logs only**.
  If a future session wants a watchdog, it must first show a session that a
  watchdog would have saved.
- The parser is hand-rolled rather than taken from `werift-rtp`, which this
  package already depends on. That library swallows a malformed sub-packet into
  a debug log — collapsing exactly the distinction above — and reads
  `cumulative number of packets lost` as unsigned, where RFC 3550 §6.4.1 defines
  it as signed. An unsigned read turns "one duplicate" into "16 777 215 packets
  lost", which is the single most misleading value this instrument could emit.
- Two SRTCP contexts now exist per leg, inbound and outbound, built from the
  same HAP master key. Sharing one would let an inbound replay-window fault
  present as an outbound encryption fault.
- This does not fix the stream. It makes the next hypothesis an observation
  instead of a guess.

## Enforcement

`packages/addon-export-hap/src/mappers/builders/__tests__/rtcp-receiver-report.spec.ts`
parses buffers written out byte by byte in RFC 3550 §6.4 layout, and
cross-checks them against the same packets produced by `werift-rtp`'s
independent serialiser — so a wrong field offset cannot pass on either side.
Removing the signed read turns 1 test red, removing the Sender-Report offset 1,
removing compound traversal 3, collapsing worst-vs-last 2, and hard-coding the
verdict 3 (each verified by deleting the code and re-running).

Nothing enforces the no-watchdog rule but this record and the docblock on
`SESSION_HEARTBEAT_MS`. A guard would have to recognise "a timer that kills a
session", which is not statically distinguishable from a legitimate one.
