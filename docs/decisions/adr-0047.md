## Context

`NotifierActionSchema.id` had been documented since the notifier cap was written
as "the stable id used in the callback when the user taps the button". **There
was no callback.** Nothing set `actions` either — the field, the
`supports.actions` capability flag, the degrade engine's slice and the ntfy and
zentik adapter mappings all existed and no notification had ever carried a
button. The same shape as the zone-crossing vocabulary in [D35](adr-0035.md):
declared, mapped, enabled, produced by nothing.

The half with a real choice in it is the callback, because **the URL travels
through infrastructure we do not own**. It goes to ntfy's server, or through a
push relay, or into whatever chat app forwarded the message. It is exactly as
public as the notification is, and a notification is routinely screenshotted,
forwarded and mirrored to a watch. Meanwhile the thing on the other end of a
button is a rule action sequence — `{cap, method, args}` against a device — which
already exists and already opens gates.

Three models were put to the operator, with the consequence of each stated:

1. **Hybrid by risk** — the token alone runs a non-destructive action; anything
   marked `destructive` lands on a confirmation page requiring a CamStack
   session. Recommended, because `destructive` already exists on the schema and
   was unused.
2. **Token only, always** — whoever holds the notification can run the button.
3. **Always confirm with a session** — the token identifies the action, never
   authorises it.

The operator chose **(2)**, having been shown explicitly that a forwarded
notification then lets a stranger do anything the owner could, until the token
expires. This record exists so that choice is legible later, and so nobody
"fixes" the missing session check as an oversight.

## Decision

**A notification button's callback is authorised by its token and by nothing
else.** There is no session check, and a tap does not identify who tapped.
Because the authorisation model does not bound the blast radius, the token
must — and every one of these is load-bearing, not defensive decoration:

- **One token grants one action of one notification.** The record fixes the
  rule, the sequence and the device at mint time. There is no shape that runs an
  arbitrary sequence, so a token cannot be re-pointed.
- **Single use, claimed atomically.** `claim()` reads the record and marks it
  spent in one synchronous step. No `await` may be introduced between the two.
- **The token is spent BEFORE the sequence runs**, and a failed run does not
  hand it back. Retrying a half-run "unlock, wait, open" executes an intent
  nobody expressed.
- **Fifteen minutes**, not the artifact plane's 24 hours, and expiry is a
  COMPARISON rather than a swept job — a reaper that failed must never leave a
  live button behind.
- **In memory**, so a link can never outlive the process that minted it.
- **A button is minted per DELIVERY**, not per notification: two recipients
  sharing a token would mean the second person's button was dead on arrival.

`destructive` stays a rendering hint. It must not be read as a gate anywhere.

## Consequences

**What it costs.** A forwarded notification is a usable credential for one
action, once, for fifteen minutes. That is the accepted risk and it is not
mitigated anywhere else in the system — no rate limit, no IP check, no
confirmation. An operator who does not want that must not author a button for
that sequence; there is deliberately no half-measure to hide behind.

**What it forbids.** Adding a session check to the plane later is a change of
model, not a tightening — it would break every button already delivered.
Reversing this decision means a new record, not an edit to this one.

**What must stay true elsewhere.** The rule action executor's device-scope check
is now the only structural bound on what a button can reach: a button runs a
sequence, and a sequence may only actuate device-scoped capabilities. If that
check ever moves or softens, this decision gets materially worse without
anything here changing. A button also cannot name a sequence the rule does not
declare — the minter refuses, and logs the refusal, because an armed-looking
button that always fails is worse than an absent one.

**A deploy kills outstanding buttons.** In-memory tokens do not survive a hub
restart. Accepted: with a fifteen-minute TTL they were nearly dead anyway, and
the alternative is a persisted store whose read-then-write single-use check is a
race a physical actuator would pay for.

## Enforcement

Tests, and they are the only enforcement — there is no guard that can check an
authorisation model.

`__tests__/action-token.spec.ts` pins single use (including three claims in one
tick yielding exactly one winner), expiry as a comparison with nothing swept,
and that a tampered id, a tampered expiry or another install's secret all fail.
`__tests__/action-plane.spec.ts` pins that a forged signature learns nothing, a
valid link runs exactly once, and a FAILED run does not return the token.

`docs/architecture/notifications.md` carries the operator-facing statement of
the risk. If the model changes, that page and this record change together.
