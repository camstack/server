## Context

T4 shipped `camera` entities on 2026-08-14: six components per
camera — three profiles × muted/unmuted — each carrying a broker RTSP url on a
`state_topic`, behind two url gates (a refusal for a credential in the
authority, a refusal for a loopback host) and a `hostname` argument threaded
through the reconcile so the broker would not mint `127.0.0.1`.

Read off the operator's live Home Assistant the same day: `platform: camstack`
held **165 entities and exactly two `camera` ones** — one per exported camera,
`unique_id` `camstack_<stableId>_camera`. Not one of the twelve announced
stream components existed.

They never could have. `custom_components/camstack/camera.py` builds its
cameras from the export MEMBERSHIP and has never read `cmps`: its still comes
from `snapshot.getSnapshot` and its live video from
`webrtcSession.handleOffer`, which is native WebRTC and has no use for an RTSP
address at all. **Neither side said anything**, and the reason is the shape of
the handshake: `/api/camstack/version` answers with the platforms the
integration BUILDS, the component builds `camera` truthfully, and the hub read
that as "it will build my camera components". A platform-name handshake cannot
express "I build this platform, from somewhere else".

So the whole T4 apparatus — the password gate, the loopback gate, the
`hostname` plumbing, the value pass that published a url per (profile, mute)
pair — guarded a value with no consumer. The `hostname` gate was worse than
inert: a hub with no reachable base url produced NO camera entity, refusing on
behalf of a reader that did not exist.

## Decision

**The export announces one `camera` component per entry of
`webrtcSession.listStreams`, carrying that entry's `target` verbatim in
`stream_target`, and no URL of any kind.** The component builds one entity per
component and hands the target straight back to `handleOffer`.

Three corollaries, each of which is the rule someone would otherwise break:

1. **The ADAPTIVE stream gets no component.** The component's membership
   entity *is* the adaptive stream — it negotiates no target and has carried
   `camstack_<stableId>_camera` since the integration shipped. A component
   claiming that `unique_id` a second time makes Home Assistant drop one of
   the two with *"does not generate unique IDs"*, and the one it dropped in
   testing was the operator's existing camera, with its history on it.
2. **A `camera` component announces neither a `state_topic` nor a
   `command_topic`.** It carries no value on the push plane, so declaring one
   would promise a value nothing publishes — and an entity Home Assistant
   shows as unavailable is indistinguishable from a camera that is down.
3. **The two url gates are DELETED, not kept.** There is no address in this
   plane to carry a password or to point at a host only the hub can reach. A
   gate guarding a value that no longer exists is the leftover that reads as
   verification.

## Consequences

- A camera reaches Home Assistant as its own entity **plus one per assigned
  profile plus one per raw substream** — six on the operator's Reolinks
  instead of one. The profiles arrive enabled; the raw substreams are
  registered-and-off, because they are the sources the profiles already point
  at.
- `cameraStreams.getProfileRtspEntries` is no longer read by this export, and
  neither is `mediaBaseUrl` for streams. A hub with no reachable base url now
  loses its image entities and keeps its cameras.
- **Both repos must ship.** The hub half is a `camstack deploy`; the component
  half is a HACS release and an HA restart. Until the component ships, the
  hub's camera components produce the same "this version does not build
  `camera`" line the old ones did — no regression, and no new entity either.
- `HaComponent` gains a field that is not a topic. That is a deliberate
  exception to the "everything here is a topic" reading of the wire format,
  and it is confined to `camera`.

## Enforcement

`__tests__/camera-entities.spec.ts` asserts, on the stream list read off the
live hub: one entity per stream bar the adaptive one, no component claiming
`<stableId>_camera`, no `state_topic` or `command_topic` on a `camera`, and —
the property that lets the gates go — **no `rtsp:`, `http:`, `@` or
`127.0.0.1` anywhere in a serialised camera component**. On the component
side, `tests/test_entities.py` asserts the entities are built and that a
stream entity negotiates the target the hub named, against a fixture generated
by running the hub's own `entity-catalog.ts`.

The handshake gap itself — a platform the component names and builds from
somewhere other than `cmps` — is **not** guarded, and cannot be from this
repo. It is the reason this record exists.
