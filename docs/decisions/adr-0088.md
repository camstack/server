## Context

`SqliteSettingsBackend.queryDeclared` appended a SQL `LIMIT` only when the
caller supplied one. **63 call sites supply none** — most legitimately, because
their filter is narrow (`where: { trackId }`, `where: { ownerId }`) and the
result is a handful of rows. The engine could not tell those apart from a full
table scan, so it served both.

hub-main died of it five times in seven days — 01/08 twice, 02/08 twice, 07/08
once — always with the same two frames under the fatal:

    FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
    12: Data::GetValueJS(…) [better_sqlite3.node]
    13: Statement::JS_all(…) [better_sqlite3.node]

**What was tried first and was wrong.** The 07/08 record attributed this to one
unbounded `Statement.all()` materialising ~3.4 GB. Measuring the database
disproves it: 153 MiB total, and 134 MB in a backup taken 14 h before the kill,
with `auto_vacuum=NONE` and `freelist_count=6` proving it had never held more.
No single read on that file can produce 3.4 GB.

What actually happened is worse for a per-query fix: **many bounded reads live
at once.** A viewer app returned from background after 244 s and requested a
12-hour window over **16 cameras with limit 960 — twice, 33 ms apart**. Heap
went 644 MB → 4 090 MB in 17 s with not one log line, and the final
Mark-Compact reclaimed **4 MB of 4 090** — every byte still reachable, so not a
GC that fell behind. `Statement::JS_all` is where the wall was hit, not the size
of the call that hit it.

The amplifier is `TrackStore.queryRecent`: the k-way merge needs `limit + 1`
rows from **each** device before it can know which survive, so the read is
`deviceCount × (limit + 1)` while `RECENT_MAX_LIMIT` bounds only the page. 16
cameras × 960 is **15 376 full track rows per request** (measured by
`track-store-recent.spec.ts`), on a table whose `positions` JSON averages
**10 KB per row** — 47 MB of the 54 MB table — parsed into JS objects on every
read.

## Decision

**A read is bounded twice: by the caller, and by the engine underneath it.**

The engine ALWAYS appends a `LIMIT` — `SETTINGS_QUERY_DEFAULT_ROW_CAP` (2 000)
when the caller gave none, `SETTINGS_QUERY_HARD_ROW_CAP` (20 000) as a ceiling
an explicit limit cannot exceed. It fetches one row above the bound so
"truncated at the cap" is distinguishable from "the page was exactly full", and
**WARNs whenever a bound it imposed actually bites**, naming the collection, the
cap and `tags.deviceId`. A truncated read that looks complete is a worse failure
than the OOM it prevents: it turns "the hub died" into "the retention sweep
quietly stopped deleting".

That cap is a BACKSTOP, not a design. **A caller that can read an unbounded set
owns its own bound** — a page size, and a loop. Where the caller's bound is
tighter than the engine's, the engine's never fires and the WARN stays silent,
which is how you can trust it when it does fire.

A caller whose read fans out across N entities bounds the **product**, not the
per-entity limit (`RECENT_FANOUT_ROW_BUDGET`). Shrinking a page is not data
loss when a cursor already exists; serving one enormous page is what loses the
process.

## Consequences

- Cap sizes are tied to MEASURED row widths, not row counts. `tracks` is the
  pacing table at 11.5 KB/row; 2 000 of them is ~23 MB of text before parsing,
  an order of magnitude under hub-main's routine p95 heap (2 108 MB) rather
  than a multiple of it. The same 2 000 rows of `motion-events` (78 B/row) is
  160 KB, so narrow tables never notice. **Re-derive these numbers from the
  live database before changing them** — an earlier draft of this rule sized
  the cap on the belief that `pipeline-analytics:faces` was the widest table.
  It is 372 rows and 4 MB.
- Callers that page must keep their page size below the engine cap, or the
  engine becomes the bound and the WARN becomes noise.
- `limit: -1` is treated as ABSENT, not as an error: SQLite reads a negative
  `LIMIT` as "no limit", and the cap schema is `z.number().optional()`, so it
  was the one input that could reproduce the OOM through a bound that looked
  applied.
- **This does not fix reading columns nobody wants.** `projection: 'slim'` on
  `TrackStore` drops `positions[]` and `snapshots[]` from the RESULT, after the
  row has been selected, transferred, msgpack-decoded and JSON-parsed in
  hub-main. The cost is already paid by then, and the projection is a comment
  that describes the right design while the wrong one runs. The remaining half
  of this work is a `select?: readonly string[]` on `QueryFilterSchema` pushed
  into the `SELECT` column list, validated against the declared columns so an
  unknown name fails loudly rather than being dropped. It is additive and
  optional, but it is a `*.cap.ts` change and therefore needs codegen plus a
  `@camstack/system` publish — deliberately deferred rather than landed beside
  the bound.

## Enforcement

- `query-row-bound.spec.ts` — the cap applies, the WARN fires with the
  collection and `tags.deviceId`, and it does NOT fire when an explicit limit
  is merely filled. Verified by removing the fix and confirming RED.
- `track-store-recent.spec.ts` — asserts the PRODUCT is bounded, that a
  single-device request is untouched, and that the whole set still pages
  through the cursor without loss or duplication.
- `face-store.spec.ts` — asserts the sweeps **never issue a query without a
  `limit`**, and that they still see rows beyond the first page. The rest of
  that file seeds a handful of rows, so a broken paging loop passes all of it;
  this is the discriminating one.
- Nothing catches a NEW unbounded call site. The engine cap makes it survivable
  and loud rather than fatal, which is the point — but a guard counting
  `query.query({…})` calls with no `limit` would be cheap and is not written.
