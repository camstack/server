## Context

The operator has reported the same defect three times: the secondary services
on a camera accessory — the privacy switch, the accessory children (siren,
floodlight), the eight PTZ switches — render in iOS Home as "Interruttore 1",
"Interruttore 2". Three rounds of fixes have been shipped and none changed what
the operator sees.

- Round 1 built the label as `${camera} — ${action}`. The em-dash (U+2014) is
  outside Apple's `checkName` set, hap-nodejs warned, and the fix was correct as
  far as it went.
- Round 2 dropped the em-dash AND moved the label from `Name` to
  `ConfiguredName`. Still unnamed.
- Round 3 (D65) saw hap-nodejs logging `Characteristic not in required or
  optional characteristic section for service Switch. Adding anyway.`, read it
  as a rejection, moved the label back to `Name` only, and asserted the new
  mechanism in three docblocks and a test. Still unnamed.

Two measurements against the installed `@homebridge/hap-nodejs` 2.1.7 settle
what actually happens, and both contradict D65:

1. `Service`'s constructor already writes its `displayName` argument to
   `Characteristic.Name`. Every round — including round 2 — therefore shipped
   with `Name` correctly set. D65's stated cause ("iOS then had no name to
   render") was never true, and D65's own text concedes the characteristic was
   "added anyway" in the same paragraph that claims it was rejected.
2. The mDNS configuration number is a sha1 over
   `Accessory.internalHAPRepresentation(false)`, which OMITS characteristic
   VALUES. Changing the string inside `Name` does not move that hash, `c#` does
   not increment, and a paired controller is never told to re-read
   `/accessories`. Measured: a name-value-only change leaves the hash identical;
   adding a characteristic changes it.

`Name` is also declared `pr` only — paired read, no write, no notify. It is the
seed a controller copies into its own database at first enumeration, not a
channel. `ConfiguredName` (`000000E3`) is `pr | pw | ev`: the only name
characteristic a controller may write and may subscribe to, and the one iOS 16+
reads for a service the user can rename.

hap-nodejs' per-service optional lists predate `ConfiguredName` being valid on
any service, which is why `Service.Switch` does not list it. That is a library
metadata gap, not a protocol rejection: `Service.getCharacteristic` calls
`addCharacteristic` unconditionally and only then emits the warning.

## Decision

A secondary Switch- or Lightbulb-shaped service on a camera accessory publishes
its label to BOTH `Name` and `ConfiguredName`, through the single helper
`applyServiceLabel` in `builders/service-label.ts`. The helper registers
`ConfiguredName` with `Service.addOptionalCharacteristic` FIRST, which takes the
branch above hap-nodejs' warning — so the accessory still builds with zero
characteristic warnings and the characteristic is still published. No builder
writes either characteristic directly.

`Service.MotionSensor` is deliberately excluded: it is not a separately named
tile in iOS Home, so a writable name there would be a guess.

## Consequences

- Adding the characteristic changes the accessory structure, so `c#` increments
  and a paired controller re-reads. It does NOT invalidate pairing.
- The zero-characteristic-warning invariant D65 introduced is kept, and is now
  the thing that proves `addOptionalCharacteristic` is being used rather than the
  thing that forbids `ConfiguredName`.
- **Confirmed on the operator's iPhone, 2026-08-07**: after the deploy the
  switches show real names. Adding the characteristic bumped `c#` AND supplied a
  new value in the same step, so which of the two the controller acted on is not
  separable from this observation — see the consequence below.
- **A VALUE-only change to `ConfiguredName` DOES reach a paired controller, with
  no `c#` bump.** Measured twice on 2026-08-07, when the labels were trimmed to
  drop the camera prefix: the config hash is byte-identical before and after, and
  the hub's own `AccessoryInfo.*.json` still read `configVersion` 3 and 4 after
  the deploy — yet the operator confirmed the new names visible on the iPhone
  (iOS 26). So the controller picks the value up on the reconnect that follows an
  accessory rebuild, via a re-read or the `ev` subscription. Renaming a service
  therefore does NOT require a structural change; it requires the addon to
  restart so the controller reconnects.
- D65 (the naming record) is superseded. D66, the hardware-decode record written
  in the same pass, stands.

## Enforcement

`service-naming.spec.ts` builds real `Accessory` objects and asserts both
halves: zero `characteristic-warning` events, AND a `ConfiguredName` present on
every switch-shaped service equal to that service's `Name`, with `pw` and `ev`
perms. Discriminating check: dropping `addOptionalCharacteristic` turns 4 red;
dropping the `ConfiguredName` write turns 1 red. Neither half can be removed
silently.
