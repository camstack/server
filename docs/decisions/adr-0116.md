## Context

The locked spec (planning repo: superpowers/specs/2026-06-10-recorder-multi-location-storage-design.md)
called for recordings spread over operator-assigned storage locations. It
shipped at N=1 and stayed there. Everything downstream of the choice is already
N-location-aware — the index stamps `locationId` per segment, eviction resolves
a physical-root DOMAIN (D-eviction-domain), retention and the relocate mover
both scope by location, playback resolves a segment's root from its own
`locationId` — and exactly one function collapses it: `resolvePlacement`, which
picks the first writable location of the preferred type and returns it.

Adding disks to that shape naively fails in four separate ways, and three of
them are silent:

**Per-segment striping does not work here.** The obvious reading of "stripe by
free space" is to send each finalized segment to whichever location is emptiest.
The recorder cannot: `.rec-tmp` staging lives UNDER the placement root
specifically so `rename()` is a same-filesystem move. A segment whose final
location differs from its staging root takes the EXDEV copy+unlink fallback,
which rewrites every byte — 2× disk writes on the hot path, the F1 regression
this repo already paid for once. And one ffmpeg `-f segment` writes one output
directory; two locations means two ffmpeg processes per profile, i.e. two RTSP
pulls of the same encoder.

**Stamping the location into the path does not work either.** The other obvious
design — encode the location in the segment path so a reader can find it — breaks
`parseSegmentPath`, which is the reason the index can never drift from disk
(paths encode start/dur/bytes and nothing else), and breaks the archive layout
every hydrate walk, calendar scan and export playlist already assumes.

**Two writable locations over one physical root corrupt attribution.** Hydrate
attributes a discovered segment by PROFILE, and when several same-type aliases
share a root `locationForHydratedProfile` can only pick the lexicographically
first. Footage written as `recordings:b` reads back as `recordings:a`: the
per-location free-space guard, per-location accounting and the drain mover all
then reason about the wrong location, and a drain of `recordings:b` believes it
has nothing to move. Stock `recordings:default` + `recordingsLow:default` share
a root deliberately and are fine — different types, and the profile
disambiguates.

**An unmounted disk is invisible.** A recordings location is normally a
mountpoint. When the disk fails to mount, the mountpoint DIRECTORY still exists
inside the container, `mkdir` succeeds, ffmpeg writes happily, and the footage
lands on the system volume while per-location accounting reports a disk that is
not there. `statfs` cannot detect this: Node's `StatFs` exposes no fsid, and
`type`/`bsize`/`blocks` are neither stable across a remount nor unique across
two identically-sized volumes — a same-size spare passes cleanly.

And one requirement that came from the operator mid-build, after watching the
naive version: creating a storage location must NOT make the recorder write to
it.

## Decision

**1. The unit of placement is a (camera, profile) ASSIGNMENT, not a segment.**
One writer run writes one directory on one filesystem. Balancing means choosing
which location each camera-profile lands on.

**2. An assignment is applied only at a WRITER-ATTACH BOUNDARY** — attach, band
rollover, give-up recovery. Never mid-run. The plan is recomputed on the
controller's existing 30 s tick (no second timer), and a running writer keeps
its root until it next attaches. After a storage migration the plan is DROPPED
rather than restored: the layout it describes no longer exists, and a cached
plan would re-point writers at the disk the operator just migrated away from.

**3. Weighting is headroom, computed by a PURE planner with the rotation
outside it.** `planPlacement(candidates, demands, current, …)` takes no clock,
no state and no I/O. Headroom is `min(free − minFreePercent floor, maxUsedGb −
used)`, clamped at zero; demand is a measured bytes/day per (camera, profile)
derived from the index in one pass, falling back to balancing by COUNT before
anything is measured. A genuine tie — two locations the capacity signal cannot
separate — is handed to a round-robin re-ranker that lives OUTSIDE the planner
(D37: a lexicographic tie-break decided every dispatch on a cluster whose load
signal was almost always zero, and one accelerator was never used at all).
Stickiness is enforced by a hysteresis band: nothing moves until a location is
off its target share by more than 15 percentage points, or must be vacated
(read-only, gone, out of headroom). A plan that churns a writer every tick is
worse than no plan — each move costs a recording gap.

**4. `isDefault` becomes a PREFERENCE, and `StorageLocation.enabled` is the
opt-in.** The default of a type is the fallback of last resort, not the only
target. Whether a location participates in balancing is `enabled`, a flag on the
LOCATION — so recordings, event media and backups all read one thing and nothing
has to be extended per consumer. A newly created sibling is stamped
`enabled: false` (creating a disk must not silently start writing to it); the
type default is always stamped `true`. The flag is OPTIONAL and ABSENT MEANS
ACTIVE, so no migration ships with it and every pre-existing location keeps
working; the recorder reads it tolerantly, so the recorder half deploys before
the framework train that carries the field and behaves identically until then.
It rides the `config` blob under a reserved `__enabled` key, because a new
COLUMN puts the table through `declareCollection`'s destructive rebuild.

**5. Two WRITABLE locations of the same type over one physical root are
refused** at the placement seam: every alias but the lexicographically first is
demoted to `readOnly`. That is the drain model's own vocabulary — placement
skips it with no new branch, footage stays readable — and the kept alias is
exactly the one hydrate attributes to, so placement and hydrate cannot disagree.
A read-only duplicate is not a conflict; it is the drain model working.

**6. Mount identity is an adopt-on-first-use marker, remembered off the
volume.** `<root>/.camstack-location` names a `volumeId`; the recorder's own
durable store (on the data dir, a different filesystem) remembers it. A marker
that is missing while an id is remembered, or that names a different volume or
location, means the bytes under this path are not the bytes we wrote: the
assignment fails over to a sibling, loudly, with an ops-log row and a liveness
alert. With only ONE location it KEEPS the assignment and shouts — a stopped
camera is the one outcome nobody asked for. Absent marker + nothing remembered
ADOPTS, so the probe is inert on the first boot after the deploy and
load-bearing from the second. A read that FAILS decides nothing (D49).

Rebalancing beyond this is operator-armed: nothing MOVES existing footage. The
plan changes where NEW writes go; the relocate mover remains the only thing that
moves bytes, and it is invoked by an operator.

Placement state is the recorder's own `recordingPlacement` DurableState blob,
never a field on the strict `RecordingConfigSchema` in `@camstack/types` — that
is what keeps the recorder half train-free.

## Consequences

- A camera's footage is spread across locations at DAY granularity at best, not
  segment granularity. Playback already handles this (each segment carries its
  own `locationId`); a human reading the disk will find one camera's archive in
  two places.
- The rotation cursor is mutable state in the recorder process. It is advisory:
  a lost cursor (a restart) costs at most one unfair choice, and it is consulted
  only for a tie.
- `enabled` on the location means every future balancing consumer must read it.
  A consumer that ignores it silently re-creates the failure the operator hit.
- The mount probe writes one file per location root. That file must stay
  dot-prefixed: the hydrate walk descends `<root>/<deviceId>/` and
  `parseSegmentPath` is digits-first, so anything else would be walked.
- Placement rows land in the ops-log under `op: 'relocate'`, because
  `OpsLogOpSchema` has no `placement` member and adding one needs a framework
  train. Every such row is prefixed `placement:` in its detail so the two are
  distinguishable — D61's lesson about sharing an op is acknowledged, not
  ignored. A dedicated op belongs in the enum the next time it is opened.
- The types + storage-orchestrator half cannot go live via `camstack deploy`; it
  needs the next framework train (`applyServerUpdate`). Until then `enabled` is
  `undefined` on every live location, which is exactly today's behaviour.

## Enforcement

`packages/addon-pipeline/src/recorder/__tests__/placement-planner.spec.ts`
(purity, headroom weighting, the hysteresis band in isolation, the injected
tie-break, the single-location invariant),
`placement-balancing.spec.ts` (a created-disabled location receives zero writes;
enabling starts balancing at the next attach; disabling drains new writes without
touching footage; one writable location is byte-for-byte today),
`placement-guard.spec.ts` (same-root demotion, and that the kept alias is the
one hydrate picks), `placement-volume.spec.ts` + `placement-service.spec.ts`
(adopt / verify / mismatch / unreadable, failover, and the per-camera log tag),
and `storage-orchestrator-enabled.spec.ts` + `location-store.spec.ts` for the
flag's creation defaults and its reserved-key persistence.

Each of the load-bearing gates — the same-root demotion, the mount-probe
failover, the hysteresis band and the `enabled` filter — was removed and
confirmed to fail before being restored.
