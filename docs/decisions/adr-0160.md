## Context

The first boot with the D148 staging reconcile relocated the whole backlog:
123 000 segments, 179 GB. The recovery itself worked. What followed it did not.

The directory walk finished — the files were moved — and the recorder's main
thread then sat at **100% CPU (84% utime) for tens of minutes without emitting a
single log line**, in a runner that was still supposed to be recording. The
damage was all downstream of the stall: 896 `camera function authority TIMED
OUT` warnings in three hours, live `SegmentWriter`s restarting, `segment file
never landed` (waits >30 s) on four cameras simultaneously, and the recorder's
cap UDS channel hitting its 60 s timeout so camera settings tabs vanished from
the admin UI. Only respawning the runner cleared it.

**The first three guesses were all wrong, and measuring is what found it.** It
was not the recovery merge, not a ledger insert, and not the file I/O of
retention deleting the new footage — that path removes whole hour directories
with one `fs.rm` each, which is why the profile was user CPU with almost no
iowait. Reproduced against the real classes at the observed scale (1 632 960
live rows + 122 400 recovered victims, all I/O stubbed to a no-op):

```
A. bucketFullyEvicted x8865            182 596 ms   ← 94%
B. index.removeSegments(122400)             44 ms
C. onEvicted x122400, 5 000 cached hours 15 285 ms   ← one unbroken block
```

`SegmentStore.evict` answered "does this eviction cover every segment the bucket
holds?" with `index.segments(deviceId, profile)` — a full COPY of the
device-profile archive plus a full `path.startsWith` scan — **once per
hour-bucket**. That is O(buckets x archive), and it was invisible until D148:
before it, a retention round touched a handful of buckets at the retention edge;
after it, six weeks of recovered footage made **8 865 sparse buckets** evictable
in one round. D148's own consequences section predicted the eviction ("retention
sees it for the first time") and nobody costed it.

The second term is `onEvicted`, fired **per row**, into
`CalendarIndex.invalidate`, which drops a whole UTC day and sweeps its hour
cache — O(cached hours), with `[...hourSegs.keys()]` materialised on every call,
in one synchronous stretch with no await in it. That is the 30-second event-loop
freeze, and it grows with how long the session has been scrubbing.

Two more found in the same trace. The boot hydrate
(`hydrateDeviceFromStorage`) runs everything between `readdir` and
`hydrateDevice` as ONE synchronous block — 963 ms measured for a single device's
544 320 entries, resolving the location alias with `localeCompare` **per file** —
and logs nothing until every device is done. And `onIndexed` fires an unawaited
`readMfraTable` for every finalized segment: the recovery queued 122 400 of them
— an `open` plus two reads each — onto the same 4-thread libuv pool the live
writers' finalize I/O uses, for tables the 26 h store can never serve. Those
tables also leaked: `prune` walks the insertion-ordered prefix and stops at the
first live entry, so an expired entry appended behind one is unreachable forever.

## Decision

Bulk recovery over stored media is BACKGROUND work, and three things follow from
that, none of them optional.

**It announces every phase, at both ends, with counts.** Start line before the
first unit of work, progress while it runs, completion always — including the
found-nothing case, because "ran and found zero" and "never got there" are
different answers and only one is reassuring. Per-camera phases carry
`tags: { deviceId }`.

**Its cost never scales with the archive.** A question asked once per bucket is
answered from ONE census pass, never by re-deriving it from the whole index —
`RecordingIndex.bucketCounts` plus an O(1) `hasSegment` per victim replaces the
per-bucket copy-and-scan. A notification whose unit is a day is sent once per
(device, day), not once per row. And a loop that spans thousands of units hands
the event loop back on a chunk boundary.

**It yields to the live path, and yields harder when the loop is contended.**
The recovery paces itself through `LoopPacer`, which measures what a zero-delay
hop actually cost and stands back proportionally (bounded) while the loop is
busy. Recording never waits behind recovery; recovery waits behind recording.

And the cheap question comes first (D54): work whose product can never be served
— an mfra table for a segment already past the serve window — is not done at all,
and the store refuses to keep it.

## Consequences

- The same eviction round is **198 715 ms → 632 ms** on the reproduction, with
  an identical outcome (8 856 of 8 865 buckets removed by `removeDir`, 122 400
  rows de-indexed). The archive can grow without the round's cost following it.
- `SegmentStoreDeps.logger` now requires `info`. A round that can take minutes
  must be able to say so; every construction site supplies it.
- `bucketFullyEvicted` no longer compares path SETS, it compares a count plus
  per-victim indexed-ness. That is equivalent only because a bucket dir
  (`<dev>/<profile>/Y/M/D/H`) names exactly one (device, profile) and a round's
  victims are unique index rows — if either ever stops holding, this becomes
  wrong in the direction that deletes a directory too eagerly, so both are
  stated at the call site.
- Recovery is now SLOWER on a contended node, deliberately. The pacer's counters
  (`hops`, `contendedHops`, `pausedMs`, `maxLagMs`) are on the completion line so
  "why did the backlog take four hours" has an answer instead of a suspicion.
- Segments older than 26 h get no mfra table, so a client seeking into recovered
  footage pays one extra tail round trip. That was already true for every
  pre-boot segment.
- The boot hydrate now emits one line per (device, root). On a 20-camera fleet
  that is 20 lines a boot — the cost of being able to answer "which camera's walk
  is slow" per camera, which is how every question here is asked.

## Enforcement

`packages/addon-pipeline/src/recorder/__tests__/segment-store.spec.ts` — five
tests, each verified by NEUTRALISING the fix and confirming it goes red: the
per-bucket archive scan restored (the `index.segments` spy fires 40 times), the
per-row `onEvicted` restored, the chunk yield removed, and the completion line
removed. The behaviour those changes could have broken is pinned beside them
(a fully-covered bucket still goes with one `removeDir`, a partial one still
falls back to per-file deletes).

Also: `recording-index.spec.ts` (the census, and that it is per-profile),
`loop-pacer.spec.ts` (back-off ramps, is bounded, and resets on one clean hop),
`mfra-capture.spec.ts` (the window gate and the unbounded-growth shape),
`staging-reconcile.spec.ts` (start line before the first rename, progress every
1 000, one pacer across every directory), `roots.spec.ts` (per-device line with
counts and the tag, chunked yields) and `retention-sweep.spec.ts` (the sweep
names its devices before pruning any).

No guard script. The "cost never scales with the archive" half is review only,
and the thing to look for is any `index.segments(...)` inside a loop over
buckets, rows or hours.
