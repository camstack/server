## Context

[D116](adr-0116.md) shipped the placement plan and drew a hard line at it:
"Rebalancing beyond this is operator-armed: nothing MOVES existing footage. The
plan changes where NEW writes go; the relocate mover remains the only thing that
moves bytes, and it is invoked by an operator." Phase 1 left that operator with
no way to invoke it per camera, and no way to see what invoking it would do.

Three things broke when Phase 2 was drafted naively.

**The mover could not express what the plan assigns.** `RelocateFootageInput`
scoped a move by SOURCE LOCATION and, at best, by `footageClass` (`recordings` =
high+mid, `recordingsLow` = low). The placement plan assigns `high` and `mid`
INDEPENDENTLY — they are two demands in the same pool. A rebalance that could
only say "recordings" would move `mid` footage the plan never asked to move,
every time only `high` was out of place.

**The engine refused its own caller.** The mover was single-flight and THREW on
a second `start()`: "a relocation is already running". That is right for a
whole-disk drain, which is one job by construction, and wrong for a rebalance,
whose unit is a pile — fifteen cameras meant fifteen `already running` errors
and fifteen manual retries in whatever order the operator guessed.

**A headroom-blind rebalance fills the target and stops.** Moving every
out-of-place pile is exactly how the new disk hits its `minFreePercent` floor
half-way through, at which point the placement planner starts evacuating it and
the two halves undo each other. And the tempting fix — crediting the source's
freed bytes as they leave — promises capacity that does not exist: nothing is
freed until a file has been copied, verified AND unlinked.

## Decision

An operator-armed rebalance plans in ONE pure function
(`planRebalance`), whose unit is a `(camera, profile)` pile on one location, and
which obeys four rules:

1. **Whole piles, never a fraction.** A pile that does not fit is REFUSED, not
   truncated. Half a camera's archive on each of two disks is the outcome nobody
   asked for.
2. **Only the planner's own headroom.** The candidate list and each candidate's
   headroom come from `PlacementService` — the same pool, the same
   `min(free − minFree floor, maxUsedGb − used)` the 30 s tick plans with. A
   location absent from that list is not a write target and nothing may be
   planned onto it. Each target's headroom is debited once per planned move; the
   SOURCE is never credited.
3. **Every refusal is reported and logged, per camera.** `unassigned`,
   `target-not-writable`, `below-threshold`, `no-headroom` — with
   `tags: { deviceId }`. A rebalance that silently leaves half the archive where
   it was is indistinguishable from one that had nothing to do.
4. **Plan and arm return the SAME shape.** `planStorageRebalance` is the dry run
   and `startStorageRebalance` enqueues it; the only difference is `jobIds`. What
   the operator confirms is what runs.

The mover gains the vocabulary to execute that plan: `RelocateFootageInput`
takes `deviceId` and `profiles`, and concurrent `start()` calls QUEUE (FIFO)
instead of being refused. The engine is still single-flight — two movers on one
disk thrash both — and a job that fails or is cancelled does not strand the queue
behind it. A job cancelled while `queued` never runs at all.

Nothing about this changes when NEW writes land: placement still applies at
writer-attach boundaries only (D116 §2).

## Consequences

- `RelocateJobState` gains `queued`, and `RecordingDeviceUsage` gains
  `oldestMs`. Both ride a framework train; `oldestMs` is OPTIONAL so a hub whose
  types carry it keeps validating an older recorder's payload, because the addon
  and the framework ship on different trains and the addon is usually later.
- The storage-migration coordinator's careful sequencing of footage classes
  (it starts the next class only after the previous is `done`) is now
  belt-and-braces rather than load-bearing. It stays: its `moverJobId` state
  machine reasons about one move at a time, and a queue it did not ask for would
  be invisible to it.
- A rebalance is only as good as the plan in force. If the placement plan has
  not run (a fresh boot, a reset after a migration), every pile reports
  `unassigned` — correct, and visibly so, rather than a rebalance that invents
  targets.
- The headroom snapshot is taken once, when the plan is built. A rebalance armed
  against a stale snapshot over-commits the target by at most the bytes written
  between the plan and the arm — small, because the operator confirms in seconds,
  and bounded below the `minFreePercent` floor the headroom already subtracts.

## Enforcement

`packages/addon-pipeline/src/recorder/__tests__/rebalance-plan.spec.ts` (whole
piles, biggest-first ordering, the four refusal reasons, headroom debited once,
the source never credited, purity) and
`packages/addon-pipeline/src/recorder/__tests__/relocate-engine.spec.ts`
(per-device and per-profile scope, FIFO order, a peak concurrency of exactly 1,
a cancelled-while-queued job that never runs, a failing job that does not strand
the queue). `recording-provider.spec.ts` pins the cap payload: one job per pile
with `deviceId` + `profiles`, a dry run that enqueues nothing, refusals reported
rather than dropped, and `oldestMs` on `getStorageUsage`.

Each load-bearing gate — the headroom debit, the no-source-credit rule, the
single-flight latch and the per-profile scope — was removed and confirmed to
fail the matching test before being restored.
