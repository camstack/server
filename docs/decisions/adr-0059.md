## Context

Two per-track operator flags shipped: `markForTrain` ("this track is training
material") and `debug` ("this track wants diagnostic attention"). They are
written by hand from three surfaces and, at the time of writing, read by nothing.

`markForTrain` raises an obvious question immediately. Tracks age out on a
per-device window (`trackRetentionDays`, default **7 days**,
`track-retention-sweep.ts:21`). A track marked as training material that
evaporates in a week is a flag that does nothing — worse than absent, because
the operator has been given a control that implies durability.

So: should the flag pin the track and its media against eviction?

**Yes, it must.** A curation mark whose subject is deleted is not curation.

**And it cannot, today.** The obvious shape of the fix — "exempt the flagged row
from the retention query" — is wrong twice over.

**First, the track row is one of FOUR independent age sweeps**, and only one of
them is keyed by track at all. Pinning just the row leaves a surviving `tracks`
entry pointing at deleted events, deleted crops and a deleted vector — a record
that looks complete in the list with nothing behind it, which is exactly the
failure `storage-pressure.ts` was written about:

| Sweep | What it deletes | Selected by | Where |
| --- | --- | --- | --- |
| `sweepTrackRetention` → `pruneTracksBefore` | the track row + its cascade | `tracks.lastSeen` | `track-store.ts:listIdsBefore` |
| `sweepRetention` → `EventStore.evictBefore` (+ `MediaStore.deleteForEvents`) | the track's object events **and their crops** | `object_events.timestamp` — *not* track-keyed | `event-store.ts:evictBefore`, `index.ts:sweepRetention` |
| `MediaStore.evictBefore(minObjectCutoff − 1d)` | **any** media row, `ownerKind`-blind | `media.timestamp` | `media-store.ts:evictBefore` |
| `ObjectEmbeddingStore.pruneDeviceBefore` | the track's CLIP vectors | `deviceId` + `timestamp` | `index.ts:sweepRetention` |

**Second, none of the four can express an exemption.** Every one is a
`settings-store` query or bulk mutation, and `QueryFilterSchema` /
`MutationFilterSchema` (`packages/types/src/capabilities/settings-store.cap.ts`)
offer exactly `where` (equality), `whereIn` (set membership) and `whereBetween`
(range). There is no negation, no `whereNot`, no `whereNull`. *"Delete everything
older than X **except** the flagged ones"* is not a sentence this filter language
can say.

Filtering after the query does not rescue it either, because `pruneTracksBefore`
is a drain loop that re-queries until a page comes back empty and stops when a
non-empty page deletes nothing. A pinned row is never deleted, so it is returned
forever: post-filtering either spins, or returns an empty page and **stops the
sweep for that device entirely**, leaving unflagged debris to accumulate behind
the pin.

## Decision

**The flags are operator curation and carry no retention effect.** `markForTrain`
does NOT pin the track; a flagged track ages out on its device's normal window
like any other. The UI says so where the operator sets it, rather than letting
them discover it when the track is gone.

**A pin is not implemented by adding a check to one sweep.** When the behaviour
is specified, the pin lands as a single mechanism covering all four paths, and
the mechanism must be expressible in the filter language the stores already have.
The shape that fits without a new predicate is a **sentinel retention column**:
each prunable family carries a `retentionAt` that normally mirrors its timestamp
and is rewritten to a far-future sentinel when the owning track is pinned, so
the existing `whereBetween: { retentionAt: [0, cutoff-1] }` excludes it
naturally. Adding `whereNot` to the settings-store cap is the alternative, and it
is a wider blast radius (every addon's store) for the same result.

## Consequences

- The flag is **inert by design** until its behaviour is specified. That is
  stated on the cap method, in the toggle's own hint text, and in a
  characterization test that asserts a flagged track IS still selected for
  eviction today (`store/__tests__/track-flags.spec.ts`) — so the gap is a
  recorded fact with a red-to-green target, not an assumption.
- **What a pin would cost, if adopted.** A pinned track holds its row plus the
  full media set the capture scheduler wrote for it: a native `keyFrame` (capped
  at 4096 px), a 960 px `keyFrameSmall`, a `thumbnail`, `firstFrame`,
  `lastFrame`, the periodic `snapshot`s at the device's cadence, and one crop per
  object event. The `keyFrame` dominates — a 4K JPEG runs ~1.5–3 MB against
  ~30–150 KB for everything else — so the order of magnitude is **~2–4 MB per
  pinned track**, i.e. roughly **2–4 GB per thousand**. This number is derived
  from the media inventory, not measured on the live fleet; measure with
  `getEventStoreFootprint` before committing to a budget. The load-bearing point
  is not the constant: it is that a pin is **unbounded in time by construction**,
  so pinned storage only ever grows and any pin design needs its own cap (a
  count, a byte budget, or a longer-but-finite window) decided at the same time.
- The `ownerKind`-blind `MediaStore.evictBefore` backstop is worth a second look
  independently of this: it deletes `identity`-owned media by age even though the
  track cascade is careful to exempt it. Not changed here — noted so the pin work
  does not rediscover it.

## Enforcement

Review, plus two tests. `store/__tests__/track-flags.spec.ts` pins the storage
contract (partial patch, `false` written not dropped, absent ≠ false, the flag
surviving the expiry-time persist) and characterizes the eviction gap.
`pipeline/__tests__/track-flags.spec.ts` pins the cap body. Nothing prevents a
future change from wiring a half-pin into one of the four sweeps; the table above
is the check, and it is why it is written out.
