## Context

`scripts/check-deployment-templates.ts` proved the Unraid templates and <!-- drift-ok -->
`docker-compose.yml` declared `ghcr.io/camstack/camstack:intel-latest` — and
passed every day while the hub actually ran
`camstack-server:intel-1.1.74`, a 13-day-old image from a repository that had
been RENAMED and received no builds, so a `docker pull` could never converge.
The agent had the right repository, pinned to `intel-1.2.0`. Nothing noticed,
because every existing surface was green: `runningVersion` was current —
`applyServerUpdate` swaps the data-root closure and never touches the image —
while the starter, entrypoint and boot seed were weeks old. The declaration
was right; reality was not; nothing compared them.

The sibling gap: the Dockerfile installs `@camstack/server@latest`
deliberately (per-package versions drift, so a `${VERSION}` pin cannot name
the closure; the tag is only the image LABEL), while the desktop pins the
exact version (`packages/desktop/scripts/stage-deps.mjs`). Built while
`latest` is not the release version, the image is labelled `intel-X.Y.Z`
while containing a different closure — and only the Electron leg fails
loudly, because only it pins.

Alternatives rejected:

- **A CI guard** cannot see a running container. The template guard is the
  proof: it verified the declaration daily while reality diverged for 13 days.
- **A `camstack doctor` command** only reports when someone runs it; this
  incident persisted precisely because nobody ran anything. It can still be
  added later as a reader of the same status field.
- **Pinning the Dockerfile to `${VERSION}`** would re-open the per-package
  version drift the `@latest` install model exists to avoid, and still would
  not catch a container running the wrong image.

## Decision

The image contract is verified where each half is actually observable:

1. **Runtime, per node**: `RootUpdateService.getServerPackageStatus` returns
   `imageContract` — `assessImageContract` compares the baked seed version
   (the only image fingerprint visible from inside a container; what
   `@latest` resolved to at image build) against the release the contract
   delivers today (registry latest when checked, else the node's own running
   version — a node can never run code newer than the newest release). The
   Cluster page renders the divergence as a red (series behind) or amber
   (patch behind) banner; `checkServerUpdate` warn-logs it. `seed == running`
   with no registry check is `unknown`, never `in-sync` — claiming sync
   without evidence is the fake-green this exists to kill. The verdict
   surfaces a fact; nothing pulls or restarts a container on its own.
2. **Build time**: `release.yml`'s first gate
   (`scripts/ci/verify-release-npm.mjs`) refuses to build unless
   `@camstack/server@${VERSION}` exists on npm AND the dist-tag `latest`
   equals `${VERSION}` — so at the moment the `intel-${VERSION}` label is
   minted, `@latest` is proven to BE that version, and the runtime half's
   "seed ⇔ image" equivalence holds.

The Dockerfile keeps `@latest`.

## Consequences

- Rebuilding an old release tag is refused (latest is ahead) — cut a new
  patch release instead. This was already unsafe; now it fails in seconds
  instead of shipping a mislabelled image.
- The runtime verdict depends on `seedVersion`, so a node whose seed dir env
  (`CAMSTACK_SEED_SERVER_DIR`) is unset reports `unknown`, not a false pass.
- A `behind-patch` banner is expected fleet-wide between deliberate container
  recreates; it is amber, not red, so it stays honest without becoming noise
  that trains operators to scroll past.

## Enforcement

`packages/node-root/src/__tests__/image-contract.spec.ts` and the
image-contract block of `root-update-service.spec.ts` pin the runtime half
(including the 2026-08-02 numbers); `scripts/__tests__/verify-release-npm.spec.ts`
pins the build half. Both suites run in CI; the release gate itself runs at
the top of every `release.yml` invocation.
