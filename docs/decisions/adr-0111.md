## Context

The pipeline watchdog reported `audio=always-on@glances(STALLED 28559s ·
exhausted 3)` on a Terminal camera for 7.9 hours — a PTY camera has no audio
plane, so the stage could never receive a signal, and the post-exhaustion retry
loop (deliberately unbounded, for transient decoder outages) fired a source
refresh every 60 s forever, silently. `buildWatchdogCamera` armed stages purely
from `audioMode` / `motionSources` — schema defaults (`always-on`,
`['analyzer']`) that every camera without onboard capabilities inherits — and
never read `pipelineEnabled`, so a camera D109 had switched off could still arm
stages if it reached a register site.

## Decision

`buildWatchdogCamera` is pure and arms nothing when `pipelineEnabled` is false;
the `audio` stage additionally requires evidence of an audio track
(`BrokerStats.audio !== null`, resolved once per dispatch; unknown or failed
read arms — the stage is diagnostic, fail-open per D49). A stage that reaches
recovery exhaustion having NEVER produced a signal is not a recoverable stall:
it logs one warn (`watchdog stage never produced a signal — disarming`, tagged
with the deviceId) and is disarmed. The unbounded retry stays exactly as it is
for stages that have lived. Every recovery emit is logged with
`{stage, camStreamId, attempt}` — the event has no ack, so the log is the only
way to see a recovery that lands nowhere.

## Consequences

A camera whose audio genuinely starts later than its first dispatch will not be
audio-watched until a re-dispatch resolves the broker stats again. A stage that
never lived is disarmed rather than retried — if the underlying cause is fixed
live, a re-dispatch is needed to re-arm it.

## Enforcement

`watchdog-camera.spec.ts` (arming rules, all four gates neutralisation-tested),
`watchdog-audio-probe.spec.ts` (one probe per dispatch, none for on-motion
audio), and the never-lived disarm tests in the watchdog spec.
