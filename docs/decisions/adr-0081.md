## Context

D59 said `markForTrain` was operator curation with no retention effect, and said
it for a good reason: pinning would have meant four exemptions across four
independent age sweeps, and the store filter language — `where` (equality),
`whereIn`, `whereBetween`, and nothing else — cannot say *"delete everything
older than X except the flagged ones"*. It closed with the shape that would fit
if the sweeps were ever unified: a sentinel retention column the existing
`whereBetween` excludes naturally.

Two things changed.

**The sweeps were unified.** D61 collapsed ten age sweeps into one: an entity a
track owns has no clock of its own and leaves only through the track cascade.
The track row is now the single CASCADING retention root. So the pin is no
longer four exemptions — it is one exemption on one query, `listIdsBefore`, and
that one exemption holds the track's object events, its crops, its keyframes and
its CLIP vector with it.

**And the flag being inert was itself the problem.** A control that says "mark
for training" and then lets the subject evaporate in seven days is worse than
no control, because the operator has been given a promise of durability the
system does not keep. That was already written down in D59 as the argument
*for* pinning; what was missing was a way to do it.

The obvious implementation is wrong, and the way it is wrong is worth stating.
The filter language offers only positive equality and `whereIn` — no negation,
no IS NULL — so a NULL is not selectable by ANY predicate it can express. A
NULLABLE column filtered directly would therefore have made every track written
before the column existed — the entire fleet history — immortal in one deploy,
silently, in the direction nobody checks.

**And then the mark turned out not to be a boolean at all.** Later the same day
the operator described what happens AFTER a track is marked: a retrain page
picks frames from it, copies them into a retrain dataset, and the track is
done. That is three states, not two, and the third one is not "still marked" —
it is "already used", which has the opposite retention answer.

## Decision

**The track carries a RETRAIN LIFECYCLE — `retrainStatus: 'none' | 'staging' |
'trained'`, stored `TEXT NOT NULL DEFAULT 'none'` — and retention holds
`staging` alone.** `listIdsBefore` selects its candidates with
`whereIn: { retrainStatus: ['none','trained'] }`; the export selection and the
budget count select `retrainStatus = 'staging'`.

**There is no `null`, and that is not a style preference.** The operator's
words were "an enum that can be null, staging or trained"; `'none'` is that
null, materialised. The filter language cannot express "is null" or "is not
staging", so a NULL row would be unselectable by every predicate available and
the whole pre-column history would be immortal — the exact trap the boolean
form was built to avoid, re-entered through a different door. Same semantics,
expressible predicate.

**`trained` is EVICTABLE again**, and this is the part that is genuinely new
rather than a rename. The retrain page COPIES each frame it selects into the
retrain dataset at selection time (it must: the picker only offers media that
still exists, so an original that has evaporated blocks the selection, never
the copy). Once the track is trained the dataset no longer depends on its
media, so continuing to hold it would cost 1–3 MB per track for nothing. This
is why the sweep names two states positively instead of asking for "not
staging" — the two evictable states are not adjacent in any ordering, and
`whereIn` is the only way to say them.

**`trained` is TERMINAL for the toggle.** `setTrackFlags` with `markForTrain`
in EITHER direction against a trained track is refused with its own error type,
`TrackAlreadyTrainedError`, beside the budget's — a surface has to say "this
track is already in the dataset", which is a different sentence from "make
room". Re-staging a trained track is how the same material gets annotated twice
under two ground truths; the deliberate return to staging is an action of the
retrain page, which is also the only thing that produces `trained`.

**The wire contract is unchanged**: `markForTrain: true` means `none →
staging`, `false` means `staging → none`, and `readFlags` / `Track` / `KeyEvent`
report `markForTrain = (retrainStatus === 'staging')`. `retrainStatus` is
exposed ALONGSIDE it on the read surfaces (and on the `setTrackFlags` result)
because the boolean cannot express the third state: a trained track reports
`false` exactly like a never-marked one, and a badge that cannot tell them apart
is the difference between "you have not done this yet" and "you already did".

### Two forms in one day, and what each cost

This record has now been amended twice on 2026-08-07. The honest version:

1. **`markForTrain` + a `retentionPinned` sentinel column.** Two columns, one
   fact. Collapsed within hours.
2. **`markForTrain` as `BOOLEAN NOT NULL DEFAULT 0`, the pruner filtering it
   directly.** Correct about retention and wrong about the feature — it had no
   way to say "used", so a track the operator had finished with stayed pinned
   for ever. It lasted about an hour and was never deployed, so there is no
   migration to write: the boolean column never existed on a real database.
3. **The enum.** The failure mode both earlier forms shared is that they
   modelled the CONTROL (a checkbox) instead of the WORKFLOW (mark → annotate →
   done). Nothing in the storage layer could have caught that; only describing
   what happens next did.

`debug` stays nullable through all three — it never pins, and nothing filters
on it.

**The exclusion is in the SELECT, never a post-filter.** `pruneTracksBefore`
drains by re-querying until a page comes back empty; a held row removed after
the query would be returned forever, spinning the loop or halting the sweep for
that device and letting unflagged debris pile up behind the held ones.

**And staging is BOUNDED in count, because it cannot be bounded in time.**
`MAX_STAGING_TRACKS_PER_DEVICE = 500`, enforced in the `setTrackFlags` body, per
device, counting `staging` ONLY — a `trained` track is evictable again, so it
costs the budget nothing. Un-marking, `debug` patches, and re-marking an
already-staging track are never refused — a limit that blocked the way out of
the limit would be a trap. `debug` does not pin at all: it is attention, not
durability.

## Consequences

- **Staging storage only ever grows until an operator releases it — or trains
  it.** Before the enum the only exit was un-marking; now finishing the work
  releases the storage too, which is the exit an operator actually takes. The
  budget caps it at roughly 1–1.5 GB per camera, derived from the media inventory
  (a native `keyFrame` at ~1.5–3 MB dominates the thumbnail, first/last frames,
  periodic snapshots and per-event crops combined). The number is a guard rail
  against a stuck script, not a curation policy — 500 hand-marked tracks on one
  camera is not an accident.
- **Retention now has an outcome that is not deletion**, and it says so. The
  sweep logs `track retention held staging tracks (retrainStatus)` with
  `tags: { deviceId }` and the count, because "retention ran and freed nothing"
  and "retention is holding 4,000 tracks the operator asked it to hold" are
  indistinguishable from deletion counters alone, and only one is a bug.
- **`setTrackFlags` stays `auth: 'protected'`.** Its own docblock said to
  revisit that the day a flag cost storage; this is that day, and the answer is
  no. Marking a track is something you do while looking at it, on the surface
  you were already looking at it on, and that surface is the viewer — an
  authenticated non-admin surface. The storage cost is answered by the budget
  instead. `deleteTracks` next door remains `admin`: destroying evidence and
  preserving it are not symmetric acts.
- **A staging track is not exempt from the ORPHAN collector, and does not need
  to be.** Orphans are collected by ownership, and a held track's row is present
  by construction, so everything hanging off it has a live owner.
- **The fake settings store models column defaults, boolean columns and
  `whereIn`.** It modelled none of the first two, and each gap diverged from
  production exactly where the retention predicate lives: an unmodelled default
  leaves legacy rows `undefined`, missing the sweep entirely. The default
  modelling is what carries the enum too — a TEXT default needs no special
  coding, but it needs to exist.
- **A persisted row always reads a `retrainStatus`.** The "never touched"
  absence survives only on LIVE (in-RAM) tracks; surfaces treat absent and
  `'none'` identically, which is what they already did with `false`.
- **`countPinned` / `listPinned` were renamed `countStaging` / `listStaging`**,
  and `PinBudgetExceededError` / `MAX_PINNED_TRACKS_PER_DEVICE` became
  `StagingBudgetExceededError` / `MAX_STAGING_TRACKS_PER_DEVICE`. "Pinned" named
  a column that no longer exists, and a selection whose name does not match its
  predicate is how the wrong one gets called.
- **Nothing writes `'trained'` yet.** The retrain page does, and it is a roadmap
  item (`docs/roadmap.md`). Until then the state is reachable only by seeding a <!-- drift-ok: moved to the private planning repo -->
  row — which is exactly how its tests arrange it — and the behaviour that
  matters (evictable, terminal for the toggle, not counted, not exported) is
  pinned by those tests now rather than discovered later.

## Enforcement

`store/__tests__/track-flags.spec.ts` — the block that used to characterize the
gap now pins the behaviour, on the same query: a `staging` track is not selected,
an unmarked one is, a `trained` one IS (the case the boolean form could not
have), un-marking releases, `debug` alone does not pin, a track marked while LIVE
survives its expiry-time persist as `staging`, and — the case that matters most
— a row written before the column existed is STILL selected. A sibling block
pins `listStaging` / `countStaging` excluding `trained`.
`pipeline/__tests__/track-flags.spec.ts` pins the budget, including the three
operations it must never refuse, and the trained refusal in BOTH directions.

Each of the five load-bearing cases was verified by removing its fix and
watching only that case fail: dropping the `whereIn`, narrowing it to
`['none']`, dropping the column default, disabling the trained guard, and
dropping `retrainStatus` from `persistCompleted`.

Nothing mechanically prevents a future query from forgetting the predicate. The
guard against that is that `listIdsBefore` is the only age-keyed selection over
tracks (D61, enforced by `scripts/check-age-keyed-retention.ts`), so there is
exactly one place it could be forgotten.
