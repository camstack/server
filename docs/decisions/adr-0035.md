## Context

`zone.enter`, `zone.exit` and `tripwire.cross` were declared in the cap types,
mapped in `DetectionEventEmitter`, and listed in its default enabled types. The
emitter had a whole branch that turned them into events.

Nothing ever produced one. The frame processor called:

```ts
this.eventEmitter.emit(trackedDetections, objectStates, [], [], deviceId)
```

with a literal empty array, above a comment calling zone events "a follow-up".
Searched the repository: the only file naming `ZoneEvent` was the emitter, which
CONSUMES them.

The consequence was total and silent. A notification rule scoped to a zone could
fire only if a MOVEMENT-state transition — `entering` / `leaving` / `stationary`
/ `loitering` — happened to land on a frame where the box overlapped the zone.
A subject that simply walked through produced nothing at all.

A second defect compounded it. `zonesByTrack` is built from the tracks the
tracker returned THIS frame, but `object.leaving` fires precisely for a track
that is absent — the emitter resolves it from its own `lastKnownTracks` for that
reason. The lookup missed, so EVERY leaving event carried `zones: []`, which no
zone-scoped rule can match.

Together they made one configuration unsatisfiable. On 2026-07-31 a person
crossed device 101's "Uscio" zone at 0.889 confidence; the live rule scoped to
`person` + that exact zone, with `minConfidence: 0.7`, did not match. Across the
whole passage the line `zone membership stamped on event` appears zero times.
Another product notified the same instant, which is how it was noticed at all.

## Decision

Zone crossings are produced per track and passed to the emitter, and a crossing
must PERSIST to be believed.

Membership is geometric and jitters at the boundary: a bbox wobbling by a few
pixels crosses in and out on consecutive frames, and each raw transition would
be a notification. So an entry is confirmed after 2 consecutive frames inside
and an exit after 4 consecutive frames outside. The asymmetry is deliberate — an
entry is what an operator wants to hear about, while an exit merely ends a
presence and must survive a momentary occlusion.

This is orthogonal to `zoneMembershipMinOverlap`, which decides how much of the
box must be inside to count as inside at all. That threshold answers "how far
in", this one answers "for how long".

Separately, an event for a track absent this frame carries the zones it was last
seen in.

## Consequences

- Zone-scoped rules can now fire on a passage rather than on a coincidence. That
  is a volume increase for anyone who had such a rule and was receiving nothing.
- The hysteresis delays an entry by up to 2 frames. At the pipeline's rates that
  is well under the second the notification path already spends.
- Both per-track caches are dropped when a track leaves — after the emit, so its
  leaving event still carries its zones. A leak here would be unbounded.
- A track that vanishes mid-zone reports the zones it still occupied
  (`ZoneTransitionTracker.forget`), so an entry always has a matching close.
  Nothing consumes that yet; the leaving event's zones cover the rule path.

## Enforcement

`packages/addon-post-analysis/src/pipeline-analytics/pipeline/events/__tests__/zone-transition-tracker.spec.ts`
— 12 tests, including the one-frame graze that must never emit, the occlusion
that must not end a presence, and the vanished track that must report what it
still occupied.

`packages/addon-post-analysis/src/pipeline-analytics/pipeline/events/__tests__/event-emitter.spec.ts`
— 5 tests asserting the emitter's zone branch works, so a refactor cannot
quietly return it to being dead code. That branch existed and was correct for
months; what was missing was anything to exercise it.

No guard script: "a parameter that is always an empty literal" is not
grep-detectable without false positives. The lesson generalises and is worth
stating plainly — a vocabulary with no producer looks exactly like a working
feature from the type system, the tests, and the configuration UI alike.
