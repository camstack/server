## Context

[D22](adr-0022.md) generated the Unraid templates because a hand-maintained
container template rots. The investigation that produced it found the same rot
one file away, in `docker-compose.yml`, and deliberately left it there to keep
that commit about Unraid.

The compose file pointed at `ghcr.io/camstack/camstack-server:intel-latest` — an
image the release workflow has not published since the single-image collapse, so
`docker compose up` failed at the pull for everyone. It set `ADMIN_PASSWORD` and
`JWT_SECRET`, which nothing in this codebase reads: the server takes
`CAMSTACK_ADMIN_PASS` and `CAMSTACK_JWT_SECRET`, so the file appeared to seed an
admin login and silently did not. It never set `CAMSTACK_ROLE`, so it could only
ever start a hub. It mapped neither `/config` — which the `Dockerfile` declares a
`VOLUME`, so Docker minted an anonymous one on every re-create — nor
`/dev/bus/usb`, without which the entrypoint's Coral fix-up is dead code. And it
had no `shm_size`, so the decoder frame rings ran against Docker's 64 MB default
and died on an uncatchable SIGBUS.

Every one of those is a defect D22 had already catalogued and fixed elsewhere.
The file had a careful header comment explaining what it was for. That is the
same evidence D22 rests on: prose in a file nothing checks decays at the rate of
a file with no prose at all.

Deleting it was the obvious alternative and was rejected. Docker Compose is how
this runs on anything that is not Unraid, and the reference cluster is not the
only deployment; removing the file would move the same facts into a docs page
where nothing could check them at all.

## Decision

`docker-compose.yml` is **generated** by `scripts/deployment-templates.ts` from <!-- drift-ok -->
the same `ROLES` spec and the same derived image facts as `unraid/**`, and must
never be hand-edited. There is one model of how to run this image, rendered
twice.

Generated, not merely checked. A checker over a hand-written compose file can
only compare the facts it knows to look for, so it proves the file has no *known*
disagreement — which is exactly the guarantee that failed here, because nobody
knew to look. Rendering both files from one spec makes the two deployments
disagree only if someone changes the spec, and the guard's job shrinks to proving
the on-disk files are what the spec produces and that the spec still matches the
image.

The two renderings are shaped for their hosts, not made identical. Compose
expresses both roles in one file — the hub by default, the agent behind an
`agent` profile, because a hub and an agent on one host under host networking
collide on every port. Unraid conventions that mean nothing elsewhere do not
travel: `/mnt/user/appdata/...` becomes a relative bind, `br0` becomes host
networking, and the `Display`/`Required`/`Mask` flags dockerMan renders a form
from have no compose equivalent and are simply not emitted.

## Consequences

- Editing `docker-compose.yml` is pointless: the pre-commit hook regenerates it
  and CI fails on drift.
- The runtime flags now have exactly one home. `--shm-size` and
  `--device-cgroup-rule` are declared once in `ROLES` and translated into
  `shm_size` and `device_cgroup_rules`; a flag with no compose equivalent throws
  at generation time rather than reaching only the Unraid path.
- Optional hardware ships commented out in compose, unlike the Unraid template
  where a user deletes rows in a form. `devices: /dev/dri` on a machine with no
  iGPU makes `docker compose up` fail outright, and a first run that errors is
  worse guidance than a first run that decodes in software.
- **A commented-out list item is a live hazard in YAML**, and this cost a real
  bug in the first generated draft. A latent `- /dev/dri:/dev/dri` sitting under
  a commented `# devices:` key attaches to whichever active list precedes it the
  moment someone uncomments only the item — which is precisely what the
  neighbouring comment invites. `docker compose config` accepts the result and
  renders a **bind mount**: the device nodes appear inside the container, no
  cgroup permission is granted, and VAAPI fails with `EACCES` three layers from
  the cause. The block is now placed where a half-uncomment is a parse error, and
  the guard refuses the arrangement. This is the compose analogue of D22's
  double-hyphen-in-an-XML-comment.
- The compose file cannot be verified end-to-end from this repository. `docker
  compose config` parses it without a daemon, and that is what CI could run;
  proving the container actually starts needs a host with the image, and the
  image is private.

## Enforcement

`scripts/check-deployment-templates.ts` — renamed from <!-- drift-ok -->
`check-unraid-templates.ts`, because it no longer checks only Unraid — wired into
`.github/workflows/ci.yml` and `.husky/pre-commit`.

It re-derives every generated file and fails on drift, then re-reads
`docker-compose.yml` independently and runs the same contract checks the XML gets:
the image is the one `release.yml` publishes, every environment variable is one
the code reads, every `VOLUME` is mapped, every published port is `EXPOSE`d, a
mapped path the server locates by env var has that variable set to it, the Coral
bus mapping is paired with its cgroup rule, a restart policy is declared and
`CAMSTACK_ROLE` matches the service. Compose's `shm_size` and
`device_cgroup_rules` are translated back into the flag strings the Unraid side
declares, so a flag lost from one rendering is detectable at all. Plus the YAML
rule above, which no general validator has any reason to check.
