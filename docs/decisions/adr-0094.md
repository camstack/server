## Context

[D93](adr-0093.md) made the snapshot URL carry the frame identity and made an
image request the thing that enrols a camera in the keep-warm loop. It is
correct, and it was incomplete in a way that took four hours to surface as a
total outage.

The client read `lastCapturedAt: null` as "there is no frame, so there is nothing
to request" and emitted no image request. But the image request is the *only*
thing that enrols a camera, and enrolment is the only thing that produces a
first capture. So a device with no frame never got one, and therefore kept having
no frame. A self-sealing deadlock: the precondition for the fix was the fix's own
output.

It stayed invisible because every camera already had a frame when it shipped. The
hub then OOM'd, restarted with an empty cache, and `getSnapshotOverview` answered
null for 15 of 16 cameras. Every thumbnail in the app went blank and **stayed
blank — on every surface, surviving an app kill** — because no client would ever
ask for an image again.

The rejected alternative was a server-side bootstrap: let the first
`getSnapshotOverview` after a boot with an empty cache enrol the cameras it was
asked about, once. It works for the incident, and it was rejected on two counts.
It does not cover a single device that has never captured (not a boot condition,
so no bootstrap fires). And it requires the overview poll to CREATE subscriptions
— exactly what D93 forbids, because that poll is app-wide and a creating overview
warms every camera on the install. Two mechanisms covering overlapping halves of
one problem is how a rule ends up disagreeing with itself.

## Decision

A snapshot surface builds an image URL for a device **whether or not the server
reports a cached frame**. With no frame identity it emits the STABLE form of the
URL (no `v`); that request is what triggers the capture and the enrolment, and
the next overview tick makes the URL versioned.

More generally: **when a request is what enrols a resource, the absence of that
resource can never be the reason to skip the request.**

## Consequences

- One extra fetch per camera on a genuinely cold start: the stable URL, then the
  versioned one once the identity lands. Self-limiting and once per camera.
- The bootstrap URL is byte-stable, so it is one request per mount, not a poll.
  A device that legitimately never produces a frame — a sleeping battery camera,
  which the wrapper refuses to wake — is therefore not hammered, and is not woken.
- `neverCaptured` stops being a reason to render an empty state on its own. Right
  after a restart every camera reports it and every camera is about to be
  captured, so the empty state must wait for the request to actually FAIL. It
  still distinguishes "never captured" from "unreachable" once it has.
- Verified against the live hub from the real cold state (15 of 16 cameras at
  `lastCapturedAt: null`): all 15 non-battery cameras painted on the FIRST load,
  at t+6 s, and the warm loop then held them at ~3 s. Device 106 stayed asleep at
  96 % battery.

## Enforcement

`camstack/src/data/__tests__/snapshot-media-url.spec.ts` —
`resolveSnapshotUri` returns a URL for `lastCapturedAt: null`, that URL carries
no version param, it is byte-stable across calls (so it cannot become a poll),
and it differs from the versioned form. Removing the fix turns those red.
