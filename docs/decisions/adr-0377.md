## Context

D372 shipped the small-subject recovery pass: the first-level detector sees a 4K
frame at 320 px, so a 100 px dog is 8 px and is never emitted; the runner now
re-runs THE SAME detector on a 640–800 px native square around the uncovered
motion regions and fuses what it finds. It works. Camera 101, 2026-09-07:

```
06:59:36.491  small-subject recovery: … {crops=2 recovered=1 classes=["animal"] ms=171}
06:59:37.464  …                          {crops=2 recovered=1 classes=["animal"] ms=159}
06:59:37.505  …                          {crops=2 recovered=1 classes=["animal"] ms=64}
06:59:38.310  …                          {crops=2 recovered=1 classes=["animal"] ms=291}
```

The operator still got no notification, and three separate things were eating
the subject downstream.

**1. The gate asked the question a third time, on worse pixels.** The
confirmation gate cuts its own crop — the box padded 15% and capped at
`CONFIRMATION_CROP_MAX_WIDTH` (320) — and re-runs the detector on it. On this
subject that verdict is a coin flip:

```
06:59:38.335  confirmation gate: birth confirmed {trackId=f585b2ee… className=animal bestScore=0.7068}
06:59:38.821  confirmation gate: birth suppressed (false positive) {trackId=f585b2ee… className=animal}
```

The second line carries NO `bestScore`: the crop held no class-compatible
detection at all. Same subject, same second. The benchmark says why — case
`miss-dog-101` in `docs/benchmarks/pipeline-frame-model-eval.md`: the dog scores
0.35–0.90 on a native region square and is ABSENT from a full-frame 320 view;
scale is what decides, and a tight ~130 px blob letterboxed to 320 with no
context is a third, different, worse image.

**2. A birth could be judged twice, and the second vote won.**

```
06:59:38.335  track started {trackId=f585b2ee… className=animal}
06:59:38.821  birth suppressed — track record retracted {trackId=f585b2ee…}
06:59:41      track lost
```

Two structural facts meet. `processFrame` reads `lastActiveTrackIds` at the top
and writes it at the bottom, and AWAITS the gate in between (130–490 ms measured
on this camera, against 100 ms frame spacing), so several frames are in flight
and each sees the same fresh id as unjudged. The other birth discriminator,
`positionsCount > 1`, does not close the gap either: a COASTED frame appends no
position by design (`TrackStore.upsert`, `matched: false`), and a subject the
full-frame pass cannot see coasts by definition — so `classifyTrackAppearance`
keeps answering `birth`. The same shape produced two `track started` lines for
one vehicle id at 07:03:48 and for the recovered animal `c2afbfc0` at
05:31:38.840 / .909.

**3. The tracker dropped recovered boxes in silence.** `isDuplicateSpawn` folds
an `animal` scoring under `animalOverPersonMaxScore` (0.6) that overlaps a
`person` track by `animalOverPersonIou` (0.2) into that person — a heuristic
about the COARSE pass misreading a bending person. A dog on a lead at its
owner's knee is that exact geometry. Neither that branch, nor the per-class
score floor, nor the cross-class association absorption (`classGroupAssoc` makes
{person, animal} ONE association group) logged anything, so on 2026-09-07 the
three candidates could not be told apart from the logs at all. Within four
minutes of shipping the diagnostics the live answer appeared:
`tracker: detection dropped — no track was born from it {reason=cross-class-absorbed
detClass=animal detScore=0.5244}`.

The first fix considered was to make the gate's own crop bigger — a native square
like the recovery's. It was rejected: it duplicates geometry that lives in
another addon (addons never import each other), it makes the gate's cost grow,
and it still spends an inference to re-ask a question that was already answered
on the same frame.

## Decision

A detection produced by the runner's native second pass carries what that pass
measured (`ObjectDetection.nativeRecovery`: score, crop side, view size), and
every downstream gate whose purpose is to doubt the COARSE pass must treat that
measurement as its answer rather than re-deriving a worse one:

- The confirmation gate returns `confirmed` with `reason: 'native-pass'` when
  `nativeRecovery.score` is at or above the bar the candidate would have faced —
  no crop fetch, no re-detection. It is an EXEMPTION, not a bypass: below the
  bar, or under a raised `minConfidenceFor` bar, the ordinary crop path runs and
  decides.
- The tracker's person-over-animal spawn fold does not apply to a box carrying
  `nativeRecovery`. Every other spawn guard still does, the per-class score floor
  included — the floor is about the SCORE, not about which pass produced it.

And a birth is judged ONCE. `StartedBirthRegistry` remembers ids whose birth
ritual has run, for as long as the tracker carries them: such an id is never
offered to the gate again, and a verdict that arrives for it anyway is logged and
discarded. A gate verdict may create a track; it may never destroy one that
already exists.

Finally, no tracker branch drops a detection in silence. Every spawn refusal and
every cross-class absorption is reported with the numbers its branch weighed, at
`info`, tagged with the `deviceId`.

This is NOT a detail/CLIP crop and shares nothing with `deriveDetailCropRect`
(D52): `nativeRecovery` is plain data about a detection, never a rectangle, never
a vector, and nothing here derives a crop.

## Consequences

- `@camstack/types` gains `NativeRecoveryEvidence` on `ObjectDetection` and on
  `SpatialDetection`. Both are type-level plus one plain property on the wire; no
  server closure update is required, but the runner and post-analysis must be
  deployed together or the field is simply absent (and everything behaves exactly
  as before).
- The gate spends nothing on a recovered subject: no capture-scheduler slot at
  priority 0, no inference, no deferral. That directly relieves the dominant
  failure mode measured on this camera — over three hours, 19 of 42 gate verdicts
  were `no-crop` (10) or `timeout` (9), i.e. the crop never arrived, against 7
  `suppressed`. For small subjects that whole class is now bypassed rather than
  fought.
- A false `animal` that the second pass measures above the bar now becomes a
  track where before the gate might have killed it. The pass is deliberately
  narrow (a small, uncovered motion region, a native square, the same model) and
  its score still has to clear both the tracker's class floor and the gate's bar.
- `tracker: detection dropped …` is a new `info` line. It is sampled inside the
  tracker (first ten per reason, then every tenth, exact total on `refusalCount`)
  precisely because a refused box is usually refused on every frame of a passage.
  **`refusalCount` belongs to the LOG record only** — since 2026-09-10 the type
  is split, `SpawnRefusalFacts` for the unsampled sink and `SpawnRefusalRecord`
  extending it for the observer, because a product path must not inherit a
  sampling counter ([D420](adr-0420-a-refusal-swept-before-the-ask-is-still-a-refusal.md)).

## Enforcement

Tests, and a counter-proof for each:
`__tests__/confirmation-gate.spec.ts` ("a birth the native second pass already
measured"), `__tests__/birth-judged-once-e2e.spec.ts` (drives the real overlap:
a birthing frame and a coasted frame back to back, with disagreeing verdicts) and
`__tests__/sort-tracker-spawn-refusal.spec.ts`. Each was confirmed to fail with
its fix removed. The type field itself is enforced only by review.
