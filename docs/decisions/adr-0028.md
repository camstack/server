## Context

Every forked addon-runner imported the root barrel `@camstack/types` for exactly
one reason: `ALL_CAPABILITY_DEFINITIONS` + `isCollectionArrayMethod`, used to build
`capDefsByName` so the child-side dispatcher could reproduce the hub's graceful
"a provider that doesn't implement a COLLECTION cap's array method contributes `[]`
instead of throwing" behaviour (`child-cap-dispatch`).

Importing that barrel eagerly constructs the Zod schema graph of all ~266
capabilities. Measured: importing `@camstack/types/dist/index.mjs` costs **+146MB
RSS** (1804 `z.object/z.enum` builders); the lightweight `@camstack/types/addon`
subpath costs **+20MB**. With 8–20 forked runners that barrel was **~1.2–2.9GB** of
pure per-process schema duplication — a runner needs the *answer* ("is this (cap,
method) a collection array method?"), not 266 live schemas to compute it.

A first pass that only swapped `addon-runner.ts`'s own import did **not** move the
footprint: the bundler still pulled the 992KB cap-schema chunk into the runner via
a *single* transitive runtime symbol — `readNodePin` imported from the barrel in
`trpc-links.ts`. One barrel value-import anywhere in the runner's transitive graph
re-drags the whole schema module (there is no runtime tree-shaking in Node, and the
package is externalized).

## Decision

The addon-runner MUST NOT import the `@camstack/types` root barrel at runtime — not
for cap metadata, not transitively. The collection-array-method predicate is served
by a **codegen'd, schema-free** lookup: `scripts/generate-collection-array-methods.ts`
runs the REAL `isCollectionArrayMethod` over `ALL_CAPABILITY_DEFINITIONS` at codegen
time and emits `packages/types/src/generated/collection-array-methods.ts`
(`COLLECTION_ARRAY_METHODS` + `isCollectionArrayMethodName`) — plain `Record<string,
string[]>` data, zero Zod. The runner consumes it, and every other runner-surface
symbol (`errMsg`, `readNodePin`, `nodePin`, …), from the lightweight
`@camstack/types/addon` entry.

## Consequences

- The runner's per-process RSS drops materially. Measured in isolation: the barrel
  costs **+84MB RSS under the production `--max-semi-space-size=2` flag** (+146MB at
  V8 defaults) vs **+18MB for `@camstack/types/addon`** — **~66MB saved per runner**.
  Verified LIVE on the hub after `applyServerUpdate` to `@camstack/server@1.2.16`
  (system 1.2.17): the deployed `dist/addon-runner.js` closure has 0 `z.object/
  z.enum` and imports only `@camstack/types/addon` + `/node`; fleet runner RSS fell
  from **6.31GB → 5.19GB** across 26 runners (smallest runner 132MB → 101MB) — a green
  suite never showed the leak, the RSS probe and the live measurement did.
- Any util the runner needs at runtime MUST be re-exported from `packages/types/src/
  addon.ts` and imported via `@camstack/types/addon`. Adding a bare
  `from '@camstack/types'` value-import to ANY file in the runner's transitive graph
  silently re-drags the 992KB schema chunk and reverts the win — check the built
  `dist/addon-runner.mjs` closure for `z.object`, not just the source.
- `COLLECTION_ARRAY_METHODS` is generated, never hand-edited; a `.cap.ts` change
  without `npm run codegen` makes it stale.

## Enforcement

- Codegen step `collection-array-methods` in `scripts/codegen.ts`; the file lives
  under `packages/types/src/generated`, covered by `codegen:check`'s git-diff drift
  gate.
- `packages/types/src/__tests__/collection-array-methods.spec.ts` reconstructs the
  truth from the live cap definitions and asserts the generated lookup answers
  identically for every (cap, method) pair — fails the instant codegen is skipped or
  the map is edited by hand.
- Review guard: no new value-import of `@camstack/types` (the root barrel) in the
  addon-runner closure; use `@camstack/types/addon`.
- 2026-10-13 - the guard was blind to `export ... from` / `export *` and the barrel came back through
  `transport/index.ts` (`local-child-registry.ts`, `log-redactor.ts`): runner closure 71 MB -> 203 MB RSS
  (13 -> 119 MB heap). Fixed in three layers: `createEvent` / `maskUrlCredentials` / `scrubKnownSecrets` are on
  `@camstack/types/addon`; `check-runner-barrel-free.ts` follows re-exports; the runner has its OWN build
  (`packages/system/vite.runner.config.ts`, one entry, no chunk shared with hub code) and
  `check-runner-dist-barrel-free.ts` checks the BUILT `dist/addon-runner.js` (schema-call density, then a runtime
  probe: RSS <= 120 MB, heapUsed <= 30 MB) in automatic CI. Release order: `@camstack/types` -> `@camstack/system` ->
  `@camstack/server` (system resolves `@camstack/types/addon` from the server closure at runtime; a new system on an
  old types gets `undefined` for the three new symbols).
- 2026-10-13 (later) - the same bug through two more doors, each costing every runner that held the code ~100 MB of heap:
  (1) `@camstack/system/addon-utils` (loaded by addon-pipeline, addon-post-analysis, addon-ai, model-studio = 7 hub runners)
  reached the 2.4 MB barrel chunk because `download/model-downloader.ts` imported `HF_REPO`, `hfModelUrl` and `MODEL_FORMATS`
  from the bare `@camstack/types`. `MODEL_FORMATS` now lives in the schema-free `types/model-formats.ts`; the three are on
  `@camstack/types/addon`. (2) Addon SERVER code read `ALL_CAPABILITY_DEFINITIONS` for two facts (`sensor-transition-gate.ts`:
  which cap derives its event from an advancing field; `addon-osd-manager/source-catalog.ts`: a cap's bindable state leaves).
  `scripts/generate-addon-cap-facts.ts` (codegen step `addon-cap-facts`) emits both as plain data -
  `CAP_ADVANCE_FIELDS`, `CAP_STATE_LEAVES` on `@camstack/types/addon`, the same pattern as `COLLECTION_ARRAY_METHODS`;
  `addon-cap-facts.spec.ts` / `cap-state-leaves-table.spec.ts` prove equality with the live definitions. Guards:
  `check-runner-barrel-free.ts` now walks the `addon-utils` entry as well; `check-runner-dist-barrel-free.ts` probes the built
  `addon-utils` closure (schema density + heapUsed <= 30 MB); the new `check-addon-dist-footprint.ts` refuses
  `ALL_CAPABILITY_DEFINITIONS` in any built addon closure and fails when an addon grows the runner's heap by more than 60 MB,
  unless `scripts/addon-dist-footprint-budgets.json` grants a reasoned budget. Inlined zod is called as bare `object(`, so none
  of these guards counts `z.object(` in an addon. Both dist guards run in automatic CI right after the build.
  Release order: `@camstack/types` -> `@camstack/system` -> `@camstack/server` (system resolves `/addon` from the server
  closure); then republish `addon-post-analysis` and `addon-osd-manager` (they bundle types; `addon-pipeline`, `addon-ai` and
  `addon-model-studio` pick up the fix through system with no republish of their own).
