## Context

`scene-monitor` landed on 2026-08-14 with a working engine, a durable latch and
its own `/scenes` page, and the operator's question was immediately the obvious
one: *"notify me about a person at the front door, but only while the bin is
still out"*.

The design that came with the cap
([`scene-state-analysis.md` §9](../design/scene-state-analysis.md)) answered it
the way `occupancy` and `audio` had been answered: a new internal
`NcSubjectKind` (`scene-event`), an in-process edge tap that produces subjects,
paired fail-closed gates on every other subject kind, a `kind: 'scene'` member
in the rule-status union, and a rule kind in the admin registry. Roughly twenty
files, and it was deferred for exactly that reason.

**That design answers a different question.** `occupancy` and `audio` are
DISCRIMINATORS: carrying one changes what the rule fires ON — a count edge, a
sampling window — and neither has a delivery of its own, so the condition has to
double as the trigger. A scene is not a thing that happens to a rule's subject.
It is a standing fact about the property, and the operator's sentence has TWO
halves: a trigger (a person at the door) and a narrowing (while the bin is out).
Modelling it as a trigger would have made the narrowing unexpressible — a
`scene-event` rule fires when the bin moves, which is not what was asked, and
the rule that WAS asked for would still have needed a gate afterwards.

There was already a gate in this engine that does exactly this shape:
`deviceState` ("only while the alarm is armed"). It composes with every trigger,
it discriminates nothing, and it reads a mirror the reload tick refreshes.

## Decision

`conditions.scene` is a **gate**, not a trigger. It carries
`{ sceneId, deviceId?, requiredState: 'matched' | 'diverged', latched? }`, is
offered for the same four deliveries `deviceState` is, and is evaluated in the
shared gauntlet of `evaluateRule` — after every subject-kind branch, so a rule
pointed at the wrong trigger still reports `delivery` rather than `scene`. There
is **no** `scene-event` subject kind, no `NcDelivery` member and no scene rule
kind; a rule carrying `scene` fires on its own trigger and never on a scene
edge.

Four sub-rules, each of which was a live choice:

1. **The gate NEVER reads the cap.** It reads `NcSceneStateCache`, an in-memory
   mirror refreshed off the event path — the reload tick (reconcile) plus the
   provider's in-process `onSceneEdge` tap (freshness). D49, verbatim: a mirror
   that fails to refresh keeps what it had and ages out; it never empties. A
   `listScenes` that threw looks exactly like the bin having been taken back in,
   and would un-gate the alarm at the moment it matters most.
2. **`unknown` satisfies neither polarity on the live reading.** A scene that
   cannot judge — no reference for this light, the view shifted, no snapshot —
   is not evidence that the bin is out and not evidence that it is back.
3. **…but the LATCH survives `unknown`.** The latch is a durable claim about the
   past, and a camera that has gone dark does not clear it. That asymmetry is
   the whole reason the operator asked for a latch.
4. **`latched` absent follows the scene's own `emit`.** `SceneMonitor.emit`
   already declares which of the two booleans drives notification rules. A
   second knob that could disagree with it is the D62 failure exactly; the
   condition's `latched` is an override for one rule, not a parallel default.

## Consequences

- Cheap: no release train for a delivery member, no viewer rule-kind work, no
  new status kind. The cost is one `valueType` (`scene`) mirrored in the viewer
  and one gate branch in the engine.
- A scene-gated rule is **silent whenever the mirror cannot answer** — cold on
  boot until the provider hydrates, and for a scene that was deleted or
  disabled. That is the safe direction and it is the confusing one, so it is
  logged (see Enforcement) and named in both rule testers' caveats.
- The mirror is only correct because `pipeline-analytics` hosts the scene
  provider AND the notification centre in one process, and gates both on the
  same `isPostProcessingNode` flag. Splitting them would turn `readSceneStates`
  into an RPC and this decision would have to be re-argued.
- A rule pointing at a scene that later disappears stays enabled and permanently
  silent. The admin editor says so explicitly when it cannot resolve the id.
- **Still open**: `nc.getRuleStatus` has no `scene` branch, so the rule card
  does not yet show why a gated rule is quiet. The suppression log covers the
  diagnosis; the card is the nicer surface and is deliberately not in this
  change.

## Enforcement

- `scripts/check-viewer-condition-mirror.ts` — the viewer must be able to render
  and round-trip `scene`, or CI fails. It already caught this class twice.
- `notification-condition-fields.spec.ts` asserts every catalog descriptor has a
  form binding; `notification-rule-kinds.spec.ts` pins the visible-field lists
  per kind, so the gate appearing (or vanishing) for occupancy/sound rules is a
  test change, not a surprise.
- `rule-engine-scene-gate.spec.ts` and `scene-state-cache.spec.ts` pin every
  branch above. Three of them carry a NEUTRALIZATION note naming the exact edit
  that makes them fail — the failed-refresh keep, the age-out, and the `emit`
  fallback were each verified by making that edit and watching the test go red.
- The suppression itself is not silent: `rule suppressed by its scene condition`
  is logged at INFO with `tags: { deviceId }` (the SUBJECT's camera — the one
  whose notification went missing), on CHANGE per rule.
