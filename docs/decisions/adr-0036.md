## Context

Zone crossings started being produced on 2026-07-31 ([D35](adr-0035.md)), but
exits were computed and thrown away at the emit boundary. The reason was real:
nothing on the persisted record told an entry from an exit, so emitting both
would have doubled every zone-scoped rule's notifications for a feature nobody
had asked for.

Adding the direction turned out to need more than a condition. Two things were
tried and did not work:

- **A condition on the cap alone.** The persisted `ObjectEvent` carried no trace
  of which event kind produced it, so there was nothing on the record for a
  condition to read. `ObjectEvent.zoneCrossing` had to be added to
  `pipeline-analytics.cap.ts` and stamped off the event TYPE — a movement-state
  event also carries the frame's crossings, so "has crossings" is not the
  discriminator.
- **Letting a zone-scoped exit rule use zone membership.** It would have matched
  nothing. Membership is the box's geometry NOW, and an exit is confirmed
  precisely when the box is outside the zone. The crossed zone therefore has to
  join what a `zones` condition tests.

Then the admin widget exposed a third, worse trap. `isConditionValueEmpty`
decided emptiness **from the value**, and treated the string `'any'` as
unrestricted — correct for `source`, where "any source" is the same as no filter.
For `crossing` it inverts the meaning: absent EXCLUDES exits, and `'any'` is the
only value that includes them. An operator authoring "entered or left" would have
saved "entering", seen no exits, and found every layer underneath — cap, engine,
frame processor — working perfectly.

## Decision

An **absent** `crossing` condition means `enter`: entries and every
non-crossing record pass, exits do not. This asymmetry is deliberate and is the
only reading under which a rule authored before the condition existed keeps doing
exactly what it did. `exit` is the mirror and **fails closed** on a record that
is not a crossing at all.

Separately, and generally: **no condition value may be interpreted as
"unrestricted" by inspecting the value.** A value that means "no filter" is a
property of the CONDITION, declared per key, never inferred from the string. A
UI may not drop a condition key because its value looks permissive.

## Consequences

- Existing rules are untouched by the arrival of exits — the point of the whole
  design. The cost is that the default is not symmetric, so a UI must say so per
  option rather than in a paragraph: three of the four choices behave differently
  from what four symmetric-looking options imply.
- "Absent" is an authorable selection, not a placeholder. Choosing it must DELETE
  the key, so an untouched rule round-trips byte-identically.
- The new `valueType: 'crossingSelect'` means every catalog consumer needs a
  widget. The admin UI has one; **the viewer does not**, and its local mirror of
  the catalog will strip the field until it gets one — the same strip-on-parse
  mechanism that silently wiped media policies the same day.
- `throttle.granularity` shipped alongside as `.optional()`, not `.default()`,
  for the related reason that a Zod default does not run on the addon cap path.
  Absent reads as `shared`.

**Changed 2026-10-01 (operator ruling):** absent now reads as `per-class`,
not `shared` — `keysPerClass` in `rule-engine.ts` treats an unset
`granularity` exactly like an explicit `per-class`, and only a `granularity:
'shared'` actually stored still reads as `shared`. The admin editor's select
had grown a THIRD value that meant the same as a second (an absent `''`
labelled "Shared across classes (default)" alongside the explicit `'shared'`
option) — fixed to exactly the two schema values, `per-class` first as the
default. Because the cooldown key differs between the two readings
(`cooldownKey` appends `:c:<class>` for per-class, nothing for shared), an
existing rule that had never set `granularity` starts fresh per-class cooldown
windows the first time it fires after this change. Accepted: a cooldown is a
volume budget, not state a wrong window can corrupt. The flip also surfaced
that `cooldownSubjectFromOutbox` reconstructed a `device-event`/`system-event`
row's DISPLAY `className` (the sensor kind, or the literal `'event'`) as if it
were a real detection class, diverging from the live key — fixed by gating
`keysPerClass` on the subject KIND (`CLASS_BEARING_SUBJECT_KINDS`) rather than
on whatever `classNames[0]` holds. See `docs/architecture/notifications.md` §
"What a cooldown suppresses".

## Enforcement

- A binding guard in `packages/addon-admin-ui` asserts that **every** catalog
  descriptor with a form key is bindable. It caught this condition's missing
  widget on the first merge, across two independently developed branches — which
  is the argument for the guard over the review.
- Tests assert the asymmetry directly, including that `exit` fails closed on a
  non-crossing and that opening a rule without touching it emits no change.
- The unrestricted-value rule is enforced by a named per-key table plus its spec;
  there is no guard that would catch a future condition adding an `'any'`-like
  member and inferring it from the value again. That is a known gap: review only.
