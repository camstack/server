## Context

This one was learned expensively. On the UDS plane a child↔child call transits the
hub-main parent router, so decoded RGB frames sent from the decoder to the
detector were **buffered in hub-main** — at `detectionFps`, per camera. hub-main
ran out of memory. Not "got slow": OOM'd, taking the whole node with it, including
the routing every agent depended on.

The general shape of the mistake is worth naming: a transport that is transparent
to the caller is not transparent to the machine. The call signature is identical
whether the payload is a boolean or a 4 MB frame.

## Decision

The decode→detect hop must be **either**:

1. in-process, via the `detection` co-location group ([D2](adr-0002.md)) — zero
   copy, and the target state; **or**
2. a compressed payload (binary JPEG) — the load-bearing mitigation when the
   addons are not grouped.

Cross-process media delivery is an event (telemetry, [D8](adr-0008.md)) plus an
**on-demand fetch of compressed media by handle** — `pipelineRunner.getNativeCrop`,
routed by `handle.nodeId`. Never raw pixels streamed at frame-rate.

## Consequences

- The `detection` group exists for this reason and no other. Dissolving it
  requires reintroducing compression on that hop, not merely accepting a slowdown.
- Post-analysis resolves media over tRPC by handle. It does not read frames
  directly, which is why the runner keeps decoded frames in a RAM
  `RetainedFrameStore` and serves crops from it.
- A "small optimisation" that passes a frame buffer to a sibling addon is a
  node-killing change, and it will look fine in a single-camera test.

## Enforcement

Review, informed by this record. There is no guard — which is a gap, and the
reason this record spells out the failure rather than only the rule.

## Later

[D18](adr-0018.md) replaced the shared-memory mechanism that originally served
option 2 with tRPC-by-handle. The rule above is unchanged; only the transport is.
This record stays `accepted` for that reason.
