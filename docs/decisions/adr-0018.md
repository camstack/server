## Context

[D9](adr-0009.md) established that raw pixels must not cross a process boundary at
frame-rate, and the answer at the time was a shared-memory frame plane
(`@camstack/shm-ring`) — a genuinely fast transport. The cost only became clear
later: it is a native host-external, so it pins ABI compatibility across every
node; it needs a prebuild per platform and a CI job to produce them; and reader
lifetime bugs surface as garbage pixels rather than as errors.

Then [D2](adr-0002.md)'s `detection` co-location group removed the need. Once
decoder and detector share a process, the hop is a pointer pass. Shared memory was
solving a problem that had been deleted.

## Decision

The detection data plane uses tRPC for cross-process frame access, never shm. The
runner retains decoded RGB frames in a RAM `RetainedFrameStore` and serves them by
`FrameHandle` through `pipelineRunner.getNativeCrop`, routed by `handle.nodeId`.
Post-analysis resolves media over tRPC. `@camstack/shm-ring` — the last native
host-external — is being removed.

## Consequences

- Removing the last native host-external removes the ABI-pinning constraint and
  the prebuild CI job with it.
- Access is by handle and on demand, so a consumer that wants one crop transfers
  one crop rather than subscribing to a stream.
- [D9](adr-0009.md)'s rule is unchanged and still load-bearing: this record
  replaces its *mechanism*, not its constraint.
- Follow-up slices still open: the legacy shared-poller
  (`useSessionDecode: false`), the decoder's `frameSink: 'shm'` mode, and the
  `packages/system` host-externals entry.

## Enforcement

Review, plus the disappearance of the API: with `FrameRingReaderCache` and
`decoder.getFrame` gone, the shm path is not reachable from the detection plane.
