## Context

`PackageDropDetector` never fired once in its life. Zero `pa-pkg-*` rows on
every camera, ever — verified against the live hub on 2026-08-13, on an install
where device 101 has a drawn `Uscio` package zone, an enabled `package`-stage
zone rule, a notification rule on `delivery: 'package-event'`, and 21 real
`package` object-events in 14 days.

Every component was correct in isolation, which is why review never caught it:

- the `package-detection` step ran (RF-DETR, `extractMode: 'crop-zone'`);
- the `MotionSettleGovernor` gated it to a settle edge or a 45 s safety poll —
  correct, a parked parcel does not need per-frame inference;
- a package became a *delivery* only once the GENERIC stationary registry
  promoted it, and that registry needs `PROMOTION_MIN_POINTS` (4) positions
  inside `PROMOTION_WINDOW_MS` (30 000 ms) — one every 10 s.

One observation per 45 s cannot produce four inside 30 s. The bug was not in
either file; it was in the ARITHMETIC BETWEEN two files that never mention each
other. The measured reality was worse than the nominal: on 101 the package boxes
arrived in bursts ~2 minutes apart (a session-dispatch camera decodes nothing
between motion sessions), each burst two frames ~1.2 s apart, each burst on a
NEW `trackId` because the track died in between.

Two further facts shaped the fix. A parcel appears at the END of a motion
episode — the courier walks up, puts it down, walks away — so the settle edge is
the moment we know something might have been left. And an operator waiting
minutes for a doorstep notification does not have a feature.

## Decision

**A promotion criterion fed by a gated step is judged against that gate's
cadence, and the gate's settle edge opens a burst.**

Concretely, three rules:

1. **The gate bursts.** A settle edge fires `burstCount` runs
   `burstIntervalMs` apart (5 × 5 s), not one. The 45 s poll remains, demoted to
   the SAFETY NET for a parcel whose motion was never observed. The burst is
   opened only by motion NEAR the package zones — the zone-union box dilated by
   `PACKAGE_ZONE_DILATION` (0.5 of its own size per side), measured in
   normalised coordinates so it means the same thing on any stream profile.
2. **Packages promote on their own path.** `PackageStillnessTracker` counts
   distinct observation ROUNDS with no look-back window, re-associating a box
   across rounds BY POSITION (IoU ≥ 0.3), because the track dies between them.
   The generic 4-in-30 s criterion is untouched: a parked car on 102 promotes
   exactly as before, and the generic loop now SKIPS the package classes so one
   parcel can never promote on both paths.
3. **The relation is a build guard, not a comment.**
   `scripts/check-package-promotion-satisfiable.ts` fails the build when the
   burst cannot satisfy the promotion (`burstIntervalMs < roundGapMs`,
   `burstCount < minRounds`, burst span < `packageDropDwellSec`), when the poll
   cannot (`ttlMs < 4 × pollIntervalMs`, `roundGapMs > pollIntervalMs`), or when
   the package path is put back on the generic criterion.

Two supporting corrections ride along. Every one of the detector's five gates
now LOGS its rejection with `tags: { deviceId }`, and so does the governor's
drop — all six were silent, which is what made the chain unfalsifiable. And a
`package-delivered` event now carries the DETECTOR's confidence instead of a
fixed 1, so a notification rule's `minConfidence` is a working lever against a
recurring false positive; `importance` stays fixed.

## Consequences

- A delivery is reported ~15–20 s after the courier leaves, not minutes.
- 5 extra inferences per motion episode, on cameras with an active package zone
  only. A camera with no package zone rule never reaches the governor at all.
- Unknown zone geometry FAILS OPEN (any motion opens the burst), degrading to
  the whole-frame behaviour it replaced. A failed geometry read must never be
  able to silence package detection — that is D49's shape.
- **The chain will now fire, and the first thing it will fire on is 101's
  doormat**, which RF-DETR scores 0.53–0.60 as a `package`. That is a MODEL
  problem this decision deliberately does not paper over: the lever is
  `minConfidencePackage` per camera, plus the rule-level `minConfidence` the
  confidence fix just made real. Calibrate both from the drop test.
- `StationaryEntry.confidence` is set only by the package path and has no ledger
  column, because that path's entries are transient. Anything that persists an
  entry with a confidence must add the column first.

## Enforcement

`scripts/check-package-promotion-satisfiable.ts`, wired into the CI guard loop.
Verified by neutralization on all eight of its failure modes. The gate logging
and the burst are pinned by unit tests that were each confirmed to go RED when
the fix is removed.
