## Context

`AddonRegistryService.getIntegrationRegistry()` hands out a VIEW of the
integration store: rows whose declaring addon is not installed are hidden, so an
uninstalled addon's data stays in the database and reconnects on reinstall
instead of vanishing. Every read went through that filter —
`getIntegration`, `getIntegrationByAddonId`, `listIntegrations`, and by
extension `getDevice` / `getDeviceByStableId` / `listDevices` / `listCameras`.

`createIntegration` did not. It was the one unfiltered entry point in the whole
surface, and the asymmetry was invisible because both failure branches look the
same from the caller: `getIntegrationByAddonId` returns `null` when the row does
not exist AND when the row exists but the caller is filtered out.

Phase 4 of the Build-your-self chapter walked straight into it. A **core block**
runs under the addon id `core-block-<uuid>`; a block is materialised and spawned,
never installed, so it is never in the set the reads are gated on. The ordinary
`DeclaredDevices` get-or-create therefore ran its mint branch on **every start**:
the read said "no integration", the write succeeded, `listIntegrations` hid the
result from the operator, and `integrations.delete` — which resolves through the
same filtered `getIntegration` — answered *"Integration not found"*. Measured on
the live hub 2026-08-09: `int_0021` and `int_0022`, two starts of one block, both
unreachable through the API in every direction. Confirmed again the same night:
`integrations.get` and `integrations.delete` both answer "not found" for a row
that exists.

The first idea was to widen the filter — teach it that `core-block-*` ids are
legitimate. It works, and it is wrong: it widens the predicate that every device
read in the product passes through, to solve a problem one shared integration
solves at the edge. Blast radius decided it.

## Decision

**The write obeys the same predicate as the read.** `createIntegration` refuses
an `addonId` that is not installed, loudly, naming the rule. A declarer that is
not an installed addon hangs its devices off an integration somebody else owns —
`DeclaredDevicesSpec.integrationId`, which uses a supplied id verbatim and mints
nothing. For blocks that owner is the `core-blocks` builtin, which reconciles ONE
shared integration on boot; a block reads its id with
`integrations.getByAddonId({ addonId: CORE_BLOCKS_ADDON_ID })` — legal, because
`core-blocks` is installed.

**And hidden is not absent.** A read that suppresses a row that EXISTS logs it,
with the integration id and the addon id. A read that finds nothing stays silent.
That single distinction is what the whole defect hid behind.

## Consequences

- A row that can be created is readable, listable and deletable by the same
  principal. There is no longer a write path without a matching read path.
- Ownership of a DEVICE is untouched: it is `(addonId, stableId)`, and
  `listOwnDevices` stays addon-scoped — which is what keeps one block's
  withdrawal sweep away from another block's devices now that the integration no
  longer distinguishes them.
- `core-blocks` reconciles its integration with `devices: []`. That makes every
  row the index returns under it a withdrawal candidate, and it is safe ONLY
  because the index is addon-scoped and blocks' devices are owned by
  `core-block-<uuid>`. Two ways to destroy that — an owner-less device listing,
  or `core-blocks` declaring a device of its own — and a spec asserts the damage
  so either shows up as a test failure rather than as devices disappearing.
- **`int_0021` and `int_0022` remain.** They carry `info.fixed`, written by the
  mint branch that made them, so even a delete that could see them would be
  refused by the fixed guard — the guard that once destroyed the NC alarm panel
  when it fired too late. They reference no device and nothing reads them. Two
  dead rows are not worth relaxing that guard; the class that produced them is
  closed.
- Two adjacent footguns are closed with it, because both are how the wrong owner
  gets in: `deviceManager.listAll` refuses an owner filter that is PRESENT but is
  not an addon id (`addonId: null` used to answer with all 319 devices —
  `ctx.addonId` does not exist, the id is `ctx.id`), and `DeclaredDevices`
  refuses ports whose `addonId` is not a real id, at construction.

## Enforcement

Tests, at each of the four sites:
`server/backend/src/core/addon/__tests__/integration-visibility.spec.ts` (the
refusal, the `addon:`-prefix normalisation, and the hidden-vs-absent log),
`packages/system/src/builtins/core-blocks/__tests__/blocks-integration.spec.ts`
(the owner is `core-blocks`, and the sweep trap made executable),
`packages/system/src/builtins/device-manager/__tests__/device-manager.addon.spec.ts`
(present-but-not-an-id is refused; omitted stays permissive), and
`packages/types/src/device/__tests__/declared-device.spec.ts` (the ports guard).
Each was verified to fail with the fix removed.

`scripts/check-declared-device-single-owner.ts` continues to guarantee there is
exactly one get-or-create for a declared device, which is what keeps this rule
enforceable in one place.
