## Context

Operator directive, 2026-08-03: *"hub e agente devono avere esattamente lo stesso
funzionamento. Niente seed, niente doppie copie degli addons. Tutto deve essere
trasparente e senza molteplici path."* [hub and agent must behave exactly
the same. No seeds, no double copies of the addons. Everything must be transparent and without multiple paths.]

It follows a full evening of the opposite. A change shipped to the whole cluster
went live on the hub and silently did not on either agent, while every status
surface reported success. Chasing which copy of `@camstack/system` was winning
took three diagnoses and each was disproved by the next measurement:

1. `/data/addons/@camstack/system` — set aside, restarted, the agent still ran
   the old code;
2. `/data/framework` on `NODE_PATH` — disproved by the hub carrying an even
   OLDER one (1.1.57 from 2026-06-28) while staying current;
3. the seed under `/opt` — never confirmed, because by then it was clear the
   question could not be answered by looking at directories at all.

The measurement that ended the guessing is the inventory. One agent, one
host-provided package, **four copies**:

| Path | Version |
| --- | --- |
| `/opt/camstack-hub/node_modules/@camstack/system` | 1.2.28 |
| `/opt/camstack-seed-framework/node_modules/@camstack/system` | 1.2.28 |
| `/data/framework/node_modules/@camstack/system` | 1.2.0 |
| `/data/server-root/current/node_modules/@camstack/system` | 1.2.30 |

Plus a fifth under `/data/addons` until it was renamed. The launcher's own log
says the single-copy collapse resolved the framework dir to the closure — and
the process still ran a non-closure copy. When four copies exist, "which one
runs" stops being a property anyone can reason about, and every version number
the system reports becomes a claim about one of them rather than about the node.

The hub and the agent also do not boot the same way: the hub has no
`/data/addons/@camstack/system` at all, the agent does; the hub's builtins track
the closure, the agent's do not. Every difference is a place where a change
lands on one and not the other, and where a runbook step is right for one node
and wrong for the next.

## Decision

**A hub and an agent are the same program with a different role flag. One copy
of every package, one resolution path, and no seeding.**

- **One copy.** A host-provided package (`@camstack/system`, `@camstack/types`,
  `@camstack/sdk`) exists exactly once per node: inside the active server
  closure. Not in `/data/addons`, not in `/data/framework`, not duplicated into
  a seed tree that later diverges.
- **One resolution path.** Everything resolves from that closure. `NODE_PATH`
  entries, framework-dir overrides and per-role resolution branches are removed
  rather than added to; if something cannot be reached from the closure, that is
  a bug in the layout, not a reason for another path.
- **No seed.** The image ships a closure to boot from, not a second tree copied
  into `/data` that then ages independently. `applyServerUpdate` replaces the
  one copy, and that is the whole update story on every node.
- **Identical boot.** Hub and agent run the same launcher, the same bootstrap
  and the same addon-loading code. A role difference may select WHICH addons run
  — never WHERE they are loaded from.
- **Transparent.** Every node states, in its log, the resolved path of what it
  loaded. A version number without a path is not evidence: this whole record
  exists because reported versions were true of a copy nobody was running.

One thing already points the right way, found while writing this: there is no
`Dockerfile.agent`. Hub and agent images are built from the **same** Dockerfile
— the runbook's instruction to build the agent with `-f Dockerfile.agent` names
a file that does not exist. The image layer is therefore not the obstacle; the
divergence is entirely in what each node does to `/data` after boot.

## Consequences

- The legacy `/data/framework` tree and the `CAMSTACK_FRAMEWORK_DIR` env var go
  away. They are already overridden at runtime by the single-copy collapse on
  both nodes, so they are dead weight that still wins a resolution race.
- The bootstrap install of `@camstack/system` into `/data/addons` goes away
  entirely, not just when the closure resolves it — the conditional shipped
  earlier today becomes unconditional once the layout guarantees the closure is
  always there.
- Container images get simpler and larger-grained: one closure, no
  `camstack-seed-framework`, no `camstack-seed-addons` divergence to reconcile.
- Existing nodes need a one-time cleanup, and it is not free: removing the stale
  copies moves an agent's builtins forward by every version it silently missed.
  That migration is a deliberate, scheduled step with a container recreate as
  the escape hatch — not a side effect of a normal deploy.
- Some of today's runbook stops being necessary, which is the point: the five
  "things we relearn every time" in `camstack-hub-image-deploy` §0.2 exist
  because the layout permits states nobody can hold in their head.

## Enforcement

All three steps exist as of 2026-08-03. What they enforce is the *direction*,
not yet the end state: the fleet is still non-compliant, and deliberately so —
see the migration note under Consequences.

1. ✅ **Log the resolved module path.** `server/backend/src/launcher.ts` names
   the copy it resolved, with its path, right after `NODE_PATH` is final and
   before anything is imported. Both live nodes report the closure
   (`/data/server-root/current/node_modules`), which retired the open question
   of whether the renamed `/data/addons` copy on `agent-a` mattered: it
   did not.
2. ✅ **A boot-time inventory check.** `server/backend/src/package-inventory.ts`
   counts every copy under the closure, each `NODE_PATH` entry, the legacy
   `/data/framework`, `/data/addons` and the `/opt` seed trees, and logs an
   error naming each one with its path and version.

   **Amended 2026-08-12** — it classifies WHERE each copy sits before deciding
   whether to shout. The `/opt` seed trees are baked into the image and
   deliberately shadowed by the `/data/server-root/current` deposit on every
   `applyServerUpdate`; counting them as a violation meant the banner printed at
   every boot of every node, and the operator learned to scroll past the one
   boot where it mattered — the failure this record exists to prevent. The check
   now screams only for a copy in a location nobody deposits on purpose
   (`/data/framework`, `/data/addons`, an extra `NODE_PATH` entry) or for two
   copies that could BOTH be the one that runs (rival seeds with no deposit).
   Expected shadowing gets one compact line: `@camstack/system — seed 1.2.78
   shadowed by active 1.2.100 (/data/server-root/current/node_modules)`. The
   check is no weaker: a copy outside the two expected locations still produces
   the full banner.

   **Amended again, same day** — `CAMSTACK_INVENTORY_STRICT` is REMOVED, flag
   and refusal both. Operator directive: *"non dovremmo mai prevenire il
   boot"*. Neither inventory may end a process under any flag. A CamStack node
   that will not start records nothing and notifies nobody, and every layout
   these checks describe is survivable at runtime and fixed by an operator with
   a shell — never by a dead container. The perverse case decides it: strict
   mode on a node with a rival addon root refuses to boot BEFORE the thing whose
   only job is to explain the layout has explained anything. Report loudly,
   exit never. Enforced by `scripts/check-inventory-never-fatal.ts`, which fails
   the build on a reintroduced flag, on `process.exit`/`throw` inside the
   launcher's inventory region, or on the region sentinels being deleted to
   escape the check.

   Measured on the cluster the day it was written — the agent reproduces the
   table above, and the hub is no better:

   | Node | `@camstack/system` copies |
   | --- | --- |
   | hub | 1.1.57 · 1.2.28 · 1.2.28 · 1.2.31 |
   | `agent-a` | 1.2.0 · 1.2.28 · 1.2.28 · 1.2.31 |

   It is therefore **reported, never fatal**: a boot check that refuses to start
   every node in the cluster it was written to describe is an outage, not
   enforcement. That reasoning did not stop being true once the fleet was clean,
   which is why the flag that could flip it is gone (see the amendment above).
3. ✅ **A guard in `scripts/`**, wired into CI:
   `scripts/check-single-copy-layout.ts`. Same reasoning — the layout is
   non-compliant today, so it is a RATCHET over
   `scripts/single-copy-baseline.json`: a new seed tree, a new framework-dir
   override or another `NODE_PATH` entry fails the build, while the ten pinned
   buckets do not. That baseline is also the cleanup list this record schedules,
   in one place and with counts.

What remains is the migration itself: removing `/data/framework` and dropping
the seed trees from the image. Each step should show up as a bucket going DOWN
in the baseline. There is no third step making the check fatal — the end state
is a quiet boot, not a refused one.
