## Context

Read-only `/proc` probing of the live hub on 2026-08-06 measured hub-main's V8
main thread busy **82.2 s out of 120**, including **42 s inside uninterrupted
synchronous blocks of 2–7.3 s** (22 blocks ≥1 s). The same request that took
20.3 s and 26.4 s during a busy bin took 0.25–0.36 s in a quiet window: request
handling is cheap, and every slow request is main-thread contention.

Part of that contention is SQLite. 20 Hz syscall sampling put **210 of 2,561
samples inside `pread64`** — 161 on `camstack.db`, 49 on `camstack.db-wal`, all
4 KiB page reads, i.e. page-cache misses. fds 79/81 of hub-main are those two
files, so it is in-process, not inferred. The database is **130 MB** and its
tenants are not settings: the analytics event/track/media stores and the
sqlite-vec index share the file. `better-sqlite3` is synchronous, so every one
of those reads happens on the thread that serves every tRPC request.

The WAL had also reached a **248,955,152-byte** high-water mark — roughly 2x the
database. The only `wal_checkpoint(TRUNCATE)` in the tree runs inside
system-backup (`system-backup.service.ts`), at backup time, on a short-lived
second connection.

**The obvious fix is the disease.** A periodic truncating checkpoint on the
live connection takes the writer lock, waits for readers, and copies the entire
WAL back into the database — synchronously, on the exact thread whose 2–7.3 s
stalls are the problem being solved. With `better-sqlite3`'s default
`busy_timeout` of 5000 ms, a checkpoint that guesses wrong about quiet parks
the main thread for five seconds. That is a longer stall than most of the ones
already being measured. system-backup's checkpoint is safe only because it is
neither periodic nor on the hot connection.

A second, smaller trap surfaced while sizing the pragmas. The premise going in
was "SQLite's ~2 MB default page cache". It is not: `better-sqlite3` compiles
with `SQLITE_DEFAULT_CACHE_SIZE=-16000`, so the starting point is ~16 MiB. It
also compiles with `SQLITE_DEFAULT_WAL_SYNCHRONOUS=1`, so a WAL database is
**already** at `synchronous=NORMAL`. Writing `PRAGMA synchronous = NORMAL`
would have changed nothing while reading, forever after, like a durability
trade-off somebody weighed — the leftover-that-looks-like-verification failure
this repo has paid for three times.

## Decision

Any recurring maintenance against the hub's live SQLite connection —
`wal_checkpoint`, `VACUUM`, `ANALYZE`, `integrity_check` — must satisfy all
four of:

1. **Cost nothing when it does nothing.** The common tick is a `stat` or a
   metadata read. It never opens a transaction to decide whether to act.
2. **Escalate only on an idle signal read from the FILE**, not from a counter
   this process maintains. The WAL's mtime covers every writer on the database
   — the settings backend, the sqlite-vec index sharing the handle, and
   system-backup's second connection — where a private counter silently
   misses all but the first.
3. **Bound its lock wait.** Set a short `busy_timeout` for the duration and
   restore the previous value in a `finally`, because the connection is
   shared and leaving it lowered turns an ordinary contended write into a
   spurious `SQLITE_BUSY`.
4. **Log both branches.** What it reclaimed, and — just as importantly — that
   it deliberately declined, because a WAL that is never reclaimed otherwise
   reads exactly like a checkpoint that never ran.

Prefer a knob that takes no lock over an operation that does: `journal_size_limit`
bounds the on-disk WAL after any checkpoint that already succeeded, and is the
mechanism expected to do the routine work.

And: **a pragma whose effective value already matches the intent is asserted in
a test, never written in code.** Writing it is a no-op that documents a decision
nobody made.

## Consequences

- On a node that is never idle for `WAL_IDLE_QUIET_MS`, the gate never opens
  and the WAL is bounded only by `journal_size_limit`. That is the intended
  failure mode: doing nothing beats a 249 MB synchronous copy in the middle of
  a live request. A WAL past 4x the high-water mark logs a `warn`, because at
  that point something is holding a read transaction open and the operator
  should see it.
- 64 MiB of page cache is malloc'd C memory on one connection, not V8 heap, so
  it does not move the heap ceiling that produced the hub's earlier OOM.
- `mmap_size` covers the main database only — SQLite never mmaps the WAL — so
  the 49 WAL `pread64` samples are addressed by keeping the WAL small, not by
  mmap. Under mmap an I/O error on a mapped page arrives as SIGBUS rather than
  a catchable error; the pragma is therefore read back and asserted, so a build
  compiled with `SQLITE_MAX_MMAP_SIZE=0` fails loudly instead of silently doing
  nothing.
- **This does not fix the real problem.** The structural fix is moving the
  analytics stores off hub-main's thread — `better-sqlite3` in a worker, or the
  analytics database owned by the analytics fork — so that a page-cache miss
  cannot block a request at all. That touches the settings capability contract
  and needs its own design. Everything above narrows the window; it does not
  close it.

## Enforcement

`packages/system/src/builtins/sqlite-storage/__tests__/wal-maintenance.spec.ts`
and `__tests__/sqlite-pragmas.spec.ts`. Three assertions carry the rule and each
was verified to go red when its fix is removed:

- *"REFUSES to checkpoint an oversized WAL that was written to recently"* —
  replacing the idle gate with `if (false)` turns it red (`expected
  'checkpointed' to be 'deferred-not-idle'`). This is the stall guard.
- *"restores the connection busy_timeout after bounding the checkpoint"*.
- The three pragma assertions read the value back off the open connection;
  deleting the three `pragma` calls turns them red.

The `synchronous=NORMAL` assertion is a characterization test: it records why
the pragma is absent from `initialize()`, and goes red if a dependency bump
changes `better-sqlite3`'s compile defaults underneath us.

No guard script — the rule is about a shape, not a token, and a grep for
`wal_checkpoint` would flag the legitimate system-backup call.
