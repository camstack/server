## Context

`DeviceBindingEntry.kind` distinguishes `'native'` from `'wrapped'` providers, and
consumer code started branching on it — `getNativeProvider(...)` in one arm,
`getProviderByAddon(...)` in the other. Every such branch is a copy of the
resolution rules, and copies diverge: one call site learns about cross-process
providers, another does not, and a capability works in the device detail page but
not in the aggregate.

## Decision

A `(capability, device)` pair is resolved by exactly one function:
`CapabilityRegistry.getProviderForDevice(capName, deviceId)`. It handles native or
system, hub-local or cross-process, transparently.

`kind` is **metadata for the UI** — it tells a human where a binding came from. It
is never a control-flow input in consumer code.

## Consequences

- New provider topologies (a new route kind, a new placement) are added in the
  resolver and every consumer gets them at once.
- If a consumer needs to know `kind` to work correctly, the resolver is missing
  something — fix the resolver.

## Enforcement

Review. A `kind ===` comparison outside presentation code is the tell.
