## Context

The retired `addon-export-ha-mqtt` mapped a **`DeviceType`** to one of five export kinds and
fell through to `'sensor'` for everything else. Measured against the live cluster
on 2026-08-05 — 293 devices, 16 device types — that produced:

- **116 devices exported correctly** (the switches, sirens and lights);
- **177 devices exported as an entity that never receives a value**, because the
  state pump only knew how to publish for two of the five kinds;
- and worse, **51 of the 92 sensors published the WRONG value**. Both the motion
  feed and the battery feed wrote to the single state topic of any device
  classified `sensor`, and 51 sensors carry a `battery` slice — so "Indoor
  Temperature" published `100`. An operator reading their dashboard saw a battery
  percentage under a temperature label, with nothing anywhere reporting a fault.

The fallback is what made this invisible. Every unrecognised device produced a
plausible-looking entity, so the failure presented as "Home Assistant is a bit
flaky" rather than as a missing mapping.

`DeviceType` was the wrong discriminator to begin with. Twelve capabilities are
bound to all 293 devices regardless of type (`snapshot`, `device-status`,
`motion-detection`, `videoclips`, `webrtc-session` and eight more); what
distinguishes a vacuum from a thermostat is the rest of the binding list. This is
[D12](adr-0012.md) — per-device aggregation walks `getBindings(deviceId)` — applied
to exports.

The alternative considered and rejected was a **denylist**: export everything,
suppress the infrastructure caps. It fails open. Each of those twelve universal
wrapper caps would have had to be added by hand, and the thirteenth would ship a
garbage entity to every device on the cluster.

## Decision

An export addon derives entities from a device's **capabilities**, never from its
`DeviceType`, and the capability→entity map is an **allowlist**. A capability that
is not in the allowlist appears in a typed `UNMAPPED_CAPS` record with a reason
(`deferred`, `no-ha-equivalent`, `infrastructure`) and produces **no entity at
all**. There is no default branch and no generic fallback kind. A capability in
neither list is reported as `unclassified` by the addon's `getStatus` and logged
on every reconcile.

`DeviceType` may still select *which component* a mapped capability renders as —
`switch` on a `Siren` becomes an HA `siren` — but it never decides *whether* an
entity exists.

## Consequences

- A capability CamStack gains exports nothing until someone maps it. That is the
  point: a gap is visible in `getStatus`, an entity that never updates is not.
- The unmapped list is a maintenance obligation, and a deliberate one — the
  distinction between `deferred` (a correct payload exists, the work is scoped)
  and `no-ha-equivalent` (§4 of the design doc) is a commitment about what will
  and will not be built.
- One device now produces MANY entities, so anything that assumed one entity per
  device — a stored `stateTopic`, a `Map<deviceId, route>` — has to become
  per-`(deviceId, entityKey)`.
- An entity's `key` is baked into its HA `unique_id`. Changing one orphans the
  entity in Home Assistant's registry and the operator loses its history and its
  dashboard placement, so keys are a wire format, not an implementation detail.

## Enforcement

`unclassifiedCaps()` in
The capability map returns every capability in
neither list; the reconcile logs it as a warning and `deviceExport.getStatus`
surfaces it. A test asserts that the union of capabilities measured across all 293
live devices is fully classified, and that no capability appears in both lists.
There is no repo-wide guard — this holds for one addon today, and should become
one if a second exporter adopts the same shape.

## 2026-08-09 — the rule outlived the addon that motivated it

`addon-export-ha-mqtt` was retired when the Home Assistant export moved to HTTP
push (planning repo: superpowers/specs/2026-08-04-ha-native-export-design.md). The rule
did not go with it: the replacement's catalog carries the same two lists —
`CAP_ENTITY_MAP` and `CAPS_NOT_EXPORTED` in
`packages/addon-provider-homeassistant/src/ha-export/entity-catalog.ts` — with
`unclassifiedCaps()` reporting anything in neither, and still no default branch.
