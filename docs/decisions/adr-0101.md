## Context

The kernel owns processes, transport and registries; every feature is an addon.
An OAuth descriptor is none of those three — who the client is, which scopes it
asks for, where it may be redirected is knowledge about one integration, and
`@camstack/system` had no way to be right about it.

It held one anyway. `export-alexa` declared its own descriptor from the addon,
but `homeassistant` was declared by the `local-auth` builtin, on the reasoning
recorded in [D92](adr-0092.md): the Home Assistant component is a client of the
hub's own tRPC API rather than a device exporter, so it had no addon of its own.
That premise expired the day `homeassistant-export` shipped. The component is
that addon's counterpart — export pushes to it, and it pins
`addonId: 'homeassistant-export'` on the cap calls it makes back.

The obvious objection to moving it is real and is the reason this record exists.
The descriptor map is rebuilt per request from the providers registered at that
moment. A builtin is up with the hub; an addon registers only after its runner
forks and initialises. **Moving the declaration into an addon widens the window
in which `homeassistant` is genuinely unknown** — and the window is not
theoretical: an operator got `invalid_request — unknown integration` from the
Home Assistant component during a night in which the hub restarted four times
for release trains, and `/api/oauth2/integrations` returning a short list is a
verdict the component keeps ("this hub is too old, use the password form").

What was rejected: waiting for the addon. A timer, a retry loop, a
"wait-for-provider" on the authorize path, or a cached last-known descriptor
map are all [D3](adr-0003.md) violations, and the last one is a shadow registry
that would keep serving a descriptor an uninstalled addon no longer owns.

## Decision

Every `oauth-integration` descriptor is declared by the addon that owns the
integration, from its own manifest and its own `onInitialize`. The kernel
declares none, and no code anywhere branches on a specific `integrationId`.

The window that creates is answered rather than waited out. The hub already
learns which addons owe the capability at addon-LOAD time —
`declareFromManifest` runs before a forked runner exists — so
`CapabilityRegistry.getManifestDeclarers(cap)` minus the registered providers is
the set still outstanding. When it is non-empty, an unrecognised `integration=`
is **`503 temporarily_unavailable`** with `Retry-After` and the pending addon
ids, never `400 invalid_request — unknown integration`; and
`GET /api/oauth2/integrations` reports `complete: false`. The server performs no
wait of any kind: it answers immediately with what is true at that instant, and
the client decides whether to retry.

## Consequences

- **Linking requires the owning addon to be installed and up.** For Home
  Assistant that is `homeassistant-export`. This is a real availability cost and
  it is the price of the rule; it is paid down by the 503, which tells a client
  that waiting will help and tells a human which addon to look at.
- **A static descriptor must not sit behind an await.** A provider is registered
  only when `onInitialize` returns, so any I/O before the return is added to the
  window. `homeassistant-export`'s boot reconcile — a fleet-wide `ctx.api` sweep
  — was detached for exactly this reason.
- **`pending_addons` is disclosed only on the session-gated route.**
  `/api/oauth2/integrations` needs no token, and "not final yet" is the whole
  signal a client can act on there; the addon ids appear on `/authorize`, where
  an authenticated human is reading them as a diagnosis, and in the `warn` line.
- **A disabled-but-installed addon stays listed as pending**, so its
  integration answers 503 indefinitely rather than 400. That is the honest
  answer — the capability is owed by something that will not supply it, and
  naming it is the diagnosis — but a client must bound its own retries.
- `getManifestDeclarers` is not a second registry: it stores an argument
  `declareFromManifest` was already handed and dropping, and is read
  synchronously at the point of use.

## Enforcement

Tests. `server/backend/src/__tests__/oauth2-account-linking.spec.ts` pins that a
declared-but-unregistered addon yields 503 + `Retry-After` + `pending_addons`
while a genuinely unknown id still yields 400, that the refusal log carries
`pendingAddons`, that discovery reports `complete`, and that the addon ids do
NOT appear on the unauthenticated route. It also runs the whole flow against the
**shipped** Home Assistant descriptor, imported from
`packages/addon-provider-homeassistant`, so drift or a second move fails the
suite. `packages/system/src/kernel/__tests__/capability-registry-manifest-declarers.spec.ts`
pins the primitive, including that a declarer is recorded for a capability this
node has no definition for.

No guard: "the kernel declares no integration" is not mechanically checkable
without pinning a file list, and the manifest is the thing a reviewer sees.
