## Context

[D62](adr-0062.md) established two things at once, and only one of them was
right.

The right half: **a per-camera function switch stores NOTHING** — it reads and
writes the authority that already owned the function (`setDisabled`,
`setWrapperActive`, `RecordingConfig.enabled`, the notification mute), and names
it in `CameraSwitch.authority`. That rule exists because this repo had already
shipped two knobs that wrote a store nobody read, and it holds.

The wrong half: the AGGREGATE. D62 also built one coherent control group over
those eight functions — a catalog with labels and cost lines, a derivation, a
`getCameraSwitches` / `setCameraSwitch` cap pair, a viewer panel, an admin panel,
a HomeKit export. The operator's verdict on 2026-08-12, having lived with it:
the layer added complexity and no clarity. Every one of these functions already
had a settings page of its own, so the group was a **second place to look** for
something that was never missing from the first. Recording is the clearest case
— `RecordingConfig.enabled` has always been first-class, editable in the
recording settings, and the switch was a veneer over
`recording.setDeviceConfig` that could only ever agree with it.

What was tried first, and did not work, was making the aggregate *better*: the
group was given per-source bounds (2026-08-08), `unavailableReason` copy for
every absent function, an inverted-polarity carve-out for the privacy mask
(D74/D83), and node pinning for the broker's audio plane. Each fix was correct
and none of them addressed the complaint, because the complaint was not that the
panel was wrong — it was that the panel existed.

One thing in D62's blast radius is NOT a convenience and must not go with it.
`CameraStatus.switchedOff` is the difference between a camera being **disabled**
and a camera being **broken**. On 2026-08-08 `getCameraStatus(105)` returned
`switchedOff: []` at the moment the operator had `stream-broker` AND `recording`
switched off, and the camera read as broken on every surface. That badge was
derived from the group. Deleting the group without moving the badge first would
re-create the incident by construction.

## Decision

**A per-camera function is turned on and off in its OWN component's settings,
through the authority that already owns it. There is no aggregate switch
surface.** No catalog, no group cap, no second panel.

**`CameraStatus.switchedOff` survives and is composed straight from the
authorities** (`composeSwitchedOff`), never from a control group. It reads the
wrapper bindings, `RecordingConfig.enabled`, the notification mute, the broker's
`DeviceOverride.audioMuted` and the camera's own microphone, each bounded
independently, and it reports what it could NOT read (`unreadable`) alongside
what is off. An empty list is a positive claim only when nothing was unreadable;
otherwise the payload says `degraded: ['switches', 'partial']` and no surface may
render it as "the operator turned nothing off".

D62's own rule is kept verbatim and is not weakened by this: **never a second
store, and an off function is REPORTED off.** What is withdrawn is the aggregate
that rule was written around.

### The fate of every switch id

| id | Where the function is turned off from now on | Status after this refactor |
| --- | --- | --- |
| `stream-broker` | `deviceManager.setDisabled` — the device list's own disable | already had its own surface |
| `object-detection` | the `detection-pipeline` wrapper binding (device capabilities) | already had its own surface |
| `audio-analysis` | the `audio-analysis` wrapper binding (device capabilities) | already had its own surface |
| `recording` | `RecordingConfig.enabled` in the recording settings | already first-class; the switch was a veneer |
| `notifications` | the notification centre's own per-device panel on the device page (`DeviceNotificationMute`) | phase 3, 2026-08-13 |
| `privacy-mask` | the privacy-mask component's own settings | already had its own surface |
| `device-audio` | the privacy-mask component's own settings (same cap, audio plane) | phase 3, 2026-08-13 |
| `broker-audio` | the stream-broker component's per-device panel, routed to the source owner | phase 3, 2026-08-13 |

**The `notifications` row did not become a `deviceConfig` cap.** This decision
originally called for one (D14 derived UI). `notification-rules` is a
system-scope cap and the mute is keyed by `deviceId` in the notification
centre's own rows; turning that into a device-scoped `deviceConfig` cap is a new
capability, i.e. a framework train, for a control that is one boolean. The rule
D62 and this record actually enforce is *write the authority that already owns
the function*, and a per-device panel on the device page does that with no new
cap, no new store and no train. The `deviceConfig` archetype remains the right
answer for camera-config caps that already exist; it is not a reason to invent
one.

### The phase plan

This decision lands in three commits-worth of work, deliberately not one.

1. **This refactor (phase 1+2).** The badge is recomposed from the authorities;
   `CameraSwitchService` is reduced to a thin compatibility shim over the same
   single read; `addon-terminal` writes `setWrapperActive` directly. The cap pair
   is marked deprecated and **keeps working**.
2. **Phase 3 — the four missing surfaces.** The four rows above that have no
   other home get one in their own component. Detection / audio-analysis /
   recording landed first as the device header cluster (2026-08-12); the mute,
   the microphone and the broker's audio plane landed 2026-08-13.
3. **Phase 4 — the removal train.** `getCameraSwitches` / `setCameraSwitch`, the
   catalog, `deriveCameraSwitches`, the viewer panel, the admin panel and the
   HomeKit switch builders are deleted together, once no caller remains.

**The cap pair may not be removed in phase 1.** Deployed viewers (v1.0.305) call
it, and a viewer on a phone is not something this repository can redeploy. A cap
removal that breaks an installed app is not a refactor, it is an outage.

**Phase 3 MUST precede phase 4, and for two rows that is not a preference.**
`device-audio` and `broker-audio` had NO other writer anywhere in the product —
not an admin page, not a viewer screen, not another cap. Deleting the shim first
would not have made them harder to reach, it would have made them unreachable:
a camera the operator muted stays muted, and the only way back is a published
`@camstack/server`. `broker-audio` is worse still, because the shim was also the
only caller that ROUTED the write to the camera's source owner. That ordering is
now mechanical — `scripts/check-switch-successor-surfaces.ts`, in CI.

**What phase 4 still owes, as of 2026-08-13.** One production caller of the pair
remains: `addon-provider-homeassistant`'s `ha-export`, which projects the whole
group as Home Assistant switch entities (`projectCameraSwitches`) and commands
them back through `setCameraSwitch`. It needs the same treatment the admin
surfaces just had — each entity bound to the authority its function lives on —
before the pair can go, and it is the reason phase 4 is not "delete some UI":
an export that stops answering leaves entities in Home Assistant that no longer
control anything. The guard prints this ledger on every green run.

## Consequences

**One read path, so two surfaces cannot disagree while both exist.**
`readSwitchAuthorities` (`switch-authorities.ts`) is the single bounded pass over
the eight authorities. The status badge and the deprecated shim both consume it.
When the shim is deleted, the badge is untouched — which is the whole point of
putting the read there rather than inside the shim.

**The badge no longer depends on anything scheduled for deletion.** Removing the
cap in phase 4 cannot reach `CameraStatus.switchedOff`.

**`CameraStatus.audio.enabled` still needs three of the eight.** `device-audio`,
`broker-audio` and `audio-analysis` each silence the analyzer, and the status
block must agree with all three (D83). Until phase 3 gives the first two their
own read paths, the authorities read here are their ONLY read path — dropping
them would turn "the operator muted it" back into "the analyzer is dead".

**An unreadable privacy mask does not degrade the badge.** The mask can never
contribute to `switchedOff` (its ON means video is obscured, not that a function
works), so failing to read it cannot make the badge incomplete. This is a
tightening: the previous derivation marked the whole stage `partial` when the
3.1–3.6 s camera probe timed out, which is most cameras most of the time, and a
marker that is always on says nothing.

**A Terminal camera's silencing now FAILS LOUDLY.** `addon-terminal` used to
route through `setCameraSwitch` and catch everything with a `warn`. It now
resolves the bound wrapper from `getBindings` and throws if it cannot write.
A silent miss there is a screen recording running a full detection pipeline
forever, with no symptom except a hub that runs hot for reasons nobody connects
to a terminal created three weeks earlier. It also switches off
`motion-detection`, which D109's gate leaves as the last remaining demand for
decoded frames on a camera whose detection is off.

**What this forbids.** No new caller of `getCameraSwitches` / `setCameraSwitch`.
No new aggregate over these functions under a different name. No per-camera
function control that writes anywhere but its own component's authority.

## Enforcement

- `packages/types/src/interfaces/__tests__/camera-switches.spec.ts` —
  `composeSwitchedOff` is pinned separately from `deriveCameraSwitches`, so the
  badge's derivation survives the group's deletion. Includes an explicit
  "the two agree" test that is deleted WITH the group. Verified to fail (5 tests)
  with the `unreadable` branch neutralised.
- `camera-status-switched-off.spec.ts` — READ / PARTIAL / NOT-READ at the
  service level, driven by RAW authority reads rather than a pre-derived group.
  Verified to fail with the `partial` branch neutralised, which is the exact
  shape of the 2026-08-08 incident.
- `camera-status-audio-enabled.spec.ts` — the three audio-silencing authorities,
  now expressed as authority facts.
- `detection-switch-authority-e2e.spec.ts` — D109's gate asserted against
  `setWrapperActive` rather than the deprecated cap, so
  [D109](adr-0109.md)'s enforcement no longer dies with the cap. Verified to fail
  on both legs with the gate neutralised.
- `silence-analysis.spec.ts` — the Terminal camera writes the authority, silences
  motion, and THROWS on a failed resolution. Verified to fail (5 tests) with
  warn-and-continue restored and `motion-detection` dropped.
- `device-notification-mute.spec.ts` + `DeviceNotificationMute.spec.tsx` — the
  mute's derivation and its write. The write reaches
  `notificationRules.setDeviceMuted` with the inverted polarity the store
  speaks, the shim is asserted NOT called, and an already-muted device renders
  muted with no write on mount. Verified to fail (3 tests) with the unknown
  branch neutralised.
- `privacy-mask-audio.spec.ts` + `privacy-mask-microphone.test.tsx` — the
  microphone. Verified to fail with the camera read-back removed, and again with
  the `setAudioEnabled` write removed: a control that only moves its own local
  state passes neither.
- `broker-audio-switch.spec.ts` + `StreamBrokerPanelAudio.spec.tsx` — the
  broker's audio plane, including the routing key on BOTH the read and the
  write. Verified to fail with the node guard neutralised (3 tests) and with the
  routing key dropped from the read.
- **`scripts/check-switch-successor-surfaces.ts` (CI).** Every retired switch id
  is pinned to the file that writes its authority, so deleting or renaming a
  successor fails the build whether or not the shim still exists — which is the
  only thing standing between "we moved the panel" and "we removed the last
  writer". It also refuses a NEW caller of the deprecated pair and prints the
  ledger of existing ones. Verified by renaming a successor's hook: the first
  version passed (substring match), which is why it matches whole identifiers.
- The `@deprecated` tag on the cap methods is still review-only — the guard
  catches a new caller, not a viewer that keeps calling the old pair, which is
  the whole reason the pair is still alive.
