## Context

The alarm panel was built, correct and inert. It had a state machine with real
exit/entry delays, a bounded siren, a persisted machine that survived deploys,
a derived coverage answer and a configuration tab — and it could not tell
anybody anything. `publish()` computed the state and wrote the cap slice;
nothing turned a transition into a notification. The one delivery it did have,
the arm announcement, rode a parallel `deliverAnnouncement` channel that wrote
no outbox row, appeared in no history, retried nothing and froze its sentence in
the hub's language at arm time.

Three smaller failures sat around it. The rule cooldown `continue`d **before**
the action runner, so a second intruder inside the notification window did not
arm the alarm, did not open a gate and did not sound a siren — a budget for
notifications was silently a budget for physical actions, which is exactly what
the sequence's own `minDelaySec` exists to be instead. The `deviceState` gate
read a cache refreshed only by the 30-second reload tick, so rules gated on
`armed_away` kept firing for up to half a minute after a disarm. And the
coverage answer said "Away armed — 2 cameras" without checking whether either
camera was muted, offline, or had detection switched off.

The obvious fix — emit `alarm-triggered` and let a rule notify on it — produces
**two pushes for one incident**: "person at the gate" with a photograph, then
"ALARM" with nothing. The advanced-notifier reference does exactly that. The
operator asked for the opposite.

## Decision

**The alarm's three transitions are ordinary `NcSystemEventKind` members**
(`alarm-triggered`, `alarm-armed`, `alarm-disarmed`), emitted once per
TRANSITION by the panel's publish hook, through the same `systemSubject` every
bus category uses. The engine keeps no alarm branch and a rule authors
`kinds: ['alarm-triggered']` exactly as it authors `kinds: ['node-offline']`.
The hook is a direct in-process call, never the event bus: D8 permits dropping
telemetry, and "the alarm went off" is not telemetry.

**A rule-triggered alarm delivers ONE row.** The attribution travels
rule → action runner → `actuate` → panel:

1. `NcRuleFireRef` (rule id, name, camera, record, track, event, timestamp) is
   handed to `NcRuleActionRunner.run({ origin })` and passed to every actuation.
   The runner does nothing with it — it is provenance, not a parameter.
2. `NotificationCenter.actuateWithAttribution` recognises
   `alarm-panel.trigger` aimed at ITS panel and calls `panel.noteRuleTrigger`
   immediately before delegating. The join lives here and not in the runner,
   because the runner must not learn what an alarm is, and not in the cap,
   because `alarm-panel.trigger` takes only a device id (a Home Assistant panel
   provides the same cap).
3. `NcAlarmAttribution` holds the note across the entry delay — up to
   `entryDelaySec` separates the button press from the siren — and drops it on
   arm, disarm, a manual trigger and after one emission.
4. The `alarm-triggered` subject carries `alarmSource`. `buildEntries` then
   uses the **source rule's** media policy and the source subject's
   track/event owners with the **alarm's** title and body keys, and
   `NcOutbox.supersede` withdraws the source rule's still-pending rows **for
   exactly the targets the alarm reached**.

**Every alarm notification is durable.** `deliverAnnouncement` is gone from the
alarm path; the arm announcement is enqueued under the synthetic rule id
`nc-alarm-announce`, addressed to `announceTargets`, skipping targets a rule
already reached — so it retries, appears in history, and is worded in the
reader's language at send time from a frozen key rather than in the hub's at arm
time.

## Consequences

- **No lost notification anywhere.** Superseding only touches `pending` rows and
  only for targets the alarm row reached: a person the alarm rule does not
  address keeps their detection notification, and a row already sent (the normal
  case once an entry delay has run) is left alone and the fact is logged.
- **With no rule gated on `alarm-triggered`, nothing is superseded** and the
  operator gets the plain detection notification. The gap is a WARN line, not a
  silence.
- The alarm event is about the CAMERA when a rule caused it and about the PANEL
  when a person did. One sentence, and it decides the media owner, the body
  variant and what a `deviceIds` filter means.
- A rule's cooldown no longer gates actuation at all. Sequences keep their own
  `minDelaySec`, which is now the only throttle on physical action.
- `NcDeviceStateCache.note()` makes an in-process device's state authoritative
  for `MAX_AGE_MS`; the reload tick remains as reconciliation, exactly as D8
  wants.
- Coverage exclusions read three EXISTING authorities (the NC's own mute, the
  device manager's `online`, a wrapped `detection-pipeline` binding) and store
  nothing (D62). An unreadable authority answers "unknown", never "excluded".

## Enforcement

- `packages/types/src/capabilities/__tests__/notification-rules.cap.spec.ts` —
  the three kinds are authorable and `skippedDevices` refuses an unrenderable
  reason.
- `packages/addon-admin-ui/src/pages/system/__tests__/notification-system-events.spec.ts`
  fails if a kind exists server-side and no editor group offers it.
- `alarm-transitions.spec.ts` pins transition-only emission (a boot publish
  announces nothing) and the whole attribution lifetime.
- `alarm-notifications.spec.ts` runs the join end to end: one combined row with
  the rule's media, a plain row for a manual trigger, an untouched row for a
  target the alarm never reached, and two sequence runs inside one cooldown.
- Neutralisation confirmed for all three: removing the `previous === null`
  guard, moving the action runner back below the cooldown `continue`, and
  emptying `NcDeviceStateCache.note` each fails the tests that claim them.
