## Context

An operator added a Dreo integration with the wrong password. The **Test** button
answered *"No stream URL provided"*, and **Next** created the integration anyway.
The integration then failed at reconcile, silently, forever.

It was not a Dreo bug. `integrations.testConnection` had exactly two behaviours:
a broker branch (`settings.brokerId` → `broker.testConnection`) and a DEFAULT
branch that read `settings.main_stream_url ?? settings.url` and ffprobed it.
Every account-based integration fell into the default, so the identical nonsense
came back for `provider-dreo`, `provider-dreame`, `provider-ecowitt`,
`provider-gree`, `provider-tuya` **and** `provider-homeassistant` — which
declares the `broker` cap and still fell through, because at create time there is
no `brokerId` yet.

That last detail is the structural gap: **at CREATE time the integration does not
exist**, so every provider surface the system had — `device-provider`,
`device-adoption`, `broker` — was keyed by something that does not exist yet
(`addonId` + a live client, an `integrationId`, a `brokerId`). There was no way
to ask "are these settings valid?" before the row existed. So the Test button had
never worked for an account integration, and `create` had nothing to gate on.

`main_stream_url` turned out never to be an integration settings key at all — it
is a *device* config key (`packages/types/src/interfaces/device-capabilities/camera.ts`).
The default branch was answering every integration in the system with a sentence
about a field none of them has ever had.

## Decision

**The provider declares its own test.** A new system-scoped collection cap,
`connection-test`, has one method — `testSettings({ settings })` — that takes the
candidate settings blob exactly as the create form collected it, opens a
throwaway session, and returns a discriminated outcome. It persists nothing.

`integrations.testConnection` and `integrations.create` route through ONE explicit
ordered resolver with **no default branch**: the addon's declared
`connection-test` provider, else a broker when the settings NAME one, else
`unsupported`. The framework never infers a test from the shape of the settings.
A stream-URL probe is now one provider's implementation of this cap
(`addon-provider-rtsp`), reached because that addon declared it.

**`create` refuses on `rejected` and only on `rejected`** — the one outcome that
means the remote was asked and said no. `unsupported` (nothing declared) and
`inconclusive` (a declared test could not complete) observed *nothing* about the
credentials: they proceed, and they are logged as "creating without validation".
Refusing on them would make every integration lacking the hook uncreatable, and
would block a good create on a flaky network.

## Consequences

- **Four statuses, never collapsed to a boolean.** `validated` / `rejected` /
  `inconclusive` / `unsupported` reach the wire on
  `integrations.testConnection`. `success` is true ONLY for `validated`, so a
  test that never ran can never render as a tick; the non-verdicts carry an
  `error` string that says the test did not run rather than inventing a failure,
  and the admin UI renders them in their own tone. This is the same distinction
  as D99: a null from a timeout must not look like a null from a refusal.
- **A provider that cannot tell a refusal from a transport fault must return
  `inconclusive`.** Guessing `rejected` blocks a good create; guessing
  `validated` waves a wrong password through.
- `getAvailableTypes` gained `canTest`, so the wizard disables a Test button that
  could only ever answer "cannot be tested".
- Adding the cap is a framework change: it ships by publish train +
  `applyServerUpdate`, never `camstack deploy`. The per-provider implementations
  ship independently by `camstack deploy`.
- Providers still without a declared test (ecowitt, gree, vesync, wyze, the
  camera vendors) are honestly `unsupported`. Wyze is deliberately left out: its
  cloud auth is rate-limited to roughly one request per 30s per IP, so a
  pre-creation probe would consume the slot the integration itself needs at boot.

## Enforcement

`server/backend/src/__tests__/cap-providers/integrations-connection-test.spec.ts`
pins the routing and the gate against a fake that behaves like a real provider —
exactly one credential set is accepted. Removing the gate fails
`REFUSES to create when the provider rejected the credentials`; removing the
routing fails four. `packages/addon-provider-dreo/src/__tests__/dreo-connection-test.test.ts`
pins that `DreoAuthError` is `rejected` while a transport error is
`inconclusive`. Beyond that: review — nothing forces a new integration addon to
declare the cap, which is exactly why `unsupported` had to be a first-class,
visible answer rather than a silent pass.
