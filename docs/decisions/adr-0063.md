## Context

Linked sensor/control events already reach a camera's timeline as **synthetic
tracks**: a `tracks` row with `positions: []`, one `keyFrameSmall` snapshot, and
a `source` naming the projection. That projector encodes contracts that were
each learned the hard way — the snapshot must be persisted as `keyFrameSmall`
and not `snapshot` (a `'snapshot'` blob is invisible to the viewer's
hero/clean/reel selectors, which stuck the reel on "loading"); the snapshot cap
must be bounded by a timeout or a hung cap stalls the ingest path; a snapshot
failure must still land the track.

Audio events had no timeline presence at all. The obvious move — a second
projector for audio — is the failure this repo keeps paying for: a parallel
projector diverges, and every contract above would have had to be re-learned in
the copy.

Two things had to be established before the criteria could be honest:

- **`audio-level-detector`'s existing "peak" is not an anomaly measure.** It is
  a fixed dB step over a 10 s rolling mean, kept as an array that is re-filtered
  and re-reduced on every frame. Worse, it is fed only by the LEVEL route: a
  frame with a confident classification returns before `observeLevel` runs, so
  the baseline is blind to exactly the loud, classified frames a marker exists
  for. A marker built on it would have been both mistuned and partially deaf.
- **A fixed dB step cannot express "out of the ordinary".** A camera on a road
  has a jittery floor and needs a bigger jump to be surprising than one in a
  garden. That difference is measurable — it is the signal's own mean absolute
  deviation — and nothing in the codebase was measuring it.

There is no recorded audio in this repo. Any threshold picked here is a guess,
and shipping a guess that creates timeline markers is how audio gets turned off
wholesale.

## Decision

**One projector.** `SyntheticTrackMaterializer` (renamed from
`SyntheticSensorTrackMaterializer`) takes a `source` on its input and is the
only way a non-spatial event becomes a track. `isSpatialTrack` is an ALLOW-LIST
(`source === undefined || source === 'pipeline'`), not `!== 'sensor'`, so a
synthetic source added later is non-spatial by default rather than being handed
to the tracker in silence.

**"Out of the ordinary" means: surprising for THIS camera.** An audio frame is a
marker candidate only when it clears three independent bars — absolute loudness
(`minDbfs`), a floor in dB above the camera's own mean (`minDeviationDb`), and a
multiple of the camera's own mean absolute deviation (`minDeviations`). The
baseline is a time-aware EWMA of dBFS plus an EWMA of its MAD: O(1) per frame,
six numbers per camera, no arrays, fed by EVERY audio frame BEFORE the
classification/level route split.

**A marker requires quiet.** It is suppressed while a track was alive or motion
was reported within `motionQuietSec`, answered from two in-RAM mirrors
(`lastTrackActivityMs`, `lastMotionInsertByDevice`) — never a query, because the
gate runs at the audio frame rate.

**It ships OFF, and counts anyway.** With `audioMarkerEnabled: false` the whole
chain still runs and the marker that would have been created is counted as
`wouldFire` on the per-camera `audio anomaly gate (window)` info line. The
operator sizes the real rate per camera before paying for a single marker. Every
gate that drops a frame which had already cleared the ones before it is counted
in the same line, with `tags: { deviceId }`.

**The ceiling, not the thresholds, bounds the worst case.**
`audioMarkerMaxPerHour` (3) and `audioMarkerMaxPerDay` (12) are hard per-camera
caps, charged before the async materialize so a second candidate sees the budget
already spent.

## Consequences

- `TrackSource` gained `audio`, which is a capability change: codegen, and
  `NcSubjectSource` / the notification-rule `source` filter had to gain it too,
  or a rule filtering on source could not address an audio marker.
- A synthetic audio track is a `tracks` row owning `ownerKind: 'track'` media, so
  [D61](adr-0061.md) governs it with no new clock — `listIdsBefore` filters on
  `deviceId` and `lastSeen` only, and must never learn to filter on `source`.
  A guard for that is a test, not a script (see Enforcement).
- The expected marker rate per camera per day is **not predicted here**. It
  cannot be, without recorded audio. The `wouldFire` counter is the measurement,
  and `maxPerDay` is the bound that makes being wrong survivable.
- `Track.audioLabels` now carries the class of an audio marker. The alternative —
  a per-audio-class event-taxonomy sub — was rejected: the audio macro vocabulary
  COLLIDES with existing subs (`dog` is a COCO animal, `siren` is a control), so
  a barking dog would have landed in the animal lane. `className` stays `audio`,
  which is a real taxonomy macro with its own timeline lane.
- The baseline learns from anomalous and silent frames alike. A sound that
  becomes continuous (rain, roadworks) stops being a marker after a few minutes;
  a quiet camera's normal stays quiet, which is why the absolute bar exists.

## Enforcement

- `packages/addon-post-analysis/src/pipeline-analytics/__tests__/audio-anomaly-detector.spec.ts`
  — one discriminating test per bar, including the case where the dB floor and
  the MAD test disagree (the only test that tells the two relative bars apart).
- `packages/addon-post-analysis/src/pipeline-analytics/__tests__/audio-marker-projector.spec.ts`
  — one per gate, each asserting the SUPPRESSION COUNT, not just the absence of
  a marker.
- `packages/addon-post-analysis/src/pipeline-analytics/store/__tests__/track-store-retention-select.spec.ts`
  — asserts `listIdsBefore` selects synthetic tracks of both sources alongside a
  pipeline track. A `source` filter added to that query fails it.
- The allow-list `isSpatialTrack` is asserted for `source: 'audio'` in
  `synthetic-track.spec.ts`.
- Nothing checks that a THIRD synthetic projector is not written. Review only.
