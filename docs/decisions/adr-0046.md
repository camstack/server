## Context

Snooze is the one Notification Center feature whose failure mode is SILENCE.
Every other defect in this subsystem announces itself — a dead-letter row, a
duplicate push, a missing attachment. A snooze that misbehaves looks exactly
like a working camera on a quiet afternoon, which is the same shape as the two
outages this system has already had: a live rule that could not fire for fifteen
hours ([D35](adr-0035.md)), and a dispatcher that dead-lettered every
notification it ever produced while the target sat healthy in the catalog.

So the design questions were not "how do we suppress a notification" — that part
is one `if`. They were the four ways this feature can become an outage:

1. **A window that does not end.** The obvious implementation is a sweeper that
   marks expired snoozes inactive. A sweeper that dies leaves the operator
   silenced indefinitely, and nothing on any screen would say so.
2. **A window that silences the wrong people.** "I am asleep" is not "nobody
   needs to know". A snooze that defaulted to the whole household would be an
   outage one person caused for everyone else.
3. **A malformed row that silences everything.** A `scope: 'device'` entry whose
   `deviceId` did not survive a schema change reads, under the permissive
   interpretation, as "matches any device" — the entire feed, from one bad row.
4. **A silence nobody is told about.** Someone silencing a nuisance camera does
   not want a summary; someone silencing a SECURITY camera needs one. Choosing
   either for everybody turns the feature into an outage for half the users.

Two smaller things were tried and rejected while building it. Storing one row
per suppressed notification is the natural shape — and a snooze exists BECAUSE
something is noisy, so that table is unbounded precisely when it is in use.
Retrying the end-of-window digest until it succeeds is the natural reliability
answer — and it means a permanently-failing target is retried every two seconds
for hours, while a half-delivered digest is re-sent to the targets that already
received it.

## Decision

**Expiry is a comparison, not a job.** A snooze ends because `now >= expiresAt`,
evaluated at the moment a notification is being delivered. Nothing schedules it,
nothing sweeps it, and no background failure can extend a window. Cancelling one
moves its expiry to the current instant rather than deleting the row, because
the digest of what it hid is still owed.

**Personal by default; global is asked for and refused, never downgraded.** A
window silences its author. It may silence everyone only where that was granted
in advance: a rule-scoped window needs the rule's `snoozeAllowGlobal` (absent =
no), and a camera-scoped or whole-feed window is admin-only, because no rule
carries the opt-in for those. A request for a global window the caller may not
have is REJECTED — an operator who believes the house is silent and is not has
the same problem as one who cannot end a silence.

**A malformed scoped row matches NOTHING**, and an unowned target is never
silenced by a personal window. Every ambiguity in this feature resolves toward
DELIVERING.

**A window always accounts for what it hid.** Suppression is counted per
(window, target, rule, camera); when the window closes, one digest per target
that was actually suppressed goes exactly where the silenced notifications would
have gone. The summary defaults ON and is per-window configurable. The digest is
marked handled after the ATTEMPT, not after a success.

## Consequences

- The suppression check runs on the dispatcher's hot path and therefore reads
  RAM only; windows are mirrored from the store and refreshed on the drain tick,
  so a window opened on the hub takes effect on the evaluating node within one
  tick rather than one rule-reload interval.
- The gate sits AFTER target resolution (a personal window needs to know whose
  delivery this is) and BEFORE the notification is built (a snoozed camera must
  not keep rendering clips nobody will receive). Moving it either way is a
  regression: earlier, it cannot tell whose silence it is; later, it costs media.
- A digest that fails to send is lost, deliberately, with a WARN carrying the
  window id. Reliability was traded for not turning a failure into a storm; the
  log line is the compensation and must not be removed.
- Windows are capped at 24h by the schema. A longer silence has to be asked for
  again, on purpose.
- `snoozeAllowGlobal` is `.optional()`, never `.default()` — a Zod default does
  not run on the addon cap path (three production failures in one day), so the
  engine reads absent as `false`.

## Enforcement

- `snooze-policy.spec.ts` (21) pins the decision layer: personal vs global, the
  window's inclusive/exclusive edges, the malformed-row case, the unowned
  target, and who may set `global`.
- `dispatcher-snooze.spec.ts` (10) pins WHERE the gate sits — including that a
  suppressed notification costs no media call, and that a vanished target is
  still a dead-letter rather than a silence.
- `snooze-lifecycle.spec.ts` (10) drives the real center end to end: hidden,
  counted, released by the clock, digested exactly once.
- `notification-rules-snooze.router.spec.ts` pins that the three cap methods
  exist on the built router and that `caller: 'required'` really injects the
  server-derived identity — the router is a structural pass-through, so nothing
  below it would notice if it did not.
- `scripts/check-viewer-condition-mirror.ts` covers the snooze scope enum and
  both snooze schemas' fields, so the viewer's local mirror cannot fall behind.
- Nothing enforces that a future scope resolves toward delivering. That one is
  review only, and it is the rule most worth guarding by hand.
