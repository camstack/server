## Context

2026-08-13, 21:35 CEST. The operator physically unplugged four Hikvision
cameras — hall (104), porch (103), sala da pranzo (111), kitchen (112). All
four flipped `device-status.online → false` within 22 seconds (the provider's
shared reachability poll: ISAPI `getDeviceInfo` every 30 s, offline after 3
consecutive misses — identical for every camera it owns, so nothing about the
cameras differed). **Two notifications arrived.** At 01:13–01:15 the next
morning, four more arrived where the operator expected two.

The logs answer both halves, and they are two unrelated bugs that happened to
land in the same hour.

**One — the seed swallowed a real outage.**

```
21:35:54  device:104   offline → flip   → notified
21:36:01  device:103   offline → SEEDED → silent
21:36:03  device:111  offline → flip   → notified
21:36:16  device:112   offline → SEEDED → silent
```

The liveness ledger (D130/D132) had been created that same day at 11:22. It
only ever learns a subject from an incoming event, so 104 and 1443 had rows
(they had emitted a state change that afternoon) and 103 and 587 had none —
their first observation *ever* was the unplugging, and "the first observation
seeds" threw it away. The rule is right against the boot flood it was written
for and wrong here: **a device that stays quiet until it dies is a device whose
death is silent, indefinitely, and the window is unbounded.**

**Two — the cooldown spent the window on the wrong edge.**

`Eventi di sistema` is `cooldownSec: 60, scope: 'rule-device'` over both
`device-offline` and `device-online`. The key was `r:<ruleId>:s:device:<id>` —
the subject, with no trace of which way it moved:

```
20:35:55  device:3219 offline → notified
20:36:08  device:3219 online  → matched, COOLING DOWN → nothing
20:39:29  device:3219 offline → notified          ← reads as a duplicate
```

The recovery is lost, so the operator's last word is "offline" about a device
that is up. And because the ledger *did* advance on the suppressed event (it is
a real flip; only the notification was throttled), the next outage is a genuine
flip again and notifies — a second identical sentence with no recovery between
them. `device:103` took the same path at 05:55:26/05:55:37 on 2026-08-14: the
durable ledger row reads `online`, the operator's phone reads offline.

## Decision

**A liveness subject is seeded from the authority at boot, not from the first
event that happens to mention it — and only in the direction that cannot
flood. A cooldown is a budget for VOLUME; the direction of a state transition
is part of the fact and belongs in the key.**

1. `NcLivenessLedger.seedFromDirectory` runs inside the boot reseed, right
   after `load()`, over the device directory that `start()` has already
   refreshed. It seeds **only devices the directory reports `online`**, and
   **never overwrites a row the ledger already holds**. Staged, not persisted:
   the value is re-derived from the authority on every boot, so a lost write
   costs nothing and the runner's frequent respawns do not offer ~500
   re-derivable commits a day to the checkpoint lottery (D96).

2. `systemEventCooldownScope` is the ONE builder of a system event's cooldown
   scope, `s:<subject>:k:<kind>`, and both `cooldownKey` and the boot-time
   cooldown reseed call it. They used to write the string separately, which is
   how a key format drifts across a restart — and that copy had already drifted
   (it never carried the class granularity).

## Consequences

- **The seed cannot re-arm the 2026-08-13 flood, structurally.** A row seeded
  `online` can only ever turn a later `device.offline` into a notification. It
  can never turn a `device.online` into one, and that is the only shape the
  flood ever had. This matters because a restarted device is optimistically
  `online: true` — `BaseDevice` re-seeds `device-status` on construction and
  `resolveDeviceOnline` falls back to `true` for a device with no mirrored
  slice — so at boot the directory says "everything is up" and the ledger
  inherits exactly that claim.
- **A device the directory calls offline still keeps the old behaviour.** No
  row is seeded, its first observation seeds silently. Deliberate: that is the
  branch that could announce a phantom recovery.
- **The directory may be stale, and the ledger wins.** D49: the ledger is the
  authority for what it ACCEPTED; a stale `online` overwriting an accepted
  `offline` would make the camera's real recovery a no-flip and lose it.
- **Rules fire more often, by exactly one class of event.** An operator whose
  camera flaps now hears both edges instead of one. That is the point — the
  suppressed edge was never noise, it was the correction.
- **Every persisted cooldown key changes shape once.** The first system event
  per (rule, subject, direction) after the deploy sees no seeded window and
  fires. One extra notification, once, in exchange for never losing an edge.

## Enforcement

- `system-event-cooldown-direction.spec.ts` — the key in isolation (both
  throttle scopes, the same-direction control, and the byte-for-byte identity
  of every non-system key), plus the incident wired through the whole centre.
  Removing the `:k:` tail fails 4 of 7.
- `system-liveness-seed.spec.ts` — the incident (a camera that has never spoken,
  then dies, IS announced); that a directory reporting everything DOWN seeds
  nothing, with a CONTROL that proves the path is alive; that the seed never
  overwrites an accepted row; and that a directory with no liveness at all is
  the older behaviour unchanged. Neutralising the seed call fails 2.
- `rule-engine-system-event.spec.ts` pins the literal key string, so a future
  change to the format is a visible edit rather than a silent one.
