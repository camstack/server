## Context

The viewer stack (`camstack-viewer`) is entirely WebRTC + frame-accurate scrub.
It never consumes HLS. The question raised was whether to change **how**
recordings are stored — segments today — to something that makes playback and
scrubbing faster, and, given that cameras carry heterogeneous audio codecs
(AAC, G.711 µ-law/A-law, native Opus), whether to transcode **on write** or
**on read**.

The obvious answer — "pick a better container" — was measured and rejected. The
storage format is **not** the lever:

- A per-frame PTS→byte-offset index already exists inside every segment
  (`mfra`/`tfra` + `trun` per-sample sizes, 0.053 % overhead, parsed in 0.5 ms).
- On the live hub, scrub is **99 % a cold read off the disk array** (100.4 ms
  median — seek-bound, not byte- or format-bound). A different container does not
  move a seek-bound number.
- The real read-path cost was **ffmpeg spawns**: full-playback feeding still
  spawned two ffmpeg processes per fragment (one video demux, one audio demux),
  and every one is fork+exec+native-lib init on a box already RAM-pressured
  (see [D25](adr-0025.md)).

So the win is not a new format. It is (a) removing the ffmpeg spawns from the
read path, and (b) making the common case — the WebRTC egress — a **passthrough**
rather than a transcode.

## Decision

**Store recordings as-is** (segmented fMP4 with the existing per-frame index);
do not migrate the storage format. Video is stored copy (no transcode, ever).

For audio, transcode **on write, once, into Opus** (`-c:a libopus`, 48 kHz,
48 kb/s VBR) so the WebRTC read path is a native passthrough. On read:

- **Native-Opus** segments and live native-Opus streams are passed through
  untouched to the browser (`Opus`/PT 111, the SDP-preferred codec).
- Non-Opus audio still needed on read — legacy AAC fragments recorded before
  this change, and live AAC/G.711 sources — is transcoded **in-process via
  node-av** (the `audio-codec` cap), **never ffmpeg**: decode → PCM → Opus encode
  in the broker process. G.711 → PCM is a table lookup.
- **PCMU (G.711 µ-law) remains a fully intact fallback.** The SDP offer is
  dual-codec (Opus preferred, PCMU fallback); a session that negotiates PCMU
  gets the byte-identical legacy path. Opus emission is strictly additive and
  demand-gated — a broker with no Opus consumer encodes nothing.

Scrub and full-playback video demux is done **in-process in JS** (the existing
per-frame index + `segment-demux-js`), removing both ffmpeg spawns from the read
path.

## Consequences

- **New recordings gain a one-time write-side encode** (libopus, ~48 kb/s). This
  is cheap relative to the read-side spawns it removes, and it makes every
  subsequent playback a passthrough. Video is untouched, so the dominant bytes
  are unaffected.
- **Legacy AAC fragments keep working** via the in-process node-av fallback; they
  never gain the passthrough benefit, but they do lose their ffmpeg spawn.
- **The broker now owns an Opus *encode* client** (`OpusEncodeSession`, mirror of
  the decode client) in addition to the decoder. It is demand-gated on consumer
  count and torn down with the session.
- Prestream/silence for an Opus session must emit **encoded Opus silence frames**
  (`encodeOpusSilenceFrame`), not the 0xFF PCMU silence byte — a codec-specific
  branch that must stay correct or the vt of the audio timeline drifts.
- Cross-process media rules from [D9](adr-0009.md)/[D18](adr-0018.md) still hold:
  this is all in the broker process; nothing here sends frames across a boundary
  at frame-rate.
- **A/V-sync at 48 kHz and real-browser Opus decode are not proven headlessly.**
  werift negotiation is proven in unit tests; actual browser playback and live
  A/V alignment are **needs-hardware-verification** and must be checked on the hub
  before this read path is trusted for every camera.

## Enforcement

Unit tests cover the codec negotiation (`opus-negotiation.spec.ts`), the RTP
clock selection and rebase (`audio-rtp-clock.spec.ts`), the encode session and
silence frame (`opus-encode-session.spec.ts`), the G.711→PCM tables
(`g711-decode.spec.ts`), and the recorded-Opus JS extraction + feeder routing
(`segment-audio-js.spec.ts`, `recorded-feeder-opus.spec.ts`). The additive,
demand-gated property (PCMU packets byte-identical when no Opus consumer) is a
review invariant, not a guard. Real-browser playback and A/V-sync are **review +
hardware only** — no automated gate exists, which is exactly why they must not be
claimed as verified.
