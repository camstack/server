## Context

Task #36. The operator's ask, verbatim: *"li voglio usare sulla app viewer
presto"* [I want to use them on the viewer app soon] — the timelapses, previews and digest mosaics the notification centre
produces should be something you scroll back through, not something that exists
for the twenty seconds a push notification is on screen.

What existed was the opposite of an index. `NcArtifactPlane.publish` put bytes on
a **six-hour** scratch, minted an HMAC-signed URL (24 h, [D47](adr-0047.md)),
handed it to a notifier backend, and kept **no record at all**. After the sweep
there was nothing to say the artefact had ever been produced.

Three shapes were considered and two rejected:

1. **Index the durable stores instead.** A "list NC artifacts" that joins
   `pipeline-analytics:media` (mosaics), `recordingExport`'s export index
   (timelapses) and the outbox `payload.artifacts[]` URLs. Rejected: three
   sources with three retentions, three id spaces, and a list whose paging is a
   merge — and two of the three do not hold the artefact at all (a timelapse mp4
   lives in `recordingExport`, and only a *copy* was ever republished).
2. **Pre-mint a signed link per artefact and let the viewer use those.** This is
   what already exists, and it is wrong for a session-holding client: a 24-hour
   bearer URL per artefact, minted for artefacts nobody may ever open, is a
   link-leak surface bought for nothing.
3. **What was built.** ONE store, with a second retention class.

## Decision

**Everything the viewer can browse is stored once, on `NcArtifactStore`'s
RETAINED shelf, and indexed once, in `notification-center:artifacts`. Bytes are
served on TWO routes over the SAME store: the existing `public` HMAC-signed
`nc-artifact` for a fetcher with no session, and `nc-artifact-read`, served
`authenticated`, for the viewer.**

The invariants that make that one decision rather than four:

- **Retention has ONE authority.** `NcArtifactIndex` takes `retentionMs` FROM the
  store's own age bound and derives every row's `expiresAt` from it. A second
  number here would eventually disagree, and the disagreement is a library of
  rows whose bytes are gone — a wall of broken tiles.
- **Expiry is a PREDICATE, never a post-filter.** An expired row must not consume
  a slot of the page the caller asked for. This is also why `ownerUserId` is
  stored as `''` for a global artefact rather than NULL: the store's filter
  vocabulary has no `IS NULL OR = ?`, and visibility that cannot be a predicate
  becomes a post-filter that silently breaks `offset`/`limit`.
- **Indexing does not depend on a reachable public address.** `publishIndexed`
  stores and indexes FIRST, then tries to mint the signed link. `publish` returns
  early on a loopback-only install because a link nobody can open is worth
  nothing — but the viewer reaches the hub directly, so gating the library on a
  tunnel would make the feature absent exactly on LAN-only installs.
- **`deviceId` is the PRIMARY camera and it is the filter authority.** A digest
  spans cameras and is filed under its rule's first one, the same camera its
  outbox row already uses. A camera filter answers "artefacts filed under this
  camera", not "artefacts this camera appears in" — that second question is what
  the `ruleId` filter is for. One row per camera per artefact would make a
  cross-camera digest appear N times in one list.
- **The read route does not re-litigate ownership.** Per-artefact visibility is
  enforced on the LIST surface; the bytes route resolves an unguessable id the
  caller was handed and refuses one that is not indexed or has expired. This is
  the rule `data-plane-access.ts` already states: *a plane serving ONE item the
  caller had to be told about is `authenticated`; a plane that walks off with a
  CORPUS is `admin`*.
- **The index is never the notifier's authority.** A row that fails to write is
  logged (with `tags.deviceId`) and costs nothing; the notification ships.

## Consequences

- The retained shelf needs **three** bounds, not two: age (14 d), count (2000)
  and **bytes** (2 GiB). A timelapse mp4 is megabytes and 2000 of them do not fit
  on an operator's disk — the count bound alone protects nothing. The newest
  entry is never swept by the byte bound, because a shelf that deletes what it
  just wrote can serve nothing.
- A row can outlive its file (a byte/count bound biting before the age one), so
  an hourly reconcile prunes the index against `store.keptIds()`. **The index is
  CENTRAL and the shelf is LOCAL**, so only the node that produces artefacts —
  the same `isPostProcessingNode` gate the timelapse and summary producers sit
  behind — may run that reconcile: any other node's shelf is empty and would read
  the entire library as orphaned. `prune(null)` is how a non-producing node says
  so, which makes the destructive half unreachable rather than merely un-called.
  The expired half is time-based and runs everywhere. The residual race — file
  swept between the list and the fetch — is a 404 **with a WARN line naming the
  camera and the artefact**, never silence.
- Adding an artefact kind means a producer that writes one. `NC_ARTIFACT_KINDS`
  holds only `timelapse`, `timelapse-preview` and `summary-mosaic` because those
  are what exists; an enum member no producer writes reads as verification.
- The producers' `publish` ports now answer `{ url, artifactId }` instead of a
  URL. The two members fail independently, and the timelapse path depends on it:
  the preview is published FIRST so the video row can name it as its poster.
- The schema lives in the ADDON, not `packages/types` — same reason the summary
  rule's does. It ships on `camstack deploy` and never waits for a train.
- **NOT closed by this record**: per-device authorisation. Neither the index nor
  the read plane filters by a principal's `allowedDevices`; they inherit exactly
  the posture `event-media` and the `view`-level cap methods already have.

## Enforcement

- `data-plane-access.spec.ts` — the plane table is exhaustive by test, and the
  new prefix is asserted `authenticated` AND explicitly `not 'public'`. The same
  spec asserts `NC_ARTIFACT_READ_PREFIX_REF` is the SAME string
  `artifactDownloadPath` writes into every row: two copies of it would be a 404
  nobody would think to look for.
- `artifact-index.spec.ts` — expiry-as-predicate, the visibility rule and the
  `prune(null)` guard are all neutralisation-verified (removing any of the three
  turns the corresponding test red).
- `notification-center.spec.ts` — the declare list is exhaustive; an undeclared
  collection answers 412 on first use and takes the runner down.
- `nc-artifact-actions.spec.ts` — fail-closed caller, per-row visibility, and the
  honest refusal on a node with no index.
- Nothing checks that a NEW producer remembers to index what it publishes. The
  port signature makes it hard to forget (`meta` is required, not optional), but
  that is a type, not a guard.
