## Context

On 2026-08-13 the hub container was recreated. Every provider reconnected and
re-announced its devices, and the operator's phone received a **"camera online"
notification for every camera on the installation** — 25 notifications across
13 devices in 26 minutes, plus `node-online` for the agents, which re-register
on hub boot for exactly the same reason (Moleculer `$node.connected`). Nothing
had come back, because nothing had gone away.

What was already there and did not work: `NotificationCenter.lastSystemLiveness`,
an in-RAM `Map<subject, kind>`. It is a correct de-duplicator — it is what stops
the explicit `device.online` category and the `device.state-changed`
`device-status` slice from notifying twice about one edge — and it is worthless
across a restart, because a process that has just started holds no previous
observation at all. Every first observation therefore read as a fresh
transition. The map's memory is exactly as long as the thing it is supposed to
survive.

This is the same shape as the occupancy cold-baseline bug fixed the previous
day (`occupancy-cold-seed.spec.ts`): a cold key fabricated a "before" that no
snapshot had ever said, and the first real reading looked like a change. It
took the same cure, and it is worth stating once as a rule rather than fixing a
third time.

## Decision

**A notification about a state may only arise from a TRANSITION BETWEEN TWO
OBSERVATIONS, and the previous observation must be as durable as the state it
describes.** For device and node liveness this is `NcLivenessLedger` — a
declared SQLite collection (`notification-center:liveness`), keyed by the
intake's subject (`device:102`, `node:agent-1`), holding the last liveness the
centre ACCEPTED. On each liveness event: no row → **seed** (write it, notify
nothing, log INFO with `tags: { deviceId }`); row equal → **discard**
(`reason=no-flip`); row different → **notify** and advance the row.

`ledgeredLiveness` is the one site that decides which kinds are governed, and
the two exclusions are part of the decision:

- **stream-online / stream-offline are NOT ledgered.** They are already
  reason-gated at the intake (`streamHealthAccepted`) — a first packet, a
  lazy-dial suspend, its resume and a released broker are all refused — so a
  boot produces no stream notification to suppress.
- **device-disabled / device-enabled are NOT ledgered.** The operator's switch
  (D62) is emitted only on a transition of the flag and never at boot;
  ledgering it would make the first disable after a fresh ledger a silent seed —
  a notification lost for an action a human performed, with no flood to trade
  it against.

Both keep the RAM same-edge dedup, which is all they ever needed.

## Consequences

- **A liveness notification is now impossible for a subject the centre has
  never seen.** After a wipe of the collection (or its very first deploy) the
  hub is silent about a camera until that camera's state actually changes. That
  is the trade, and it is deliberate: a lost "camera online" costs one line
  nobody reads, a phantom flood costs trust in every notification the hub
  sends — the operator has just experienced the second one.
- The gate reads **only the in-RAM mirror**, refreshed off the event path by
  one boot `load()`. Nothing an event does depends on an I/O that can fail
  (D49), and a load that fails leaves the mirror empty, which SEEDS — the
  failure direction is toward discard, never toward a flood.
- The durable write is **write-behind and best-effort**: the mirror advances
  first so an immediate duplicate is caught anyway, and a lost write costs at
  most one silent re-seed on the next boot.
- The row set is bounded by the installation (one per device, one per node) and
  is deliberately **NOT pruned** against the device directory: a prune is work
  destroyed on a fallible read, and a directory that answered empty once would
  wipe the ledger and re-arm the flood.
- `onSystemEvent` now returns early on a non-evaluating node. `consumeEvent`
  dropped the event there anyway; what changes is that such a node no longer
  writes ledger rows for notifications it will never send.

## Enforcement

- `liveness-ledger.spec.ts` — the three verdicts, durability across a fresh
  instance, the governed-kind list (including the two exclusions above), and
  the D49 failure direction.
- `system-liveness-seed.spec.ts` — the wiring, end to end, including the
  incident itself: 15 cameras re-announcing `online` across a restart produce
  ZERO outbox rows. Every negative is proved by a CONTROL event that must
  produce exactly one row, so the assertion can never pass vacuously; all five
  fail when the gate is neutralised.
- `notification-center.spec.ts` — the declare-completeness list, which an
  undeclared collection would 412 the runner over.
