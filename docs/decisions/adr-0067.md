## The problem

Every ffmpeg in this repo was built and spawned differently, and the differences
were invisible.

**Two argv builders for the same job.** `buildFfmpegArgs`
(`stream-broker/stream-broker/ffmpeg-invocation.ts`) was hwaccel-aware, picked a
hardware encoder and emitted `-threads` — and served exactly ONE call site, the
broker transcode pool. `buildTranscodeFfmpegArgs` (`webrtc/session.ts`) was
hand-rolled with **no hardware encoder and no `-threads`**, and served the
derived feeder and the WebRTC transcode leg. Both looked correct in isolation.

**Five sets of encode constants**, in four packages, that nobody could diff.
Three of them disagreed about Opus channel count alone.

**No hardware decode anywhere on egress.** HomeKit had zero `-hwaccel`
references; the derived path hardcoded `decodeHwAccel = null`. Meanwhile
`docs/design/decode-path.md` records **10 concurrent 4K vaapi decodes passing on
this hub**. Every egress transcode was decoding in software on hardware that
works.

**And two hwaccel opinions that disagree in the direction that breaks things.**
The kernel resolver returns `['qsv','vaapi']` for an Intel host — qsv first.
`addon-decoder-ffmpeg`'s `DECODE_HWACCEL_RANK` puts **vaapi above qsv on
purpose**: on this exact hub a qsv decode child exits `code=171` producing no
frames, while vaapi does 8 MP h264 at ~50 fps.

## The decision

**One argv builder, one spawn wrapper, one set of constants, one hwaccel
authority — in `@camstack/types`.**

The primitive lives in `packages/types/src/ffmpeg/` rather than in an addon
because three separate addons need it (`addon-pipeline`, `addon-export-hap`,
`addon-export-alexa`) and **addons may never import each other**. That
constraint is also why Alexa's encode profile was "intentionally duplicated" in
the first place; `@camstack/types` is the only legal shared home.

| File | Owns |
| --- | --- |
| `ffmpeg/invocation.ts` | THE argv builder + the `EncodeProfile` adapter |
| `ffmpeg/encode-defaults.ts` | the collapsed constants |
| `ffmpeg/hwaccel.ts` | egress decode-backend resolution |
| `ffmpeg/sharing-key.ts` | the dedup/refcount key |
| `ffmpeg/process.ts` | spawn / lifecycle (node-only, `@camstack/types/node`) |

### `-hwaccel` is an INPUT option

ffmpeg accepts `-hwaccel` **after** `-i` without any error and then silently
decodes in software: the CPU cost stays, the GPU is idle, and the log line still
says "using hardware decode". `buildInputArgs` is the only function that may
emit it, and every test asserts an INDEX relative to `-i`, never membership.
Moving the flag after `-i` turns 3 tests red.

### Hardware acceleration comes from the DECODER ADDON, never the kernel resolver

`resolveEgressDecodeHwAccel` reads `probedBestHwaccel` off the `decoder` cap's
`getInfo` — the per-node value the decoder addon computed with
`rankDecodeHwAccels`, and the same value `AgentLoadService.readNodeDecodeHwaccel`
already surfaces in the UI. The ranking constant is **not copied**; a second copy
is how the two opinions appeared.

The kernel resolver remains a dependency for ONE purpose: naming the
disagreement in a log line. It may never select a backend. When the decoder
cannot answer, the resolver returns **software** rather than adopting the
kernel's qsv-first order, because that order is the known-bad one.

Hardware is the DEFAULT for an egress transcode, and **every** software outcome
is announced at `warn` with `tags: { deviceId }`. On this hub a silent fall back
to software is a flow bug, not a capability limit.

### The primitive is a CAPABILITY, so a transcode is placeable

`streamBroker.acquireEgressTranscode` / `releaseEgressTranscode`. `stream-broker`
is a `mode: 'singleton'` cap with `placement: "any-node"`, and `classifyCapRoute`
gives Priority 1 to `hub-in-process` — so an unpinned call never leaves the hub
and placement is a caller-side `nodePin(nodeId)`, exactly as the recorder and
pipeline-runner already pin their broker calls. The returned url is
host-substituted via the existing `hostname` field so a remote caller can dial it.

**What is NOT true yet**, and must be before a transcode really runs off-hub —
**the list below is superseded by [D68](./adr-0069.md), which retired three of
these**; read that one for the current state:

- nothing selects a node — every caller today passes no pin, so every transcode
  lands on the hub;
- the source stream must be reachable FROM the chosen node; the broker's
  restream urls are hub-local and `substituteRtspHost` rewrites the CONSUMER's
  dial address, not the producer's;
- a consumer that dies without releasing leaks a refcount (below), which is
  benign on one host and is not once the holder is on another node;
- there is no lease TTL and no `transcodeNode` role.

### Exact-match dedup, and an IMMUTABLE handle

Two requesters whose requests produce the same `egressTranscodeSharingKey`
receive the same `pipelineKey` and the same child. **Exact match, never fuzzy** —
a quantised ladder merging nearly-identical requests would make the stream you
receive a function of who else is watching and in what order they arrived.

The key is derived from the STRUCTURED plan with defaults applied before
hashing. `getStreamWithCodec` folds a raw `outputArgs: string[]` into
`pipelineKeyFor`, so its extensibility hatch and its sharing key are the same
field: a consumer needing one flag silently stops sharing. The new request
schema therefore has **no raw-flag escape hatch at all** — every knob is a named
field, and `EgressEncodeSchema` omits `inputArgs`/`outputArgs`. The
operator-facing derived-stream transform editor keeps them; that is a different
surface for a different job (reshaping a badly-behaved SOURCE).

**There is no `reconfigure`.** A consumer whose requirements change releases and
re-acquires. A mutable shared handle is exactly what made Alexa's
`derived:alexa-<id>` a co-tenant hazard: it is a *publicly selectable camStream*,
so a browser viewer or the recorder can attach, and one Alexa consumer's
downgrade drags them all to 360p. Rule 3 of the guard enforces this.

### Sharing is NOT the goal

The operator: *"It's fine to have several processes — as you say they can
disturb each other — but what's needed is a single convenient primitive for
accessing ffmpeg."* Alexa going from one encoder for N consumers to N encoders
is the intended outcome. **Say the cost plainly: N concurrent Alexa sessions on
one camera will now run N ffmpeg processes instead of one.** That is accepted,
and dedup-on-exact-match still collapses the common case where they ask for
identical parameters.

## Consequences

- A cap change: **`npm run codegen` was run**; reaching real nodes additionally
  needs a force-publish of `@camstack/system` (`nx affected` misses it).
- `-vf scale=WxH` replaces HomeKit's `-s WxH` when HAP migrates — equivalent,
  but noted because the two are not identical in the presence of another `-vf`.
- The WebRTC transcode leg's elementary `-f h264 pipe:1` sink now emits `-an`
  instead of an audio encode block ffmpeg discarded. Pure CPU saved.
- The RTP audio sidecar's `-sdp_file` now precedes `-f rtp` (both valid), and it
  regained the shared audio preset it had silently lost during the migration.

## Constants: what changed and what kept a divergence

KEPT, with the reason recorded in `encode-defaults.ts`:
- **VBV window** — HomeKit ONE second (its budget is enforced per second by the
  controller), browser/Alexa TWO (let a keyframe spike, keep the average).
- **`preset`** — `ultrafast` for the interactive paths, `veryfast` for Echo.
- **`-bsf:v dump_extra`** — HomeKit only; it negotiates its own SDP.

CHANGED:
- **Opus channels 2 → 1** in the broker preset. Every source here is a mono
  camera mic; the stereo preset spent bitrate duplicating a channel. The
  broker's `2` was the outlier and it is the one that moved.
- **Alexa gains `level: '3.1'`** — its SDP advertises `profile-level-id=42e01f`
  and its encoder was unconstrained. A stream that does not match its own
  advertisement is the defect class that kept HomeKit black for a year.

## Alternatives rejected

- **A shared-encoder API.** Explicitly not the goal; see above.
- **Copying `DECODE_HWACCEL_RANK` into the primitive.** That is how two
  disagreeing opinions appeared. The primitive asks the decoder.
- **Normalising requests onto a quantised ladder** so near-identical requests
  merge. Rejected: unpredictable in exactly the way a debugging session cannot
  tolerate.
- **Absorbing all thirteen spawn sites.** Decode sessions own the hwaccel
  cascade the primitive CONSULTS (absorbing them inverts the dependency); source
  ingress is `-c copy` with no encode plan; the file-oriented jobs (segment mux,
  export, still, clip, timelapse, snapshot) run to completion against file sinks
  and are mostly copies. Each boundary is recorded in the guard's allowlist.
