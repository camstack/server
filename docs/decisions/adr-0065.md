## Context

Camera 112 arrived in Apple Home with **two switches and no names on either**.
The operator could not tell the siren from the privacy toggle without opening
each one.

The hub had been naming the cause on every accessory build, all day, and nobody
had read it:

```
[Camera front door@Siren@Configured Name] Characteristic not in required or
  optional characteristic section for service Switch. Adding anyway.
[Camera front door@Privacy@Configured Name] …
```

The label was being written to `Characteristic.ConfiguredName`. Enumerating
hap-nodejs 2.1.7's own service definitions, **exactly five service types list it**
— `AccessoryInformation`, `InputSource`, `SmartSpeaker`, `Television`,
`WiFiRouter`. `Switch` and `Lightbulb` are not among them; both list `Name`,
required *and* optional. `Service.getCharacteristic` adds an unlisted
characteristic anyway and emits that warning, and the label then has no slot iOS
reads.

The wrong turn worth recording is the one BEFORE this. A previous round found
the same switches unnamed, correctly diagnosed an invalid `Name` — the labels
were `${camera} — ${action}` and the em-dash U+2014 is outside the character set
`util/checkName.ts` permits — and then fixed it by moving the label to
`ConfiguredName` *and* dropping the camera prefix. Only the em-dash had been the
fault. So one naming defect was traded for another, and the accompanying
docblocks asserted the new mechanism as fact ("iOS Home renders sibling services
by their `ConfiguredName`") in three files, which is what made it survive.

Six more services had the same defect and were never reported, because only the
one non-PTZ camera was looked at: every PTZ preset, the four directional
switches and the autotrack toggle.

## Decision

A service label is written to `Characteristic.Name`, and to nothing else, unless
the service type's own required-or-optional list contains the characteristic
being written. `ConfiguredName` may be used only on the five types that list it.
Every label is constructed by `service-names.ts`, which cannot return a string
that fails hap-nodejs' `checkName` pattern, and every label is derived from the
device — the child's own operator-given name, or the camera's name plus the
function — never a bare hardcoded English word.

## Consequences

- Every sibling service on a camera accessory is `<camera> <function>`, so two
  cameras no longer publish two switches called "Privacy". The camera prefix
  that the previous round removed comes back; the em-dash does not.
- `child-accessory.ts` no longer title-cases the child's `role` slug ahead of the
  child's stored name. A siren the operator called "Sirena" publishes as
  "Sirena", not as the English "Siren".
- `service-names.ts` duplicates hap-nodejs' `checkName` regex, which is
  `@private` and not exported. That duplication is a liability and is guarded
  behaviourally rather than textually — see Enforcement.
- Renaming a service changes what iOS shows but not the accessory's identity:
  the `subtype` values are untouched, so no re-pair is needed.
- **Unverified from this repo.** That `Name` is what iOS Home renders for a
  sibling Switch service cannot be checked without the Home app. What IS
  established is that the current mechanism is rejected by the library before it
  ever reaches iOS.

## Enforcement

`packages/addon-export-hap/src/mappers/builders/__tests__/service-naming.spec.ts`
builds real `Accessory` objects through the real builders and attaches a listener
to the **same `characteristic-warning` event** hap-nodejs emits into the log,
asserting the count is zero. It does not match on source text, so it catches any
future service that adds an unlisted characteristic, and it is the guard against
the duplicated regex drifting: a label this module builds that hap-nodejs would
reject fails there.

Discriminating check: reverting one call site from `Name` to `ConfiguredName`
turns 2 tests red.
