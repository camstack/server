## Context

Addons used to be grouped by policy — a subsystem decided which addons shared a
process, which meant the answer to "where does this code run?" lived somewhere
other than the addon. Two failure modes followed. Updating one addon silently
restarted unrelated ones. And the grouping applied at boot but not on later
respawns, so a hot-install or a crash-restart produced a *different* topology
than a cold boot — the hardest kind of bug to see, because both states look
plausible in isolation.

## Decision

Every addon runs in its own `addon-runner` subprocess. Co-location is opt-in and
declared by the addon itself: addons sharing an `execution.group` string collapse
into the same runner, so their cap calls resolve in-process through
`localProviderLink` with zero copy.

The runner id is resolved by exactly one function — `resolveRunnerId` in
`packages/types/src/interfaces/addon.ts` — and **every** lifecycle path calls it:
`buildAddonGroupPlan` at boot, and `ensureForkedRunner` for every post-boot
spawn (hot-install, retry, operator restart, deploy hot-reload). Updating one
group member respawns the whole group, because they share a process.

## Consequences

- Grouping is a functional decision, not a performance knob: the only reason to
  use it is that a call must not cross a process boundary. The `detection` group
  (`pipeline-runner` + `detection-pipeline` + `motion-wasm`) exists because of
  [D9](adr-0009.md).
- A node whose addons declare no group gets one process per addon, which is
  version-skew safe: they can be updated independently.
- No second generic runner may be introduced, and no grouping policy may live
  outside `resolveRunnerId`. Two resolvers would reintroduce the boot-vs-respawn
  divergence this record exists to prevent.

## Enforcement

Review only. The single-resolver property is the load-bearing part: if you find
grouping logic anywhere other than `resolveRunnerId`, that is the bug.
