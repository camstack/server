## Context

`AgentRegistryService.reconcileAgentAddons` ran on every `registerNode` ack and
did exactly one thing: `$agent.undeploy` whatever no longer belonged. It had no
opposite branch. An agent whose `<dataDir>/addons` had been emptied therefore
came back with only its bootstrap packages — `@camstack/system` plus
`camstack.agentBootstrapAddons` — and the hub never sent the rest. Measured on
the live cluster: **4 of 14 packages on `agent-a`**, and the method's very
first statement was `if (agentAddons.length === 0) return`, so a fully wiped node
was an instant no-op.

That was survivable while the image baked a seed copy of every addon into
`/opt/camstack-seed-addons` and the container entrypoint `cp -a`'d it into the
volume. It stops being survivable under the volume-only image (no addons in the
image at all), where an empty addons dir becomes the ordinary first-boot state of
every new or rebuilt node. A planned wipe test of both agent nodes was blocked on
exactly this.

The hard part was never the transport — `$agent.deploy` + `$agent.reload` already
exist and already work. It was **what the intended set is**. Two candidates were
tried on paper and rejected:

- **"Every agent-deployable package the hub has installed."** This is the
  predicate `packageHasAgentDeployable` already applies when broadcasting an
  upload, so it looked like free symmetry. It is wrong in both directions: it
  would push the hub's ~20 agent-capable packages onto a Mac that deliberately
  runs 5, and it would silently undo `nodes.undeployAddon` — an operator gesture
  that exists and works — on the next reconnect.
- **A new hub-side "assignment" table the operator populates.** This is a
  parallel map of what each node should have, invented by the hub. It is the
  shadow registry [D3](adr-0003.md) forbids, and it needs a UI and a migration
  before it holds a single true fact.

The fact that actually exists, is already durable, already hub-side, and is
already authored by the node is the node's own last declaration. `$agent.status`
reports it every reconcile; `ClusterNodeHistoryStore` already persisted a
weaker form of it (`descriptor.addonIds`) for the offline-topology rows.

## Decision

**A node's intended addon set is the package roster that node itself last
declared while online, remembered durably hub-side. The record GROWS when a node
declares a package and SHRINKS only on an explicit undeploy. The hub computes the
difference and delivers it by RPC; the node never installs its intended set
itself.**

Concretely, on each `registerNode`-triggered reconcile:

1. read the node's live roster from `$agent.status`;
2. undeploy what is stale (unchanged);
3. `recordPackages` — merge the live roster into the durable record, never
   replace it, so a node reporting 4 of 14 cannot erase its own record;
4. `prunePackages` — drop what this pass undeployed;
5. deliver `record − live` via `$agent.deploy`, then one `$agent.reload`.

The version pushed is the **hub's installed version**, falling back to the
version the node last reported. Never `latest`.

## Consequences

- **Hub-computed, node-triggered, node-authored.** The trigger stays the D3
  handshake — no timer, no scan, no readiness poll. The node remains the author
  of what it should have. The hub only remembers and answers.
- **The rejected alternative was a node-driven pull** (the node asks the hub what
  it should have, then installs from npm itself). It loses on three counts: the
  node cannot author the answer after a wipe, so the record must be hub-side
  either way and the pull is a hop with no added authority; it needs a new
  `$hub.*` Moleculer action for business logic, which the repo forbids; and it
  puts registry reachability on every agent's critical path, which is fatal on a
  packaged Electron host with no npm (`addon-installer.ts` treats that failure as
  FATAL) and reintroduces per-node version drift.
- **Version coherence comes free.** Every node lands on the hub's resolved
  version, so the cluster cannot silently fan out across `latest` resolutions.
- **A brand-new node gets nothing back-filled**, because the hub has no record of
  it. That is correct: its intended set is defined by the operator's first
  deploy, not guessed. It is also why this must ship and be observed BEFORE the
  seed is removed.
- **`nodes.undeployAddon` now has a durable side effect.** It prunes the record.
  Without that the back-fill would undo the operator on the next reconnect.
- **This is not a shadow of `HubNodeRegistry`.** That registry is the ephemeral
  capability-routing authority and stays so; nothing here participates in
  routing. The roster lives in the store that already held `addonIds`, and every
  value in it was written by the node.
- **Retries are bounded, not endless.** A `(node, package, version)` that fails
  delivery is retired after `MAX_BACKFILL_ATTEMPTS` and logged as leaving the
  node degraded — the same circuit-breaker shape as
  [`CrashSupervisor`](adr-0006.md). A different hub version reopens the breaker.
- **A malformed `$agent.status` back-fills nothing.** `extractAgentAddons`
  returns `null` (not `[]`) when the response carries no addon array, because
  "the node runs no addons" and "the node did not tell us" must not be the same
  input to a delivery decision.

## Enforcement

Unit tests. `server/backend/src/core/agent/__tests__/agent-addon-backfill.spec.ts`
pins the plan and the breaker; `agent-registry-backfill.spec.ts` drives the whole
reconcile (wiped node converges, complete node is a no-op, one-missing gets
exactly one, failure is bounded, an operator undeploy is not undone, a racing
reconcile does not double-install, a malformed status is inert);
`cluster-node-history-store.spec.ts` pins the grow-only merge and that a topology
`snapshot` cannot erase the roster.

Review otherwise. Two shapes are violations even when they work: deriving the
intended set from the hub's installed-package list rather than the node's
declaration, and making the record shrink on anything other than an explicit
undeploy.
