## Context

D42 unified scrub onto the WebRTC track and its amendment added SWEEP mode —
predicted P-frames between consecutive drag targets, engaging only while the
per-tick target delta stays inside a 4 s window, forward only. 48 hours of
feeder telemetry then measured what actually ran: **102 `mode=jump` pushes vs
3 `mode=sweep`**, and six drag-ends that delivered zero access units. The
investigation found the cause was not storage and not the feeder: the timeline
maps ~8.8 s of media per pixel at default zoom, so a careful 3 px move is a
~26 s delta — outside the window every time. ffprobe over 12 real `low`
segments showed the storage can already serve second-by-second: keyframes at
exactly 4.0 s, IDR 34–38 KB, P-frames 23 B–1.4 KB. **It was a mapping problem.**

Two constraints shape the fix. First, the camera GOP is FIXED at 4.0 s — the
operator ruled out shortening the sub-stream I-frame interval, so no future
recording will ever have a closer keyframe to land on. Second, the first scrub
of a session paid a serial chain through a saturated hub-main (profile pin →
locate, an RPC measured at 1–8 s → a `readSegmentBytes` that read the WHOLE
file against D31's letter → demux → credit arming), all between finger-down
and the first painted frame.

What was tried first and did not work is recorded in D41/D42: three pull-model
attempts, a thumbnail tier that served zero frames in production, and a sweep
mode that the px→time mapping starved of every chance to engage.

## Decision

Four rules, one per failure measured:

1. **The client maps drags by VELOCITY, not by zoom alone.** A slow, careful
   drag whose absolute mapping would overshoot the sweep window switches to a
   fine per-pixel scale (1 px = 1 s, capped at 3.5 s per sample — inside the
   feeder's 4 s window by construction); a fast drag keeps the absolute zoom
   mapping and its reach. `embed/src/scrub/drag-mapping.ts` is the single
   authority — pure, and the viewer app ports it verbatim. The timestamp label
   renders the mapped cursor synchronously from the gesture, never from frame
   arrival.

2. **The feeder sweeps in BOTH directions, and the cost asymmetry is
   permanent and explicit.** Forward: the new P-frames only (0.6–35 KB/step).
   Backward: the covering IDR plus the P-prefix to the exact frame
   (41–173 KB/step — a GOP walk per step, every step, forever, because with a
   fixed 4 s GOP there is never a closer keyframe behind). With the GOP fixed,
   this P-frame walk is the ONLY mechanism that can land between keyframes —
   it is load-bearing, not an optimisation. Beyond the window (either
   direction) the step degrades to a keyframe JUMP — the documented
   degradation, visible as `mode`/`dir`/`bytes` on every
   `scrub-feeder:pushed` line; ack-gating makes the same degradation emergent
   on a thin pipe. A whole run costs ONE credit and is repaid per rendered
   frame.

3. **Scrub reads ONE GOP by byte range** (`recording.readGopBytes`): mfra
   tail + moov head + the single moof/mdat covering the target — D31's letter
   on the D42 path. A segment whose index will not parse degrades INSIDE the
   mechanism to the whole file, logged. Playback keeps whole-segment reads: it
   consumes every byte of them, so there the file IS its byte range.

4. **A seek does not teleport — it travels, under a wall-clock BUDGET.**
   (Operator: "enable fast scrub also during jumps, for example during
   seeks; direct movements should be avoided.") The feeder animates
   [from → target] with intermediate `low` keyframes before the exact
   landing: ≤16 stills at ~60 ms, hard 1 000 ms budget — bounded by BUDGET,
   never by distance (a 4-hour and a 30-second seek animate for the same
   time). 16 not the reference's 33: our stills are full 34–38 KB keyframes,
   and 33 would be a ~10 Mbit/s burst that congests the thin links this
   serves; 16 is ~0.6 MB. Each still's fetch races the remaining budget — a
   slow hub SHORTENS the animation (lands early), it never queues; a newer
   seek abandons it instantly (latest-wins token); a scrub COMMIT never
   animates (the drag showed the travel). The landing is not optional: the
   final frame and position are the exact target. Drag-jump flings get the
   same treatment CACHE-ONLY (≤3 warm stills, zero added I/O — cold footage
   degrades to today's single keyframe). `TimelineSession` carries the
   viewer's last shown position into the fresh feeder (`travelFromMs`) so
   per-tap feeder rebuilds can still animate.

5. **The first-scrub chain is pre-run on timeline OPEN** (`{t:'warm'}`):
   locate + GOP fetch + demux into a SESSION-scoped fragment cache that
   outlives feeder rebuilds and commits (footage is immutable; only the LRU
   bound evicts). A warm drag tick consults coverage first and skips `locate`
   entirely — the 1–8 s RPC leaves the drag path. Warming never gates live,
   never builds a feeder, never moves the pointer.

## Consequences

- A slow drag now produces sweeps — asserted end-to-end (real mapping → real
  feeder) with a control that pins the causality: the same gesture under the
  raw zoom mapping is jump-only.
- Precision mode is a jog dial: the cursor detaches from the absolute finger
  position while fine. That is inherent to the fix — 8.8 s/px cannot be both
  absolute and second-granular.
- A sustained slow BACKWARD drag costs a GOP walk per second-step (~10× the
  forward bytes). The credit gate paces it to what the link renders; past the
  window it falls back to keyframe granularity rather than silently flooding.
- No new stored artefact: everything reads the `low` profile that already
  exists. The reference product's cached per-second JPEG readout remains a
  LATER option only if a slow drag still feels sparse after this lands
  (roadmap, Scrub section) — do not build it pre-emptively.
- Version skew is tolerated one step: a broker with `readGop` against a
  recorder without `readGopBytes` degrades per-call to whole-segment reads,
  logged once.

## Enforcement

The suites pin each rule with a discriminating test (removal verified red):
`drag-mapping.spec.ts` + `scrub-drag-mapping.integration.spec.ts` (rule 1 — 6
red with precision mode removed), `recorded-feeder.spec.ts` backward-sweep
describe (rule 2 — 4 red with the backward branch removed),
`gop-range-read.spec.ts` byte-accounting asserts reads in bytes against a real
segment (rule 3 — 2 red when the fragment fetch reads the whole file; 3 red
with the feeder's coverage tier removed), the seek-travel describe (rule 4 —
"more than one displayed frame AND the last position is exactly the target",
both halves asserted; 2 red with the animation removed, 1 red with the
jump-travel removed), `warm-fragment.spec.ts` + timeline-session/track-session
warm specs (rule 5 — red with the `warm` case removed). Field visibility:
`scrub-feeder:pushed {mode, dir, aus, travel, bytes}`,
`scrub-feeder:drag-end {jumps, sweeps, backSweeps, aus, bytes}`,
`recorded:seek-travel {fromMs, toMs, stills, elapsedMs}`,
`recorded:warmed {locateMs, readMs, demuxMs}` — a drag that regresses to
jump-only is one Loki query away, which is how the original defect was found.
