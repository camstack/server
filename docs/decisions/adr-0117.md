## Context

Two operator reports on the same notification, both about the same class of
mistake: a subsystem answering a question it was not asked.

**"Il video è danneggiato."** The 11:29Z timelapse for camera 101 carried an
artifact URL that served **262 bytes**. Diagnosed end to end rather than
guessed: the served bytes were `md5`-identical to the export on disk
(`59675c1d…`), and so were the 1.13 MB bytes of the next window
(`cdb5c80e…`) — so the artifact plane, the base64 crossing and the tunnel were
all byte-exact and none of them was the fault. `ffprobe` on the 262 bytes:
`nb_streams=0` — `ftyp` + `moov` + an empty `mdat`. The render had matched zero
frames (the exact-modulo `select` predicate, fixed the same day in D115), ffmpeg
had **exited 0**, and `ExportEngine.finish` stamped `state: 'ready'` on it. Every
layer downstream then behaved perfectly: the provider served it, the publisher
republished it, the dispatcher attached it, and a phone was handed a file no
player can open.

**"La copertura dice il 100%."** [The coverage says 100%.] The same notification's body read *"ATTENZIONE:
registrazione disponibile solo per il 100% della finestra"* [WARNING: recording available only for 100% of the window]. The window was
36,000,000 ms and 35,858,961 ms were covered: 141,039 ms short, so
`complete` (a 30 s absolute slack) was false — while `percent`
(`Math.round(99.608)`) was 100. The gate and the figure it printed were computed
from different things, and a warning about a complete window is worse than no
warning, because it is the line that teaches an operator to skip the line.

## Decision

**Exit 0 is not "the file holds a video".** `ExportEngine.finish` refuses an
output below `EXPORT_MIN_PLAUSIBLE_BYTES` (1 KiB): it removes the file, marks
the row `failed` with `render produced no video frames`, and emits no
`RecordingExportCompleted`. A frame-free MP4 is ~262 bytes and a real one-frame
render is kilobytes, so the floor separates them with room on both sides — and
it is a byte floor rather than an `ffprobe` call so the engine can refuse an
empty render without a second process, on any node, whatever ffmpeg is
installed.

**A figure in a notification never contradicts the gate that decided to print
it.** The coverage sentence is gated by `coverageWorthReporting` —
`!complete && percent < 100` — and not by `!complete` alone.
`FootageCoverage.complete` remains the physical fact for anything that needs
it; reporting reads the predicate.

## Consequences

- A timelapse whose window genuinely renders nothing now surfaces as
  `export-failed` in the scheduler, which leaves the (rule, camera) pair
  UNSTAMPED and eligible for the next tick — the right outcome, and a change in
  behaviour: it will retry where it used to deliver a broken file once.
- The floor is a heuristic on bytes. A legitimate export under 1 KiB would be
  rejected; no such export exists (the smallest real 640×360 h264 render
  measured here is several KiB), but if a future codec makes one, this is the
  constant to revisit — not the branch to delete.
- A shortfall between 30 s and 0.5% of the window is now SILENT in the body. It
  is still in `coveragePct` on the `timelapse produced` log line, which is
  where a per-camera question is answered anyway.

## Enforcement

Tests, all three neutralisation-checked (the fix removed, the test confirmed
red): `export-engine.spec.ts` ("marks failed and removes the file when the
render produced no frames", plus a small-but-non-empty render that must still
pass); `footage-coverage.spec.ts` and `timelapse-delivery.spec.ts` pin the
sentence at exactly 100 and at 99. No guard script — a byte floor and a
predicate are both single call sites, and both are named in the code that reads
them.
