## Context

Operator directive, 2026-08-11: *"Agent e hub dovrebbero utilizzare la stessa
infra di packages, non vedo un motivo perché debbano divergere a parte motivi
storici."* [Agent and hub should use the same packages infra, I see no reason why they should diverge apart from historical reasons.] The reason was indeed only historical.

The hub stopped loading framework builtins from a physical
`<addonsDir>/@camstack/system` on 2026-07-18 — the "single-copy collapse". It
resolves `@camstack/system` from the ACTIVE CLOSURE it is itself running and
skips the addon-root copy explicitly
(`addon-registry.service.ts`: `loadFromAddonDir(closureSystemDir)` then
`loadFromDirectory(addonsDir, ['@camstack/system'])`). The comment there states
the motive plainly: *"that copy drifted because no update channel refreshed
it"*.

The agent never got the change, and drifted exactly as predicted. Measured on
the live cluster 2026-08-11: agent-a held `@camstack/system@1.2.61` and
macmini `1.2.62` in their addon roots while both ran a `1.2.78` closure. The
hub dutifully advertised a pending update for 17 versions' worth of drift and
the number never went down, because the only thing that cleared it wrote the
copy again.

Three things kept this stable and invisible:

- `seedBuiltinsFromClosure` wrote the copy **only when absent**. It guaranteed
  a copy existed and never that it was current — a self-heal that made the
  symptom survivable and therefore permanent.
- It contradicted `AddonInstaller.shouldSkipClosureProvidedSeed`, which already
  refused to plant that copy *for this exact reason* ("Measured 2026-08-03: both
  agents on a 1.2.0 copy…"). One module refused to create the thing another
  module re-created on the next greenfield.
- [D87](adr-0087.md) had made the copy load-bearing: deleting it left the node
  with no infra at all, so the copy could not simply be removed. That is a real
  constraint and it is what this record dissolves, rather than works around.

**The wrong turn.** Earlier the same day the stale copies were diagnosed as
inert residue and deleted from both agents, on the strength of the launcher's
`resolved @camstack/system@1.2.78 from <activeRoot>/…` line. That line reports
which copy the LAUNCHER resolves for its own imports; `bootCoreAddons` scans the
addon root and nothing else — a different consumer reading a different copy.
Recoverable only because the retired self-heal would have re-seeded at the next
boot. [D45](adr-0045.md) says a version is a property of a path; the corollary
this cost is that **a path is only evidence about the consumer that reads it.**

## Decision

An agent resolves `@camstack/system` from the running closure and loads the
builtins from there, then scans its addon root with that package skipped —
byte-for-byte the hub's sequence. `planAgentAddonScan` (`agent/addon-scan.ts`)
owns the decision as pure data so it is testable without a broker, the same
extraction `infra-boot-plan.ts` got after 2026-08-08.

The skip is a **correctness** requirement, not tidiness: `AddonLoader` keys its
map on `declaration.id`, so loading both the closure and a stale copy through one
loader is last-load-wins, and which builtins a node runs would depend on `readdir`
order.

When the closure cannot be resolved, the copy is NOT skipped and the node boots
from it. A node with neither source must fail through the D87 guard, which names
every required capability it could not resolve — never through a silent "no addon
packages found" early return.

`seedBuiltinsFromClosure` is deleted. It exists only to guarantee a copy that
nothing reads any more.

## Consequences

`@camstack/system` stops appearing in an agent's `listUpdates`, because the roster
is built from `loadedAddons` and now reports the closure's version. The number
reaching zero becomes true instead of merely reachable.

A server release is now the *only* way an agent's builtins change, which is the
point — and it means an agent's infra can no longer be updated independently of
its runtime. That was never safe anyway: a 1.2.61 builtins copy against a 1.2.78
closure is a version pair nobody tests.

`@camstack/system` stays in `AddonInstaller.AGENT_PACKAGES` and
`AGENT_BOOTSTRAP_PACKAGES` stays protective. Both are last-resort paths for a
closure-unresolvable node and are spec-pinned; removing them is a separate
question this record does not open.

The stale copies already on disk become inert but are still adopted by
`AddonManifest.reconcileFromDisk`, so a node-local manifest keeps reporting the
old version until they are removed. Cosmetic, and cleaned up separately —
**after** the node in question is verified running this code, never before.

## Enforcement

`server/backend/src/agent/__tests__/addon-scan.spec.ts` — six cases. Removing the
closure-first plan fails two (the live 1.2.61-vs-1.2.78 shape, and the greenfield
node whose scan must stay non-empty); removing the skip-list match fails three.
Both verified by deleting the code and re-running.

`infra-boot-guard.spec.ts` still pins the both-sources-absent abort. Nothing
guards the ORDER of the rollout below — that is review only, and it is the part
that can gut a node:

1. This change ships alone, and both agents are verified booting from the closure
   (`getNodeInferenceDevices({nodeId})` → `reachable: true`, and the boot log's
   scan list naming the closure dir).
2. Only then: the hub-side refusal of a framework package aimed at an agent, and
   the rewrite of the `cap-providers.ts` comment that currently — correctly —
   forbids exactly that guard.
3. Only then: removal of the stale addon-root copies.

Shipping 2 before 1 breaks the only builtins channel an agent on old code has.
Shipping 3 before 1 is the 2026-08-07 gutting, verbatim.
