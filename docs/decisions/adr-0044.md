## Context

The table map (`docs/design/2026-08-03-storage-table-map.md`) found seven ways to
reach the database that are not the capability. The remediation plan written the
same day answered "one door" — and meant the `settings-store` cap itself. That
answer is wrong in a way that is easy to miss: `settings-store` is *the SQL
addon's own cap*. Unifying on it makes SQLite the interface rather than an
implementation, which is the opposite of the requirement that produced the work
(*"non si deve mai accedere al db puntualmente, perché un giorno potremmo
cambiare db"* [the DB must never be accessed point-wise, because one day we might change
DB]).

The right shape already exists in this repo, for files:

```
storage (public singleton) ── storage-orchestrator ──▶ storage-provider (internal, collection)
                                                              └── filesystem-storage
```

Structured data skips that middle box entirely. 102 `settingsStore.*` call sites
talk to the engine's addon directly.

The two bypasses that cost the most are both symptoms of having no owner to add a
method to:

- **The `settingsBackend` tRPC router** was built so forked workers could reach
  structured storage, re-exposing eight methods on an arbitrary
  `collection: z.string()` with **no namespace field**, bridged to every forked
  addon. The consumer it was written for was never built: zero callers, and any
  addon could have read or written any other addon's collection through it.
- **`ensureTable` plus six `table*` methods** are a second SQL surface reachable
  by holding the concrete provider object, which four consumers do — owning seven
  tables the generated map could not see. `tableDelete(table, filter)` has
  existed there the whole time, which is why *every* retention path in the system
  is an N+1 drain loop: the door lacked a bulk delete, so callers went around it.

Both were built because there was nowhere else to put the thing that was
missing. A door that cannot express what callers need does not stay the only
door; it becomes one of several.

## Decision

**The storage addon is the only public entry point for data — files and rows
alike — and every storage engine sits behind it as a capability registrant.**

- `storage-orchestrator` owns the public surface. `sqlite-settings` declares an
  **internal collection cap** (`data-store-provider`, the sibling of
  `storage-provider`) and nothing else public.
- Nothing outside `storage-orchestrator` holds a concrete provider object, a
  `Database` handle, or an engine import. A second tRPC router onto storage is
  not a transport, it is a rival API, and there is not one.
- **A missing query capability is fixed on the door, never beside it.** Bulk
  delete and update, aggregates, an expression grammar past equality,
  transactions and batch insert, and schema introspection belong on the cap. The
  bypass list is the evidence for what happens otherwise.
- A collection declares which **engine** serves it, and the orchestrator routes
  on that. A vector store is therefore a second registrant, not a second door.

## Consequences

- **It costs nothing on the hot path.** Both are `@camstack/system` builtins and
  boot in-process on hub-main (`addon-registry.service.ts:866`), so the
  delegation is a function call. A forked addon still pays exactly one UDS hop,
  the one it pays today.
- **A non-builtin engine registrant would pay a real hop**, and that is the
  deliberate trade: the boundary exists so the engine is replaceable. An engine
  that cannot afford the boundary is an argument for co-locating it as a builtin,
  not for reopening a direct path.
- `settings-store` keeps its name and its 102 call sites through the topology
  change; the rename to `data-store` / `ctx.data` is a separate mechanical
  commit. Mixing a behaviour change with 102 sites of churn makes a regression
  unattributable.
- The name is on notice regardless: the collection holds motion events,
  embeddings, media and tracks. It has not been about settings for a long time.
- **Every future capability lands on one surface**, which is wider than a
  minimal store would be. That is the accepted cost. The alternative was
  measured: six gaps, seven bypasses, and a `zoneCrossing` field that was
  declared, computed, and never reached disk because the door dropped unknown
  columns in silence.

## Enforcement

Partially guarded today, and the gap is worth stating plainly.

- **Generated and checked:** `docs/reference/storage.md` is regenerated on every
  commit and CI fails on drift, so a new table or creation path cannot land
  unnoticed. `npm run codegen` is authoritative for the cap routers.
- **To be written** (roadmap, storage section): a `scripts/` guard covering every
  route to the engine — `better-sqlite3`, `node:sqlite` **and** direct `.db`
  access — allowlisted to the storage builtins only. One import name is false
  assurance: `scripts/migrate-auth-caps-only.ts` uses `node:sqlite`, and the
  originally-proposed guard would have missed it.
- Nothing yet enforces "no second tRPC router onto storage". The `settingsBackend`
  deletion is the precedent; review is the current bar.
