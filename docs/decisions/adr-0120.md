## Context

A live audit of one rule (`Persona su Uscio`, device 101, media
`{attach:'best', frame:'full', gif:true}`) over 15 fires: **11 notifications
carried both attachments, 3 shipped GIF-ONLY, 1 image-only**. The operator's
question was the obvious one — why does the same rule on the same camera
sometimes arrive without the picture?

The order of the dispatch answered it. `resolveAttachments` resolved the still
FIRST, at the instant the outbox row drained, and then rendered the footage —
which blocks the same dispatch for 7–8 s while the broker waits out the
post-roll. The subject's own media (`keyFrame`) lands **1.5–5.5 s after the
trigger**. So the still was read one second too early, found nothing, and was
never read again, while the very same dispatch then stood still for long enough
that the keyframe arrived, was written, and sat there unused. The picture
existed before the notification was sent. Nobody looked.

Three smaller findings from the same audit:

- `framePreference('full','track')` was `['keyFrame','keyFrameSmall',
  'firstFrame']`. One track only ever held a `lastFrame` — a clean full scene of
  the same camera, stored, and unreachable. The ladder's strictness is about
  FAMILY (clean vs boxed vs crop), which `lastFrame` and `snapshot` do not
  violate; it stopped one rung short of the honest answer.
- One row straddled an addon restart and drained 45 s late. Both cut sources read
  the same retained clip buffer (`CLIP_RETENTION_SEC = 25`), so the render could
  only fail — and it failed twice, in two log lines that describe a broker fault
  rather than the queueing delay that actually happened.
- The delivered log line said nothing about attachments, and the dropped-footage
  line was `debug`. Reconstructing which of the 15 notifications carried what had
  to be done by hand, from media rows and timestamps.

## Decision

The still is resolved **as late as the dispatch is already waiting**, and a
dispatch that drops media the rule asked for says so.

1. When the first still resolution returns null and a footage render was
   ATTEMPTED, the ladder is run again after it. The wait already happened; the
   second look costs one media read and no latency.
2. When NO footage was requested there is nothing to piggyback on, so the ladder
   is polled for `NC_STILL_WAIT_MS` (3 s at 500 ms) and then abandoned. Bounded,
   and skipped entirely for a subject with no media owner or one older than
   `NC_STILL_WAIT_MAX_AGE_MS` — those cannot gain anything from waiting.
3. `framePreference('full','track')` ends `…, 'firstFrame', 'lastFrame',
   'snapshot'`. Every rung is a clean, unannotated whole scene; the family rule
   is unchanged.
4. `notification delivered` carries `attachments: ['still','gif',…]` and, when
   the rule asked for something that did not ship, `dropped: [...]`. A failed
   footage render is a WARN.
5. A row whose footage window has aged past `NC_CLIP_RING_RETENTION_SEC` is not
   rendered at all: it logs `footage window expired while queued — shipping
   without` once, with the age, and ships the still.

## Consequences

- A notification whose rule wants a picture and no footage can now arrive up to
  3 s later than before when nothing is stored for it. That is the price of the
  picture, it is bounded, and the alarm is never held beyond it.
- `NC_CLIP_RING_RETENTION_SEC` mirrors a constant in another addon
  (`stream-broker-manager`). Raising the broker's retention without raising this
  one means the centre refuses a cut the broker could still serve. It is stated
  in the doc comment; nothing enforces it across the package boundary.
- Two log lines are now part of the contract with the operator
  (`attachments` / `dropped`). The live audit that produced this record is only
  repeatable because they exist.
- Still OUT of scope: the outbox is not drained on shutdown, so a row enqueued
  seconds before a restart still loses its footage — it now says so instead of
  blaming the broker. Draining on shutdown is the real fix and is a separate
  piece of work.

## Enforcement

Tests, and they are neutralisation-verified — removing the re-resolve fails
`a keyframe that lands DURING the render is still attached`, and removing the
`lastFrame` rung fails both ladder tests:

- `packages/addon-post-analysis/src/notification-center/__tests__/dispatcher-still-rescue.spec.ts`
- `packages/addon-post-analysis/src/notification-center/__tests__/frame-preference.spec.ts`
