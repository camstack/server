## Context

Every camera-configuration capability — `ptz`, `osd`, `stream-params`,
`motion-zones` — needed a device-detail settings form. Each vendor provider
therefore hand-wrote three methods: `getDeviceSettingsContribution`,
`getDeviceLiveContribution`, `applyDeviceSettingsPatch`. With four vendors and a
dozen such capabilities that is a large amount of near-identical code whose only
job is to restate, in an imperative form, information the cap definition already
declares. It also drifted per vendor, so the same capability rendered differently
depending on which camera you opened.

## Decision

A `scope: 'device'` camera-config capability declares the **`deviceConfig`
archetype**:

```ts
deviceConfig: { ui: { kind: 'derived-form' } }   // or { kind: 'widget' }
```

The framework derives the device-detail contribution and the save routing from the
capability's existing surface — `getOptions` / `getStatus` / `set<X>`. Vendor
providers carry none of the three contribution methods.

`deviceConfig` and `exposesDeviceSettings` are mutually exclusive: the second is
the older escape hatch for ad-hoc settings UIs.

## Consequences

- The capability surface becomes load-bearing for the UI, which makes the
  `getOptions` availability convention mandatory: a provider must advertise what a
  given camera actually supports (`hasZoom`, `{min,max,step}`, `codecs: [...]`),
  probed from the camera, never hardcoded. A dishonest `getOptions` now renders a
  control that does nothing.
- Adding a vendor to an existing config capability requires no UI work.
- `ui.kind: 'derived-form'` needs a registered `builderId`; `'widget'` embeds a
  single live component instead.

## Enforcement

Codegen: `scripts/codegen.ts` auto-injects the framework methods from the cap
definition, so a hand-written contribution method on a `deviceConfig` provider is
dead code rather than an override. Review catches it; `npm run codegen:check` in
CI catches the drift that follows from skipping codegen.
