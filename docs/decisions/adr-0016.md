## Context

Hub and agent were separate packages. They shared the kernel, the transport, the
addon loader, the update mechanism and the starter — that is, everything except a
handful of boot decisions. Two packages meant two publish paths, two version
numbers that had to be compatible, and two copies of the stage/apply update engine
that could drift. The update engine drifting is the dangerous one: it decides
whether a node comes back after a restart.

## Decision

One root package, `@camstack/server`. A node's role is the `CAMSTACK_ROLE`
environment variable, defaulting to `hub`. The stage/apply engine lives once in
`@camstack/node-root` (`RootUpdateService`) and both roles bind their own
parameters to it — the hub via `ServerUpdateService`, which supplies the
`@camstack/server` root spec, the `CAMSTACK_SERVER_*` env markers and the data-dir
default.

The framework travels **inside the root package's dependency closure**. Addons
live in `<dataDir>/addons` and travel separately.

## Consequences

- A framework change (`@camstack/types`, `@camstack/system`, `@camstack/sdk`,
  `@camstack/ui-library`) reaches a node **only** through a root-package install —
  `applyServerUpdate`, or "Update all nodes" in the Admin UI — pinned to the exact
  version the published `@camstack/server` carries. `camstack deploy` cannot ship
  it. This has bitten us: a fix in `@camstack/system` was believed deployed when
  the running `@camstack/server` still pinned the previous `system` version.
- Publishing a framework fix therefore means publishing `@camstack/server` too,
  even when nothing in `server/backend` changed.
- `@camstack/node-root` is bundled into each starter and never published.

## Enforcement

`scripts/ci/pin-root-deps.mjs` in the publish workflow pins the closure. Beyond that,
review — and `docs/reference/packages.md`'s "Reaches a node via" column, which
exists to make this distinction visible without reading the Dockerfile.
