## Context

[D52](adr-0052.md) routed the CLIP embedding rebuild through
`pipelineRunner.runDetailSubtree` so that ONE crop derivation serves both the
live detail plane and the rebuild. That part was right and is preserved. What it
did not survive was contact with how cameras actually run.

`runDetailSubtree` resolves its step tree from the **live attach state**
(`resolveChildSteps` → `null` when the camera is detached). That is correct for
it: its reason to exist is a frame HANDLE, and a handle is only resolvable while
a decode session is open. But cameras run `detectionMode: 'on-motion'` — they
attach when motion fires and detach ~30 s later — so a pass walking historical
tracks at an arbitrary time finds most of the fleet detached. The first full pass
on the live hub:

```
scanned 1125   rebuilt 121   missingKeyFrame 391   missingBbox 12   notRunnable 601
runDetailSubtree: camera is not attached — no detail steps to run
  {parentClass=person requestedSteps=["clip-embedding"]}
```

A later pass the same day: 3,611 scanned, 198 written, 2,598 refused. And the
refusals were not free. `loadSource` called `mediaStore.listByOwner`, which reads
and base64-encodes **every** blob a track owns (23 files / 7.67 MB / ~10 MB of
string on one measured track) to `.find()` two — and it paid that **before**
runnability was known. Roughly 90% of the pass's I/O and allocation bought
nothing, on hub-main's single thread: measured busy 82.2 s out of 120, 42 s
inside uninterrupted 2–7.3 s synchronous blocks, with `nodes.topology` degraded
from 0.25 s to 26 s for the 43 minutes the pass ran.

Three alternatives were rejected:

- **A mode on `runDetailSubtree`.** Its `deviceId` is load-bearing twice over —
  it mounts the method on `DeviceProxy` and it routes the call to the camera's
  owning node. One input field would have silently selected between two routing
  tiers and two step-resolution strategies, and its `null` return (the rebuild's
  only signal) would have had to mean different things in each. That is the
  shape D52 itself warns about: a fix that reads as verification.
- **Attaching the camera for the duration of the rebuild.** Attachment exists to
  make frame handles resolvable. A caller that supplies its own frame needs none
  of it, and temporarily mutating live placement races the orchestrator.
- **Letting each node resolve its own model.** Step model config is
  per-(node, device) (`DeviceStepConfigSchema.modelId`), and
  `resolveModelForFormat` **substitutes** a model with no build for the node's
  format with that format's default — silently, with one info line. A pass
  round-robining across nodes would then fill one index from several encoders:
  D52 recreated one level down, and this time with nothing in the stored data to
  hint at it.

## Decision

Bulk enrichment over stored media runs through `pipelineRunner.runStatelessStep`:
image bytes, a normalised box and a step id, resolved from the **catalog**, on
whichever node the caller pins with `nodePin` — no attach, no handle, no device
affinity. Three rules bind it:

1. **The crop derivation stays single.** The stateless path cuts through
   `detail-subtree.ts`'s `cutFromFullFrame`, the one permitted caller of
   `deriveDetailCropRect`, with the one cluster-wide convention. It never
   imports the derivation itself.
2. **ONE model is pinned for the whole pass and sent with every request, and a
   node that cannot serve that exact model REFUSES** — `model-not-servable`,
   counted and logged — rather than substituting. A node that answers with a
   different `modelId` is retired from the pass and its vector discarded.
3. **The cheap question is asked before any media is read.** "Can this pass
   still dispatch anywhere" is answered from memory, per track, before
   `loadSource`; and `loadSource` reads metadata plus exactly one blob, never
   the whole track.

Node selection is plain round-robin over the online fleet, with an optional
operator override (`executeOnNodeId`). Deliberately NOT the balancer's node tier:
its lexicographic tie-break is right there and is a starvation bug here, because
every candidate scores 0 at dispatch for work that lasts a second.

## Consequences

- A decommissioned or permanently detached camera's tracks are rebuildable
  again. The `notRunnable` counter no longer means "camera not attached" — it
  now means the stored media is unusable — so a pre-2026-08-06 reading of that
  number is not comparable with a later one.
- `RebuildOutcome` gains `noCapableNode`, distinct from `notRunnable`: it answers
  "could this work be done at all" rather than "was this track done". It is
  terminal for the pass and always comes with `complete: false`.
- The rebuild will not START without a resolvable CLIP model. The previous
  `?? 'unknown'` stamped rows with a model id nothing ran, which the search gate
  cannot reason about.
- Nodes only ever LEAVE the rotation, never rejoin it. A node that was briefly
  unreachable sits out the rest of the pass; the alternative is re-paying its
  failure once per track. Departures are logged with reasons and summarised at
  the end.
- The pass yields between tracks (`pacingMs`, default 50 ms). It costs wall-clock
  on a job that already runs detached, and it is the only thing standing between
  bulk maintenance and hub-main saturation.
- The stateless path does NOT do the step-tree device jump: the jump roster lives
  on the attach config. Steps run on the node's default engine — acceptable for
  maintenance, and it is why the format the servability check verifies is exactly
  the format the dispatch uses.

## Enforcement

`scripts/check-clip-crop-single-owner.ts`, extended twice for this change: the
stateless path and the rebuild's request builder are added to `NON_CUTTER_FILES`,
and the image-library check now also matches `lazy-sharp` — the helper this repo
ACTUALLY imports sharp through. Before that, a check looking only for
`from 'sharp'` would have waved through every real cutter in
`packages/addon-pipeline`: green and blind.

Tests, each verified to go red when its fix is removed:
`packages/addon-pipeline/src/pipeline-runner/__tests__/stateless-step.spec.ts`
(the refusal never dispatches; the crop matches `deriveDetailCropRect` under a
non-default convention);
`packages/addon-post-analysis/src/pipeline-analytics/__tests__/rebuild-step-dispatch.spec.ts`
(rotation spreads, a wrong `modelId` retires the node, a mid-pass dropout costs a
node not a track, an empty fleet answers without calling);
`.../__tests__/rebuild-source-loader.spec.ts` (exactly one blob, read after the
event resolve — a cost assertion, because cost is invisible in the result);
`.../__tests__/embedding-rebuild.spec.ts` (no media touched when there is nowhere
to dispatch; the yield happens on skipped tracks too).

Not enforced by a guard: that a future caller of `runStatelessStep` remembers to
pin a model. The cap makes `modelId` required, which is the strongest structural
answer available — a caller can still pass a value it resolved per-call.
