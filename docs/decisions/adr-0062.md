## Context

The operator asked (2026-08-05) for a switch per camera per pipeline function —
audio detection + classification, object detection + event tracking, stream
broker, notifications, recording — presented as one group.

The obvious build is a `Record<switchId, boolean>` per camera, written by the
group and read by the group. **That is the shape of the two knobs this repo has
already shipped that were unreachable**, because each wrote a store the reader
never read: the per-device settings knob that wrote `addonSettingsRaw` while a
forked addon read `<addonId>:addon-devices`, and the `disableInference` flag
that lived in a map the resolver did not consult. A second switch that disagrees
with the first is worse than no switch — it tells the operator a camera is on
when it is off.

Surveying first found that four of the five functions already had exactly one
authority, and that the repo had **already decided** what a per-camera function
on/off is: `legacy-migrations.ts` migrated the legacy `audioEnabled`,
`pipelineEnabled` and `motionDetectionEnabled` booleans ONTO
`deviceManager.setWrapperActive`. What was missing was not state. It was a
surface.

Two smaller failures came out of the same survey and are part of what this
record fixes:

- `CameraStatus.audio.enabled` was a **hardcoded `true`** returned whenever an
  audio node assignment existed. A camera whose operator had turned audio off
  reported enabled audio and produced nothing — indistinguishable, on every
  surface, from a camera whose analyzer had died.
- `setCameraStepToggle({ addonId: 'audio-classifier', enabled: false })`
  persists and stops **nothing**: the audio subscription is gated by
  `audioMode` and the `audio-analysis` binding, and the resolved `audio` block
  the toggle produces is never consulted by `subscribeAudioStream`. The group
  therefore does NOT surface it. (The defect itself is untouched here and
  recorded in (planning repo: sessions/sessions.md).) <!-- drift-ok: moved to the private planning repo -->

## Decision

**A per-camera function switch never stores its own state. It reads and writes
the authority that already owned the function, and `CameraSwitch.authority`
names which one.** Adding a switch means finding that authority, not adding a
map; if a function genuinely has no authority, add one where the function lives
and route to it — never in the group.

| Switch | Authority | The gate that proves OFF stops the work |
| --- | --- | --- |
| `stream-broker` | `deviceManager.setDisabled` | `StreamBrokerManager.reconcileAllCatalogs` releases the brokers; `ensureBroker` refuses re-creation |
| `object-detection` | `deviceManager.setWrapperActive('detection-pipeline')` | `PipelineSettingsStore.resolvePipelineForDevice` returns `{ steps: [], audio: null }` |
| `audio-analysis` | `deviceManager.setWrapperActive('audio-analysis')` | `AudioSubscriptionController.subscribeAudioStream` returns `null` before opening the stream |
| `recording` | `recording.setDeviceConfig` → `RecordingConfig.enabled` | `band-decision` returns false and `RecordingController` detaches the device |
| `notifications` | `notificationRules.setDeviceMuted` | `NotificationCenter.evaluateAndEnqueue` returns before any rule is evaluated |

Four consequences of that rule are not optional:

1. **Availability is derived, never hardcoded.**
   `deviceManager.listBindableCapsForDeviceType` decides whether a switch is
   offered at all, and a capability with no registered wrapper is not a switch —
   nothing could apply it.
2. **A source that did not answer is `available: false`, never a control
   defaulted to on.** Guessing renders a switch the operator believes is on that
   is not.
3. **Recording flips `enabled` and nothing else.** `bands` is the only authored
   intent and `mode` is derived from it; clearing bands to express "off"
   destroys the operator's schedule, and turning the camera back on would then
   silently record nothing.
4. **Every switch off is REPORTED off.** `CameraStatus.switchedOff` carries the
   ids an operator turned off, and every status surface must render that
   differently from a failure. A camera producing nothing because somebody
   switched it off must not look like one that is broken.

**Notifications is the one function that had no authority**, and it gets a
purpose-built one rather than a widened snooze: `NC_DEVICE_MUTES_COLLECTION`,
admin-only, indefinite. A snooze is bounded at 24h deliberately — "a snooze that
could not expire would be an outage the operator asked for once and forgot" —
and stretching it to carry a permanent silence would take that property away
from every snooze.

## Consequences

- The group is a read fan-out over four sources. `getCameraSwitches` costs one
  bounded parallel round of `getDevice` + `getBindings` +
  `listBindableCapsForDeviceType` + `recording.getDeviceConfig` +
  `notificationRules.listDeviceMutes`. `CameraStatus` now pays the same fan-out
  once per camera to fill `switchedOff`; the mutes call is list-shaped for
  exactly this reason (a per-camera fan-out over the viewer's single WebSocket
  is N frames on one socket).
- The group cannot express a state its authority cannot. There is no "detection
  off but tracking on", because there is no store that would hold it.
- Two surfaces (admin UI, viewer) render from one server-side composition, cost
  lines included — a cost line duplicated per client is one that will disagree
  with itself.
- A new switch is a new `CameraSwitchAuthority` variant. The `switch` in
  `resolveState` and in `applyWrite` is exhaustive, so adding one without
  wiring both is a compile error.
- **What this deliberately excludes:** snapshot capture, face recognition and
  plate/LPR as separate switches. Face/LPR run through
  `setCameraStepToggle`, whose gate is proven for VIDEO steps only — and the
  `audio-classifier` counter-example above is why "it is the same mechanism" was
  not taken on trust. They belong in the pipeline editor until someone proves
  their gates the way these five are proven.

## Enforcement

Tests, at three altitudes, plus the compiler.

- `packages/types/src/interfaces/__tests__/camera-switches.spec.ts` — the pure
  derivation: capability-derived availability, an unreadable source never
  defaulting to on, `switchedOff` never naming an unavailable function.
- `packages/addon-pipeline-orchestrator/src/__tests__/camera-switch-service.spec.ts`
  — routing: each switch writes its authority and only its authority; recording
  leaves `bands` byte-identical; an unavailable switch is refused rather than
  persisted.
- `packages/addon-pipeline-orchestrator/src/__tests__/camera-switches-e2e.spec.ts`
  — through the REAL addon: the group's buttons land on the resolved pipeline,
  the runner attach payload and the audio subscription map.
- `packages/addon-post-analysis/src/notification-center/__tests__/device-mute-gate.spec.ts`
  — a muted camera enqueues nothing, for every subject kind, and the drop is
  logged at info with `tags: { deviceId }`.
- `packages/addon-pipeline-orchestrator/src/__tests__/camera-status-audio-enabled.spec.ts`
  — `audio.enabled` follows the switch. It exists as a separate file because the
  end-to-end assertion could not reach the block, and a guarded
  `if (status.audio !== null)` would have passed against the lie.

The exhaustive `switch` over `CameraSwitchAuthority` is the compiler's share.
There is **no guard script**: "the group stores nothing" is not mechanically
checkable, so it rests on the record and on review.
