## Context

The detector emits a cyclist as two independent detections. Measured by running
the pipeline on the stored media of device 102 track `9eaa0320`, at 1280x720:

```
person   0.720  x=1122 y=204 w=70 h=164
vehicle  0.572  x=1112 y=271 w=79 h=139   ← the bicycle, under the rider
```

Both clear their floors (0.65 / 0.50) and the boxes overlap by 58% of the
person. The tracker took them as two subjects, so one passer-by on a bike
produced a `person` track AND a `vehicle` track — and which one a notification
rule saw depended on which detection won association that frame. A rule on
people fired for a cyclist; a rule on vehicles counted them as a car.

Three options were on the table. Leaving both tracks was the status quo and is
what produced the ambiguity. Calling the pair a PERSON matches "there is a human
there" but makes every cyclist trip a pedestrian rule, which is not what an
entrance rule is for. The operator chose VEHICLE, with both entities kept on the
record.

## Decision

When a `person` detection is riding a two-wheeler, the RIDER is dropped before
the tracker and the machine is kept: the passage is tracked once, as a vehicle.
The fold is RECORDED on the surviving subject as `Track.hasRider` — a
composition note, not a class — and logged with both scores, the overlap and the
fine class.

### Amendment, 2026-08-14 — the record gap this ADR claimed was closed

As originally written this record said the person half "is recorded rather than
silently disappearing", and the code said the same in a comment. **Neither was
true.** The pair went into `FrameProcessor.lastRiderPairs`, a per-processor RAM
field, and out through `getLastRiderPairs()` into ONE `logger.info` line. It
carried `{overlap, personScore, vehicleScore, vehicleClass}` — scores, not
entities — and nothing about the person reached the track row, the event row,
the notification or the timeline. Every durable surface said `vehicle`, full
stop. A record that describes the right design and does not do it reads as
verification of it, which is the failure this repo names first.

Closed by making the fold name the SURVIVING TRACK
(`FrameProcessorResult.riderFolds`, resolved through the tracker's bbox-object
reference) and stamping `Track.hasRider` on it. A fold the tracker did not emit
a track for that frame (below `minHits`, or stationary-gated) still ships
WITHOUT a `trackId` and is logged as such: the drop is now sayable, which it
never was.

`hasRider` is a COMPOSITION and deliberately not a fourth class axis. "This
vehicle contains a person" is not an answer to "what is this" — both label tiers
would refuse a macro token anyway (D89), correctly. It changes nothing about
what the subject IS: one vehicle track, occupancy counts one, and a
person-scoped rule still does not fire for someone cycling past. Absent ≠ false,
exactly like `hasFace`.

A pair qualifies only when all three hold:

1. the vehicle's ORIGINAL (fine) class is a two-wheeler — `originalClass`
   survives the macro mapping, so a person beside a CAR can never qualify;
2. a real share of the person's box lies over the vehicle's;
3. the person's centre sits ABOVE the vehicle's — a rider is on top of the
   machine, which is what separates them from a pedestrian walking in front of
   a parked bike.

## Consequences

- A cyclist no longer triggers a person-scoped rule. That is the point, and it
  is a behaviour change an operator can be surprised by: a rule meant to catch
  "someone at the door" will not fire for someone arriving by bike.
- Occupancy counts a rider as one vehicle, not one person plus one vehicle.
- Dropping the RIDER rather than the machine is deliberate: the machine is the
  larger, more stable box and the one that keeps existing when the rider
  dismounts.
- Condition 1 makes this dependent on `originalClass` continuing to survive the
  macro mapping. If a future model or class map stops populating it, the pairing
  silently stops — it fails toward the old two-track behaviour, not toward a
  wrong fold.

## Enforcement

`packages/addon-post-analysis/src/pipeline-analytics/pipeline/__tests__/rider-pairing.spec.ts`
— 12 tests against the measured boxes above, including the parked car in that
same frame as the distractor that must never pair, a walker with identical
overlap but a lower centre, and two bikes that must not both claim one rider.

The RECORD half (the amendment above):
`packages/addon-post-analysis/src/pipeline-analytics/pipeline/__tests__/rider-fold-record.spec.ts`
pins that the fold resolves to the surviving vehicle's track and that a fold
with no surviving track still ships so the drop can be logged;
`packages/addon-post-analysis/src/pipeline-analytics/store/__tests__/track-store-has-rider.spec.ts`
pins that the note survives the expiry-time persist, the late patch and the slim
projection, and that absent stays absent.

Review only beyond that: no guard can tell a correct fold from an incorrect one
without ground truth.
