## Context

Removing a feature removes its readers, not its rows. The keys stay in the
settings store, nothing consults them, and nothing breaks — which is precisely
the failure mode: **a dead key is indistinguishable from live configuration
until you trace the reader.**

On 2026-08-07 an audit read `object-detection: yolo26m-256` out of
`detection-pipeline:addon-settings` row `root`, key `pipelineSteps`. That key is
a global step seed removed months earlier; the live per-camera dispatch path has
never consulted it. An hour went into investigating a package-zone fault against
a model the node was not running. Eleven keys in that one row were dead, and one
of them (`pipelineEngine`) was literally `null`.

The obvious remedy — delete the rows on the box — cleans exactly one machine
exactly once. A fresh node seeds them again through whatever wrote them, and any
restore of a backup taken before the delete brings them straight back. The
codebase had already tried the cheaper alternative, a comment: *"Old stores may
still carry the keys; they are simply ignored."* That comment was true and it
did not stop the hour.

## Decision

A configuration key whose feature was removed is declared in
`RETIRED_SETTINGS_KEYS` — `(namespace, collection, row, keys, perNodeKeys,
reason)` — and **deleted at every HUB boot** of the settings engine, before
anything can read it. Never a hand `DELETE`, never a "kept for compatibility"
reader, never a comment saying the key is ignored.

**It runs on the hub and nowhere else.** The addon settings store is hub-central:
`settings-store` is a `singleton` cap that resolves to the hub, so every node's
`ctx.settings` reads and writes the HUB's rows. An agent's own SQLite file holds
node-local collections only — measured 2026-08-07, neither agent even has a
`detection-pipeline:addon-settings` table. There is exactly one copy of the data
to clean, so running the machinery at every node's boot is work that can never
find anything. The gate is `settingsStoreIsAuthoritativeHere(env)`, mirroring
`resolveNodeRole` (unset or `hub` ⇒ hub), and an agent skips **silently** — a
"skipped" line on every agent boot forever is noise about work with no reason to
happen there. An unrecognised role also skips: a missed cleanup is fixed by the
next hub boot, a write to a store this node does not own is not.

This scoping is specific to the settings store and does NOT generalise. The
addon manifest (`{dataDir}/addons/manifest.json`, [D79](adr-0079.md)) is
genuinely PER-NODE state — each node has its own addons directory and its own
manifest — and its reconcile must keep running everywhere. Verified the same
day: the agent's manifest carried seven corrections of its OWN installs that the
hub's manifest knew nothing about.

The purge is idempotent, silent when the store is already clean, and logs exactly
one line naming the addon, the row and the keys when it actually deletes. Match
is **exact**, plus the `<key>@<nodeId>` form for `perNodeKeys` — never a prefix
or substring, because `videoPipelineSteps` is live and must survive the
retirement of `pipelineSteps`. A read that FAILS never writes (same rule as
`settings-read-guard.ts`): rewriting a row from a failed read replaces live
configuration with nothing.

Only add a key you have traced to having no reader. The `@<nodeId>` suffix is
not evidence of deadness — `probedBestHwaccel@<node>` and
`probedBestAudioBackend@<node>` are live.

## Consequences

- The hub's store converges, and a restored backup is re-cleaned on the next hub
  boot. There is no "clean machine" and "dirty machine".
- If an addon store ever becomes genuinely per-node, this gate becomes wrong and
  the registry needs a per-spec scope instead of one global one.
- The registry is a CLAIM that a key is dead, and nothing verifies it. A wrong
  entry deletes live configuration on every node at once — which is why the
  match rule is exact and why the reason field is mandatory.
- The purge lives in `@camstack/system`, so it ships on the framework train, not
  through `camstack deploy`.

## Enforcement

`src/builtins/sqlite-storage/__tests__/retired-settings-keys.spec.ts` — the
exact-match rule is pinned with fixtures that contain a retired key verbatim
(`videoPipelineSteps` escapes a naive `includes` only by capitalisation, so it
alone is not a discriminating test), plus convergence, silence-when-clean, and
"a failing read never writes" against a real `SqliteSettingsBackend`. The
registry itself is review-only. The hub gate is covered for hub / unset / agent
/ unrecognised role, plus a "does not read, does not write, says nothing"
assertion on the agent path — removing the gate fails that test.
