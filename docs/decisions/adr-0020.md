## Context

A log destination for Grafana Loki can be built two ways.

**Promtail** (or its successor, Grafana Alloy) is a *file tailer*: a sidecar process
watches log files and ships what it parses to Loki. It is the documented path for
applications that only know how to write to disk.

**Loki's own ingestion API** — `POST /loki/api/v1/push` — takes structured entries
directly.

CamStack is not an application that only knows how to write to disk. Every entry
already exists in memory, structured, at the moment it is emitted: level, scope,
tags, meta. `LogManager` fans it to every registered `log-destination`. Writing
that to a file so a separate process can parse the structure back out of a text
line loses information and adds a process to deploy, configure and monitor.

Promtail is also end-of-life — Grafana deprecated it in favour of Alloy in 2025.
Building a dependency on a deprecated shipper to reach an API we can call in twenty
lines would be an odd trade.

## Decision

The `loki-logging` builtin pushes to `/loki/api/v1/push` itself, batched. No
sidecar, no file intermediary.

**Labels are only `job`, `node` and `level`.** Everything per-entry — `scope`,
`message`, `tags`, `meta` — goes in the line body as JSON, queryable with `| json`
at query time. Loki indexes labels and every distinct label-value combination is a
separate stream with its own chunks; high-cardinality labels are the documented way
to bring a Loki cluster down. The policy caps it at `4 × nodes` streams.

**Opt-in through config-default inertness**: `enabled: false` and an empty `url`,
either of which makes the destination inert. The provider registers regardless, so
the Logging page can list it and an operator can turn it on without restarting
anything.

## Consequences

- Anyone who *does* run Promtail or Alloy loses nothing: the `winston-logging`
  destination still writes rotated files to tail. The destinations are independent
  and both can be on.
- The destination must **never log** — it is on the logging path, so one log line
  from it becomes a push, which logs, which becomes a push. It therefore reports
  health through `getStatus()` for the UI instead of through log lines, and it does
  not throw out of `write()` either, because `LogManager` fans one entry to every
  destination and a throw would take the siblings with it.
- Queue is bounded (10k, oldest-dropped). A logger that OOMs the process it is
  observing is worse than one that loses lines, and during an incident the newest
  lines are the ones being read.
- `query()` returns empty. Reading back would mean implementing LogQL; Loki is a
  shipping destination and Grafana is its reader. The Admin UI's log viewer reads
  the in-memory ring buffer and the rotated files.

## Enforcement

`packages/system/src/builtins/loki-logging/__tests__/` — 34 tests, including that
labels are exactly `job`/`node`/`level`, that entries are sorted within a stream
(Loki rejects out-of-order), that `write()` never throws, and that the queue bound
drops oldest-first.

The never-log rule is review-only. It is stated at the top of
`loki-destination.ts`, and `hub-forwarder` carries the same warning for the same
reason.
