## Context

The hub used to *discover* what a node could do: a timer fired, scanned the
registry, and assembled a picture of the cluster's capabilities. This has a
boot-race window by construction — between a node finishing boot and the next
sweep, its capabilities exist but the hub does not know it. The symptom was
capabilities that "appeared a moment later", which invites exactly the wrong fix:
a retry loop, a `[100, 500, 2000]` backoff, a `waitFor` helper. Every one of
those makes the window smaller and permanent.

## Decision

A node pushes its **complete** capability manifest once its boot finishes, via
the `$hub.registerNode` / `$agent.registerNode` RPC, retried until acked.
`registerNode` replaces that node's entire capability set atomically. The hub
never guesses completeness and never scans.

Reconnect is the same single call — re-handshake, not a resync protocol.
`HubNodeRegistry` is the sole authority: the union of registered manifests minus
disconnected nodes.

## Consequences

- Zero boot-race window. The acceptance criterion is literally "native caps are
  present in the hub registry immediately after the handshake acks".
- Liveness and discovery are Moleculer's job: `$node.connected` /
  `$node.disconnected` and `broker.waitForServices`. Do not re-implement them.
- No shadow registries. A `knownAgents` map, a `remoteNativeCaps` pull cache or a
  hydrate-on-reconnect layer would each reintroduce a second source of truth that
  can disagree with the first.
- Because registration must not be lost, it is an RPC. This is the general rule
  from [D8](adr-0008.md): broadcasts are lossy, so anything whose loss corrupts
  durable state cannot be an event.

## Enforcement

Integration tests in `packages/system/src/kernel/__tests__/moleculer/` assert the
no-race property and same-nodeId reconnect. Review otherwise: a timer or a retry
backoff added "to wait for a node to be ready" is a violation of this record even
when it works.
