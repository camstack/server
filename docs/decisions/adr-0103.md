## Context

The `/addon/:addonId/*` catch-all gates two surfaces — the addon-route registry
and the HTTP data plane — and it had two disagreeing answers to the same
question.

A `cst_` scoped token needed an `addon:<addonId>` grant. **A JWT needed nothing
but a valid signature**, plus `isAdmin` when the route said `access: 'admin'`.
Every OAuth account-linking token, every SSO hand-off token and every login-leg-1
challenge verifies under the same hub secret, so "the signature is good" had
quietly come to mean "this is an API credential for anything".

Measured on the live hub 2026-08-09, with a probe chosen to actuate nothing (a
malformed command topic, which the domain layer answers `422 malformed topic`
after a single parse — reaching it proves auth PASSED without touching a
camera):

| Bearer | `POST /addon/homeassistant-export/command` |
| --- | --- |
| none | `401 Unauthorized` |
| admin session JWT | `422 malformed topic` |
| **`oauth-access` token minted for `export-alexa`** | **`422 malformed topic`** |
| **`oauth-code` (60 s, single-use, travels in a browser redirect URL)** | **`422 malformed topic`** |
| **`oauth-refresh` (30 d, belongs to `/token`)** | **`422 malformed topic`** |
| `cst_` with `capability:device-manager` | `403 Token scope mismatch` |
| `cst_` with `addon:homeassistant-export` | `422 malformed topic` |
| `cst_` with `addon:export-alexa` | `403 Token scope mismatch` |

That route actuates PTZ, reboot, the per-camera switches and notification
snooze. A token issued to Alexa drove Home Assistant's controls, and so did an
authorization code. `access: 'admin'` routes held throughout (`403 Admin
required`), and `/trpc` held too — its scope matcher answered
`No scope grants view on 'device-manager' … Have: category:device[view,create]`.
The hole was the `authenticated` tier of the addon surface, and nothing else.

It is **pre-existing**: `git log -L` on the branch dates it to the initial commit
(2026-05-21), touched since only by the 2026-06 biome/oxlint migration.

Two related facts surfaced with it. Revoking an OAuth session does **not** stop
its access token on this path — measured: `oauthVerifyAccessToken` returned
`null` while the same token still answered `422` — because nothing re-reads the
session on the JWT path. And `scopesAllowDeviceCap` lived in `@camstack/system`,
which addons may not import, so `addon-export-alexa` had hand-copied it into
`directive-router.ts` twice, each copy carrying a comment admitting as much.

## Decision

**A bearer JWT is classified before it is trusted, and an integration token is
confined to the addons its grant names.**

`classifyBearerPrincipal` splits a verified payload three ways: a **session**
(no `kind` claim), an **integration token** (`kind: 'sso-bridge'`,
`provider: 'oauth-access'`), and **not-a-credential** (every other bridge
provider and every other `kind` — codes, refresh tokens, TOTP challenges, SSO
hand-offs). Then:

- a **session** passes exactly as before — the route's own `authenticated` /
  `admin` level governs it, and nothing about non-admin viewers changes;
- an **integration token** must hold `addon:<addonId>` at the access the HTTP
  verb asks for (`GET`→`view`, `POST`/`PUT`/`PATCH`→`create`, anything else
  →`delete`), which is the rule the `cst_` branch already applied. Its `isAdmin`
  claim is ignored;
- **not-a-credential** is refused unconditionally, `401`.

Every refusal logs its reason.

The derivation — `scopesAllowDeviceCap`, `scopesAllowAddon`,
`methodAccessForHttpMethod`, `classifyBearerPrincipal`, `principalMayReachAddon`
— lives in `@camstack/types` so the kernel, `server/backend` and addons share
ONE copy. `@camstack/system` re-exports it; Alexa's hand-copies are deleted.

**Consequently `OauthIntegrationDescriptor.requestedScopes` has exactly one
meaning: what the integration NEEDS to function.** Not a blast radius, not a
conservative under-declaration. It was being used to mean two different things
across two integrations; the operator ruled there is one. It is now the
enforcement input, so an under-declaration is a broken integration — the honest
response to a route that refuses is to widen the descriptor with the call that
justifies the entry, never to weaken the check.

Home Assistant therefore gains `addon:homeassistant-export [view, create]`,
justified by the `/command` route its component POSTs every actuated entity to.
Alexa gains nothing: both of its hub-side routes are `access: 'public'` and
authenticate the bearer themselves via `oauthVerifyAccessToken`, so neither
traverses this gate. `category:system [create]` stays rejected for both — it
would hand `addons.installPackage` to a home-automation bridge.

The same principle extends to lifetime: `refreshTokenTtlSec` on the descriptor
(seconds, or `'never'` for no `exp` claim; absent means the 30-day default). The
value is baked into the authorization code at consent and carried on the tokens,
so editing a descriptor changes future links only.

## Consequences

- **Order of shipping is load-bearing.** The widened Home Assistant descriptor
  must be LIVE before the enforcement is, or every HA control answers
  `403 Token scope mismatch` in the gap, and any link created before the
  widening carries the old scope set and must be re-linked. Descriptors ship by
  `camstack deploy`; the gate ships in the `@camstack/server` closure.
- The `authenticated` tier keeps admitting any user session. This is deliberate:
  requiring `addon:<id>` of sessions too would lock non-admin viewers out of
  recorder playback, snapshot media and the stream-broker embed — a worse
  outcome than the hole, and not what was measured to be wrong.
- An integration token still reaches every `authenticated` route of an addon it
  is granted, not a chosen subset. Per-route scope declarations would be finer;
  they are not built, and the addon boundary is the unit the vocabulary already
  has.
- **A `'never'` refresh token is permanent access if it leaks.** What bounds it
  is revocation, not time — `oauthRefresh` and `oauthVerifyAccessToken` re-read
  the session and refuse once `revokedAt` is set. The session check in
  `oauthRefresh` must therefore never become optional or cached.
- **Revocation is still not immediate on the JWT paths.** An access token
  remains usable for its remaining hour on `/trpc` and `/addon/*` after the link
  is revoked, because neither re-reads the session. That hour is why the access
  TTL stays fixed at 3600s and is not configurable. Closing it means routing
  `provider: 'oauth-access'` JWTs through the session store on every request —
  a hot-path read that wants its own decision.
- A throw from an addon's own route handler used to be reported as
  `401 Invalid token`, because the handler call sat inside the token-verify
  `try`. It no longer does.

## Enforcement

- `packages/types/src/__tests__/principal-scope.spec.ts` — the derivation,
  including the exact live-hub scenario, and the "unknown verb fails closed"
  case.
- `server/backend/src/auth/__tests__/addon-route-authorization.spec.ts` (D892) — the gate,
  including that sessions are unaffected and that every refusal logs.
- `server/backend/src/__tests__/oauth2-account-linking.spec.ts` — asserted over
  the SHIPPED descriptors: Home Assistant declares the addon route it posts to,
  Alexa declares none, and each declares the refresh lifetime it needs. A future
  edit that drops either fails here.
- `packages/system/src/builtins/local-auth/__tests__/oauth-refresh-lifetime.spec.ts`
  — the per-descriptor lifetime, asserted with values that DIFFER from the
  default, plus the revocation bound on a `'never'` token.
- Nothing checks that a NEW integration's descriptor lists every addon route it
  calls. That is review only, and the cap docblock says so.
