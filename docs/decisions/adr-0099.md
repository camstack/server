## Context

This is the fourth record about the same snapshot, and the first three are why it
is worth reading.

[D93](adr-0093.md) established the design: the image URL carries the frame
identity from the cache-only `getSnapshotOverview`, and an image REQUEST is what
enrols a camera in the keep-warm loop. [D94](adr-0094.md) fixed a device with no
frame never being requested. [D95](adr-0095.md) fixed the identity freezing when
the socket that carries the overview drops.

Each of those closed a way for the request not to happen, and each was correct.
None of them could close the last one, because it is not in our code at all.
`expo-image` is URL-keyed and never revalidates — D93 says so in its own text —
so a URL this app painted in a PREVIOUS SESSION is served from disk with no
network. No request. Therefore no enrolment, therefore no warming, therefore an
overview that keeps reporting the same identity, therefore the same URL, forever.

Measured on the live hub, cold, from the operator's exact scenario (app reopened
after the 120 s warm window lapsed): **15 of 16 tiles painted at 168.7 s old, max
177 s, with zero HTTP requests.** The operator's report — "ho snapshot vecchi; se
aggiorno arriva uno più recente ma non il più recente; devo aggiornare più volte"
[I have old snapshots; if I refresh a newer one arrives but not the newest; I have to refresh several times]
— is that measurement. Each manual refresh mints a new URL, which finally
produces a request, which finally enrols the camera; a few refreshes later the
warm loop has caught up.

The tempting fixes were all wrong in the same way. Shortening the warm interval
does nothing when nothing is enrolled. Letting `getSnapshotOverview` create
subscriptions is exactly what D93 forbids and for a reason that still holds: that
poll is app-wide, so a creating overview warms every camera on the install.
Making the URL unique per paint works and costs a full re-download of sixteen
unchanged tiles every five seconds on a phone.

The general shape of the mistake is worth naming, because D94 already stated half
of it ("when a request is what enrols a resource, the absence of that resource
can never be the reason to skip the request") without noticing the other half:
**a request is only a demand signal if it is guaranteed to be MADE**, and an
HTTP GET for a cacheable URL carries no such guarantee.

We also checked whether the frames being decoded for detection could feed this
cheaply, and they cannot: `RetainedFrameStore` lives in the forked `detection`
runner (the snapshot wrapper is hub-main), holds ≤640 px RGB for ~0.6–3 s, has no
"latest handle for device N" accessor, and `detectionMode` defaults to
`on-motion` — so for most cameras, most of the time, there is nothing decoded to
ride. The ffmpeg ladder and its `MAX_CONCURRENT_GRABS` pacing stay.

## Decision

The signal that a client is watching a resource travels on a path **no client
cache can satisfy** — an RPC — and never on the fetch of the resource itself.

Concretely: `snapshot.getSnapshotLinks` is both the demand signal and the answer.
It notes every target it is asked about (creating a keep-warm subscription, which
`getSnapshotOverview` still may never do), joins the ordinary non-forced capture
path, waits a bounded 2.5 s for what it triggered, and returns a signed expiring
link plus `capturedAt`/`ageMs`. The client stops inferring freshness and is told
it.

Only a MOUNTED surface may appear in `targets`, at the width it actually paints.
That is what keeps a creating call affordable, and it is the same constraint D93
imposed on the overview, relocated rather than relaxed.

## Consequences

- `getSnapshotOverview` keeps its cache-only, renew-only contract unchanged. Two
  methods now exist with deliberately different powers, and the difference is not
  "one is newer": the overview is app-wide, the links call is per-surface.
- The links poll and the server's warm interval are coupled (both 5 s) for the
  same reason the overview poll was.
- A **public** data plane now serves camera frames, authorised by an HMAC and an
  expiry rather than a session. What sits behind it is a live view of the
  operator's home, so: the TTL is 120 s, the width is inside the signed identity
  (a leaked 240 px tile cannot be escalated to the full frame), and `force` is
  dropped on that route entirely so a public URL can never wake a battery camera.
  A leaked link grants one camera, at one thumbnail width, for at most the TTL.
- `exp` is bucketed to 30 s so an unchanged frame remains a byte-identical URL.
  A per-mint-unique URL would also fix the freshness bug and would re-download
  every tile on every poll; the bucketing is what keeps the cache useful.
- A sleeping battery camera reports `sleeping: true` and its last frame, however
  old, and is not captured. The wrapper's existing sleep gate owns that and gains
  no second opinion — a rule that disagrees with the authority it duplicates is
  what D93 warned about.
- Age is now expressible. Nothing on the tRPC path carried a capture time before
  this, which is why a two-minute-old frame could render as current with nothing
  able to contradict it. `stale` is never invented: an unknown age is not a
  stale one.
- Rollout is a NEW METHOD, not a new field, and that is deliberate. An additive
  input field is silently stripped by the hub router's compiled Zod until the
  train lands (`includeCrops` was inert for a day); a missing method is a clean
  NOT_FOUND, which `capQuery` degrades to `supported: false` and the entire
  D93/D94/D95 path underneath. Ordering the ship chain wrong costs nothing.
- The signed-URL HMAC is now one derivation in `@camstack/types/node`. The
  notification artifact plane and the HA media plane each carried a byte-identical
  copy, correctly reasoning that addons never import each other and wrongly
  concluding that the crypto had to be restated; a framework package is a place
  every addon may depend on. Both now delegate.

## Enforcement

- `packages/system/src/builtins/snapshot/__tests__/snapshot-links-integration.spec.ts`
  replays the cold reopen against a real `SnapshotAddon`: the warm loop goes
  quiet, an overview poll captures and enrols nothing, and the links call does
  both — plus the sleeping-battery camera that must not be captured, and the
  minted link that must refuse escalation, replay and tampering. Removing the
  `subscriptions.note` / `awaitFreshEnough` pair turns it red (verified).
- `packages/system/src/builtins/snapshot/__tests__/snapshot-link-url.spec.ts` —
  the URL moves when the frame moves and only then; expiry, width and device are
  all inside the signature.
- `packages/types/src/utils/__tests__/expiring-url-signature.spec.ts` — expiry is
  checked before the constant-time compare, so a leaked link dies on its own.
- `camstack/src/data/__tests__/snapshot-media-url.spec.ts` — a link wins over the
  identity-versioned form, and a null link falls back byte-identically.
