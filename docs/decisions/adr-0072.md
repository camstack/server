## Context

[D49](adr-0049.md) was written on 2026-08-06 because camera 101's virtual
doorbell had eaten three real presses: the ring path re-derived its binding via
`deviceManager.getBindings`, got an answer that omitted its own activation, and
dropped the press. The fix was a mirror refreshed off the event path, where a
negative read only ARMS a revocation and a second consecutive negative applies
it. Its whole argument was that a real unbind is permanent and a store blip is
not, so **repetition** is the discriminator when the response itself cannot be
graded.

On 2026-08-07 at 10:40:47 UTC camera 101 dropped a real press again:

```
virtual-doorbell: ring DROPPED — the wrapper is not bound to this camera,
but a trigger source is still configured for it   {bindingState=unbound}
```

The binding was intact the entire time. `deviceManager.getBindings({deviceId:101})`
over tRPC returned `{capName:"doorbell", kind:"wrapped", providerAddonId:"virtual-doorbell",
providerNodeId:"hub"}`, and the durable store held
`deviceBindings["101"] = {"doorbell":{"wrapperAddonId":"virtual-doorbell"}}`.

**The cause is not a store blip, and it is not `getBindings`.** It is
`AddonContext.id`. The two addon-context factories spell it differently and
nothing says so:

| where | `ctx.id` |
| --- | --- |
| forked addon (`kernel/moleculer/addon-context-factory.ts`) | `virtual-doorbell` |
| hub-main builtin (`server/backend/src/core/addon/addon-registry.service.ts`) | `addon:virtual-doorbell` |

`virtual-doorbell` is a builtin; it runs in hub-main. Its gate read

```ts
entry.providerAddonId === this.ctx.id     // 'virtual-doorbell' === 'addon:virtual-doorbell'
```

which is false for every entry that has ever existed. Verified on the live
closure (`@camstack/server@1.2.70` carries ``id: `addon:${addonId}` ``,
`@camstack/system@1.2.57` carries the raw `===`), and against the live tRPC
answer, which is correct.

So D49's corroboration corroborated nothing. **Two systematically wrong reads
agree with each other.** The mirror walked `bound → unbind-pending → unbound`
twice in twelve hours, and there was no way back: only a positive read (which
could never happen) or `confirmBindingFromCapCall`, i.e. the operator opening
the settings page. That is a latch, and it silently disarmed a doorbell.

Three separate things had to be true for this to survive:

1. **The suite could not see it.** The fake supplied `ctx.id = 'virtual-doorbell'`
   — the bare form production never has. This is the third time in this repo a
   test has passed because the fake supplied the value production got wrong.
2. **The log could not answer it.** The revocation line said `from`/`to` and
   nothing else. A systematic wrong answer and a genuine unbind produced
   byte-identical lines, so twelve hours of them read as an operator action.
3. **The defect is invisible per-process.** The same source file is correct in
   a forked runner and wrong in hub-main. Nothing in review distinguishes two
   strings both named like addon ids.

Two more instances of the same defect were found while fixing this: a `linked`
binding entry published `providerAddonId: ctx.id` (i.e. `addon:device-manager`,
which no consumer can route), and the snapshot addon logged a data-plane URL
of `/addon/addon:snapshot/media`.

## Decision

**Three rules, in the order they matter.**

1. **`ctx.id` is never compared to, or published as, a registry/store addon id
   without normalisation.** `bareAddonId` / `isSameAddonId` in
   `@camstack/types` are the only spelling. Every field an addon might match
   against — `providerAddonId`, `wrapperAddonId`, `nativeAddonId`, capability
   registry keys, `/addon/<id>/…` routes — carries the manifest id.

2. **A gate that can DESTROY work reconciles against the DURABLE authority, not
   only against a view derived from it.** For the doorbell that authority is
   the `device-manager` addon store's `deviceBindings` map, read directly
   (`addonSettingsRaw.getGlobal({addonId:'device-manager'})`) — the row the
   operator's toggle actually writes, with no registry resolution,
   `defaultActive` auto-binding or cluster cap-folding in between. That read
   also grades its own trustworthiness, which the derived view genuinely
   cannot: a store answering from an empty snapshot ([D44](adr-0044.md)) has no
   `deviceBindings` key at all, whereas a real unbind leaves the key present
   and merely omits the row. `bound` / `unbound` / `unreadable` — and
   `unreadable` never revokes anything.

   Concretely: a POSITIVE derived read is still believed immediately; a
   NEGATIVE one is never believed until the durable authority agrees. The
   authority wins in the direction that destroys work.

3. **A mirror that says "drop this" is not the last word on a one-shot event.**
   D49 forbade all I/O on the ring path. That was right about the read it had —
   the same fallible derived read that caused the problem — and wrong as a
   general rule. The ring path now performs **no I/O when the mirror is open**
   (unchanged, and still pinned by a test), and exactly ONE durable-authority
   read on the single branch that would otherwise drop a press. A ring is rare,
   a query is cheap, and a dropped ring has no retry, no reconcile and nothing
   downstream that notices.

   And every negative — refresh or drop — logs the entries it was actually
   handed plus the id it matched with, tagged `deviceId`.

## Consequences

- **`unbound` is no longer terminal.** The mirror reconciles on every
  assignment-reload cycle regardless of its current verdict, so a camera
  returns to `bound` on its own the moment the authority says so. No operator
  click is part of any recovery path.
- **A wrong derived view is now survivable AND loud** — the wrapper rings, and
  says at `warn` that the two sources disagree. That line is a defect report,
  not weather; if it appears, something between the store and `getBindings` is
  broken and D72 is masking it.
- **One extra query per dropped ring.** Only on the drop branch. The happy path
  is byte-identical to D49.
- **A genuine unbind still silences the camera**, after two corroborated
  negatives, and now prints the entries and the addon id it used — so the next
  investigation starts from evidence instead of from a verdict.
- D49's mechanism is superseded; its Context — *why a `getBindings` response
  cannot be graded* — is still correct and still the reason the derived view
  alone is not enough.

## Enforcement

- **Guard.** `scripts/check-addon-id-comparison.ts`, wired into
  `.github/workflows/ci.yml`. Scans `packages/system/src/builtins/**` and
  `server/backend/src/**` — the trees whose code runs in hub-main, where the
  prefix exists — and fails on a raw `ctx.id` equality, a hand-rolled
  `addon:` strip, or a `providerAddonId`/`wrapperAddonId`/`nativeAddonId`
  assigned from an unnormalised `ctx.id`. Confirmed to reject the exact
  production line it was written for.
- **Tests.** `packages/system/src/builtins/doorbell/__tests__/binding-mirror.spec.ts` <!-- drift-ok: deleted in slice 6 (D671), task 17 -->
  pins the pure predicates; `virtual-doorbell.addon.spec.ts` pins the four
  properties that matter — *"a persistently negative derived read never
  silences a camera the store still binds"*, *"a mirror already latched
  unbound rings again once the store says bound"*, *"a durable authority that
  cannot answer never destroys a press"*, and D49's surviving
  *"the ring path still does NO I/O when the mirror is bound"*.

  **The fake now supplies `ctx.id = 'addon:virtual-doorbell'`** — the
  production value. That single line is what the old suite got wrong.

  Both fixes were confirmed to go red when removed: reverting
  `entriesBindWrapper` to a raw `===` fails the mirror spec; neutering the
  durable-authority read fails five addon-spec properties.
