## Context

D96 measured the hub-main freezes (6.2 s – 27.2 s inside one 28-minute window)
down to the WAL checkpoint rather than the write, and ranked its levers. Lever 1
was the only one that removed the cause:

> **Get `camstack.db` off the FUSE share.** Every other number here is arithmetic
> on top of the 43x shfs multiplier. This is an operator change, not a code
> change.

**That change has been made.** Measured on the live hub, 2026-08-14:

```
$ df -hT /mnt/cache/appdata/camstack/addons-data/sqlite-settings
Filesystem     Type   Size  Used Avail Use% Mounted on
/dev/nvme1n1p1 btrfs  472G  261G  192G  58% /mnt/cache

$ docker inspect CamStack   (mounts)
bind  /mnt/cache/appdata/camstack  ->  /data   RW
```

`/data` is bound **directly** to `/mnt/cache/appdata/camstack`, so the container
never touches shfs at all — `docker exec CamStack df -h /data` reports the same
`/dev/nvme1n1p1`. The pool is btrfs **RAID1 across two devices**:

```
$ btrfs filesystem show /mnt/cache
	devid 1 size 465.76GiB used 291.03GiB path /dev/nvme1n1p1   (WD SN550 NVMe)
	devid 2 size 476.94GiB used 291.03GiB path /dev/sdd1        (SATA SSD)
Data, RAID1: total=274.00GiB, used=257.10GiB
```

The WAL is healthy at 5.0 MB against `wal_autocheckpoint = 1000` (≈4.1 MB) —
the normal steady state, and far from D96's pathological 15–33 MB range.

**The thing that was tried first and did not work is the part worth recording.**
D96 named the cost of the move in advance:

> Relocating the database off shfs changes the backup story: Unraid's Appdata
> Backup walks the share, and a cache-only path is outside it. That has to be
> arranged before the move, not after.

It was not arranged. But the failure did **not** arrive by the predicted
mechanism, and that matters, because acting on the predicted mechanism would
have fixed nothing:

- the share is `shareUseCache="prefer"`, `shareCachePool="cache"`, and
  `/mnt/user/appdata/camstack` **does** resolve through shfs;
- the plugin's `allowedSources` lists **both** `/mnt/user/appdata` and
  `/mnt/cache/appdata`, and `globalExclusions` is empty.

The path was never the problem. The problem is one line in
`/boot/config/plugins/appdata.backup/config.json`:

```json
"CamStack": { "skip": "yes" }
```

`ABHelper.php:319` drops a skipped container before selection, and the last run's
log confirms it — `CamStack` does not appear in `Selected containers`, and no
`CamStack.tar` exists in any backup run. The only camstack data captured is the
`/config` bind (`config.yaml`, via `includeFiles`). **No DB, no addons-data.**

The one DB backup that does exist is CamStack's own backup-orchestrator
(`backup_schedules`: cron `0 3 * * *`, retention 7), and it writes to
`/data/backups` — which is `/mnt/cache/appdata/camstack/backups/`, **the same
btrfs pool as the database it is backing up**.

## Decision

**`camstack.db` lives on the NVMe cache pool (`/mnt/cache/appdata/camstack`),
deliberately and permanently. D96's lever 1 is CLOSED.**

No design may reason from the 43x shfs multiplier for this database again. Every
write-volume argument that used it as its premise — checkpoint cost, commit
budgets, "offering commits to the checkpoint lottery" — now sits on top of a
direct NVMe write and must be re-derived before it is used to justify
conservatism. Reducing writes to `camstack.db` is still worth doing on its own
merits; it is no longer worth doing on D96's arithmetic.

**RAID1 is not a backup, and the pool holding the only copy is not a backup
either.** A mirror covers a dead drive. It does not cover a bad write, a bad
migration, or an `rm` — which are the three things that have actually threatened
this database. A copy of `camstack.db` must exist on storage that is not the
cache pool.

## Consequences

- **OPERATOR ACTION, OPEN.** Flipping `"CamStack": {"skip": "yes"}` to
  `"skip": "no"` in `/boot/config/plugins/appdata.backup/config.json` is the
  one-line fix. Note before doing it: `/mnt/cache/appdata/camstack/` also holds
  ~3.3 GB of loose `.tar.gz` / `.db` blobs, which would land in every nightly
  tar unless excluded — and the appdata dir includes the orchestrator's own 7
  rolling backup tarballs (164–266 MB each), so an unfiltered run would back up
  the backups.
- Until that is done, the honest statement of the risk is: **a cache-pool loss
  takes the database and every copy of it at the same time.** The
  backup-orchestrator's nightly tarball is real and does contain
  `addons-data/sqlite-settings/camstack.db`, but it is stored beside the
  original.
- The June `preswap` / `rekey-bak` snapshots that used to sit in the DB
  directory were deleted on 2026-08-14 (9.2 MB, 45 days old, referenced by no
  code). They were never a restore point — they predate the analytics growth —
  and a stale `camstack.db.*` sibling next to a live SQLite file reads as
  corruption to whoever greps that directory during an incident.
- `VACUUM` remains the wrong tool and is not implied by any of this: the file is
  99.83 % live data (freelist 146 pages of 86,675), so a vacuum would reclaim
  ~600 KB while taking a global write lock. The file is large because
  `pipeline-analytics:tracks` carries 114 MB of JSON position arrays — a
  retention and shape question, not a slack question.

## Enforcement

**Nothing automatic, and that is worth stating plainly.** Both halves of this
record live outside the repository: the mount layout is Unraid/docker
configuration, and the backup coverage is a plugin's JSON on the USB flash. No
guard, codegen check or test in this repo can observe either, so nothing will
tell you when it regresses.

What that means in practice: the backup gap above was introduced by an operator
change that D96 explicitly warned about, and it went unnoticed for as long as
nobody looked. Treat "is `camstack.db` in a backup that is not on the cache
pool" as a question to re-ask by hand — when the storage layout changes, when
the Appdata Backup plugin is reconfigured, and after any greenfield rebuild of
the container — rather than something the repo will answer for you.
