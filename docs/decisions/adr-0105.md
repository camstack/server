## Context

A capability call reaches a provider by one of two routes, and they are written
by different code. The hub's tRPC cap-router (`cap-router-builder.ts`) serves
calls arriving over HTTP. A forked addon's `ctx.api.<cap>.<method>` instead
reaches its parent's `onUnownedCall`, which classifies the call with
`resolveCapRoute`.

`resolveCapRoute` takes `nodeId` and `deviceId`. `CapRouteOpts` has no other
field. So every other routing selector a caller supplies is discarded — not
rejected, not logged, discarded — and the call is answered by whichever provider
the resolver happens to pick.

For a `mode: 'collection'` cap that is decisive, because its providers own
DISJOINT resources. The hub's router routes such a call by the `{ addonId }`
selector the codegen injects on every method of a system-scoped collection cap
(`broker.getBrokerConfig`'s own input schema declares only `{ id }`). The child
path dropped it, so the call landed on the first-registered provider — for a
resource that provider does not own, whose honest answer is `null`.

Measured on the live hub, 2026-08-09:

```
hub,   getBrokerConfig {id:'ha_001'}                       → null
hub,   getBrokerConfig {id:'ha_001', addonId:'provider-…'} → the config
addon, getBrokerConfig {id:'ha_001', addonId:'provider-…'} → null
```

The third row is the finding: from an addon the PINNED call returns exactly the
UNPINNED answer. Home Assistant's export half read Homematic's `null` for
`ha_001`, could not tell it from "no such broker", and never opened a link — for
as long as the feature had existed. Nothing was wrong with the pin, the addon,
or the provider.

**What was tried first, and cost the most.** The pin was blamed. A session
concluded the pins deadlocked the provider's own boot and reverted all eight of
them; the provider did not come back, because it had never been running (a
different fault, [D29](adr-0029.md)). Every write-up of this pin — the package's
`CLAUDE.md`, `ha-broker-source.ts`, and `check-collection-cap-pin.ts`, which
*enforces* it — had been validated against the first two rows only. A selector
measured on one route and asserted on both is not measured.

This is the second instance. `callCollectionAggregate` exists because the same
two paths disagreed about array methods: routing picked one provider while the
router returned the union, and `notification-output`'s empty answer made the
Notification Center dead-letter every notification it ever produced
(2026-07-30). The pattern is not "collection caps are tricky". It is that a
routing rule written in one path does not exist in the other.

**Amended the same day, before anything depended on this record.** The first fix
was written into `onUnownedCall` alone, shipped, and changed nothing on the live
hub. `LocalChildRegistry` decides FIRST whether a child's egress is
short-circuited to a local sibling, and for `broker` it always was —
`resolveChildId` picks the first-registered provider of the cap NAME, so
`onUnownedCall` was never invoked and the fix inside it was unreachable. The
same class of bypass already existed three lines away, for array methods. What
settled it was not more reading: a probe called `getBrokerConfig` with a
DELIBERATELY BOGUS `addonId` — refused if the selector routes, `null` if it is
discarded. It returned `null`. **A rule that spans two decision points must be
implemented at the first one; verifying the fix means exercising the real
caller, not the function you changed.**

## Decision

A routing selector the tRPC cap-router honours must be honoured on the
child→parent path **by calling the router's own resolution code**, not by a
second implementation of the same rule — and it must be honoured at **both**
decision points that path has: `LocalChildRegistry`'s sibling short-circuit,
which runs first and can end the call, and then `onUnownedCall`'s routing.
Neither package holds a cap registry by design, so each rule is a pair of
injected hooks over ONE shared predicate — today `isAggregatedCollectionMethod`
+ `callCollectionAggregate` for the array union, and `isAddonPinnedCall` +
`callPinnedCollection` over `addonPinOf` for `{ addonId }`, all delegating to
`resolveCollectionProvider`.

Two limits are part of the rule, both paid for:

- **An enumeration is never pinned.** Its contract is already the union, so a
  pin converts a provider's absence from "returns fewer rows" into a throw. That
  took an operator from "one Home Assistant instance" to "no instance at all".
- **Only an EXPLICIT top-level selector routes.** The router's nested-`addonId`
  recovery reads a domain payload against a known schema; this path has no
  schema and must not guess.

A selector naming a non-provider REFUSES, listing the registered ids. Silently
answering from another provider is the defect, not the fallback.

## Consequences

Adding a routing rule to the cap-router is now a two-site change, and the second
site is not optional — a rule added to only one path is a live bug that
type-checks, passes review, and shows up months later as a wrong answer rather
than an error. The hook shape keeps the kernel free of the cap registry, which
is what let these two paths drift in the first place; it does not remove the
obligation, it makes it cheap.

The hook's result must be BOXED (`{ value }`). `getBrokerConfig` answers `null`
legitimately, so an unboxed `null` cannot be told from "not handled" and falls
through to routing — reinstating the exact defect. There is a test for that
specific mistake.

Any measurement of a routing selector is invalid unless taken from the surface
the caller actually uses. An addon's behaviour is measured from an addon.

## Enforcement

Tests, at both sites, verified discriminating: removing the handler call fails
two of the four kernel tests (`parent-unowned-call.spec.ts`), and the two that
still pass are the ones asserting the fall-through. The server side pins the
refusal, the boxed `null`, the array-method exemption and the non-collection
exemption (`pinned-collection-call.spec.ts`).

No guard catches a NEW router rule that is never mirrored — a script cannot tell
which branches of `cap-router-builder.ts` are routing rules and which are
payload handling. Review only, which is why the obligation is written here.
`scripts/check-collection-cap-pin.ts` still enforces that callers pin an
id-keyed collection call; it asserts an intent, and as of this record the
transport finally implements it.
