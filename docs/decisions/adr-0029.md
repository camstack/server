## Context

Every solitary runner carries a fixed floor — after [D28](adr-0028.md) about
**80MB RSS** of Node + Moleculer + UDS transport + the `@camstack/types/addon`
subpath — before its addon does any work. The hub ran ~22 solitary runners, so
the floor alone was ~1.7GB of pure per-process overhead. [D2](adr-0002.md)
already provides the lever (`execution.group` co-locates addons on one runner)
but **reserves it for addons that pass live JS objects across the cap surface**
(the `detection` group): grouping for RAM is a different motive and D2 does not
sanction it on its own.

The tempting move was the biggest count-win: fold the ~8 solitary device
providers (reolink, hikvision, amcrest, dreame, …) into a few shared runners.
That was rejected. Providers drive external hardware and cloud SDKs — the highest
crash rate in the fleet — and [D6](adr-0006.md)'s `CrashSupervisor` respawns the
**whole** runner on any co-located addon's crash. Grouping providers would couple
an unrelated provider's SDK fault to live camera ingestion, and some providers
sit on the capture path. `embedding-encoder` was likewise excluded: it feeds the
live similarity-search path per detection and is `protected`.

## Decision

Co-locating addons via `execution.group` **solely to reclaim the per-runner
floor** is allowed only when every member of the group is:

1. **not on any live camera / frame data path** (no capture, no per-frame or
   per-detection latency contract), and
2. **frame-free** — passes no media across the runner boundary ([D9](adr-0009.md)), and
3. **low-crash / user- or admin-triggered**, so a `CrashSupervisor` respawn of
   the shared runner can never interrupt capture or recording.

The first such group is `ml` = `ai` + `benchmark` + `model-studio` (LLM profiles,
detection benchmark, model registry). Device providers, decoders, `stream-broker`,
`recorder`, the `pipeline-*` addons and `matter-broker` stay isolated. D2's
live-object grouping (`detection`) is unaffected — that is a separate, stronger
justification and is not weakened by this.

## Consequences

- A grouped runner inherits the **heaviest** member's `heapProfile` — a runner is
  "heavy" if any co-located addon declares `heapProfile: 'heavy'`
  (`process-service.ts`). A light member (`ai`) therefore runs in a heavier
  runner than it needs; that is the price of sharing the floor.
- Each merged addon saves ~one 80MB floor; `ml` collapses 3 runners into 1
  (verified live: 27→25 hub runners).
- Any member crash respawns all members. Acceptable **only** under the three-part
  gate above — which is why the gate is non-negotiable, not the group membership.
- The big RAM consumer is not the runners but the in-process hub-main (one
  process, ~20 core addons); this decision does not touch it.

## Enforcement

Review only. No guard can read "live-critical" off a manifest, so the gate is a
judgement made when adding a member to a RAM-motivated group. A future editor who
adds a provider or a data-plane addon to such a group is violating this record,
not the type system.
