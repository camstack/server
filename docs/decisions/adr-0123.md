## Context

The snapshot wrapper is a `@camstack/system` builtin, so it loads in the hub
ROOT process — the same event loop that serves the tRPC API, the WebSocket and
the Admin UI. It owns per-camera capture, an ffmpeg keyframe grab, a sharp
resize per (device, stream, width), a base64 JPEG cache and a variant cache.
Measured on the live hub on 2026-08-11, while the operator reported the devices
page cycling empty: `starter.js` at 90.1 % CPU / 4.4 GiB RSS, ~1.6 concurrent
`image2pipe` children all parented by the root PID, and `deviceManager.listAll`
answering the same call in 1.38 s and then 4.30 s. Nobody has profiled that
90 %, and this record does not claim to explain it. Capture plus transcode plus
base64 for every camera does not belong on the process that answers the API
either way.

**The blocker that was not one.** `buildAddonGroupPlan` dropped builtins by
package name, with the rationale that "moving them into a sibling subprocess
would isolate them on a separate Moleculer node that child brokers cannot
reach". That is false, and `docs/architecture/transport.md` says so plainly:
there is no per-addon Moleculer broker, and a child reaches the hub **and its
siblings** over the UDS channel. `LocalChildRegistry` implements exactly that.
The comment nearly stopped the change; the real reason builtins stay in-process
is narrower — storage, settings and logging must be resident in the process
every runner depends on — and it does not apply to snapshot.

**The blocker that was real, and is not in the design doc.** The design assumed
`ctx.getNativeProvider` keeps working in a runner because "a runner has the same
`ctx.api`". It does not. A wrapper shares its cap NAME with the natives it
delegates to, and the runner path resolves by name twice over:
`localProviderLink` short-circuits to the runner's own provider before the call
reaches the socket, and the parent's `resolveChildId` falls back to a
deviceId-less descriptor — the wrapper's own child — if it gets there. Either
way the wrapper calls itself; the re-entrant call joins the first's
`SingleFlight` and waits on a promise only the outer call can settle. Nothing
throws and nothing logs. The vendor native is simply never invoked, every camera
silently drops to the ffmpeg fallback, and any caller without a deadline hangs.
The `bypassWrapper: true` flag `buildRemoteNativeProvider` has been sending
since it was written is read by nothing on the server.

A third hazard is smaller but permanent: the link plane needs a persisted
signing secret, and it was minted once at init. In hub-main the settings store
was always already there. In a runner it may not be, and `state.get()` cannot
tell "never written" from "could not be read" — `readAddonStoreWithRetry` gives
up and answers `{}`. One slow boot then produces either a link plane that never
serves for the life of the process (every grid tile blank, nothing failing
twice) or a second secret that invalidates every link the fleet is holding.

## Decision

A `@camstack/system` manifest entry may declare `execution.isolate: true`, and
the hub then treats it as an ordinary forked addon — planned, spawned, mounted,
restarted and uninstalled through the same paths, with `resolveRunnerId` still
the only source of its runner id. One predicate,
`AddonRegistryService.runsInOwnRunner`, answers "does this fork" for the runner
plan, the in-process boot filter and `isForkedAddonEntry` alike; a spawn failure
never falls back to running the builtin on the hub. Isolated builtins are
spawned AFTER the in-process builtins, because everything they persist lives
behind one of them.

A forked wrapper reaches its per-device native by asking for it explicitly:
`ctx.getNativeProvider` in a UDS runner emits a `cap-call-out` carrying
`native: true`, which bypasses every capName-based route and is answered by the
parent's `CapabilityRegistry.getNativeProvider` — the single authority that
already spans in-process natives, hub-local vendor children and remote agents.
No native for that `(cap, device)` FAILS the call; it never degrades into
wrapper routing.

## Consequences

- The snapshot cap's byte-returning methods now cross a process boundary as
  MsgPack over UDS. That is inside [D9]/[D18] — snapshots are compressed and not
  frame-rate — but it is the shape the rule likes least. The high-volume path
  does not pay it: `getSnapshotLinks` returns handles and the client fetches
  bytes over the HTTP link plane, which the runner serves itself (the data-plane
  facility binds the listener in the ADDON's process and the hub reverse-proxies
  by bare addon id, so `/addon/snapshot/link/*` URLs are byte-identical).
- `native: true` is a fourth member of the "an explicit intent must win over a
  co-located provider" family, alongside the node pin, the collection union and
  the `{ addonId }` selector — all decided in `LocalChildRegistry` before
  `onUnownedCall`, because a decision made only in `onUnownedCall` is made
  never.
- The failure MESSAGE is load-bearing: a wrapper matches "no native provider for
  capability" / "no provider for" to decide "absent → run my own strategy"
  rather than "the camera is broken". Rewording it silently changes behaviour.
- Anything an isolated builtin persists must tolerate a store that is not
  answering yet. Snapshot now retries the link plane on demand and gates the
  minted secret on reading it back.
- `bypassWrapper` remains unread by the server. It is the broker-mode worker
  path's hint and is left alone deliberately — the UDS path no longer depends on
  it, and honouring it would change behaviour for callers not examined here.

## Enforcement

Tests, not a guard — the three fork questions are now one function, so there is
no second implementation to drift from.

- `packages/system/src/kernel/__tests__/transport/native-cap-route.spec.ts` —
  the sibling short-circuit is bypassed, the resolver is never consulted, the
  absent-native message is the one wrappers match, and the agent forwards the
  flag. Verified discriminating: with the two branches removed, 7 of its 8
  assertions fail.
- `packages/system/src/kernel/__tests__/moleculer/addon-context-factory.spec.ts`
  — a UDS context whose runner registers the cap itself does NOT resolve its own
  provider from `getNativeProvider`.
- `packages/system/src/kernel/__tests__/moleculer/addon-runner.spec.ts` — the
  runner-plan re-derivation includes an `isolate` builtin and still drops an
  `agent-only` one.
- `packages/system/src/builtins/snapshot/__tests__/snapshot-link-plane-boot.spec.ts`
  — a store that is down at init serves the plane on a later call and never
  rotates the secret.
