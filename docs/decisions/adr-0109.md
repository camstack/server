## Context

Operator directive, 2026-08-11: *"Se la Object detection è ferma anche il
decoder deve essere killato e mai startato"* [If object detection is stopped, the decoder too must be killed and never started], extended in the same breath to
`audio-analysis`.

The `object-detection` switch already worked, in the sense [D62](adr-0062.md)
requires: it writes the authority that owned the function
(`setWrapperActive` on the `detection-pipeline` binding), the camera reports
`switchedOff: ['object-detection']`, and no detections are produced. Every test
covering it was green.

It stopped the wrong half. Two mechanisms were believed to be the gate:

1. **`pipelineEnabled`** — derived from the binding, carried through
   `CameraDetectionConfig` into `RunnerCameraConfig`, shipped to the runner on
   every `attachCamera`. `grep -rn pipelineEnabled packages/addon-pipeline`
   returns **nothing**. No consumer, ever. A flag that names the right gate and
   enforces nothing reads as enforcement — the exact leftover the working-style
   rules warn about, and it survived because the assertions were written
   against the flag's VALUE rather than against its effect.
2. **Empty `steps`** — the "F12 runner gate". Real, and correctly tested:
   `runInference()` returns before `runPipeline`. But it gates INFERENCE, which
   is the last step of the chain and the only one that was not already paid for.

Dispatch is what makes a runner dial RTSP, spawn ffmpeg and open a decode
session. So a switched-off camera did all of that and discarded the result.
Measured on camera 3218 with the switch off, from a clean create:

```
[hub/stream-broker]    (glances) ffmpeg source: streaming
[hub/stream-broker]    (rtsp) RTSP client connected {streamName=3218/glances}
[hub/pipeline-runner]  session-decode-coordinator: still waiting for its first
                       decodable frame — holding the dial {waitedMs=40001}
```

The teardown side was never broken: flipping the switch emits
`DeviceBindingsChanged`, which runs `handleSettingsChanged` → `stopDetection`.
What kept the decoder alive is that `startDetection` immediately re-attached
the camera on the way back.

## Decision

`startDetection` does not attach a camera whose `pipelineEnabled` is false —
no standing dispatch and no motion watch. The camera produces no frames at all
rather than producing frames nobody reads.

Dropping the motion watch is part of the decision, not a side effect: that
attach exists to run the grey-decode analyzer, so leaving it would have kept a
decoder alive for a camera the operator switched off.

Audio is **not** gated here. It is a separate branch behind its own
`audio-analysis` binding, already enforced inside `subscribeAudioStream` via
`isAudioAnalysisActive` — which returns before opening a subscription. Gating
audio on the detection switch would drag one function off with the other.

## Consequences

**Off means free.** A switched-off camera costs no RTSP dial, no ffmpeg, no
decode session — not "costs inference-free frames".

**`pipelineEnabled` is now load-bearing for the first time.** It reaches the
runner unchanged and is still unread there; what changed is that the
orchestrator acts on it before dispatch. Deleting it from
`RunnerCameraConfig` is the honest follow-up and is deliberately NOT bundled
here — the field is in the generated cap schema
(`pipeline-runner.cap.ts`, `.default(true)`), so removing it is a codegen
change with its own blast radius.

**Three tests changed meaning, not implementation.** They asserted that an
unbound camera IS dispatched with `pipelineEnabled:false` and empty steps —
the old contract, faithfully pinned. They now assert it is not dispatched. The
`resolvePipeline`-returns-empty coverage is untouched.

**Re-enabling must still work.** The bindings round-trip test asserts
off → detach → on → fresh attach, so the gate cannot regress into a one-way
door.

## Enforcement

- `detection-wiring-e2e.spec.ts` — "never attaches a camera whose
  object-detection switch is off, and detaches one when it is turned off".
  Asserts on `attachedCameras`, never on the flag: asserting
  `pipelineEnabled === false` is precisely what a dead flag passes. Verified to
  FAIL with the gate neutralised, on the re-attach leg.
- `detection-switch-authority-e2e.spec.ts` — the same claim expressed against
  the AUTHORITY (`setWrapperActive` on `detection-pipeline`), including the
  cold-start leg: a camera whose binding is already inactive when its streams
  first register is never handed to the runner at all, and a second dispatch
  trigger does not resurrect it. Verified to FAIL on both legs with the gate
  neutralised. This is the guard that SURVIVES — see below.
- `camera-switches-e2e.spec.ts` — the switch surface: OFF → the runner is
  never handed the camera. **Deprecated guard.** It drives
  `pipelineOrchestrator.setCameraSwitch`, a compatibility cap scheduled for
  deletion ([D113](adr-0113.md)); it is deleted with that cap, and this
  decision's enforcement must not depend on it. The load-bearing assertion was
  ported to `detection-switch-authority-e2e.spec.ts` first, on 2026-08-12.
- `bindings-e2e.spec.ts` — the binding surface, plus the off → on round trip
  and an explicit detach-count assertion.
