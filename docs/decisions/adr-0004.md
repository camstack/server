## Context

Behavioural facts about a capability — is it a wrapper, is it active by default,
what mode does it run in — were declarable in two places: the `*.cap.ts`
definition and the providing addon's `package.json` manifest. Two places holding
the same fact is not redundancy, it is a pending disagreement. The manifest is
also the copy that ships inside an addon bundle, so it could be stale relative to
the framework's own definition while looking authoritative.

## Decision

`kind`, `defaultActive`, `mode` and any other behavioural metadata may appear
**only** in the `CapabilityDefinition` in `packages/types/src/capabilities/`. An
addon manifest declares a capability by **name only**. Runtime
`ProviderRegistration` objects carry no behavioural metadata either.

## Consequences

- The framework is always the authority on what a capability *is*; an addon only
  claims to implement it.
- Changing a capability's behaviour is a framework change, which means it reaches
  a node via a root-package update ([D16](adr-0016.md)) rather than an addon
  deploy. That is the honest shipping story for something the whole cluster
  interprets.

## Enforcement

`scripts/check-capability-metadata-drift.ts` — fails the build if any addon
manifest declares behavioural metadata. Wired into CI.
