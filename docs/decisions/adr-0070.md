## Context

[D68](adr-0068.md) rebuilt the scrub — velocity-adaptive drag mapping,
bidirectional P-frame sweep against the fixed 4 s GOP, GOP byte-range reads,
timeline warm-up, and a budget-bounded seek travel animation — and **none of it
had run on real hardware**. Every one of its five rules is a tuning claim, and
the lines it shipped could not check any of them:

- **Mapping.** The fine/coarse decision is made in the CLIENT, from a velocity
  the server cannot observe. "Did this drag ever enter fine mode" — the question
  that decides whether anything downstream matters — was unanswerable.
- **Locate.** D68's whole first-scrub argument is that the 1–8 s `locate` RPC
  left the warm path. Nothing recorded whether a tick hit coverage or paid the
  RPC, and nothing timed it.
- **Fetch.** `readGopBytes` replaced whole-file reads. Bytes read were never
  logged, so "41–173 KB instead of 100–600 KB" was an assumption.
- **Demux.** `demuxSegmentPreferJs` falls back from the in-process mp4box parse
  to an ffmpeg subprocess (~140 ms floor). That fallback was logged **once per
  session** and counted **nowhere**, so its RATE — the number that decides
  whether it is the real cost of a scrub — could not be read at all.
- **Ack.** With `SCRUB_CREDIT_CAP = 2` the achievable scrub frame rate is
  `2 / RTT`. The push→render RTT was never measured.

Two of the existing lines were also actively wrong. `scrub-feeder:parked` fired
per zero-credit tick, and at zero credit **every pointer move parks** — a line
per pointer sample, on the exact path that must stay cheap. And every scrub line
carried `deviceId` only inside `meta`, never as `tags.deviceId`, so the one
question a tuning session always asks — "why is 102 different from 101" — could
not be grouped in Loki at all.

The constraint that shapes the answer: the hub is measured at 70–95% main
thread with 42 s of synchronous blocks per 120 s. An instrument that costs that
much is not an instrument. The obvious version — add the phase fields to the
existing per-push line — is ~16 lines/s per camera during a drag, and it is also
the wrong shape: tuning reads counts and distributions, not individual pushes.

Rejected alternatives:

- **Keep the per-push line as the phase surface** (D68's design, which named
  `mode`/`dir`/`bytes` "on every `scrub-feeder:pushed` line"). Rejected on
  volume, and because the per-push line answers no aggregate question without
  the operator summing it by hand.
- **A metrics counter instead of logs.** Rejected: Loki is what the operator
  reads, it carries info+ from the hub, and a per-camera per-drag question needs
  a label a scrub metric plumbing does not have. This is a tuning pass, not a
  permanent SLI.
- **Infer the mapping mode server-side from target deltas.** Rejected: it is not
  derivable. A fine tick and a coarse tick can emit the same delta, and the
  mode's hysteresis is client state.

## Decision

**A drag reports itself in ONE line.** `scrub-feeder:drag-end` carries counts,
sums and min/median/max per phase — mapping, locate, fetch, demux, push, ack —
for the whole drag, emitted exactly once, by the commit `seek` or by `dispose`
(a drag abandoned by goLive still owes its line). A per-tick line is admissible
only when it is SAMPLED (`scrub-feeder:pushed`: the drag's first push, then one
per second), THROTTLED (`scrub-feeder:slow-locate`, the ffmpeg-fallback warn),
or ONCE-PER-DRAG (`scrub-feeder:parked`, `scrub-feeder:no-footage`). **Never a
line per pushed frame, and never a line per pointer sample.** Every line carries
`tags: { deviceId }`.

Three things follow from it:

1. **The client reports its mapping decision on the wire.** `scrubTo` gains
   optional `m` (`fine`/`coarse`) and `v` (px/s). Optional and terse: it rides
   every pointer move, and a client that predates the field leaves the drag's
   mapping `mapUnknown` — never mis-attributed to a mode it did not report. A
   half-reported hint (mode without velocity) is dropped whole rather than
   putting a guessed number into the percentiles.
2. **Both demux paths are counted, not just the failure.** `FullDemuxOptions`
   replaces `onJsFallback` with `onDemuxPath`, which fires on the JS SUCCESS
   too. A session-scoped `DemuxPathTally` holds the counts; the feeder diffs it
   across the drag (`demuxJs` / `demuxFfmpeg` / `demuxFallback` reason) and the
   tally itself rate-limits the per-fallback warn, reporting how many it
   suppressed. A counter that only ever hears about failures cannot answer "how
   often do we fall back".
3. **The percentile window is BOUNDED** (512 samples/phase). A drag can be
   arbitrarily long; an unbounded array on this path is a leak on the code we
   are trying to make cheap. Count, sum, min and max stay exact past the cap.

## Consequences

- **D68's "`mode`/`dir`/`bytes` on every `scrub-feeder:pushed` line" no longer
  holds** — that line is sampled. The mode census moved to the aggregate
  (`jumps` / `jumpsBack` / `sweeps` / `backSweeps`), which is a strictly
  stronger statement ("exactly one jump, every other push a forward sweep") and
  is what D68's own enforcement tests now assert.
- The aggregate costs one bounded-size object per live drag (six 512-slot number
  windows, worst case ~24 KB, typically a few hundred bytes) and one log line
  per drag. Per tick it is ~15 field writes and no allocation on the hot path.
- Timings come from `performance.now()` around the awaits the tick already made;
  no phase was added to measure a phase.
- A drag whose ticks are still in flight when it ends loses those ticks' samples
  — the aggregate describes what LANDED, not what was attempted. `parks` and
  `failures` cover the rest.
- The mapping fields stay `mapUnknown` until the viewer ships its half
  (`docs/design/2026-08-07-viewer-scrub-instrumentation-spec.md`). That is
  visible, not silent, which is the point.

## Enforcement

`scrub-instrumentation.spec.ts` pins the shape, and its load-bearing assertion
is a COUNT, not a content match: a 10-tick drag emits exactly ONE
`scrub-feeder:drag-end`, fewer `scrub-feeder:pushed` lines than ticks, fewer
than pushed frames, and ≤5 lines in total. Removing the sampling gate turns it
red (1 failed), as does removing the aggregate (17 red across three suites), the
mapping hint (2), the coverage tier (1), the fetch/demux timings (1), the ack
RTT (1), the once-per-drag park guard (1) or the slow-locate throttle (1).
`demux-path-tally.spec.ts` pins the JS-success count and the suppression
counter (removal: 1 red each); `segment-demux-full-js.spec.ts` pins that a
successful in-process demux announces itself (removal: 1 red).
`scrub-drag-stats.spec.ts` pins the bounded window (removal: 1 red).
`tags.deviceId` on the log seams is review-only.
