## Context

[D61](adr-0061.md) made retention ONE age-keyed sweep over tracks: everything a
track owns has no clock and leaves through the cascade. It did not touch the
settings form. So five per-device numbers survived an hour into a world where
they decided nothing:

| Setting | Claimed | Actually decided, after D61 |
| --- | --- | --- |
| `retentionObjectDays` (30) | how long object events live | **nothing** — object events are track-owned and die with their track at 7 |
| `retentionMotionDays` (14) | how long motion events live | motion, a terminal root — a second clock over an entity always swept beside the track |
| `retentionAudioDays` (7) | how long audio events live | audio, same |
| `bufferRetentionDays` (3) | the face/plate buffer window | **nothing** — D61 deleted the age half of the buffer prune |
| `trackRetentionDays` | the track window | the track window — but through **two** parsers |

The `retentionObjectDays` case is the sharpest. An operator sets 30, the form
saves 30, `hydrateSchema` renders 30, and the events are gone at 7. The value on
screen had been a lie since D61 shipped, and nothing in the repo could tell.

That last row is its own defect and was not on anyone's list. `trackRetentionDays`
was declared in `retention-policy.ts` **and** in a second Zod schema in
`track-retention-sweep.ts`, with its own default, its own `resolveTrackRetentionDays`
and its own `trackRetentionCutoff`. None of the three had a production caller —
the sweep is handed a resolved cutoff — and all three had passing unit tests.
Six tests, green for months, over code that ran nowhere.

This is the third knob-decoupled-from-its-reader defect found in this repo in a
single day; `zoneMembershipMinOverlap` and `rescueCentroidFactor` both wrote a
store nobody read. The shape is always the same: the reader moves or dies, the
writer and the form stay, and nothing connects them. Review cannot see it — each
half is locally correct — and the test suite cannot see it either, because a
settings test that reads back what it wrote passes the entire time.

The option considered and rejected was to *reconnect* the per-family windows —
give object events their own sweep again so `retentionObjectDays` means
something. That is D61 run backwards: it reintroduces exactly the second clock
whose disagreements were measured at 14–21 days on the live fleet.

## Decision

**A device has ONE retention window. Everything scoped to that device is deleted
on it. A retention setting the sweep does not read is deleted, not tolerated.**

The operator-visible surface is two fields per camera:

- `retentionMode` — `follow-recordings` (default; the window is the oldest
  segment still on disk) or `custom`.
- `trackRetentionDays` — the window in days, default 7, `0` = keep forever.

Both are enumerated in `RETENTION_SETTING_KEYS`, both are read by
`resolveRetentionCutoffs`, and `DeviceRetentionCutoffs` now carries ONE
`cutoffMs` instead of four per-family ones.

**The terminal roots take the device's window.** Motion, audio and sensor events
are not owned by a track — no `trackId`, no media, referenced by nothing — so
the cascade can never reach them and a clock is the only thing that can. Without
one they are immortal, and motion alone runs ~7,200 rows/day/camera. They get
the same `cutoffMs`, for the same device, resolved once for the whole pass
(`retention/trackless-root-sweep.ts`). This is the part of the change that
needed a decision rather than a deletion, and the test for it is whether an
operator can state the policy in one sentence: *a device has one retention
window, and everything scoped to that device is deleted on it.*

**The ops log is the single stated exception**, and it is named as one. It is
global, fixed at 30 days, and does not follow any device window, because it
records what retention DID — including for cameras that no longer exist. A
camera configured above 30 days outlives its own audit trail; the trail is
history of the sweep, not of the camera.

**`0` = keep forever covers the terminal roots too**, because one window means
one. It is an operator choice and it is legitimate, but its consequence — motion
and audio growing without any bound at all — must not be *inferred from
silence*, so the sweep emits one `warn` per device per process saying the device
ages out nothing. A pass that deletes nothing and logs nothing reads identically
to a pass that never ran.

**`FOLLOW_FLOOR_DAYS` stays 7, and the reason is stronger than it was.** It is
the same number as the `custom` default, which is now load-bearing rather than
coincidental: since the cutoff governs the whole cascade, that equality is what
guarantees follow mode can never be more aggressive than `custom(7)` — switching
a camera to the default can only ever keep MORE. What changed is the *cost*: the
floor is now measured in media bytes (~2–4 MB/track), not event rows, so a
camera whose footage is down to hours still holds 7 days of crops. That is the
right trade for a floor whose job is to stop a young recorder from erasing
history, and the lever for a camera under disk pressure is `custom` with a
smaller number, which has no floor at all.

## Consequences

- **What an operator sees.** Three fields disappear from the retention section
  and one from the face section. On the first retention pass after the upgrade,
  each device that had set one of them logs `analytics retention setting RETIRED
  — one window governs now` at `warn`, with `tags: { deviceId }` and both
  numbers in the meta (`wasSetTo`, `effectiveWindowDays`, `effectiveMode`), then
  the key is unset. Absence of the key IS the migration marker — no flag, no
  version row, and a second pass is silent. A failed write drops the device back
  out of the checked set so the next pass retries rather than swallowing the
  announcement.
- **What actually changes at runtime.** Less than the removal suggests, and this
  is worth stating precisely because the settings diff looks alarming. Object
  events and buffer rows were ALREADY on the track window — D61 did that; D62
  only stops lying about it. Motion and audio move from 14/7 days to the device
  window (7 by default, or the footage horizon in follow mode), and sensor
  events move off `retentionObjectDays` — a window named after an entity sensor
  events have nothing to do with, which is how that wiring survived review.
- **The migration is announce-then-delete, and the deletion is a JSON drop.**
  `writeDeviceStore` merges and preserves an explicit `null`, which would leave
  exactly the accepted-but-ignored residue this change removes; the patch sets
  each retired key to `undefined`, which the settings blob's JSON round-trip
  discards.
- **A behaviour change that is NOT bundled here.** `bufferMaxPerDevice` is
  rendered per device and the sweep reads `FACE_DEFAULTS.bufferMaxPerDevice` —
  the same defect class, one layer over. It is left alone on purpose: honouring
  the per-device override would change what gets deleted on cameras where an
  operator set one, and a silent behaviour change is the thing this record
  exists to forbid. It needs its own change, with its own announcement.
  **Amended 2026-08-28:** it got one. The sweep now resolves the operator's cap
  (`resolveBufferCap`, `pipeline-analytics/index.ts`) instead of the module
  constant, so this paragraph no longer describes a live defect — it records
  one that was closed.
- **Not verified on live data.** There is no hub in this branch. The per-device
  windows, the 19.8-days-of-object-events measurement and the ~7,200 motion
  rows/day are from earlier sessions, not re-measured here. In particular,
  **which devices actually have a non-default retired value is unknown**, so the
  size of the first-pass `warn` burst is unknown; it is bounded by one line per
  retired key per device, once per process.

## Enforcement

`scripts/check-retention-settings-consumed.ts`, wired into
`.github/workflows/ci.yml`. Four checks, each comparing two declarations that
already exist in the source:

1. Every `key` in the `retention` settings section is in
   `RETENTION_SETTING_KEYS`, and every key in that list is in the form.
2. Every key in `RETENTION_SETTING_KEYS` appears in the body of
   `resolveRetentionCutoffs` — the one function that turns a setting into the
   instant rows are deleted before.
3. Every field of `DeviceRetentionCutoffs` is read outside `retention-policy.ts`.
   A cutoff no sweep passes to a store deletes nothing.
4. The names in `RETIRED_DEVICE_SETTINGS` do not appear in analytics source
   outside the file that declares them (comments stripped first, so documenting
   what was removed is free).

**False-positive argument.** There is no heuristic and no judgement about intent
anywhere in it: it compares a form key list, an exported const array and an
interface's fields, and asks whether a name occurs in a named function body. If
the declarations agree it is silent. It is scoped to three files plus one
directory tree, skips tests, and the comment stripper is deliberately naive in
the direction of stripping too much — over-stripping makes the guard quieter,
which is the correct bias.

**Blind spot, stated plainly.** It is a *surface-size* guard, not a semantic
one. It proves a setting reaches the cutoff resolver and that the cutoff reaches
a sweep. It cannot prove the cutoff a key produces is applied to the entity the
key is NAMED after — **D61's own hole would have passed every check here.**
`retentionObjectDays` did reach `resolveRetentionCutoffs`; the `objectCutoffMs`
it produced WAS read by the sweep; it had simply been repurposed to sweep sensor
events while object events moved to the cascade. All four checks green.

That gap is behavioural and only behaviour closes it:

- `retention/__tests__/one-window-governs.spec.ts` drives the shipped chain
  (`resolveRetentionSettings` → `resolveRetentionCutoffs` → `sweepTrackRetention`
  / `sweepTracklessRoots`), changes ONE operator value at a time and asserts the
  set of DELETED rows moves — and that a stored `retentionObjectDays: 365` moves
  nothing.
- `__tests__/retired-retention-settings-wiring.spec.ts` boots the real addon and
  asserts the `warn` and the store write happen from the real retention pass,
  because the pure planner's test would pass just as happily if nobody called it.

The guard stops a knob being ADDED without a reader; the tests stop a reader
reading the wrong thing. Neither can see a retention value stored by another
addon, or a form field built dynamically rather than as a literal.
