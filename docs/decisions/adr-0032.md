## Context

A notification's gif/mp4 was cut from the camera's RECORDING
(`recording.renderGif` / `renderClip`). It produced a file, so it looked correct,
and it was wrong in two ways the operator saw immediately: the clip showed the
seconds BEFORE the trigger — the approach, not the event — and a camera that was
not recording contributed nothing at all.

The cause is structural, not a bug: only FINALIZED segments are addressable, and
the segment covering the moment is still being written (~13 s behind, measured).
The first attempt was to slide the window back onto the last finalized segment.
That is what produced "the approach": the attachment existed and did not contain
its own moment. The second attempt deferred delivery until the segment closed —
correct in principle, but it holds an alarm hostage to the recorder, and the
operator rejected the premise outright: *"non utilizziamo i segmenti"*.

Two rings then looked like the obvious source, and both were traps:

- The AnnexB `preBuffer` is deliberately EMPTY for RTP sources — most cameras.
  The WebRTC join path reads it, and RTSP streams bootstrap from the raw-RTP ring
  instead. Filling it there would have changed what every late-joining viewer is
  flushed on every RTSP camera, in order to buy a notification clip.
- `EncodedRingBuffer.getPackets()` cuts at the most recent keyframe, because its
  consumers are decoders that must start there. That cut is exactly the pre-roll
  a clip needs; reading it yields a clip that starts AFTER the moment it
  announces.

## Decision

Notification footage is cut from a **dedicated clip ring** on the broker, filled
only while `setClipRetention(sec) > 0`, read with `getAllPackets()`, and selected
by WALL CLOCK anchored on the newest packet's age — never by taking the tail.
Retention is opportunistic: it must never count as demand, so it never dials a
camera. It sits on the cheapest assigned profile by default, plus any profile a
rule has actually asked for.

No notification path may read the recording for footage.

## Consequences

- A camera does not have to be recording to produce a notification clip.
- A camera nobody is watching yields a SHORTER clip (nothing accumulates while
  the broker is idle) rather than a warm stream. That is the accepted trade: the
  alternative is keeping every stream dialed for a clip that may never be asked
  for.
- Retention costs RAM on the retained profile only, bounded by
  `CLIP_RETENTION_SEC`.
- A window the ring cannot cover fails immediately and the still ships alone.
  Retrying is pointless — the ring only grows forward, so a retry ages the
  pre-roll out. Any "wait and re-attempt" logic in the dispatcher is a bug.
- The packets never leave the process: the cap returns muxed BYTES, one
  compressed payload per notification ([D9](adr-0009.md), [D18](adr-0018.md)).
- The elementary stream must be converted to Annex-B and the demuxer matched to
  the codec. Broker packets are not guaranteed Annex-B, and `-f h264` on
  length-prefixed or HEVC input decodes NOTHING while exiting cleanly enough to
  look like a render.

## Enforcement

Unit tests in `packages/addon-pipeline/src/stream-broker/__tests__/`:
`prebuffer-clip.spec.ts` fails if the window is taken from the tail instead of
around the moment (four cases), and if the elementary stream is not converted;
`clip-retention.spec.ts` fails if the ring is shared with `preBuffer` or read
with the keyframe-truncating accessor. No guard script — the "never read the
recording" half is review only.
