## Context

A forked runner reaching a hub-core cap (`addons`, `nodes`, `integrations`,
`system`…) has no resolver provider to route to: the hub serves those caps
itself, and the only way across the process boundary is the `$core-caps`
Moleculer service the bridge builds from the appRouter. Which namespaces the
bridge exposes was a hand-written set in `core-cap-bridge.ts`, copied from
`buildServerProviders` in `trpc.router.ts` at the time the bridge was written.

Two things then happened, on the same day.

The inference-timeout guard (D357) took its first fingerprint through
`serverManagement.getServerPackageStatus` and failed on all three nodes with
`no provider registered for cap "server-management"`. The server provides that
cap; no addon does; the copied set predated it. `network-quality` was missing
the same way. The guard read the closure version from disk instead — a
workaround for a list that had drifted.

And the line the handler logs on the legitimate bridge route —
`routing child unowned cap call via broker fallback`, at WARN — fired 3,647
times in 24 hours on the live hub: `addons.listCapabilityProviders` from
addon-pipeline's custom-model cache, `nodes.topology` and
`integrations.getByAddonId` from addon-terminal's reconcile, ha-export's
five-minute reads. Every one was the designed path. None named the caller, so
the only question the line is ever asked — which addon is polling this — could
not be answered from it, and the warnings that were NOT by design were buried.

## Decision

The capabilities the server provides are declared once, in
`server-provided-caps.ts`, split by who actually answers: hub-service caps
(`HUB_SERVICE_CAP_NAMES`: no addon ever registers a provider) and addon-backed
server factories (`ADDON_BACKED_SERVER_CAP_NAMES`: a per-request wrapper over an
addon singleton, `webrtc-session`). `buildServerProviders` is typed over the
union, so a factory without a name, or a name without a factory, does not
compile. The `$core-caps` bridge derives its namespace set from the hub-service
list plus the hand-written core routers; it never carries a copy. Addon-backed
factories are NOT bridged: a resolver miss on one means the addon is down, and
the bridge answering for it would hide that.

The bridge route is not a fallback and is not logged as one. The handler emits
it at debug level, naming `capName`, `method`, `callerAddonId` and
`route: '$core-caps'`. WARN on that path is reserved for a route that is not
designed.

## Consequences

A new server-provided cap is reachable from forked runners the moment it is
added, and forgetting the list is a compile error rather than a 30 s deadline
in production. The wiring in `moleculer.service.ts` must inject a `debug` sink
into the handler's logger, or the line is dropped silently — it did not before.
Reading who polls a core cap now needs the hub at debug level; the default log
carries none of it.

## Enforcement

`core-cap-bridge.spec.ts` builds a synthetic appRouter with `serverManagement`
and `networkQuality` and asserts every `HUB_SERVICE_CAP_NAMES` entry is bridged
and every `ADDON_BACKED_SERVER_CAP_NAMES` entry is not. `tsc` on
`buildServerProviders` catches a list/factory mismatch (verified: removing
`server-management` from the list fails the build at the factory).
`parent-unowned-call.spec.ts` asserts the bridge route calls `debug` with the
caller and never `warn`.
