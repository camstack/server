## Context

`addon-export-hap` advertised **every** resolution to HomeKit at 30 fps. That
number is not a measurement and never was — before 2026-08-06 the string
`inputFps` did not appear anywhere in the addon. It was a literal in an array.

Measured on the live hub on 2026-08-05, device 101's profile slots run at:

| Profile | Resolution | Real rate |
| --- | --- | --- |
| high | 3840×2160 | 25 |
| **mid** | **1280×720** | **10** |
| low | 640×360 | 25 |

Two independent measurement paths agreed (RTP timestamp deltas from
production's own ffmpeg argument vector, and the broker's `inputFps` telemetry),
so this is the camera's substream and not an artefact.

The part that made it a defect rather than a discrepancy: `startFfmpegForSession`
resolves `streamPreference: 'auto'` through `pickPreferredRtspEntry` using **the
controller's negotiated target resolution**. A controller that asks for 1280×720
is therefore steered onto Mid *by construction* — the one slot running at 10 fps.
So the accessory promised 30 and delivered 10, for the most commonly negotiated
resolution, on every camera whose Mid slot is a low-rate substream. The failing
HomeKit session of 2026-08-06 used exactly that slot.

`-c:v copy` means the frame rate cannot be honoured even in principle: ffmpeg
forwards the source's own cadence untouched. So the two candidate fixes were
**transcode to hit the advertised rate** — rejected, it puts a per-session x264
encoder on the hub for every camera and abandons the whole point of the
pass-through path — or **advertise what we will send**.

A third alternative, **exclude slots whose measured rate is far below what was
advertised**, was rejected because it does not remove the lie, it only narrows
which lie is told: the remaining slots still carry an invented 30.

## Decision

An exporter's advertised stream parameters are **derived**, and derived through
the *same* selection code that will serve the stream. `addon-export-hap` attaches
a frame rate to each advertised resolution by running the real
`pickPreferredRtspEntry` against that resolution and reporting the chosen slot's
rate, resolved in falling order of authority: the broker's measured `inputFps`,
then the provider's published cam-stream `fps`, then — and only then — an assumed
constant, which is **labelled `assumed` in the log**. Never advertise a
capability figure that no probe produced without saying so.

## Consequences

- HomeKit now sees `1280x720@10` where it saw `1280x720@30`. That is honest and
  it is worse-looking. Raising the number is a **camera-side** fix (reconfigure
  the substream), not an exporter-side one.
- The advertisement is frozen when the `CameraController` is constructed, so it
  is probed once per accessory build. A profile reassignment reaches HomeKit only
  through the existing reconcile → rebuild path; changing `streamPreference`
  already forces that rebuild.
- The picker and the advertisement are now coupled on purpose. Changing the
  steering changes what is advertised. Do not add a second, independent opinion
  about which slot serves which resolution.
- `addon-export-alexa` shares `pickPreferredRtspEntry` and has the same
  unprobed-advertisement shape. It was not changed here.

## Enforcement

`packages/addon-export-hap/src/mappers/builders/__tests__/stream-fps.spec.ts`
drives the real picker and asserts that 1280×720 is advertised at Mid's rate,
that a measurement outranks a publication, that a cold broker's `inputFps === 0`
is treated as "not measured" rather than "0 fps", and that a pinned preference
makes every advertised rate that slot's rate. Removing the derivation turns three
of them red (verified). Beyond that: review only — nothing stops a future
exporter from hard-coding a figure again.
