## Context

[D126](adr-0126.md) gave the panel a voice — `alarm-triggered`, `alarm-armed`,
`alarm-disarmed` — and shipped the same day the operator reported the two things
it still could not say.

**Nothing covered the exit delay.** `disarmed → arming → armed_away` is thirty
seconds of `arming`, republished once a second, and it produced exactly one
notification: the one at the END. The window during which the operator is
walking out of the door — the only window in which they can still change their
mind — was silent, and "armed" arrived when the decision was already a fact.

**An arm into a mode that watches nothing had no words for it.** The
announcement was deliberately suppressed for a mode with zero gated rules: D126
argued that "Night armed" followed by an unwatched night is a false assurance,
and that is true. But the `alarm-armed` EVENT was emitted anyway, and with no
coverage sentence to carry it fell back to `system.alarm-armed.body` — **a key
that existed in neither shipped locale**. The catalog renders an unknown key as
the empty string, so the operator's phone showed "Casa attivato" with a blank
line under it. Live evidence: mode `home` on this hub has `ruleCount: 0`, and
every arm into it since D126 delivered exactly that. The locale-parity guard
could not catch it — the two files agreed perfectly about a key neither had.

The operator's words for the second gap were "un messaggio di errore quando non
può essere armato" [an error message when it cannot be armed]. Tracing it produced a finding worth recording: **the panel
never refuses an arm.** `alarmPanel.arm` returns `z.void()`, `requiresCode` is
false, and every mode in `availableModes()` is armable. The blocking semantics
the wording implies (open contacts preventing an arm, as the advanced-notifier
reference implements with `bypassableDevices`) would need a sensor-state
authority this hub does not have.

## Decision

**`alarm-arming` is a fourth `NcSystemEventKind`**, emitted on the transition
INTO `arming` and carrying the mode and the whole seconds remaining. Same
invariants as D126's three — transition-only, never on the first publish, never
on the once-a-second re-publish (the `previous === next` guard covers it), and
null for a mode the panel does not offer. Two further refusals are its own:
`exitDelaySec: 0` produces no arming event, because there is no window; and a
provider that reports the bare word without saying what it is arming into gets
none either, because a countdown that can state neither the mode nor the seconds
is not a countdown. The pair `exitDelayAt(machine, now)` is derived from the
same instants `stateAt` compares — never a second copy that can disagree.

**An arm that watches nothing SAYS so.** `alarmCoverageGap()` names the two
ways: `uncovered` (no enabled rule is gated on the mode) and `all-skipped`
(every device the gated rules NAME is muted, offline or has detection off). The
gap selects a body variant rather than suppressing the message, and the same
warning rides the arming sentence thirty seconds earlier — the moment at which
it can still be acted on. An `allDevices` mode is never a gap, because
`skippedDevices` only ever probes the ids a rule wrote down. **This is a report,
not a refusal**: the arm proceeds, and no second authority over the panel's
state is created (D62).

**Every key a transition can freeze must exist in every locale**, and the check
lives next to the producer — `alarm-texts.spec.ts` obtains the coverage-derived
bodies by CALLING the builders, so a variant added with no sentence behind it
fails. `scripts/check-nc-text-catalog.ts` cannot answer this: it compares the
locales to each other, and both were equally missing the key.

## Consequences

- **The lifecycle is four notifications, not three**, and an operator who arms
  with a 30 s exit delay now gets two pushes 30 s apart. That is the feature —
  the reference plugin the operator's expectations come from does the same
  (`Preactivation` then `Activate`).
- `buildArmAnnouncement` no longer returns null, so `announceArm` now delivers
  for an uncovered mode where it used to stay silent. The message is a warning,
  not an assurance, which is the only reason that is an improvement.
- The `alarm-arming` notification carries the destructive **Disarma** button
  with no new wiring: `buildAlarmButtons` already falls through to disarm for
  every kind that is not `alarm-disarmed`. It is the only alarm button that
  cancels something rather than undoing it.
- **A rule cannot be authored on `alarm-arming` until the enum ships in a
  `@camstack/server` closure.** The generated hub router validates
  `createRule`/`updateRule` against the HOST copy of the schema and rejects the
  member (verified live against the running cluster). The addon bundles its own
  `@camstack/types` and can emit it today, so the delivery that works pre-train
  is the panel's own `announceTargets` announcement — an existing durable outbox
  path, not a second delivery channel. Post-train step: add `alarm-arming` to
  the live "Allarme" rule (`019e9ebf`).
- `historySystemEventKind()` downgrades `alarm-arming` to `alarm-armed` in the
  cap-facing history view — the same device as the `recordKind` downgrades, and
  for the same reason: one row carrying a member the host enum lacks does not
  degrade, it fails the whole `getHistory` call. **Delete it** when the closure
  ships everywhere this addon runs.

## Enforcement

- `alarm-transitions.spec.ts` — the arming transition, the tick, the boot
  publish, the unoffered mode, the negative and the rounded countdown.
- `alarm-state-machine.spec.ts` — `exitDelayAt` answers only while the delay is
  the running one.
- `alarm-mode-coverage.spec.ts` — every gap and every body variant, rendered
  through the real catalog in both languages.
- `alarm-texts.spec.ts` — every producible key exists and renders non-empty in
  every locale.
- `alarm-notifications.spec.ts` — the arming row end to end, the announceTargets
  path, and the history downgrade.
- Neutralisation confirmed: deleting the `next === 'arming'` branch, the
  `stateAt !== 'arming'` guard in `exitDelayAt`, the history downgrade, and
  `system.alarm-armed.body` from `en.json` each fails the test that claims it.
