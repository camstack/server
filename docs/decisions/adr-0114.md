## Context

A capability has two names for the same thing:

- the **registered name** (`cap.name`) — what a provider registers under and what
  `CapRouteResolver` looks up;
- the **router key** — `kebabToCamel(cap.name)`, the property a caller types
  (`ctx.api.streamBroker`) and the key the generated tRPC router mounts under.

The two are joined by a pure string transform in BOTH directions. The forward
direction is `kebabToCamel` (`cap-router-predicates.ts`, used by
`addon-context-factory.ts` and `cap-router-builder.ts`). The reverse — the one
that matters — is `toKebab` inside `parsePath()` in
`packages/system/src/kernel/moleculer/trpc-links.ts`, which turns the tRPC
`op.path` namespace back into a cap name for `localProviderLink`,
`brokerTransportLink` and, above all, `ipcParentLink` (the child→parent UDS
`cap-call-out`, whose `capName` the parent's `onUnownedCall` hands straight to
the resolver).

`toKebab` is the inverse of `kebabToCamel` **only for kebab-case input**.

`recordingExport` shipped camelCase — the sole camel name among 149 caps.
`kebabToCamel('recordingExport')` is the identity, so the `ctx.api` property was
correct and everything type-checked; `toKebab('recordingExport')` produced
`recording-export`, a name nothing registers. Every forked-addon
`ctx.api.recordingExport.*` call had therefore failed since the cap was created,
with:

```
parent could not route child unowned cap call "recording-export":
no provider registered for cap "recording-export"
```

Nothing caught it. The hub's own tRPC router mounts by KEY and never re-derives a
name, so the admin UI's exports worked perfectly; `check-registered-caps-declared`
compares the manifest to the registration and both said `recordingExport`; codegen
was happy; the registering end logged `Provider registered for capability
{capability=recordingExport}`. The bug was invisible until the first
addon-to-addon caller appeared — the pipeline-analytics timelapse renderer, one
year of cap life later — and then presented as "the recorder has not registered
yet", a boot-window race that did not exist.

**The alternative that was tried first and rejected: replace `toKebab` with a real
key→name map.** The generated map already exists (`CAP_ROUTER_KEYS`,
`ALL_CAPABILITY_DEFINITIONS`). It cannot be used here: `trpc-links.ts` is in the
addon-runner's transitive closure, where a runtime value import of the
`@camstack/types` barrel is forbidden by [D28](adr-0028.md) and refused by
`check-runner-barrel-free.ts` — it costs ~66MB RSS per runner, ~1.2GB fleet-wide.
A second, schema-free codegen'd map (the `COLLECTION_ARRAY_METHODS` shape) would
work mechanically, but it would exist solely to accommodate one name that already
violated the documented contract (`capability-definition.ts`: *"Unique capability
name (kebab-case)"*), and it would legitimise a genuine ambiguity: `recording-export`
and `recordingExport` both derive the router key `recordingExport`, so allowing
camel names makes the key space non-injective.

## Decision

**A capability's `name` is kebab-case** — `^[a-z0-9]+(-[a-z0-9]+)*$`, equivalently
any name for which `toKebab(kebabToCamel(name)) === name`. The transport keeps
recovering the name with a string transform; it is not given a lookup table. A
capability that wants a camel-looking call site gets it for free, because the
router key is derived.

`recordingExport` was renamed to `recording-export`.

## Consequences

- Renaming a cap name to kebab does **not** change any client path: the router key
  is `kebabToCamel(name)`, so `recording-export` still mounts as
  `trpc.recordingExport.*`. Viewer, SDK, admin UI and the generated `AppRouter`
  type were untouched by the rename.
- What DOES have to move with the name: the `capabilities[].name` entry in the
  declaring package's `package.json` manifest, then `npm run codegen`. Cap names
  are not persisted — a provider re-registers its name on every runner boot — so
  there is no migration on a live hub beyond deploying the addon and shipping the
  framework.
- `trpc-links.ts` stays barrel-free, so D28's per-runner footprint holds.
- The cost is that the key space stays non-injective *by construction avoidance*
  rather than by a map: two caps may never be named such that they collide on
  `kebabToCamel`. The guard's kebab check makes that impossible in practice.

## Enforcement

Two, deliberately at different layers:

- `scripts/check-cap-name-kebab.ts` (wired into `.github/workflows/ci.yml`) —
  textual, fast enough for the pre-commit hook, refuses a non-kebab `name:` in any
  `*.cap.ts` and names the rename + manifest + codegen steps in the error.
- `packages/system/src/kernel/__tests__/moleculer/cap-name-router-key-roundtrip.spec.ts`
  — drives EVERY cap in `ALL_CAPABILITY_DEFINITIONS` through the REAL
  `ipcParentLink` and asserts the `CapCallInput.capName` on the wire equals the
  registered name. This is the assertion the guard is a cheap proxy for: it fails
  if the transform on either side ever changes, not only if a name does.
