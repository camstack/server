## Context

Removing a Terminal camera (device 3217, 2026-08-12 05:38) resurrected it inside
the pipeline seventeen seconds later, and the pipeline watchdog then screamed
`STALLED` about it every 60 s, forever, firing recovery requests nothing could
serve. The chain had five links, each individually reasonable:

1. The stream-broker's `DeviceUnregistered` handler retracted the device with
   `preserveAssignments: true` — a flag built for provider restarts — and the
   assignments map is persisted (`profileMap`), so deleted deviceIds survived
   restarts. The live hub carried **15** of them.
2. The dispatch-reconcile `desired` set is derived from those broker slots, so a
   deleted device stayed "desired" forever — and the teardown that correctly ran
   on the removal event *shrank `known`*, making the deleted device MORE
   eligible for gap-fill re-dispatch. The removal event's own slot-change
   trigger scheduled the reconcile that resurrected it.
3. Device removal deleted the `deviceBindings` row, and `getBindings` fails OPEN
   for an unknown device type — so deletion silently re-enabled every switch the
   operator had turned off (`pipelineEnabled` came back `true`).
4. `handleDeviceRegistered` / `dispatchCamera` never asked whether the device
   exists; per-device settings survive removal (`clearDeviceStore` is per-addon
   namespaced — the "delete all per-device config rows" comment was false), so
   the ghost came back fully configured.
5. The snapshot builtin's cache has no eviction on removal, so the deleted
   camera kept serving its last frame with `ageMs` unbounded.

## Decision

A device the device-manager does not know is torn down, never dispatched, and
leaves nothing behind. Concretely: the reconcile pass splits `desired` by a live
`deviceManager.listAll` read and tears down ids absent in TWO consecutive passes
(a failed or empty read tears down nothing — D49); `handleDeviceRegistered`
refuses a device whose `getDevice` returns null (an RPC *error* still proceeds);
the stream-broker purges assignments on permanent removal and prunes its
persisted `profileMap` at load; `getBindings` returns no auto-bound entries for
a device that is ABSENT (unknown *type* keeps failing open); device removal
purges the orchestrator's own per-device store row; the snapshot builtin evicts
the removed device's cache.

## Consequences

Every reconcile pass costs one `listAll` RPC. Teardown of a ghost takes two
passes instead of one — the price of never destroying work on a single fallible
read. Addons that keep per-device rows must purge them in their own
`DeviceUnregistered` handler until a kernel-level cross-addon purge exists.

## Enforcement

Tests in `dispatch-reconcile.test.ts` (existence split, two-pass rule, D49
fallback), `device-removal-assignments.spec.ts` (broker purge + boot prune),
`bindings-store.spec.ts` (absent-device fail-closed), and
`snapshot-device-removal.spec.ts` (cache eviction). No guard script — the rule
lives in the single funnel (`handleDeviceRegistered`) plus the reconcile filter.
