## Context

Operator directive, 2026-08-11: *"Rimuovi questo ricaricamento dello snapshot.
Deve essere sempre e solo on demand."* [Remove this snapshot reloading. It must always and only be on demand.]

[D93](adr-0093.md) built a keep-warm loop, and it was the right answer to the
problem it faced. The cache has exactly one writer — a successful capture — and
every capture was triggered by somebody asking, so with no viewer open every
thumbnail was as old as the last time anyone looked. Measured then: 15 of 16
cameras cached, all captured in one 55 ms burst, all ten minutes old and not
moving. The loop refreshed only cameras somebody was watching, on a 5 s chained
tick, and went quiet two minutes after the last observer.

What changed is not the operator's tolerance for stale frames; it is that the
job acquired a second owner. The demand signal used to come from IMAGE
requests, which the client's own cache could satisfy without touching the
server — `expo-image` is URL-keyed and never revalidates, so a URL painted in a
previous session came off disk with no network, no demand, and no capture. The
link plane closed that: `snapshot.getSnapshotLinks` is an RPC no image cache can
answer, the client polls it every 5 s while it is showing tiles, and it calls
`awaitFreshEnough` → the ordinary capture path.

So by 2026-08-11 two mechanisms refreshed the same cameras at the same cadence.
The loop's own module named its cost — *"the single biggest cost lever in the
design (16 cameras × 12 ticks/min against a pool of 3 ffmpeg)"* — and that cost
was being paid twice.

## Decision

The snapshot wrapper runs no timer. A frame is captured when a caller asks for
one, and at no other time. `getSnapshotLinks` is the demand signal: it is what a
rendered surface calls, naming the tiles it is actually painting.

Subscription bookkeeping goes with the loop. Tracking who is watching has no
consumer once nothing runs on a tick, and a record of watchers that steers
nothing is the kind of leftover that reads as a live mechanism.

## Consequences

**A camera nobody is looking at costs exactly nothing.** Not "nothing after the
two-minute window lapses" — nothing at all.

**The client is now solely responsible for freshness.** If a surface stops
polling `getSnapshotLinks`, its tiles freeze and the hub will not notice. That
is the intended trade, but it makes the 5 s poll load-bearing in a way it was
not before: it used to be one of two paths to a fresh frame, and is now the
only one.

**Width variants are no longer pre-derived.** The warm tick used to derive the
widths a client had asked for, so a grid tile did not pay a resize on the
request path. The first request per (width, capture) now does. Acceptable
because the same session moved `resizeJpeg` from an ffmpeg spawn to sharp —
52 ms to 4.8 ms measured in the hub's own container — but it IS a consequence,
not a wash.

**D93's stale-frame problem can return** if the link plane ever stops being
called on a surface that shows snapshots. The measurement that justified the
loop is still valid; only its second owner is gone.

## Enforcement

`snapshot-links-integration.spec.ts` — its cold-reopen case now asserts that
after the link call NOTHING captures for 60 s, and the same test still proves
the link call itself lands demand where an overview poll does not. Restore a
timer and it goes red.

The two suites that tested the loop (`snapshot-keep-warm.spec.ts`,
`snapshot-warm-integration.spec.ts`, 623 lines) were deleted with it — a suite
for a deleted mechanism is worse than no suite, because it reads as coverage.
