## Context

A detection session attaches when motion has ALREADY been detected, so by
construction its first decoded frame is at best the live edge — after the event
that triggered it. Stage 0 ([D57](adr-0057.md)'s live-edge withhold, exempted
for a dial that declares `/muted-detection`) removed the blind wait; Stage 1
keeps the source warm across the cooldown so there IS retained media to take.
Stage 2 is the remaining half: spend that retained history so the first
ANALYSED frames predate the trigger.

The broker already retained everything needed and threw it away. Two rings hold
recent media — the source-RTP `rtpRing` for RTP sources and the Annex-B
`decoderSeedBuffer` for push sources — and both are read at their LAST keyframe:
`captureRtpForPreBuffer` splices the ring's head at every IDR, and
`EncodedRingBuffer.getPackets()` cuts at the most recent keyframe because "its
consumers are decoders that must start there". The history existed for a few
hundred milliseconds and was discarded one IDR later.

**The obvious implementation is the dangerous one, and it was rejected first.**
Widening what the ring retains and letting `getRtpPreBuffer()` return it is two
lines. It is also exactly the failure `webrtc-join-burst-exemption.spec.ts`
predicts in prose: that one snapshot is BOTH the WebRTC bootstrap AND the
ordinary RTSP join burst, so widening it hands seconds of backlog to every
viewer, recorder leg and HomeKit ffmpeg copy — the measured D57 failure (a
2 996 ms burst reappearing as 3 030 ms of controller-visible jitter), recreated
from one level above the decision that prevents it.

The second rejected option was to let pre-roll ride the existing bound. It
cannot: a pre-roll of 4 s is by definition wider than the 2 000 ms join-burst
bound, so the knob would read as ON and behave as OFF on every camera — a
setting that silently does nothing is worse than no setting.

## Decision

**Pre-roll is a SECOND, separately-supplied window, served only to a session
that declared the detection intent. The shared pre-buffer keeps returning the
current GOP.**

- `StreamBroker.getRtpPreBuffer()` returns `[current keyframe AU .. now]`
  EXPLICITLY (sliced at the newest keyframe mark), not "whatever the ring
  holds". Those were the same thing until pre-roll and must never be the same
  thing again.
- `getRtpPreRollBuffer()` / `getDecoderSeedPackets()` return the pre-roll
  window, and `RtspRestreamer.setPreRollSupplier` is a second supplier, never a
  widening of `setRtpPreBufferSupplier`.
- The window ALWAYS starts at a keyframe access unit, chosen by one pure
  selector (`selectPreRollStart`) shared by both planes: the oldest keyframe
  still inside `preRollMs`, or the current GOP when none is. D57's "the choice
  is the whole GOP or none of it" is why the selector picks among keyframe
  marks instead of slicing by time.
- For the detection session only, the span bound becomes
  `max(joinBurstMaxSpanMs, preRollMs)` and the packet ceiling scales by the same
  factor — the ceiling was always a RATE ("more packets than this much media can
  contain"), and reading it as an absolute would cap the feature on exactly the
  4K cameras that need it. A window wider than THAT is still withheld, and the
  session joins clean at the next live keyframe.
- The knob is `preRollMs`: cluster default in the stream-broker addon settings
  (**0 — off**), per-camera-stream override in the device Streams tab, resolved
  by `resolvePreRollMs`. Cluster-scoped rather than per-node because the ingest
  node is a movable role (D52/D56); per-STREAM because the retention cost is set
  by that stream's bitrate and the reachable window by its IDR interval.
  `pull-http` relays — the terminal cameras — do not inherit the cluster
  default (operator decision); an explicit override still reaches them.

## Consequences

- **Pre-roll spends history; it never creates any.** It does not dial a camera
  and does not keep one warm, so a source that was idle when motion fired
  retains nothing, the selector degrades to the current GOP, and the outcome is
  Stage 0 behaviour. Reaching further back is Stage 1's job, not this one.
- **The retained history is bounded twice.** By `preRollMs` (clamped to
  ≤ `PRE_ROLL_MAX_MS`, 6 s) and by `PRE_ROLL_MAX_BYTES` (8 MB), over the history
  only — the current GOP is the Stage 0 baseline and is served whatever it
  weighs. The byte budget is its own and not a share of `RTP_RING_MAX_BYTES`
  because that cap's overflow calls `resetRtpPreBuffer`, which drops EVERY
  consumer's bootstrap: without a separate budget, one camera's pre-roll would
  degrade every viewer's picture on the same node.
- **A detection decode now drains a backlog on attach.** That is the population
  the Stage 0 exemption was reasoned for (it decodes at source rate and
  publishes throttled by its FrameSlot), and the burst is still PACED through
  the one shared `PacedRtpReplay` — a refused write aborts the whole replay
  exactly as before.
- The `restream prime` log line carries `preRollMs` (configured) alongside
  `preRollSpanMs` (delivered). The two differ whenever the source had not been
  warm long enough, which is the difference between "the knob is off" and "the
  knob is on and the history was not there" — otherwise indistinguishable.
- `DECODER_SEED_BUFFER_SEC` is no longer a fixed 6 s: `setPreRollMs` widens the
  seed ring so the push plane can honour the same number the RTP plane can.

## Enforcement

`packages/addon-pipeline/src/stream-broker/__tests__/pre-roll.spec.ts` pins the
boundary (a keyframe exactly `preRollMs` old is delivered, one millisecond older
is not, and no selection is ever older than the window unless it is the current
GOP itself), `stream-broker-pre-roll-ring.spec.ts` pins the retention, the byte
budget and — the one that matters — that `getRtpPreBuffer()` does NOT move,
and `rtsp-pre-roll-prime.spec.ts` pins that a plain muted session and a viewer
joining the same stream receive the ordinary burst. Each was confirmed to fail
with its fix removed: dropping the window filter fails 10 tests, serving the
pre-roll list to every session fails the blast-radius test, and returning the
whole ring from `getRtpPreBuffer()` fails the fork test.
