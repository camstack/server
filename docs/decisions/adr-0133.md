## Context

[D46](adr-0046.md) built the snooze around three scopes — a rule, a camera, the
whole feed — and that is the shape the admin page authors. Living with it
exposed two things it cannot say.

**The operator does not think in rules.** The sentence is "silence the cat on
the courtyard camera", and the rule that produced the notification they are
holding is an implementation detail they did not choose and often do not know.
A `scope: 'rule'` window silences that rule and leaves the other three rules
that also match a cat delivering; a `scope: 'device'` window silences the
courtyard entirely, including the person walking in behind the cat. Neither is
the sentence. What the operator pointed at is a CAMERA and a KIND OF THING.

**And the surface was unreachable from the notification.** A snooze could only
be opened from the app or the admin page. The moment it is wanted is the moment
the phone buzzes, and D47 had already built everything needed to act from
there — a signed, single-use, short-lived callback — for `onTrigger` sequences
only. `NcActionGrant` was a flat record that always meant "run this sequence",
so a snooze button would have had to fake a sequence the rule does not have.

The dangerous adjacency is the alarm. A household window opened at 22:00 to
stop the garden camera would, under any camera-or-feed scope, also swallow
"ALLARME" at 03:00. The operator would learn that the next morning. Storing a
per-rule "not snoozeable" flag was rejected for the reason D62 gives: a second
authority that can disagree with the first is worse than no authority, and the
direction it would disagree in here is a silent siren.

## Decision

**A snooze window's key is `(deviceId, classes[])`; `ruleId` is provenance.**
`classes` is an orthogonal optional field on `NcSnoozeInputSchema` /
`NcSnoozeSchema` — ABSENT means every class, which is exactly what every window
written before this field meant, so no persisted row changes meaning. A classed
window matches only a subject whose class it names; a subject that carries NO
class never matches a classed window (fail toward DELIVERING); and at equal
scope the classed window is NARROWER, so an overlapping unclassed window owns
the silence and therefore owns the digest.

**A rule the alarm is about, or that arms the alarm, is exempt automatically.**
`isSnoozeExempt(rule)` is true when `conditions.systemEvent.kinds` intersects
`NC_ALARM_SYSTEM_EVENT_KINDS` or any `onTrigger` step calls the `alarm-panel`
cap. It is applied in BOTH places, and both are load-bearing: the button surface
offers no snooze on such a rule, and the suppression gate refuses to let a
window opened elsewhere silence it — a window created in the app knows nothing
about which rules it will meet. A non-suppression is logged at INFO with
`tags: { deviceId }`. `snoozeOptions: []` remains the operator's explicit
button-surface override and is NOT an exemption.

**A snooze suppresses the NOTIFICATION and nothing else.** The gate stays in
`NcDispatcher.deliver`; `runRuleActions` fires at match time and is untouched,
exactly as the cooldown already is.

**`NcActionGrant` becomes a discriminated union** — `sequence | snooze | alarm`
— with a per-kind TTL resolved in one place (`actionTtlMs`): 15 min for a
sequence and an arm, **60 min** for a snooze (its blast radius is silencing the
one person the notification was already addressed to), **5 min** for a disarm
(the only button that REMOVES a protection). A snooze grant freezes
`userId` at mint, so the window a tap opens is always personal to the
addressee — a tap identifies nobody, and this is what makes a public callback
safe to hand a snooze. A grant minted from a button gets `summary: false`: a
lock-screen dismissal answered half an hour later with a digest of what it hid
re-delivers exactly what the operator said they did not want.

**`NotificationAction` gains `mode: 'navigate' | 'background'`.** Absent =
`navigate`, which is every button authored before this. `background` asks the
notifier to POST the callback without leaving the notification — Zentik
`BACKGROUND_CALL` (`POST::<url>`), ntfy `{action:'http', method:'POST'}`. A
backend that cannot do it renders an ordinary link, so this is a preference and
never a requirement. The action plane answers a POST with one line of
`text/plain` instead of an HTML page.

## Consequences

- **A camera window is now the default thing a button opens**, not a rule
  window. The rule the notification came from is recorded in the grant and the
  log line, and is not what the window is keyed on.
- **`classes` lives in the Zod blob, not in a SQLite column.** Nothing queries
  windows by class (the gate reads the whole mirrored set), and a column would
  be a second copy of a fact the validated blob already holds.
- **An alarm rule can never be silenced**, including by a whole-feed window an
  admin opened. The cost is that an operator who genuinely wants the alarm
  quiet has to disarm the panel — which is the honest way to say it.
- **A disarm link outlives its notification by five minutes.** Past that the
  operator opens the app. `destructive: true` on the button is a rendering hint
  and never a gate (D47); the TTL is the actual bound.
- **`snoozeOptions` is `.optional()`, never `.default()`** — a Zod default does
  not run on the addon cap path, so an absent list (use `NC_DEFAULT_SNOOZE_MINUTES`
  = `[10, 30, 60]` minutes) and an empty one (no buttons) have to stay
  distinguishable in code.
- Zentik now declares `actionIcons: true`. That is a PASS-THROUGH claim: the
  intent name travels verbatim, as the webhook kind already does, and a name
  the client does not know renders as no icon rather than a wrong one.

## Enforcement

- `snooze-class-scope.spec.ts` — the class overlap, the absent/empty readings,
  the no-class subject, and the breadth ordering. Every negative is paired with
  a CONTROL that must still be silenced.
- `snooze-exempt.spec.ts` — both exemption sources, plus the controls that keep
  "everything is exempt" from passing.
- `snooze-does-not-suppress-actions.spec.ts` — on the real centre: an active
  window hides the delivery and the `onTrigger` sequence still actuates, with a
  control run proving the rule fires at all.
- `action-buttons-snooze.spec.ts` / `action-buttons-alarm.spec.ts` — the two
  refusals and the state-driven alarm button set, each with a control.
- `scripts/check-viewer-condition-mirror.ts` already refuses an `NcSnoozeSchema`
  key the viewer cannot round-trip, which is what keeps `classes` from reaching
  a client that would strip it.
