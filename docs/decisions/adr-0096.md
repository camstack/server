## Context

Hub-main froze for 6.2 s, 18.3 s, 27.2 s and 23.5 s inside one 28-minute window.
`/api/auth/whoami`, which touches no addon, hit p99 6.4 s. Six captured stacks
were unanimous:

```
run (native better_sqlite3)   ← 1.9 s – 27.2 s
sqliteTransaction             better-sqlite3/lib/methods/transaction.js:52
setAddonDevice                sqlite-settings.addon.js:941
writeDeviceRuntimeState       @camstack/system
(anonymous)                   device-manager.addon.js:3651
listOnTimeout / processTimers ← the per-device 1 s debounce timer
```

 stopped the writes that changed nothing — polled providers were
re-pushing identical slices every tick and each paid a commit. That lowered the
rate. It did not change the shape, so the obvious next question was the operator's:
*does that slice need to be in the database at all, or can it live in RAM?*

The answer to the question turned out to matter less than what measuring it
found.

**The write is not expensive.** On the live hub, against a **copy of the real
227 MB `camstack.db`, in the real directory, on the real shfs FUSE share**, with
production pragmas, the exact statement shape of `setAddonDevice` (range `DELETE`
+ 3 upserts in one transaction) costs **p50 0.14 ms**. The live database is
`journal_mode=wal`, `synchronous=1` (NORMAL) — so an ordinary commit does not
fsync at all. The 56 ms figure that had been attributed to "a write via FUSE" is
an **fsync**, and at NORMAL a commit does not do one. Only a checkpoint does.

**The checkpoint is expensive, and it runs inside somebody's commit.** Same file,
same directory, same workload, one pragma changed:

| `wal_autocheckpoint` | n | p50 | max | >1 s | total blocked |
| --- | --- | --- | --- | --- | --- |
| 1000 (production) | 900 | 0.14 ms | **3001 ms** | 1 | 3765 ms |
| 1000 (production, repeat) | 900 | 0.17 ms | 229 ms | 0 | 975 ms |
| 0 | 900 | 0.14 ms | 52 ms | 0 | 206 ms |
| 0 (repeat) | 900 | 0.16 ms | 47 ms | 0 | 223 ms |

An earlier 300-iteration pair put the production max at 3852 ms against 56 ms.
The multi-second frame is `sqlite3WalCheckpoint` copying WAL frames back into a
227 MB file and fsyncing it over FUSE, entered from whichever commit happens to
push the WAL past 1000 pages. `writeDeviceRuntimeState` is not the cause; it is
the most frequent writer, so it draws most of the checkpoints.

**It reproduces the reported wall-clock loss exactly.** A 60 s soak paced at
50 writes/s in the production shape: 2,929 writes, 12 over 100 ms, max 265 ms,
**5,662 ms blocked = 9.4 % of wall-clock** — against the 8.3 % of wall-clock in
uninterruptible I/O measured on the live hub. Runtime-state writes alone
reproduce it.

**Checkpoint cost scales with WAL size, which is where the 18–27 s stalls come
from.** Checkpointing a WAL that had been allowed to reach 15–33 MB took
**25,178 ms, 4,491 ms and 3,969 ms**. A stall is not one write; it is one
checkpoint of a WAL that something kept from resetting.

**The obvious fix was tried and is wrong.** Disable `wal_autocheckpoint` on the
writer and drive `wal_checkpoint(PASSIVE)` from a worker thread on its own
connection — the textbook answer. Measured over 60 s, it made things **6x
worse**: the writer's max went from 265 ms to **25,178 ms** and total blocked
from 5.7 s to **35.8 s**, because the contention is the shfs FUSE share, not the
thread. A second thread does not buy a second filesystem. Recorded because it
looks correct and would have shipped.

**And the slice cannot move to RAM anyway.** Three findings, from a full reader
audit:

- The persisted blob is the **only seeder of the hub mirror** — `loadRuntimeState`
  calls `seedMirror` before returning (`device-meta-actions.ts:971-990`). RAM-only
  means the mirror is empty at boot too, for every device, until each provider
  happens to push.
- Two readers consume the persisted copy **directly**: the Notification-Center
  `deviceState` rule gate (`pipeline-analytics/index.ts:2356`) and the admin-UI
  rule editor (`NotificationRules.tsx:177`). An empty blob leaves every
  state-gated rule unarmed and the rule editor's device-state picker empty —
  silently, because absence is deliberately read as "unknown".
- Of 62 caps declaring `runtimeState`, exactly two slices are genuinely durable:
  `native-object-detection.enabled` (a Reolink operator toggle with no hardware
  mirror, `refresh` a no-op, `staleMs: Infinity`, and the **only**
  `getCapState(...) === undefined` guard in the repo, which exists precisely to
  protect the restored value — `reolink-camera.ts:4620`) and
  `doorbell.{pressCountSinceStart,lastPressedAt}` on the virtual doorbell, a true
  accumulator with no other home (`virtual-doorbell.addon.ts:252-276`).
  Everything else is regenerated within one poll, push or probe.

The database is **not** the cross-process channel: live cross-process reads go
through the `device-state` cap over the UDS plane against the hub mirror. Disk
exists so that mirror is not empty at boot.

## Decision

**The device runtime-state slice stays persisted.** Nobody may make it RAM-only
without first rehoming `native-object-detection.enabled` and the virtual
doorbell's counter, and re-pointing the two rule surfaces off the persisted read.

**And no stall in `camstack.db` may be attributed to the statement in the stack
without measuring the checkpoint.** The write in a captured frame is usually the
victim, not the cause: at `synchronous=NORMAL` a commit does no fsync, so a
multi-second native frame is a checkpoint the commit was unlucky enough to enter.
The levers, in the order the evidence supports them:

1. **Get `camstack.db` off the FUSE share.** Every other number here is
   arithmetic on top of the 43x shfs multiplier. This is an operator change, not
   a code change, and it is the only one that removes the cause.
2. **Treat write volume into `camstack.db` as a budget.** It holds 176,846
   motion-events, 129,268 audio-events, 127,740 media rows and 34,898
   object-events against 1,118 runtime-state rows. Runtime state is 0.3 % of the
   file and is not where the volume is.
3. **Do not move the checkpoint to another thread.** Measured, worse, twice.

## Consequences

- Whoever removes the runtime-state write removes ~a tenth of the checkpoint
  triggers and leaves the loaded gun for pipeline-analytics. The freeze survives.
- remains correct and remains worth having — fewer writes is fewer
  checkpoints — but it was never going to bound the tail, and neither will any
  further reduction in that one writer.
- Relocating the database off shfs changes the backup story: Unraid's Appdata
  Backup walks the share, and a cache-only path is outside it. That has to be
  arranged before the move, not after.
- `WalMaintenance`'s 64 MiB high-water gate is now known to be far above where
  checkpoint cost becomes multi-second (15 MB was 25 s). Its refusal-first design
  is still right; its threshold is not evidence-based and should be revisited
  against these numbers rather than left as-is.

## Enforcement

Nothing automated, and that is worth writing down. The runtime-state half could
be guarded — a test asserting the two durable slices survive a
`fromInitial → setCapState` round-trip would catch a future RAM-only refactor —
but the storage half cannot be: no guard can tell whether `/data` is a FUSE
share. The reusable instrumentation is committed in `scratchpad/`
(`wal-checkpoint-ab.mjs`, `wal-soak.mjs`, `rtstate-probe.mjs`), and the A/B is
one pragma; run it before believing a write is slow.
