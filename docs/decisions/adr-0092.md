## Context

The hub has been an OAuth 2.0 authorization server since Alexa account linking.
Every assumption baked into it came from that one client: the redirect lands on
one of three fixed Amazon origins, and the `client_id`/`client_secret` pair is
checked at the cloud Lambda rather than here — `/authorize` and `/token` never
looked at either.

Onboarding the Home Assistant component needed the same server and broke both
assumptions at once. The component is **published source**, so any secret
shipped in it is a decoration; and its callback is
`http://<the operator's own LAN address>:8123/auth/external/callback`, which the
hub cannot be told about in advance.

The obvious shortcut — widen `allowedRedirectPrefixes` to `http://` — turns a
token-minting endpoint into an open redirector. The second shortcut — a static
`homeassistant` branch inside `oauth2-routes.ts` — makes the route compose
backend state with collection-cap output, and the next integration copies it.

## Decision

An `oauth-integration` descriptor may declare itself a **public client**
(`requiresPkce: true`), in which case `/authorize` refuses without an S256
`code_challenge` and `/token` refuses without the matching `code_verifier`. The
challenge is baked into the signed authorization code, so **the requirement
travels with the code**, not with mutable config: a code minted with a challenge
stays unredeemable without its verifier regardless of what the descriptor says
later.

A descriptor may also declare `allowedPrivateHostPaths`. A `redirect_uri` is
then admitted if its URL **path matches exactly** *and* its host is private by
**literal inspection** — loopback, RFC1918, CGNAT `100.64/10`, link-local, IPv6
ULA, or a `.local` / `.internal` / `.home.arpa` / `.ts.net` name. Never a
wildcard prefix, never a DNS lookup, never a public host. The consent page
renders the destination so the operator is the last check.

A client with no addon of its own is declared from the `local-auth` builtin as a
normal `oauth-integration` provider. The route keeps seeing exactly one list.
**This last sentence is superseded by [D101](adr-0101.md)**: the premise (Home
Assistant has no addon of its own) expired when `homeassistant-export` shipped,
and every descriptor is now addon-declared. The rest of this record stands — the
"one list" property is what D101 preserves.

## Consequences

- `client_secret` remains unchecked, and that is now a documented property
  rather than an oversight: for a public client there is nothing to check, and
  PKCE is what binds the code to its requester.
- No resolver runs on the authorize path. That is deliberate: resolving a
  caller-supplied name would be SSRF-shaped and would race DNS rebinding — the
  address that answers at validation time is not the one the browser uses. The
  cost is that a private host reachable only through a public DNS name cannot be
  used as a callback; such an operator uses the My Home Assistant bounce.
- A `.local`/`.ts.net` name is trusted without proof. The remaining exposure is
  an attacker who can already answer on the operator's LAN *and* has the
  operator's hub session *and* gets an explicit Allow click.
- Adding a wildcard or a `plain` challenge method to make some client work is a
  violation of this record, not a configuration choice.

## Enforcement

Tests, not a guard. `server/backend/src/api/oauth2/__tests__/oauth2-routes.spec.ts`
pins the private-host matcher (including the 172.32 off-by-one and the
`local.example.com` suffix trap) and the S256-only rule;
`packages/system/src/builtins/local-auth/__tests__/oauth-grants.spec.ts` pins
that a missing, wrong, or replayed-challenge verifier all fail, and that the real
`SsoBridgeClaimsSchema` carries the challenge — the fake bridge would otherwise
have hidden a claim stripped in production.
`server/backend/src/__tests__/oauth2-account-linking.spec.ts` runs the whole
flow through the real Fastify routes against the **shipped** Home Assistant
descriptor, so drift in that descriptor fails the suite.
