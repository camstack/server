> **Superseded by [D72](adr-0072.md) on 2026-08-07.** The Context below is
> still correct — a `getBindings` response genuinely cannot be graded, which is
> why the derived view alone is not enough. The *mechanism* is not: it assumes
> a bad read is TRANSIENT, and defends by repetition. On 2026-08-07 the same
> call site was **systematically** wrong (`ctx.id` carries an `addon:` prefix in
> hub-main; `providerAddonId` never does), so both reads agreed on the wrong
> answer, the mirror latched `unbound` with no recovery path, and camera 101
> dropped another real press. D72 keeps the mirror and the no-I/O happy path,
> and adds the durable authority as the corroborating input plus a
> single confirming read on the one branch that destroys a press.

## Context

Camera 101's virtual doorbell rang **zero times out of three real presses** over
48 hours (2026-08-04/05). Nothing was broken along the path you would suspect:
the source device (1031, a Home Assistant switch) fired, the wrapper received
every `device.state-changed`, loaded its assignments, and detected the rising
edge. Then it asked `deviceManager.getBindings` on the ring path, got an answer
that did not contain its own activation, and dropped the press:

```
13:35:03.854Z  DEBUG  virtual-doorbell: trigger matched but wrapper not bound — skipping {deviceId:101}
```

The binding **was** persisted — proved from a same-day backup taken before the
presses, and the same process later returned the binding correctly to a tRPC
query. So the store answered transiently without it. `getBindings` reads the
device-manager addon store, which is exactly the surface that can silently
answer `{}` ([D44](adr-0044.md), `server/backend/src/core/addon/addon-registry.service.ts`).

The first instinct — "grade the response, and only believe a negative that looks
trustworthy" — does not work, and knowing why is the whole point of this record.
A genuinely unbound pure-wrapper cap and a store answering from an empty
snapshot produce the **same** `getBindings` response: no `doorbell` entry, with
the camera's native entries (snapshot, motion, …) present in both cases, because
those come from the capability registry and not from the store. There is no
field to grade. Nor is the response empty enough to look suspicious.

A doorbell press is a one-shot event. There is no retry, no reconcile, and
nothing downstream that notices it went missing — the [D8](adr-0008.md) shape,
with the worst possible payload.

## Decision

**A gate on a one-shot event reads mirrored in-memory state and performs no
I/O.** The mirror is refreshed off the event path, on an existing cadence. A
read that fails leaves the mirror untouched — an unanswerable store carries no
information. A read that succeeds but contradicts the mirror in the direction
that DESTROYS work is not believed until a second, independent read agrees;
a read that restores work is believed immediately. Where the mirror has no
entry at all, the gate opens, because reaching the gate is itself evidence of
the intent it is checking for.

Concretely for `virtual-doorbell`: `bound → unbind-pending → unbound` requires
two consecutive negative reads; `unbind-pending` still rings; a camera never
read rings. Nothing about a ring can fail, and nothing about it makes a call.

## Consequences

- A camera the operator genuinely unbinds keeps ringing for at most two
  assignment-reload cycles (≤2 minutes at the 60s TTL, and zero if the operator
  saves settings, which invalidates immediately). That is the price, and it buys
  the press.
- The mirror only opens on a never-read camera because a trigger source can only
  be configured through the wrapper's own binding-gated settings surface — a
  configured source is evidence the wrapper was bound. **If a future change lets
  `doorbellSources` be written by any other path, this reasoning dies with it**
  and the cold-start default must be revisited.
- A persistent store failure spanning two reload cycles still revokes. Nothing
  can prevent that without a signal the store itself does not provide; the
  revocation now logs at `warn` instead of vanishing, and re-arms on the next
  positive read.
- Cap methods that only the binding can route to (`applyDeviceSettingsPatch`,
  `getDeviceSettingsContribution` — [D12](adr-0012.md)) are treated as first-hand
  positive evidence and write the mirror directly.
- Every suppression is now reported by the trigger engine rather than returned as
  an empty array, so the addon can say which press it dropped and why.
