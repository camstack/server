## Context

For several sessions the roadmap carried "deploy every pending addon update" and
the count never reached zero on either agent. On 2026-08-11 the hub had 31
pending, agent-a 9 and macmini 9, including `@camstack/system` at `1.2.61`
and `1.2.62` against a `1.2.78` closure — which on an agent means the node's
only builtin infra was 17 versions behind ([D87](adr-0087.md)).

Two independent defects kept it there.

`StartJobInput.nodeIds` is documented "reserved for future cluster jobs" and
nothing reads it. The engine is hub-local. But each task it creates carries a
`nodeId`, and the Addons page renders per-task progress under the node the
operator selected — so "Update all" with an agent selected applied every target
to the **hub** while displaying agent-labelled progress. Confirmed by running it:
`startJob({nodeIds:['agent-a']})` came back with every task `nodeId: hub`.
An operator doing the obvious thing got a green screen and an unchanged agent,
every time.

And `fetchAddonTarball` resolved `meta.versions[version]` only. `updatePackage`
defaults an absent version to `'latest'`, which is a dist-tag key and never a
`versions` key, so every version-less API update failed with `no tarball url`.
The UI hid this by always sending the resolved `latestVersion`;
`AddonInstaller.downloadNpmTarball` had the dist-tag fallback right all along.

**The wrong turn, recorded because it nearly cost a cluster.** The stale
`@camstack/system` in each agent's addon root was first diagnosed as inert
residue — a copy nobody loads — on the strength of the launcher's
`resolved @camstack/system@1.2.78 from <activeRoot>/node_modules/…` line. A guard
was written to refuse framework deploys to an agent, a residue class was added to
delete such directories at boot, and both agents' copies were deleted. All of it
was wrong. That log line answers which copy the LAUNCHER resolves for its own
imports; the agent's builtin addons come from `bootCoreAddons`, which scans the
addon root and nothing else. Two consumers, two copies. Deleting it is precisely
the 2026-08-07 cleanup that left an agent with no `filesystem-storage`,
`sqlite-settings`, `storage-orchestrator`, `hub-forwarder`, `metrics-native` or
`platform-probe` — unobservably, because the log shipper was in the same package.
Nothing fell over only because neither agent rebooted in the window. [D45](adr-0045.md)
says a version is a property of a path; the corollary this cost is that **a path
is only evidence about the consumer that reads it.**

## Decision

`addons.startJob` refuses any `nodeId` that is not the hub, with a message naming
`updatePackage({nodeId})` as the per-node path. It does not accept-and-ignore.
The Addons page's "Update all" branches on the selected node: hub goes through the
job engine, an agent issues one serial `updatePackage` per package.

`fetchAddonTarball` resolves a dist-tag before failing, mirroring
`AddonInstaller.downloadNpmTarball`. Ranges stay unsupported.

Nothing refuses `@camstack/system` on the agent deploy path, and nothing filters
it out of an agent's roster or pending-update list. On an agent that package IS
the builtin infra; a pending update on it is a true and actionable signal, and
the count reaching zero is the whole value of the count.

## Consequences

An agent's bulk update loses the durable journal and the parallel fetch — it is
N serial calls, and a failure part-way leaves the node half-converged with no
resume. Acceptable while agents hold ~9 packages; if that grows, the answer is to
teach the engine about nodes, not to re-add a silent fallback.

`startJob` now throws where it used to succeed. Any caller passing an agent id
and ignoring the result will surface as a new error rather than as a node that
quietly never updates — which is the trade being bought.

## Enforcement

Review only for the `nodeIds` guard: it is a `TRPCError` on a path with no
regression test, because the engine's own suite has no multi-node fixture to
extend. The dist-tag resolution is exercised by every version-less
`updatePackage` call, which previously could not succeed at all.

No guard stops the misdiagnosis this record documents. The countermeasure is the
launcher's own D45 inventory, which already prints
`D45 violation — a host-provided package exists more than once on this node` on
both agents — a line that is EXPECTED there and must not be read as a defect.
