## Context

The snapshot cache had exactly one writer — a request — so freshness was a
function of whether somebody was looking. Measured on the live hub: 15 of 16
cameras cached, all captured inside one 55 ms burst, all **607 s old and not
moving**. "The list of snapshots is not always up to date" was literal and total.

Adding a warm loop is the obvious half. The half that was not obvious is **what
tells the server somebody is watching**, and the first answer was wrong.

The client cache-busted with `?v=floor(now/30000)`, a wall clock. That had to go:
on web it made a 304 structurally impossible (the browser cache keys on the full
URL, so a rolled-over bucket had no stored entry to revalidate against, and every
window was a full 200 with a full body). The obvious replacement — delete `v`,
keep a stable URL, let `ETag` revalidate — is correct on web and **broken on
native**. `expo-image` is URL-keyed and does not revalidate; its own contract
defines the default `cachePolicy: 'disk'` as "queried from the disk cache if
exists, otherwise downloaded". `Cache-Control` and `ETag` never enter into it. A
permanently stable URL is a thumbnail frozen until eviction.

So the URL had to carry the frame identity, which meant the client had to learn
it, which is what finally gave `getSnapshotOverview` a consumer.

And then the deadlock, which was **only found by measuring the deployed loop**:
if the client re-requests an image only when the frame identity changes, and the
identity changes only because the warm loop captured, then a subscription keyed
on image requests expires 120 s after the last one — warming stops, the identity
freezes, the client never asks again, and the tile is stuck forever. Measured
exactly: ages held at ~13 s and jumped to 49.7 s at t+120 s.

Two further defects surfaced the same way, both invisible in review. Warming only
when the frame has actually expired refreshes at `maxAge + tick + capture`,
measured 13–15 s against a 10 s window. And fifteen independent cameras shared an
*identical* 42.6 s worst-case age — the signature of a tick awaiting its slowest
member, caused by an unbounded ffmpeg resize per (device, width).

## Decision

A snapshot image URL carries `v = <lastCapturedAt>` — the capture identity from
`snapshot.getSnapshotOverview`, never a clock. It changes when, and only when,
the frame changes.

The keep-warm loop is **subscription-scoped**: only a rendered surface's image
request creates a subscription, and `getSnapshotOverview` **renews** existing
subscriptions but can never create one. The client's metadata poll is the
heartbeat; the image request is the enrolment.

Every step inside a warm tick is bounded by one tick interval, and the loop warms
one tick ahead of expiry.

## Consequences

- With nobody watching, the loop walks an empty list and costs nothing. That is
  the property that makes it affordable, and it is the reason the overview poll
  must not be able to create a subscription: that poll is app-wide, so a creating
  overview would warm every camera on the install.
- `getSnapshotOverview` is now load-bearing, not advisory. A client that stops
  polling it stops being warm — correctly, but it means the poll cadence and the
  warm interval are coupled and should stay matched (both 5 s).
- Battery cameras get **no new gate**. A warm tick is a plain non-forced
  `getSnapshot`, so the 3600 s battery max-age and the sleeping-battery gate that
  already own the decision both apply. A second knob that disagreed with them
  would be worse than none.
- Giving up on a slow device mid-tick loses nothing: a capture that lands later
  still populates the cache, and an underived variant is derived by the next
  request.
- Measured on the live hub after all three fixes, with one observer: per-camera
  cache age p50 **5–7 s** (from 607 s), fleet-wide worst case 28 s (from 43 s).

## Enforcement

> The two suites below were DELETED with the keep-warm loop on 2026-08-11
> ([D108](adr-0108.md)). They are named here as the record of what enforced this
> decision while it stood, not as coverage that exists.

- `packages/system/src/builtins/snapshot/__tests__/snapshot-keep-warm.spec.ts` — <!-- drift-ok: suite deleted with the mechanism, see D108 -->
  `renew` cannot create a subscription; the window expires.
- `.../__tests__/snapshot-warm-integration.spec.ts` — drives real HTTP requests
  through the real handler: warming continues past two windows under an
  overview-only client, stops when nobody watches, never wakes a battery camera,
  and survives a camera whose capture or resize never returns.
- `camstack/src/data/__tests__/snapshot-media-url.spec.ts` — the version tag is
  reproducible for a given (frame, epoch), so it cannot have consulted a clock.
- `camstack/src/data/__tests__/snapshot-surfaces-width.spec.ts` — a source-level
  guard: every `useSnapshot` call site must pass a target width, or be listed as
  an intentional full-frame surface with a reason.
